# MinoNexus 开发手册


> **前端架构硬约束（2026-10-14）**：Mino 项目只有 **MinoWorkbench** 一个前端。MinoConsole 与 MinoStudio 已取消，不再开发、构建、交付或作为配置/验收入口。管理、用例、环境、控件配置和证据查看全部在 Workbench；Nexus 与 Scout 保持后端和执行节点职责。历史文档中的 Console/Studio 入口均以 Workbench 为准。“三端”仅指 Web、移动、PC 被测平台。
面向在本仓库改代码、联调 Workbench / Scout、用 Agent 辅助排查的同学。**与** [排查手册](排查手册/排查手册.md)（按 ID 查日志）**互补**：本文规定日常开发纪律，避免把个人调试写进真库。

---

## 1. 数据目录与真源

| 项 | 说明 |
|---|---|
| 默认路径 | `~/.mino-nexus/`（可用环境变量 `MINO_NEXUS_DATA_DIR` 覆盖） |
| 业务库 | `mino.db`（项目、号池、设置、能力目录、跑批元数据等） |
| 约定 | 本机这份库常等同「个人/团队测试环境真源」，**不是**可随意灌脏数据的沙箱 |

表结构与路径详见 [基础框架/DATA_MODEL.md](基础框架/DATA_MODEL.md)。

## 2. 硬约束：调试不得直接改库

**无论人工还是 Coding Agent，在排查、验证、复现问题时，一律不得对 `mino.db`（及同目录下业务数据）做写入类操作。**

禁止包括但不限于：

- `sqlite3 mino.db` 下的 `INSERT` / `UPDATE` / `DELETE` / `REPLACE` / `DROP` / `ALTER`（只读 `SELECT` / `.schema` / `PRAGMA` 除外）
- 在终端或脚本里调用 `session_scope()`、`upsert_one`、`save_one_test_account`、`run_store.put` 等**落库 API** 做「试一下能不能存」
- 复制、覆盖、删除整个 `mino.db` 或 `~/.mino-nexus`（除非本人明确要做备份恢复，且与当前调试无关）
- 为验证逻辑而批量创建号池账号、项目、跑批记录等**污染性**数据

允许：

- **只读**查库（对照 `session_events`、号池行数等），见 [排查手册/01-Session-Log与数据库.md](排查手册/01-Session-Log与数据库.md)
- 走 **HTTP API**（Workbench 已登录会话），与真实用户路径一致
- 单元测试使用 **临时库** 或 mock（测试进程内 `data_dir` 指向临时目录，测完即弃）
- 只读调用 `python3 -c` 引用 **纯函数**（解析、编译、无 `session_scope` 的路径）

**原因**：Agent 在 shell 里「复现 bug」时很容易往号池、任务表插入半拉子数据；列表里会出现重复邮箱、`*@g.com` 占位账号、与业务无关的 `acc_*`，且难以区分是产品问题还是调试残留。

## 3. 推荐的验证方式

| 目的 | 做法 |
|---|---|
| 改 Nexus 逻辑 | 起本地 `mino-nexus`，用 Workbench 点路径；或 `curl` 带 Bearer（与 [HTTP.md](基础框架/HTTP.md) 一致） |
| 改号池 / 环境 | Workbench **账号管理**、**项目环境** 页保存；不要 shell 直写 `pool_accounts` |
| 改协议 | golden fixture + 两仓 `protocol.py` round-trip（见 [PROTOCOL.md](基础框架/PROTOCOL.md)） |
| 必须自动化 | 在 `tests/` 或脚本里把 `MINO_NEXUS_DATA_DIR` 指到 **临时目录**，或在 PR 说明里写清「未动共享库」 |

需要「空库」时：用**新的** `MINO_NEXUS_DATA_DIR` 启动 Nexus，而不是在现有库里删表清数据（除非本人运维操作）。

## 4. 误写入脏数据时怎么清理

1. **优先 Workbench**：项目 → 资源 → 账号管理，删除明确是调试用的行（如 `test1@g.com`、`test2@g.com`、`acc_testdebug01`、重复 Gmail 别名等）。
2. **单条删除 API**：`DELETE /project/{project_id}/accounts/{account_id}`（与 Workbench 同权，需登录）。
3. **禁止**把「清脏数据」交给 Agent 在 shell 里执行 `DELETE FROM pool_accounts …`，除非**你本人**明确要求且已备份。

号池真源是表 `pool_accounts` / `pool_account_facets`（见 DATA_MODEL）；删行只影响对应 `acc_*`，不会动项目环境 JSON 里的 `gmail_inbox` 等配置。

## 5. 看图规划 / 执行（agent-vision-plan · agent-vision-exec）

**版本与变更**只记在 `llm_jobs.prompt_version` 与 `revisions`，**禁止**在 `system_blocks` / `user_blocks` 里写「v4」「改了什么」等注释；prompt 只描述角色与输入输出。

### 5.1 分工与状态机

详见 [里程碑-Plan-Exec-状态机.md](架构/V2/里程碑-Plan-Exec-状态机.md)。

| Job | 职责 |
|-----|------|
| **agent-vision-plan** | `milestones_append`、`step_requirements_complete`（状态仅程序写回） |
| **agent-vision-exec** | **仅**对 `in_progress`（`active_focus_milestone_id`）调一个 capability |

编排（`milestone_orchestrator`）：无 `pending`/`in_progress` 不调 exec；有程序图的稳定焦点跳过 plan 直接 exec（绑定缓存唯一命中可再跳过看图）；`observe=visual_each_run` 每轮看图且不写缓存；工具 pass 后程序推进焦点。规划只在打断、未准出时出场。

### 5.2 允许注入 LLM 的字段

- **plan**：`success_criteria`、可选 `knowledge_body` / `nav_assist` / `doc_context` / `hierarchy_text`、复核时的 `review_program_fail`、截图。
- **exec**：同上（无 `review_program_fail`），工具列表由程序附带，不在 user 正文重复叙述。

**禁止**注入：`task_context`、`case_context`、`RunContext` 展平、`session_json`、`accounts_json`、`prep_program_plan`、`phase_step_text`、`plan_digest`、`history`、`hook_calls`（历史字段，新 prompt 不再使用）。

### 5.3 milestones 谁写入

有 `*_program_plan` 时由 **程序种子**，规划不得改业务边。详见 [用例程序图固化与可测性拦截](架构/V3/用例程序图固化与可测性拦截.md)。

| 时机 | 谁写 |
|------|------|
| **prep 开局** | 程序 `seed_prep_milestones_from_claim`（用例密钥 → claim → milestones） |
| **do / check 开局** | 程序 `seed_do_milestones_from_plan` / `seed_check_milestones_from_plan`（`step_program_keys` → 子里程碑）。有程序图时 **不再** 让 vision-plan 生成首包 |
| **执行后** | 程序根据 tool pass/fail 更新 `status`（`note_tool_pass_milestone` 等）；稳定步写入绑定指纹（不含坐标） |
| **规划追加** | 仅打断 / 未准出补洞。有 `do_program_plan.steps` 时 `milestones_append` 业务边一律 `plan_append/rejected`。不重排、不删已有 id |
| **打断 pop** | 回到原来的 `in_progress`。连续成功只发 `interrupt/promote_hint`，不静默改用例 |

### 5.4 Nexus 内数据（不喂模型）

| 对象 | 作用 |
|------|------|
| **RunContext** | 单轮跑批运行时：`ctx`（设备、租号、session_fact、case 引用等），供程序与 `fill_*_from_ctx` |
| **task_context** | 批次维度：run_id、app_id、平台、sn（派单结果） |
| **case_context** | 用例维度：case_id、步骤文案、前置/操作/预期、session 摘要 |

三者只在 Nexus 维护；需要账号/登录态时由程序注入 tool 参数，不把 JSON 塞进 plan/exec prompt。

## 6. Agent / 协作者自检清单

改代码或跑命令前自问：

- [ ] 这条命令会不会 `commit` 到 `~/.mino-nexus/mino.db`？
- [ ] 能否改成只读查询或临时 `data_dir`？
- [ ] 能否用已有 HTTP 接口代替 Python 一行 `save_*`？

PR 描述中若动过本机共享库，应写明「已手工清理号池 / 未写库」。

## 7. V5 配置与运行入口

唯一界面为 Workbench。项目环境中的“控件定位”提供 typed 定位、敏感属性、版本冲突处理、人工发布和只读探测；探测只导航和读取，不点击/填写，不代表用例通过。用例面板负责文字编译、资格预览、基线配置、预期强度审阅、冻结发布；运行只消费冻结计划和已配置能力快照，不在运行时调用模型猜动作。

资源沿用真实 ResourceClaim `version`（当前目录版本 10），不是新增 schema 字符串。首期 Web 仅支持 logged_out/guest 且不含未支持 prep；`resource_key.v5_baseline.control_id` 必须由项目配置选择已发布登录标记。每案新 context 后实际确认该标记 not_visible，失败即停。账号 resource_ref 必须指向本项目可用账号及支持字段；缺值/锁定/未知源不猜测。

控件定位或能力目录更新使已有发布需要重新核对；文字保存/导入/重编译只更新草稿，不改已发布内容。发布事务重新核对资源、编译产物、全部控件及能力快照；不以页面先前的资格状态替代并发校验。

视觉断言格式修改须同时检查 `agent-vision-assert` 和 `assert-vision` 的顶部范例、判定流程与收尾提示，更新 job version，并记录实际调度 prompt_version/prompt_sha。详见 [cr-008eeb42ce13 诊断](架构/V4/视觉校验输出契约冲突-cr-008eeb42ce13.md)。

辅助请求幂等与 IM 确认异常详见 [cr-72f483f92cdf 故障记录](架构/V4/辅助请求幂等键冲突与IM确认异常-cr-72f483f92cdf.md)。负编号本身不代表只读，插件发送也必须保留完整身份和业务 delivery_id 去重；无任务 RPC 不伪造活动任务。
