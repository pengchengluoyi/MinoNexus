# 按 ID 查询日志

## 1. ID 层级（先对齐名字）

```text
任务 / 批次 run_id          cr-9478d0b7d12d
    └── 用例 case_id        case-7bff9406
            └── 会话 session_id（轨迹主键）
                    cr-9478d0b7d12d::case-7bff9406
```

| 名称 | 示例 | 说明 |
|------|------|------|
| **任务 ID** | `cr-9478d0b7d12d` | `run_store.new_run_id()`；Studio 任务中心、表 `app_regression_runs.run_id` |
| **用例 ID** | `case-7bff9406` | 项目用例库内的 `case_id` |
| **会话 ID / report_run_id** | `cr-9478d0b7d12d::case-7bff9406` | `session_meta.session_id` 与 `session_events.session_id` 的默认值 |
| **按设备覆盖** | `cr-…::case-…::<sn>` | `coverage=per_device` 时同一 case 多设备各一条 session |

函数定义：`mino_nexus/services/run_store.py` → `report_run_id(run_id, case_id, sn=..., coverage=...)`.

**注意**：`cr-9478d0b7d12d::case-7bff9406` 是 **会话/轨迹 ID**，不是「任务 ID 的子路径字符串」而已——查 log 时用它作为 `session_id` 最准确。

## 2. 我只知道任务 ID `cr-9478d0b7d12d`

### 2.1 看批次里每条用例结论

```sql
SELECT run_id, app_id, json_extract(payload, '$.status') AS task_status
FROM app_regression_runs
WHERE run_id = 'cr-9478d0b7d12d';
```

用例列表在 `payload` JSON 的 `cases` 数组里（也可用 Python 解析）：

```bash
python3 << 'PY'
import json, os, sqlite3
db = os.path.expanduser("~/.mino-nexus/mino.db")
row = sqlite3.connect(db).execute(
    "SELECT payload FROM app_regression_runs WHERE run_id=?",
    ("cr-9478d0b7d12d",),
).fetchone()
if not row:
    print("run not found")
else:
    p = json.loads(row[0])
    for c in p.get("cases") or []:
        print(c.get("case_id"), c.get("status"), (c.get("summary") or "")[:80])
        print("  report_run_id:", c.get("report_run_id"))
PY
```

### 2.2 列出本任务下所有 Session

```sql
SELECT session_id, case_id, status, event_count, summary, started_at, finished_at
FROM session_meta
WHERE run_id = 'cr-9478d0b7d12d'
ORDER BY started_at;
```

HTTP：

```http
GET /case-runner/sessions?run_id=cr-9478d0b7d12d&limit=100
```

若某 case **没有** `session_meta` 行：可能未执行到 `open_session`（排队取消、409 DeviceBusy、配置错误等），先看 `app_regression_runs` 里该 case 的 `status` / `summary`。

## 3. 我直接有会话 ID `cr-9478d0b7d12d::case-7bff9406`

这是查轨迹的 **首选键**。

### 3.1 摘要

```sql
SELECT * FROM session_meta
WHERE session_id = 'cr-9478d0b7d12d::case-7bff9406';
```

### 3.2 全量事件（分页）

```sql
SELECT seq, type, turn, phase, substr(payload, 1, 120)
FROM session_events
WHERE session_id = 'cr-9478d0b7d12d::case-7bff9406'
ORDER BY seq;
```

事件很多时按段拉：

```sql
SELECT seq, type, payload
FROM session_events
WHERE session_id = 'cr-9478d0b7d12d::case-7bff9406' AND seq >= 200
ORDER BY seq LIMIT 100;
```

HTTP：

```http
GET /case-runner/sessions/cr-9478d0b7d12d::case-7bff9406/events?from_seq=0&limit=500
```

### 3.3 只看工具调用链

```sql
SELECT seq, type,
       json_extract(payload, '$.capability_id') AS cap,
       json_extract(payload, '$.status') AS st,
       json_extract(payload, '$.summary') AS summary
FROM session_events
WHERE session_id = 'cr-9478d0b7d12d::case-7bff9406'
  AND type IN ('tool/call', 'tool/result')
ORDER BY seq;
```

### 3.4 只看 Guard / 熔断

```sql
SELECT seq,
       json_extract(payload, '$.guard_id') AS guard_id,
       json_extract(payload, '$.reason') AS reason,
       json_extract(payload, '$.capability_id') AS cap
FROM session_events
WHERE session_id = 'cr-9478d0b7d12d::case-7bff9406'
  AND type = 'guard/block'
ORDER BY seq;
```

```sql
SELECT payload FROM session_events
WHERE session_id = 'cr-9478d0b7d12d::case-7bff9406'
  AND type = 'ops/guard_summary';
```

### 3.5 结束原因

```sql
SELECT json_extract(payload, '$.status') AS st,
       json_extract(payload, '$.summary') AS summary
FROM session_events
WHERE session_id = 'cr-9478d0b7d12d::case-7bff9406'
  AND type = 'session/end';
```

或读 `session_meta.summary` / `status`。

## 4. Studio 里只有「流 ID」或旧 run 别名

`GET /case-runner/agent/steps/{run_id:path}` 会调用 `resolve_session_id`：

1. 若参数本身已是 `session_meta` 主键 → 直接用。
2. 若是 `cr-xxx` + 已知 `case_id` → 尝试 `cr-xxx::case_id`。
3. 若同批仅一条 session → 可能自动匹配（多 case 时勿依赖猜测）。

代码：`mino_nexus/services/session_store.py` → `resolve_session_id`。

## 5. 与 LLM dispatch 对照

1. 在 `session_events` 找 `type = 'llm/response'` 的 `payload.dispatch_id`。
2. `GET /settings/dispatch/{call_id}` 看完整 messages / 原始 JSON。

反向：在 dispatch 详情里若有 `run_id` / `session_id` 绑定字段，再回查 session。

## 6. 快速检查清单

| 目标 | 命令 / SQL |
|------|------------|
| 任务是否存在 | `app_regression_runs` WHERE `run_id` |
| 哪条 case 失败 | 解析 `payload.cases[]` |
| 有无轨迹 | `session_meta` WHERE `run_id` 或 `session_id` |
| 失败一句话 | `session_meta.summary` 或 `session/end` |
| 卡在哪一步 | `tool/result` + `turn/end` + `guard/block` |
| 模型为何这么选 | 同 turn 的 `llm/response` + dispatch |

## 7. 复跑与对比

单会话复跑（需 token + 设备 SN）见 [CASE_RUN_FIXES.md §3.2](../CASE_RUN_FIXES.md)：

```http
POST /case-runner/sessions/{session_id}/replay
```

对比两次跑批时，用 **不同** `run_id`，分别查各自的 `session_id`，不要混用 `seq`（会话内单调，跨会话不可比）。
