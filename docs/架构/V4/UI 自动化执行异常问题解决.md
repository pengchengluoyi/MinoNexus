## 1. 结论与本轮目标

MinoNexus 的服务端决策、Scout 设备执行、工作台展示这一分层应保留。当前 UI 自动化的主要阻塞集中在执行契约、状态依赖、证据判定和错误归因，不宜继续只靠增加提示词、扩大能力菜单或提高重试次数解决。

V4 现有工作主要是提示词文件化及 IM/MCP 接入。它们改善维护与入口体验，但不能代替执行核心的可靠性建设。社交方案明确不改 `loop/*`、`catalog/*`、`action_space/*`，因此 V4 应增加一条独立的“UI 执行可靠性”主线。

本轮先收敛“账号输入 → 发码 → 取码 → 登录验收”链路，再扩大用例和应用范围。成功标准不是任务被成功创建，也不是某次偶然跑通，而是：成功有证据、失败可归因、必要前置不被越过、相同条件下结果可重复。

### 1.3 运行基线与因果判断

本次读取的最近 100 条 Session：`fail=84`、`pass=7`、`cancelled=7`、`blocked=2`。这是不同版本、用例和反复调试混合样本，不是当前版本通过率，也不是模型准确率。

核心因果链：

```text
计划/状态/能力/证据契约不一致
→ 上游继续选择下游不允许的动作
→ 局部守卫和恢复反复介入
→ 没有新事实却继续循环、重复输入或重新规划
→ 超时/熔断覆盖首个原因

动作成功、模型判断与业务验收混用 pass
→ 无逐项证据强约束
→ 状态提前或批量推进
→ 报告无法证明究竟验收了哪些内容
```

优先堵住错误通过与无进展循环，再提升执行成功率。不能靠放宽准出和增加重试获得更好看的绿色结果。

## 2. 实际故障、输入契约与改进

### 2.1 取验证码能力与当前菜单不一致，最后被误报为“只有规划”

**证据：日志确认、代码确认。**

Session：`cr-f7b7e433cbf0::case-ed53e597::webe22615fbbb917111`。

| seq | 事实 |
|---|---|
| 288 | 里程碑切换到 `otp_fetch` |
| 296 | `context/menu` 只有输入、点击、滑动、等待等能力，没有 `get_otp` |
| 306 | `exec/vision` 记录“未注册能力已跳过：get_otp”，没有动作 |
| 313、323 | 再次出现缺少能力的菜单和无动作结果 |
| 326 | 最终失败摘要为“连续两回合只有规划、没有可下发的动作，已停止。” |

当前 `mino_nexus/ai/planner.py::vision_exec_turn` 在聚焦能力与可用菜单求交后为空时，返回无 action 的 `continue`。这把可识别的能力路由问题转成了后续空转熔断。

**不能据此认定 `get_otp` 在整个能力目录中未注册。** 仍需区分注册、启用、阶段过滤、平台过滤、节点可用性和程序钩子分流。

**改进：**

1. 编译计划为每步明确执行类别：UI 动作、程序钩子、断言、等待或恢复。内部标识可沿用现有字段，不要求另建重复真源。
2. `get_otp` 等程序钩子走既有程序执行路径，不因当前聚焦而误入视觉设备菜单。
3. 开跑前展开逻辑块，检查完整依赖：能力启用、平台支持、执行实现、节点、插件及必要资源。
4. 运行时依赖失效立即给出结构化阻塞原因，禁止返回无动作 `continue` 消耗空转预算。
5. 日志记录过滤前候选、过滤规则及排除原因；不将所有缺失统一描述为“未注册”。

**建议错误分类：** `capability_not_registered`、`capability_disabled`、`capability_filtered_by_phase`、`platform_unsupported`、`executor_unavailable`。具体枚举应并入现有统一错误契约。

**验收：**正常路径能派发取码钩子；能力不可用时在准确位置停止，摘要指出依赖原因，不再以“只有规划”结束。

### 2.2 已下发坐标，却报“连续三次没有坐标”

**证据：日志确认、代码确认。**

Session：`cr-56102136b3ee::case-ed53e597::webe22615fbbb917111`。

| seq | 事实 |
|---|---|
| 169 | 程序链 `account_fill` 触发 `no_web_coords`，转视觉兜底 |
| 183、184 | 下发带 `x/y` 的 `input_text`，工具返回失败 |
| 194 | 再次进入程序链视觉兜底 |
| 208、209 | 再次下发带 `x/y` 的输入，工具返回失败 |
| 219 | 第三次进入同类兜底 |
| 223 | 最终报“连续 3 次没有坐标可填写” |

`loop/program_device_fallback.py::note_vision_fallback_streak` 计数的是同一里程碑进入兜底的次数；`loop/agent_loop.py` 将其解释成没有坐标的次数。两种事实并不等价。

**改进：**

- 分离程序定位未命中、视觉输出缺坐标、设备执行失败、焦点未确认、读回失败和业务后置条件不成立。
- 程序链定位未命中仅表示应选择另一条已允许的定位路径，不直接等于视觉失败。
- 按 `step_id + attempt_id + failure_stage` 记录尝试和计数，避免同一次动作经过多个模块后被重复计为多次失败。
- 达到熔断阈值时保留首个有因果意义的失败、最近失败及导致停止的阈值，不用最后一层兜底名称覆盖原始原因。
- 显示重试链：为什么重试、换了什么、是否产生新证据。

**验收：**带坐标动作已派发时，不能总结为“视觉没有提供坐标”；程序未命中后视觉成功不应继续消耗“缺坐标”计数。

**待核实：**Scout 输入失败究竟来自焦点、元素位置、输入实现还是读回规则。现有失败字段部分只重复输入摘要，证据不足以确定设备侧根因。

### 2.3 必要输入失败后，仍推进到发码

**证据：历史日志确认；是否符合用例原始意图仍需核对。当前已出现改进：后续任务 `cr-737065156a7f` 明确以 account_fill 未通过阻止后续步骤；这只证明该次阻断出现，不能证明所有路径已经统一。**

在 `cr-f7b7e433cbf0` 中，账号输入两次返回失败；seq 210 记录 `milestone/program_fail(account_fill)`；后续仍执行发码并进入取码。

**改进：**

1. 为里程碑明确依赖和失败处理：成功路径所需前置必须获得验证结果后才能推进。
2. 区分“执行尝试失败”与“业务条件不成立”。工具返回失败但有充分独立证据证明输入已达成时，可以按明示规则重新裁定，必须记录证据，不能静默越过。
3. 异常测试允许继续，但必须由用例显式定义。例如无效邮箱提交后检查错误提示，不能被全局登录块强制改成成功登录。
4. 后续准出统一读取依赖契约，不分别由宏、视觉回看和普通循环各自决定。

**验收：**普通成功登录路径中，账号输入未验证不得进入发码；异常路径能按作者定义继续，并保留其独立预期。

### 2.4 “验证码框可填写”不足以证明已发码

**证据：代码确认、设计风险。**

初次检查时，`loop/visual_review.py::_visible_expected` 将 `send_code` 的可见预期设为“验证码框已经可以填写”，可能误通过。最新检查已见其改为倒计时、发送成功提示或已发送状态，属于部分实现；尚未拿到对应构建的运行验收，且仍需确认应用中这些信号是否足以证明本次请求被接受。

**改进：**

分别描述三个事实：

- `otp_input_available`：验证码输入框可操作。
- `otp_request_accepted`：本次发码请求已被接受。
- `otp_received`：本次请求对应的验证码已到达。

纯 UI 路线使用该应用明确约定的发送成功提示、倒计时等证据；接口辅助路线使用约定响应或业务事件。证据不足应停止或补充观察，不能以输入框存在替代发送成功。

取码需要关联收件对象、发码时间窗口、用途以及可获得的请求标识，避免读取旧验证码。日志不得记录验证码、密码等敏感值。

**验收：**输入框始终可填、发码请求失败、邮箱存在旧验证码三个场景，均不能误判为本次发送并取码成功。

### 2.5 输入事件优化：无坐标输入与可见部分验证

> **决策**：采用“点击定位、输入写入、截图确认”的分工。输入事件去掉坐标；对于输入框宽度造成的省略或裁切，允许仅验证可见部分并按该策略通过输入步骤。不得把这一结论描述为隐藏部分已完整验证。  
> **状态**：当前焦点输入及部分门禁已见于代码；部分可见验证的结构化结果仍待核验/实施，完整链路待运行验收。本节细化 §3.2、§3.3 中输入事件的契约；与旧版输入必须携带坐标、视觉必须读到完整字符串的要求不一致时，以本节目标方案为准。

#### 2.5.1 演进背景与当前差距

初次排查时的 Web 看图输入链路不是完全基于截图：先点击输入框，模型在 `input_text` 中再次提供坐标；Scout 根据坐标查找 DOM 可编辑元素，调用 `fill()` 或键盘操作，再读取节点值检查是否包含完整预期文字。工具成功后，Nexus 下一回合再看图确认。

代码入口：

- Nexus：`action_space/assemble.py::visual_point_missing`、`action_space/visual.py::apply_visual_point`、`loop/visual_review.py`。
- Scout：`executors/playwright_executor.py::_input`、`_commit_input_value`、`web_focus.py::locate_editable_at`。
- Scout ADB 分支：`executors/adb_executor.py::_input_text` 再按坐标点击，然后执行文字输入，以命令结果报告执行状态。

旧链路问题是重复定位可能改变输入目标，节点定位或读回失败可能阻断后续视觉确认。最新代码已新增 `current_focus`：Web 使用键盘选中/插入，ADB 直接调用文字输入。不能继续把“Web 一定要求坐标”作为当前代码结论；最新 ADB 替换语义、焦点关联和兼容检查的问题见 §2.6。其他设备执行器仍需独立核对。

本轮在运行代码中未检索到 `evidence_scope`、`visible_partial`、`hidden_content_verified`、`verification_policy` 等方案字段。`visual_review` 检查单仍主要传递 x/y、role、field、截取后的 expected，回看主要返回 pass/fail。因此不能将“文档或提示词允许部分匹配”宣称为“结果已可审计”。

#### 2.5.2 目标执行链路

```text
看图识别目标输入区域
→ 点击该区域建立焦点（点击事件有坐标）
→ 向当前焦点写入（输入事件无坐标、不再次点击）
→ 获取输入后的新截图
→ 验证目标区域中的可见内容
→ 通过后才允许推进依赖步骤
```

当前焦点输入模式不再要求或隐式补充 `x/y`，不按坐标重新查找另一只输入框。坐标输入和节点输入保留各自校验，不能全局删除所有输入模式的坐标约束。目标描述、前次点击区域和控件身份保留在观察/验证上下文中，而不是作为输入事件的第二次定位指令。

建议参数形状（新契约示意，不代表已实现）：

```json
{
  "capability_id": "input_text",
  "params": {
    "text_ref": "leased_account.email",
    "target_mode": "current_focus",
    "mode": "replace",
    "focus_ref": "focus-action-123"
  }
}
```

- `mode=replace` 表示替换，`append` 表示追加，二者不能靠执行器自行猜测。
- `target_mode` 明确输入目标方式；`mode=replace` 只说明写入方式，不能据此推断目标是当前焦点。
- `focus_ref` 关联同一会话中的具体聚焦动作 ID，不等于证明焦点始终有效。若上游使用 `previous_focus_action` 别名，须由 Nexus 在派发前解析为具体引用；未解析或引用失效不得静默采用任意焦点。
- `text_ref` 是 Nexus 侧资源引用，派发前按现有资源绑定契约解析为 Scout 所需输入值；不要求 Scout 理解账号池业务引用，日志不记录敏感明文。
- 同一设备/浏览器会话串行操作；点击与输入之间不插入其他点击、导航或窗口切换。发生这些变化时废弃旧聚焦上下文，重新定位。
- 普通场景点击后紧接输入，再统一回看，避免默认增加一轮只验证焦点的模型调用；焦点可能被弹窗等改变时才增加中间观察。
- 纯图路线由键盘/输入通道写入，不能继续将 DOM 读回作为唯一成功门槛。允许 DOM 辅助的混合路线另行声明，不能静默混入纯图评测。
- 执行器只说明写入动作是否完成；目标正确性与内容正确性由后续验证裁定。回执未知时先观察，禁止直接重复追加。

#### 2.5.3 支持输入框截断后的部分文案确认

普通可见文本输入默认采用 `visible_content` 策略：完整显示时进行完整匹配；存在明确显示截断证据时允许部分匹配。作者明确要求完整值断言的检查点仍使用 `exact_value`，不得自动降级。

例如完整预期值是 `xxxx.@gmail.com`，输入框因宽度显示为 `xxxx.@gmail...`，其中末尾 `...` 为界面省略标记：允许验证 `xxxx.@gmail` 与预期前缀一致，并将输入步骤按部分可见策略判为通过，无需因为 `.com` 隐藏而失败。

部分验证必须同时满足：

1. **区域正确**：文字位于本步骤的目标输入区域，不能用其他字段、页面提示、输入法候选栏或旁边已有的账号文字证明。
2. **观察新鲜**：使用本次输入动作之后的截图，关联该动作及尝试；若之前已有相同内容，只能证明当前可见状态满足，不能宣称本次写入动作已被独立证明。
3. **确有显示截断依据**：有省略标记、输入框边界裁切或横向滚动等证据。不能仅因实际内容比预期短，就假设剩余文字被隐藏；`maxLength` 导致内容根本未写入不属于显示截断。
4. **匹配方式明确**：尾部隐藏比较前缀；头部隐藏比较后缀；中间隐藏分别比较可见前后段及其顺序；只露出中间片段时需有位置/滚动上下文，不能任意子串出现即通过。
5. **可见内容无冲突**：可读部分任何字符与对应预期冲突，应判不通过；不因“整体像邮箱”忽略错误。
6. **片段有区分度**：结合目标字段和本次预期值，能排除当前已知候选或旧值。仅看到 `@gmail...`、一个字符或通用后缀等无法区分的内容，记证据不足，不设置适用于所有字段的武断固定字符数。
7. **省略号按来源处理**：只有确认属于渲染省略标记时才从比较中排除；实际输入值中的 `...` 或 `…` 不得被自动删除。无法区分时记证据不足。示例中的 `xxxx` 也是示例字符，不是匹配通配符。

截图只支持部分内容时，允许在上述条件满足后关闭普通输入里程碑，但必须保留验证范围；后续发码、提交、登录身份仍按各自独立条件验收，不能借用输入通过结论。

#### 2.5.4 验证结果与状态

下列字段为建议补充，应并入现有检查单和 Session 投影，不另建执行真源：

```json
{
  "verification_policy": "visible_content",
  "verdict": "pass",
  "evidence_scope": "visible_partial",
  "match_kind": "prefix",
  "truncation": "tail_ellipsis",
  "hidden_content_verified": false,
  "action_ref": "input_attempt_id",
  "target_ref": "target_control_id",
  "observation_ref": "post_input_screenshot_id"
}
```

| 观察结果 | 判定 | 是否推进普通输入步骤 |
|---|---|---|
| 完整可见且与预期一致 | 通过，`visible_full` | 是 |
| 明确显示截断，足够的可见部分匹配且无冲突 | 通过，`visible_partial` | 是，记录隐藏内容未验证 |
| 输入到错误字段或可见字符有冲突 | 不通过 | 否 |
| 页面仍在加载或输入法仍在组合输入 | 待观察 | 有界等待，不提前通过 |
| 片段不足、截断原因不明、图像模糊或省略号来源不明 | 无法判定 | 补充观察或结束为证据不足 |
| 检查点要求完整值，但当前只有部分可见 | 尚未满足完整值断言 | 不以部分匹配通过该断言 |

工作台建议显示“输入通过（可见部分匹配）”，不能显示“完整值已确认”。Session 记录策略、范围和证据引用；敏感文本沿用脱敏要求，不为展示匹配详情新增明文凭据日志。

#### 2.5.5 回看、重试和扩展边界

保留下一回合先验证上一输入的机制。检查单从“本次输入坐标”调整为“目标区域/控件 + 输入模式 + 预期引用 + 验证策略 + 动作后的截图”。历史点击区域仅为辅助，页面移动后重新识别，不能把旧像素当作永久目标。

模型同一回合可以提出下一动作，但程序须先接受上一输入的验证，再检查下一动作的依赖。部分验证符合本节策略时可以推进；失败或无法判定时不得执行同时提出的发码动作。

无法确认时可放大截图检查清晰度；放大不能恢复画面中未显示的字符。必要时通过明确的光标或水平滚动观察补充片段，但不得默认重复输入，也不得滚动到另一字段后继续沿用旧目标。仅追加新观察，避免焦点变化造成误写。

密码掩码、富文本、分格验证码、中文输入法组合输入单独定义规则。圆点数量不证明密码内容；部分匹配不证明完整验证码；超过实际字段长度限制而丢失的字符不能算隐藏成功。

#### 2.5.6 实施与验收

同步修改 Nexus 能力参数 Schema、视觉提示词、坐标必填校验、程序链兜底和回看检查单；Scout 增加明确的当前焦点输入语义，分别实现替换/追加；同步协议文档与 golden fixtures。不可只改提示词让模型省略坐标，否则现有两端仍会拒绝。

| 场景 | 必须结果 |
|---|---|
| 点击邮箱框后无坐标输入 | 不重新点击，正确写入并回看 |
| `xxxx.@gmail.com` 显示为 `xxxx.@gmail...`，确认是尾部省略 | 前缀匹配可通过，记录部分验证 |
| 输入框横向滚动只显示有区分度的尾部 | 后缀与预期一致且截断证据充分时可通过 |
| 仅显示通用域名，无法区分账号 | 证据不足，不误通过 |
| 可见前缀出现错误字符 | 不通过 |
| 邮箱进入验证码框，或页面其他位置已有同一邮箱 | 不通过目标验证 |
| 界面真实文本包含省略号 | 保留字符，不把它无条件当显示标记 |
| 字段长度限制丢弃尾部字符 | 不当作显示截断通过 |
| 明确要求完整值但画面只显示前缀 | 完整值断言不通过验收，继续补证或报告不足 |
| 替换输入重试、回执超时 | 不重复追加；先观察再决定重试 |

本项只允许按声明的部分可见策略通过输入步骤，不降低其他业务断言要求。

### 2.6 Scout 输入契约升级与运行能力协商

> **决策**：当前焦点输入需要更新 Scout 的实际执行实现；不能仅删除 `x/y` 校验。后续只有设备执行语义或采集能力变化才需要相应节点实现升级，业务流程和验证规则尽量由 Nexus 演进。  
> **新增依据**：任务 `cr-65b60adb09d9` 最初由用户报告，最近深度分析已独立核对 Session：三次无坐标输入被旧 Scout 拒绝，最终被重复输入熔断覆盖。当前已见能力上报、门禁和新输入分支，但尚未进行对应运行验收。

#### 2.6.1 本次失败分类

按已核对的 Session，打开页面、租号、点击登录入口及邮箱框成功；随后三次 `input_text` 均带 `mode=replace`、`focus_ref=previous_focus_action`，不带 `x/y`。运行中的旧 Scout 三次返回“Web 输入(email) 需要坐标 x/y”，最终触发同字段失败熔断。

该现象首先归类为 Nexus 与运行中 Scout 的输入契约不兼容，不能归为被测产品输入失败，也不能据此否定无坐标方案。相同旧执行器重复接收相同新参数不具备恢复条件，第一次明确拒绝后就应阻塞，不再重试三次。

#### 2.6.2 按模式校验，而非整体取消校验

| `target_mode` | 必需条件 | Scout 行为 |
|---|---|---|
| `current_focus` | 有效会话、受支持的写入模式、有效聚焦关联 | 向当前焦点输入；不要求坐标，不隐式点击或另找控件 |
| `coordinate` | 有效 `x/y` 及对应坐标约定 | 按该模式定位再输入，缺坐标明确拒绝 |
| `node` | 有效节点或定位参数 | 按控件定位输入，定位不成立明确拒绝 |

`replace` / `append` 与目标模式正交，分别定义清空替换和追加语义。实际支持情况按平台/执行器声明，不假设所有组合都可用。

Scout 仍检查设备/页面会话有效、请求上下文一致、参数合法、执行能力支持及可观察的焦点失效事件。焦点是否属于业务上的邮箱框，在纯视觉路线由后续截图验证；不能为此强制恢复 DOM 定位门槛。纯视觉难以直接证明的焦点状态应明确为未知，不伪造“焦点确认”。

当前焦点输入使用已声明的键盘/输入通道，不通过 DOM 直接赋值冒充真实焦点输入。节点 `fill()` 如需保留，归入节点或明确声明的混合实现。

旧协议缺少 `target_mode` 时按其原有、明确记录的旧版本语义处理，不将“缺坐标”自动解释成当前焦点模式。新协议要求显式模式。避免参数缺失被静默解释成另一种动作。

**当前实现差距（需在宣称完成前修正）：**

- `mino_scout/input_contract.py` 声明 ADB 当前焦点输入支持 `replace/append`，但 `adb_executor.py::_input_text` 当前焦点分支没有读取 mode、没有清空旧值，直接输入。先实现替换，或撤回 replace 声明；坐标分支的 replace 声明也需对照清空语义核验。
- Web `_input_focused` 使用 `ControlOrMeta+A` 和 `keyboard.insert_text`；需按所支持控件验证替换、追加及输入事件兼容性，不以“键盘 API 未报错”代替字段验收。
- Nexus 当前任何成功 `tap_element` 都可设置 `focus-{seq}`；Scout 主要检查引用非空且不是占位符，并未在该分支验证引用确实对应当前会话中的目标聚焦。应绑定会话/页面/动作，区别普通点击与输入目标建立，并处理导航、窗口切换、重启等失效。
- 当前能力清单是静态声明；必须保证与实际实现及可用执行器一致，不能把“已声明”视为“已验证”。协议版本和支持组合需要共同校验。

#### 2.6.3 运行节点上报能力，Nexus 派单前匹配

能力目录仍由 Nexus 维护业务声明与路由真源；Scout 上报的是当前运行实现的支持清单，不复制一套业务目录、不决定步骤顺序。注册及能力变化后的上报至少包含：运行版本/构建标识、协议支持版本、执行器、能力及支持的参数组合。心跳可携带清单摘要与变化标识，避免每次重复传整表。

示意形状（待纳入现有协议，不表示当前已有字段或版本号）：

```json
{
  "runtime_version": "running-build-id",
  "capabilities": [
    {
      "id": "input_text",
      "executor": "playwright",
      "platform": "web",
      "contract_version": 2,
      "supported_combinations": [
        {"target_mode": "current_focus", "write_modes": ["replace", "append"]},
        {"target_mode": "coordinate", "write_modes": ["replace"]},
        {"target_mode": "node", "write_modes": ["replace"]}
      ]
    }
  ]
}
```

上述组合仅为格式示例，节点只上报实际已实现且可用的组合。Web 支持不代表 ADB、Android 其他执行器或桌面执行器支持。

Nexus 开跑前将编译计划依赖与节点能力求交；缺少 `current_focus + replace` 时启动前阻塞并提示具体节点升级。依赖在运行中变化时，在下一次相关动作派发前重新检查；Scout 仍在接收端验证，防止能力快照过期。不得仅凭包版本字符串猜测支持情况。

兼容性判断和命中的运行清单摘要写入 Session。安装文件已更新不代表进程已更新，必须等重启后注册的新运行信息确认，才允许新契约派单。

#### 2.6.4 不兼容错误立即阻塞

建议并入统一错误契约：

```text
code: contract_unsupported / parameter_contract_mismatch
failure_stage: compatibility
retryable: false
execution_started: false
```

以上 `execution_started=false` 仅用于确认在执行前拒绝的请求。未知执行结果不得套用此结论。

错误同时携带所需能力、模式、节点实际支持范围及节点运行版本。Nexus 停止该依赖链，投影为环境/依赖阻塞，不调用模型补坐标、不重复同一请求、不消耗输入业务失败预算，也不伪造被测产品缺陷。

兼容旧 Scout 的过渡期，优先通过能力声明判断；对旧格式错误只在结构化上下文充分时做明确兼容映射，保留原始原因，不用宽泛中文关键词永久代替错误码。

焦点偶发丢失或页面未就绪可按规则恢复；回执超时、连接中断导致执行结果未知时先取证，不盲目重发，尤其禁止重复追加文本。

#### 2.6.5 发布、重启与恢复顺序

1. 同一变更周期更新协议文档、两仓解析/校验及 golden fixtures，明确新旧格式兼容边界。
2. Scout 先发布兼容所需新旧模式的实现，并具备准确运行能力上报。
3. 节点按已有部署方式更新、重启，重新注册；有运行任务时先排空或暂停，不能升级中静默重放旧动作。
4. Nexus 仅向已确认支持的节点派发新格式；旧节点执行兼容任务或明确阻塞，禁止临时补坐标掩盖不兼容。
5. 重启或重新连接后旧焦点上下文作废；恢复任务先观察实际页面，必要时重新点击目标，再执行输入，不能直接复用升级前的 `focus_ref`。
6. 回滚同样重新读取运行能力；不支持的模式重新阻塞。部分可见验证仍按 §2.5 执行，不因升级改变验收含义。

#### 2.6.6 哪些变更需要发布 Scout

| 变更 | 是否需要更新 Scout |
|---|---|
| 提示词、用例拆解、业务顺序、恢复策略 | 通常不需要，前提是不依赖新设备能力 |
| Nexus 截图验证允许部分可见匹配 | 通常不需要，沿用已有截图能力 |
| 用已有点击、输入、等待组合新逻辑块 | 通常不需要 |
| Nexus 管理的等待预算、错误归因、结果展示 | 通常不需要 |
| 输入从坐标定位改为当前焦点写入 | 需要相应执行实现，本次属于此类 |
| 新增拖拽、上传、原生窗口操作方式 | 节点没有该实现时需要 |
| 新增设备端属性读回或证据采集 | 节点没有该采集能力时需要 |

原则：Nexus 管业务决策、组合和验收；Scout 提供稳定原子操作并报告执行事实；协议管理支持边界。不为每条业务用例发包，也不为绕开发包而允许下发任意脚本绕过现有能力契约。

#### 2.6.7 验证粒度与验收

每个事件都需要参数/兼容性校验和执行回执，但不要求每个事件后额外调用一次模型。

- 点击输入框与输入可组成一个操作组，在输入后统一截图验证；保存组内各动作的执行记录。
- 输入与发码之间存在业务依赖，必须先接受输入验证结果再发码。
- 租号、取码等程序事件以结构化结果验证，不强行依赖截图。
- 工具成功不代替业务准出；组内验证不能抹掉用例明确要求的中间检查点。

| 验收场景 | 预期 |
|---|---|
| 新 Nexus 对接不支持当前焦点输入的旧节点 | 开跑前阻塞；快照过期时首次明确拒绝即阻塞，无三次重复 |
| 节点文件已更新但旧进程未重启 | 仍以旧运行能力判断，不提前启用新契约 |
| 新 Scout 接收合法当前焦点输入 | 无坐标也执行，不重新点击；按 §2.5 回看 |
| 坐标模式缺少坐标 | 明确参数错误，不偷偷改成焦点输入 |
| Web 支持而 Android 不支持 | 按平台/执行器独立判断，不误派 |
| 更新重启后恢复原任务 | 重新观察并建立焦点，旧引用不直接复用 |
| 焦点失效、输入超时 | 区分可恢复与结果未知，不盲目重复输入 |

## 3. 统一执行与验收契约

### 3.1 收敛“成功”的定义与状态修改入口

V3 动作空间文档同时保留“点下去即成功”和“下一回合回看通过才记 pass”等表述；准出方案又调整了读回方式。应明确新旧方案的替代关系，避免不同模块依照不同版本实现。

统一语义：

```text
动作已派发 → 执行器已完成 → 后置条件已验证 → 里程碑完成
```

建议分开记录 `dispatch_status`、`execution_status`、`verification_status`。字段命名应与现有协议协调；跨 Nexus/Scout 的变更按仓库协议 golden fixture 流程同步。

状态机拥有里程碑状态的最终修改权。规划器、宏、视觉回看和钩子只提交事件及证据，由统一归约逻辑处理，防止先 pass、切阶段后再回滚。

一次结果至少关联 `run_id`、`case_id`、`step_id`、`attempt_id`、动作标识和证据引用。设备断线或响应超时造成结果未知时，应先核实是否执行，不能直接重复有副作用的动作。

逐步收敛三个最终决策点：派发门禁决定当前动作是否合法；状态归约决定新事件如何改变状态；验收聚合决定哪些检查点有充分证据。规划、宏、回看、守卫恢复只提交候选动作或结果，不能各自直接给不相关步骤补通过。先迁移登录输入链路，不以一次性重写整个 loop 作为前提。

### 3.2 定位策略与验证策略分离

禁止视觉坐标被设备层悄悄替换成另一节点是正确的；但不能由此推导出视觉点击后禁止一切结构化验证。

| 维度 | 可选策略 |
|---|---|
| 定位 | 视觉坐标、DOM、无障碍节点 |
| 验证 | 截图、节点属性、接口、业务事件 |

同一个动作必须明确实际采用的定位策略，不静默换点。验证可以按预先声明的契约组合证据。例如视觉点击、节点读回、接口确认身份。

保留纯视觉模式用于真正的 Computer Use 评测；保留混合模式用于工程回归。两者分别报告能力范围和成功率，不混为一个指标。此项属于建议调整，需同步更新目前“不改道”的产品契约后实施，不能在执行器里私自添加 fallback。

### 3.3 不把证据不足强制压成 pass/fail

画面稳定不等于证据充分，密码掩码、异步任务、短暂提示、后台状态均可能无法从截图证明。

| 验证结果 | 含义 | 处理 |
|---|---|---|
| 通过 | 证据证明条件成立 | 允许推进 |
| 不通过 | 证据证明条件不成立 | 按用例失败策略处理 |
| 待观察 | 仍在规定等待窗口 | 有界等待后重新观察 |
| 无法判定 | 观察渠道无法提供充分证据 | 补充允许的证据或结束为证据不足 |

待观察必须有截止时间；无法判定不能算产品缺陷，也不能算通过。模型漏填字段属于输出契约错误，应与界面失败分开。

### 3.4 控件身份加入页面和容器作用域

`services/control_registry.py::ensure_control` 当前以 `project_id + desc_key` 查询复用控件，查询没有纳入具体页面和容器身份。不同页面同名“确认”按钮有错误复用风险，尚未证明导致上述失败。

建议区分：业务控件身份、页面/容器身份、各平台定位绑定。至少能表达应用、页面或页面状态、容器、控件角色及业务用途。`scope=dialog` 只说明容器类型，不能区分两个不同弹窗。

跨平台可共享业务语义，但不能仅因文本相同就共享具体绑定。绑定应记录平台、适用版本、来源、最后验证时间及状态。旧控件拆分采用显式映射迁移，保留历史 Session 的引用意义。

### 3.5 编译合格不等于运行就绪

保留作者原文、编译计划和运行绑定的分层。进一步分开：

- 编译有效：原文映射、参数、断言结构符合契约。
- 能力可覆盖：所需能力及验证方式已实现。
- 本次运行就绪：节点、账号、插件、环境及定位条件满足。

现有 `_stored_plan_fresh` 主要检查编译器名称、目录版本、原文和阻塞警告。建议补充实际影响产物的依赖版本或摘要，例如编译提示词、Schema、平台、逻辑块版本；是否需要失效应按依赖关系判断，避免每次保存全部重编译。

当前 `loop/input_contract.py::focus_input_block_reason` 将 case 序列化后查找“输入 / input_text / login_flow”，固定检查 replace；这可能漏掉逻辑块内依赖，或把预期文字误当动作需求。非 Web 被归为 ADB/Android 的分支也不能自动代表其他平台的执行器选择。

改为编译计划显式导出 `required_capabilities`，展开逻辑块后记录平台、执行器、契约版本和参数组合；派单时按实际路由复核，不靠自然语言关键词。

不能为了提高启动率而绕过未映射片段或未知断言；也不应把暂时节点离线永久写成用例不可自动化。

### 3.6 断言严格解析与逐项验收

**历史风险与当前整改，不直接等同于已确认历史误通过。**

1. 旧解析曾使用 `bool(raw.get("passed"))`，非空字符串 `"false"` 可误变为 True；当前已严格要求 JSON 布尔值。
2. 旧路径空 evidence 只记警告；当前不再允许空证据通过。模型 confidence 仍是自报分数，不是独立证据或经校准的准确率。
3. 旧批量总 passed 可覆盖剩余检查点；当前已强制逐项 ID、布尔值及观察证据，不能总结果补绿。

**2026-10-11，cr-d284bca36cd8 / case-ed53e597 的已确认误失败：**校验模型原始响应（ds-69ee3c08ec46）总体和 ck_s1_0 均为 passed=true，且有完整证据。vision_assert 将 seen 集合与 requested 字典直接比较，恒不相等，误报“逐项结果未覆盖全部校验点”并改成 false。已修正为与 set(requested) 比较，同时检查请求 ID 是否为空或重复；未知 ID、重复响应、缺项、非法布尔及无证据仍拒绝通过，保留合法逐项结果供诊断，不以丢空数组掩盖原因。

**本轮代码变更，待新 Session 验收：**AssertResult 增加内部 error_kind；无截图、模型服务不可用/空响应、输出契约异常、检查点应用失败进入 blocked，记录 check/blocked 和 business_verdict=unknown，不再生成“页面预期未成立”。真实且完整的必选项不通过才判 fail。assert/vision、assert/dom 同时记录 status/error_kind，Session 归因同步读取；不改 Scout 协议或历史任务。

整体通过由有效逐项结果中的 required 项计算；选填项仍须返回合法结果，选填不通过如实记录 failed，但不阻止必要检查点准出。DOM 不支持的检查、缺少参数或目标不唯一通过显式 CheckUnavailable 报校验未完成，而非页面失败；本轮不伪称实现了 DOM 居中样式等能力。结构化看图不再丢弃前后对比上下文，element/rules 仍是目标真源；历史上下文不是新增断言依据，单张截图无法证明完整过程。agent-vision-assert 提示词 version 3 统一 ai_reasoning/checkpoint_results 字段及必选聚合语义。上述代码校验不代替新任务运行验收。

**目标规则：**

- 严格接收布尔值或声明的 verdict 枚举；字符串布尔、缺字段、结构错误归为输出契约错误，不做 truthiness 转换。
- 输出以 checkpoint_id 为键，每项带 verdict、观察事实、证据引用、evidence_scope、未验证内容；拒绝未知 ID、重复 ID，缺失必要 ID 保持未验证。
- 单项通过要求满足该项证据契约。空证据、错截图、无关目标不能通过；通过文字本身不能代替证据。
- 整体结果由程序聚合，所有适用的必要项目通过才验收。未知/缺失不能补绿，单个整体 true 不再覆盖未完成项目。
- 批量模型调用可以保留以节约耗时，但必须逐项返回。程序化验证也须说明覆盖哪些 ID，而不是通过一个总开关覆盖全部。
- 模型调用失败、返回空、解析失败与真实断言不成立分开。受控异常输出通过现有回放/验收设施验证，不新增被仓库禁止的 pytest。

## 4. 在 AppIntel 上补可执行业务契约

**运行事实：** `cr-65b60adb09d9` 的 6 条 intel/context_pack 均没有 citations、knowledge body 和 doc context。不能据此认定整个知识库为空，但这次任务确实没有获得这些业务资料。排查顺序是知识是否存在、作用域是否一致、查询是否命中、筛选是否剔除、最后是否注入。不能仅因 AppIntel 已实现就认为模型已了解当前应用。

保留现有 NavFSM、知识条和文档库，不增加一套重复知识真源。必要前后置关系绑定到编译计划，不完全依赖每回合自由文本召回；AppIntel 提供解释、来源和适用例外。把确认过的业务规则投影成执行可消费的结构：

```text
规则来源与版本
当前业务状态
前置条件
允许动作
预期状态变化
禁止副作用
验证方式与证据要求
失败、等待与恢复策略
```

登录只是示例，不是全局硬编码流程：

```text
登录界面已打开
→ 选择验证码登录方式（适用时）
→ 账号输入已验证
→ 发码请求已接受
→ 收到本次验证码
→ 验证码输入已验证
→ 登录提交
→ 当前身份已确认
```

不同应用可有不同分支；异常测试也应有独立路径。全局登录块提供可复用机制，应用绑定提供页面与规则，不能让一种固定登录流程成为所有应用的事实。

模型负责解释页面、解析意图及提出动作；状态机负责合法转换与预算；验证器负责裁定；知识层提供带来源的规则。模型提出恢复建议后，仍须满足原用例边界，不得把失败路径改成另一条成功故事。

知识区分“已确认规则”“当前版本观察”“待验证推测”，避免一次错误运行污染长期知识。评估理解能力可用状态预测、非法操作识别、跨页面一致性和变更影响分析，而不是只评估回答是否流畅。

**结构化执行规则（代码已接入，待运行验证）：**已审核且启用、归属当前应用/项目并带正文的知识条可在扩展字段中声明 `execution_contract`，例如 `{"case_step": 1, "capability_id": "request_sms_code", "requires_milestones": ["account_field"]}`。派发前读取本次运行的里程碑状态，仅全部为 `pass` 才放行该能力；缺失、失败或跳过都产生带知识条 ID 的 `business_precondition_unsatisfied` 阻塞事件。知识正文、推测性条目和模型建议不自动转化为强制规则。业务规则应由维护者确认适用步骤、能力及里程碑 ID；未绑定时沿用已有执行路径。

## 7. 验收场景与指标

遵守仓库 AGENTS.md：本项排查不新增或修改 `tests/test_*.py`，不以 pytest 自证；使用真实 Session 轨迹、受控场景和现有协议 golden fixtures 验证。协议修改仍需两仓同步。固定场景不等于只看一次成功，应记录基线和修复后同条件结果。

### 7.1 最小验收场景

| 场景 | 必须观察到的行为 |
|---|---|
| 正常验证码登录 | 每个必要阶段有证据，最终身份正确 |
| 断言返回字符串 `"false"`、缺失 passed、非法类型 | 输出契约错误，不能判通过 |
| passed=true 但证据为空或目标不相关 | 不通过验收，明确证据不足/契约错误 |
| 批量断言少一个必要 ID、重复 ID 或未知 ID | 不给缺项补绿，拒绝无效结构 |
| 没有已派发动作却返回 prior_status=pass | 不构造虚假回看，不推进 |
| 模型要求跳过必要断言 | 拒绝；条件不适用须有明确谓词 |
| prep 阶段带 flow_block 前缀的重复取码守卫 | 补前置或有界停止，无数百回合空转 |
| ADB replace 输入到已有值的字段 | 完整替换而非追加；不支持则能力声明不包含该组合 |
| 连续两个不同目标的 tap_element | 不因 cap 相同误判重复 |
| 新节点/旧节点、运行版本未重启 | 正确能力匹配；不兼容首次明确拒绝即阻塞 |
| 程序定位未命中、视觉定位成功 | 正确执行，不累积成虚假的视觉缺坐标 |
| 输入框未获得焦点 | 明确焦点或输入验证失败，不盲目推进 |
| 发码失败但验证码框可输入 | 不能将发码标成通过 |
| 邮箱中存在旧验证码 | 不能用于证明本次发送或本次取码成功 |
| `get_otp` 不可用 | 明确依赖阻塞，无空转规划 |
| 页面延迟或截图证据不足 | 有界等待或无法判定，不强行 pass/fail |
| 两个页面有同名确认按钮 | 使用正确页面作用域的控件 |
| 异常输入用例 | 保留异常路径，不被恢复逻辑改成成功登录 |
| 动作回执超时、结果未知 | 先核实是否生效，不直接重复有副作用的动作 |

### 7.2 执行漏斗

```text
选中用例 → 编译合格 → 能力与环境就绪
→ 动作实际下发 → 后置条件可验证 → 业务验收通过
```

每层记录数量、分母和阻塞原因，不能把编译失败、节点离线、模型无动作和产品断言失败合并成同一种失败。

| 指标 | 定义与注意事项 |
|---|---|
| 启动就绪率 | 通过本次运行依赖检查的用例数 / 请求执行的用例数 |
| 有效回合率 | 产生有效动作、有效验证或必要等待进展的回合数 / 执行回合数；无意义重复等待不算进展 |
| 错误归因准确率 | 人工标注样本中，最终归因与实际因果链一致的比例 |
| 证据完整率 | 通过检查点中具备所需、可关联证据的比例；不代表证据本身一定正确 |
| 误通过率 | 受控失败场景中被判通过的比例，需独立标注基准 |
| 部分可见验证占比 | 按 `visible_full` / `visible_partial` / 无法判定分别统计；部分验证计入其声明策略的通过，不计入完整值确认率 |
| 检查点结果覆盖率 | 必需且适用的检查点中有合法逐项结果的比例；不以总 passed 代替 |
| 重复阻塞率 | 状态未变时重复同一阻塞的回合数 / 执行回合数，分别统计程序与模型路径 |
| 业务上下文覆盖 | 有所需确认规则的步骤数 / 需要规则的步骤数；检索次数不代表知识命中 |
| 首次/重试后通过率 | 分别报告，不以重试后成功覆盖首次失败 |
| 无人工干预完成率 | 无接管且得到可信最终结论的运行数 / 总运行数；不等于业务通过率 |
| 运行耗时与维护成本 | 按场景观察耗时分布，并记录版本变化引起的失效与修复成本 |

P0 的硬性验收是不发生上述已知错误归因和无证据推进，且所有必需检查点有证据。总体通过率、耗时目标在固定场景基线建立后制定，不先承诺未经测量的百分比。

## 8. 待补证与文档维护规则

### 8.1 尚需核实
