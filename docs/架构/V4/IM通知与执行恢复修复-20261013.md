# IM 通知与执行恢复修复说明

日期：2026-10-13。修改范围：MinoNexus、MinoScout、MinoWorkbench。未修改已废弃的 Studio、Console 或 MiniOrangeServer。

## 1. 通知现在怎样展示

- 单条用例：第一个内容块显示用例名称、结果和实际摘要，应用/渠道放在其后；链接直接定位该用例。
- 多条用例：先显示通过、失败、执行受阻的数量，未通过用例排在前面；随后保留每条用例结果。通过项只显示名称与“通过”，不展开重复摘要。
- 未通过用例超过 5 条：显示前 5 条的简短摘要，明确剩余明细在完整测试报告中。这里包含失败、阻断、不可执行等状态，避免漏掉尚未执行的用例。
- 已删除“1 条用例需要关注”和固定的“在任务页查看问题并重跑”。建议仅在能从真实错误确定下一步时展示；没有证据时明确原因未记录，不猜根因。
- 消息按适配器字符上限和 characters/utf16 计量。通常控制在 1600 字符以内；较小渠道分页，每页保留完整报告 URL。URL 不按字符切成两段。极短渠道或过长标识退化为计数与报告入口，并明确明细省略。
- 飞书原生结果通知增加“查看测试报告”跳转按钮；文本渠道保留完整 URL。Workbench 支持新的 case_results 内容块，失败摘要突出，通过项简短。

已知错误的文案示例：

> 模型未提供可执行的操作指令，本轮没有下发设备操作。

> 建议：在报告中查看模型调用结果，修复模型响应或工具解析后重试。
>
> 查看测试报告：对应 Workbench 用例详情链接。

## 2. 报告链接与设置

实际 Workbench 路由：

```text
单用例：<Workbench 内网入口>/testing/<app_id>?tab=tasks&run=<task_id>&tcase=<case_id>
多用例：<Workbench 内网入口>/testing/<app_id>?tab=tasks&run=<task_id>
```

应用 ID 与查询参数进行 URL 编码。报告仍由 Workbench 登录及 Nexus 任务归属校验保护，未新增公开报告接口。未登录时进入登录页，登录后保留原 run/tcase。

Workbench 的“我的助手 → 对话设置 → 测试报告链接”新增可维护的报告入口。可使用当前网页的内网地址、保存手填地址或恢复默认。

入口来源优先级：当前账号配置 → `MINO_WORKBENCH_PUBLIC_URL` → 同机部署的内网 IP 与 Workbench 端口。默认端口为 5273，可经 `MINO_WORKBENCH_PORT` 调整。默认地址只适用于同机部署，分机、容器或反向代理部署须填写真实的 Web 入口。

拒绝 localhost、回环 IP、通配 IP、外网 IP/域名及包含账号或查询参数的入口。支持内网 IPv4/IPv6；URL 拼接保留配置中的路径前缀，使用前缀部署时还需让 Web 服务和前端路由支持同一前缀。本次浏览器验收使用无前缀部署。没有可用入口时明确说明，不发送 localhost 或 Nexus API 地址冒充报告入口。

接口：

```text
GET /assistant/report-settings
PUT /assistant/report-settings
body: {"workbench_url":"http://<内网IP>:<Workbench端口>"}
```

配置使用当前账号 AssistantProfile.extra，继承登录校验，无新增数据库表或生产数据修改。

## 3. 同时修复的执行问题

### 3.1 Scout 批量取证没有真正执行

`probe_device_state` 下发的是 shell_batch + commands，但 AdbExecutor.supports 原来只检查 shell/command/items/steps。路由在调用执行器前过滤了这条能力。

修复后按真实支持的 kind 检查声明：shell、shell_batch、shell_seq；commands/steps 必须为有效非空结构。没有增加一个硬编码的 probe_device_state 白名单，目录新增的合法批量能力也能沿同一通路执行。

回放使用实际 Router、AdbExecutor 和 low_level 解释器，只替换 shell 回调，不运行 adb。确认批量取证派发到了 adb 执行器并获得两项事实。

### 3.2 流式工具调用丢失与诊断不足

兼容现代 delta.tool_calls、legacy delta.function_call、完整 message 快照，以及 SDK dict/typed chunk。完整快照替换累计结果，避免 arguments 重复拼接；支持分片名称。

当 finish_reason 声称有工具调用、实际没有可执行内容时，明确标记“本轮未下发设备操作”。在既有解析重试额度内改用一次非流式重试，保留必需工具和 schema；视觉执行不允许把正文 JSON 降级为设备动作。

dispatch 增加不含参数正文的 stream_structure：分片类型计数、工具名称是否存在、参数长度和结束标记。没有把凭据或图片原文加入该诊断。

历史任务没有保存原始流式分片，所以只能证明旧解析器存在兼容缺口，不能断言该次供应商一定返回了 legacy 字段，也不能把供应商故障视为已证实。

### 3.3 弹窗、恢复与业务里程碑衔接

规划器增加 screen_obstacle 结构：consent、permission、overlay、loading。发现障碍时禁止凭“前置工具全部完成”直接进入业务阶段。没有原生 UI 树的视觉业务焦点首次执行前需要看图规划，避免漏掉图片中的挡屏。

恢复步骤单独压栈，原业务焦点保持不变。修复里程碑归一化丢失 hook_params 的问题；恢复成功只返回原焦点，不把关闭弹窗计为打开帖子。恢复失败保留失败事实，不吞掉失败后继续盲点。

等待能力按当前目录开放；等待成功不能把点击/输入里程碑标记通过。未命中有效恢复规则时，不再猜测“关闭”按钮或执行系统返回。

应用协议弹窗自动恢复：优先使用目录中匹配的恢复规则，没有规则时由独立视觉点击步骤确认协议。有业务焦点时压入 interrupt 栈，没有焦点时追加独立恢复里程碑，适用于清缓存、启动应用后首次出现协议弹窗的前置阶段。恢复焦点再次识别到同一弹窗时继续执行，不重新阻断或重复插入步骤。点击仍经 RouterProxy 委托 Scout；回看必须确认弹窗关闭，不能把协议确认算成业务目标完成。用例明确要求拒绝协议或验证弹窗时遵循原目标，不自动接受；系统权限继续按已配置的恢复规则处理。

cr-8c76990e9037 的直接原因是旧挡屏分支在前置焦点为空时直接 blocked，没有下发确认协议的点击。本次删除该人工确认兜底，同步修正 plan/exec 提示词；没有可用点击能力或恢复未完成时返回具体失败说明。错误摘要拼接统一句末标点，避免出现重复句号。

协议修复验证：10 项隔离控制流检查通过，覆盖前置无焦点、恢复焦点放行、挡屏状态清理、原业务焦点压栈与恢复、配置规则与参数、已有协议步骤、点击能力缺失、重复恢复防护、权限边界和可见结果回看。提示词仓库加载及 prompt 字面量守门检查通过。未运行 pytest，未连接真实设备或模型，未修改业务数据库，未重跑历史任务。代码与提示词需由 Nexus 重载后生效，不以这些离线检查宣称实机点击已经验证。

这些事实不能证明 Scout 拒绝了“逻辑块之外的点击”，也不能证明新增确认工具就足以解决空响应。供应商原始响应与 SDK 标准化响应的差异仍需进一步证据。第 6 节的方案是第一轮修复记录，下面的统一方案取代其中“仅末尾确认、仅由编排器消费确认”的设计。

### 7.2 排查发现的执行规则差异

1. 普通视觉动作和回看通过、回看失败分支各自计算菜单：普通执行可以选择阶段内设备技能，回看却收窄成下一里程碑的声明能力，同一个目标前后收到的可用操作不同。
2. 下一步属于程序执行时，要求模型返回上一设备工具作为占位，程序再丢弃这个动作；一个没有执行目标的点击仍被要求提供点击参数。
3. 末尾确认只在里程碑编排器中消费，其他看图执行入口没有同样的结果处理入口。
4. 普通动作、逻辑块 hook、恢复动作分别处理本地执行；部分调用未向 RouterProxy 传递本次运行上下文，本地等待的截图和操作方案也容易因调用入口而不同。
5. allow_program 之前只按调用者类型放行，能够绕过禁用、渠道和阶段检查；空设备菜单还有固定设备能力兜底，模型可能看到实际不可执行的动作。

这些都是确定存在的代码差异，但不应把它们全部等同于此次模型空响应的已证实根因。

### 7.3 统一规则与本轮实现

步骤来源只决定编排顺序、恢复结束后返回的位置，以及结果属于哪个目标，不决定事件是否被特殊放行。普通用例、逻辑块和恢复步骤使用同一 capability_id 和参数契约。

- milestone_exec_menu_ids 是执行与回看分支共同的能力范围计算。依据当前能力目录、设备渠道、显式可选动作和凭据就绪状态计算，不依据 source 或 source_block 改变点击能力范围。没有实际可用设备技能时返回空集合，不再虚构默认能力。
- 账号、验证码准备和填写仍是两种真实事件。凭据未就绪时执行资源事件，就绪后执行输入事件；不因来自逻辑块而略过资源准备。程序能力准入补齐禁用、渠道和阶段校验，程序 hook 的识别依据能力调用者而非必须带有 hook 标签。
- 所有有效的待回看动作都提供 confirm_action_result。没有下一设备动作或下一步由程序执行时，用这个结果事件确认画面证据，不要求坐标、不伪装成上一个设备动作。存在下一设备目标时仍优先返回该目标的真实动作。
- 确认、等待和重做统一由 apply_same_turn_prior 消费，继续校验已派发动作归属和新观察。重做也必须符合目标允许的能力范围；等待保留原回看，不把等待或恢复成功记成业务目标通过。非法确认、同轮观察、过期动作和空响应均不记通过。
- 普通执行、逻辑块 hook 和恢复事件均经过 RouterProxy 的本地/远程执行路由。RouterProxy 保存本次运行上下文，并向本地执行传递截图；嵌套程序事件也使用同一上下文。设备操作继续经协议委托 Scout，没有在 Nexus 直接操作设备。
- RouterProxy 在最终下发处统一检查视觉坐标和输入焦点引用。结果确认若没有被状态机消费，会被共同入口拒绝，不能下发给 Scout。不存在“恢复事件可以省略普通点击必需的参数”的例外。
- agent-vision-exec 提示词更新为 v17，移除上一设备工具占位要求。未新增独立 JSON 回看 Job，未增加模型全局重试次数。

统一契约不表示把资源获取、设备操作、结果确认当成同一种事件：它们各有输入和执行器，但同一种事件不能因为放在逻辑块或恢复流程中就换一套参数、权限或结果规则。被禁用、渠道不支持、缺少操作参数或缺少真实回看证据时，应在任何入口给出一致的阻塞原因。

- 普通执行、恢复执行和直接事件通过实际 RouterProxy 生成相同的 Scout 参数、执行器顺序和实现配置；逻辑块本地 hook 经过同一 RouterProxy 并获得当前上下文，本地等待获得同一截图。
- 共同下发入口拒绝缺坐标、不完整滑动、未消费的结果确认和禁用设备动作。
- 保留旧 success_criteria 输入的解析兼容行为，显式空菜单不会扩大为所有动作。十个修改的 Python 文件语法、提示词仓库加载、提示词字面量守门与 git diff --check 通过。

本轮只修改 Nexus 的执行与提示词逻辑，没有提交、推送、重启正在运行的服务或重跑真实任务。需要重载 Nexus 代码与 v17 提示词后进行实机验证；Scout 本轮没有协议或执行器改动，不需要因此增加版本和重新打包。如果实际模型继续返回空工具内容，必须继续按输出契约问题排查，不能宣称本任务已经通过。

### 7.5 后续建议

将事件来源保留为诊断字段，统一记录目标、实际 capability、参数准备、准入结果、执行器、设备回执和回看归属，便于直接对比同一事件在不同编排入口的轨迹。供应商诊断只保存脱敏后的结构事实，区分“供应商未返回调用”和“SDK/解析层未保留调用”；不要把空工具响应、设备操作失败和业务断言失败合并成一种失败原因。

### 8.2 本轮补充的共用诊断

没有继续增加某一事件来源专用的执行分支，也没有增加调用或解析重试次数。所有使用 llm_client 的文本、视觉和 IM 原生工具调用共用 request-local ChatResponseTrace：

1. request：从 SDK pre_call 记录实际工具数量、工具名集合是否与菜单一致，以及 tool_choice。只保存结构事实，不保存完整请求、截图或认证信息。
2. provider_parsed：在 SDK post_call 能提供响应对象时记录第一选择的消息结构、工具数量、是否有名字、是否属于菜单、参数类型和字符串长度。当前 OpenAI 兼容路径的这一边界位于 provider SDK 解析之后、LiteLLM 最终标准化之前，不是 HTTP 原始响应。
3. sdk / sdk_stream：记录 LiteLLM 标准消息的结构，或标准流中有工具、有名字的 chunk 数量。流式上游只提供包装器时，provider_parsed 明确标为不可观察，不能将不可观察当成空响应。
4. decoder：记录 Nexus 抽取后工具数量，与前一边界比较。empty_call_origin 区分 provider_parsed_output_empty、sdk_normalization、nexus_decoder、unobserved。not_empty 只表示存在有名字的调用，不表示参数、权限或业务结果已通过。

response_trace 同时进入 dispatch_calls、session 的 llm/response 以及 llm.get 的诊断投影；session 也补充 finish_reason 和 stream_structure。新日志使用 raw_response_source=nexus_decoded_message 明确原来 raw_response 的含义。历史任务没有这些新边界记录，不能追溯补造。

诊断不保存调用参数值、任意工具名、模型正文、headers 或 Key；只在符合安全字符约束时保留服务商 request ID。每次调用使用独立观察器，不更改 SDK 的全局回调或消息脱敏开关。

### 8.3 离线验证与结论边界

使用实际 LiteLLM 和其 OpenAI 兼容路径，通过 httpx.MockTransport 注入响应，并禁止真实 socket 连接，验证共享 _post_chat_completions → SDK → Nexus 解析链路：

- 完整非流式点击工具调用能保留工具名与坐标，正确生成事件。
- 分片流式点击工具调用能拼接参数，正确生成同一事件。
- 非流式只有 tool_calls 结束标记、工具列表为空时，复现 no_tool_calls，并准确记录标准化前已为空。
- 流式同类空响应也复现 no_tool_calls；上游不可观察时标记 unobserved，不虚构模型端责任。

额外检查确认 SDK 标准化丢失与 Nexus 解码丢失能记录为不同来源，独立调用不会串用结构记录，Key、正文和参数值不会进入 response_trace；调度记录、session 记录和诊断查询均保留这些字段。五个 Python 文件语法检查、提示词字面量守门与 git diff --check 通过。

以上只证明受控响应能通过当前转换链路，以及新的诊断不会把空响应当动作执行。它们不能证明真实模型的下一次输出一定正确，也不能排除真实响应存在尚未覆盖的结构差异。本轮没有重跑真实任务、修改业务数据库、重启生产服务、提交或推送代码，执行提示词仍是 v17，Scout 协议和执行器未改。

下一次真实失败，应先检查 request 的工具菜单是否完整，再对比 provider_parsed、sdk 和 decoder。若标准化前已有调用而下游丢失，修复对应转换边界；若标准化前已为空，继续核对 provider SDK/HTTP 响应和模型输入契约。不能靠猜测坐标、把正文强制变成动作、无限增加重试或将测试记为通过来掩盖本次阻塞。
