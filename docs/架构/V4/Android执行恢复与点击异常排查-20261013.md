# Android 执行恢复与点击异常排查

日期：2026-10-13（Asia/Shanghai）

涉及任务：`cr-61804b3ec47a`、`cr-6dc2781d8d44`。两次记录中的 Scout 均为 `0.1.86`。证据来自只读的 `session_events`、已有会话截图、模型派发记录和当前仓库代码。本文不修改历史任务结果。

## 1. 结论与证据范围

新任务中点击指令已经到达 Scout，ADB 返回成功；业务目标没有完成。最直接的异常是：实际画面停留在隐私协议弹窗，执行模型没有收到截图，却生成了帖子列表的点击坐标。

上一个黑屏任务确有 recovery 链路缺陷，但旧日志没有完整记录规则匹配及唤醒动作，不能仅凭没有动作事件就断言“指令完全没有下发”。已确认的代码缺陷包括取证结果缓存复用、恢复动作缓存复用、屏幕守护线程未继承账号/会话上下文，以及把没有执行恢复也描述为“recovery 未能恢复”。

没有找到里程碑直接拦截 recovery 下发的证据。恢复规则的子动作经 `RouterProxy` 直接派发；里程碑接收本地 `wait_screen_ready` 的执行结果。里程碑最终失败属于下游表现。

## 2. cr-6dc2781d8d44：为什么点击没有完成目标

| 证据 | 记录 | 含义 |
| --- | --- | --- |
| 第 6 回合点击 | `tap_element`，协议坐标 `(500,350)`，ADB `pass`，487ms | 指令已送达执行器，不等于业务点击成功 |
| 第 8 回合点击 | 相同坐标，ADB `pass`，408ms | 重新点击仍没有完成业务目标 |
| 第 6～9 回合画面 | 同一截图指纹，页面显示“造物者，你好”的隐私协议弹窗 | 当前不是模型描述的帖子列表 |
| 执行上下文 | `app_foreground=no`，`case_policy=deny`，`hierarchy_text` 为空 | 截图准入拒绝送图，且没有替代控件信息 |
| 模型派发 | 规划请求有 1 张图；第 6、8、9 回合执行请求的 `images=[]` | 规划与执行观察不一致，执行模型缺少现场证据 |
| 前台探测 | 多次 `get_foreground_app` 都使用 `step_idx=10003`，Scout 耗时反复为107ms，Nexus请求耗时仅2～3ms | 与 Scout 返回缓存而没有重新查前台的行为一致 |

错误链路：

> 旧前台结果被缓存复用 → 启动应用后仍判断不在前台 → 执行截图被拒 → 模型缺图仍生成点击坐标 → 点击未达成目标 → 里程碑回看失败。

此次不自动接受用户隐私协议，也不更改用例的隐私同意策略。恢复真实观察以后，协议弹窗仍应由已有、明确的用例/前置授权流程处理，不能把点击“同意”计为已经打开帖子。

## 3. cr-61804b3ec47a：黑屏与 recovery

会话记录显示截图全黑。第 7 回合 `wait_screen_ready` 在4992ms后失败，随后里程碑以 `screen not readable` 结束。前台探测反复使用 `10003`，Scout耗时固定366ms，Nexus耗时约2ms，而且持续返回相同失败结果。

原实现的缓存问题有三层：

1. `probe_device_state` 固定使用 `frame_step(case_seq, 2)`，同一用例内的后续取证可能返回初次探测结果。
2. `get_foreground_app` 固定使用 `frame_step(case_seq, 3)`，应用启动前后也共享同一个结果。
3. recovery 动作编号仅由 case、agent turn、action index 推导。重复执行同一规则、规则第二次尝试、守护线程再次唤醒都会复用旧动作键；Scout 可能直接回旧结果而不重新操作。

另一个问题是守护线程通过原生 `threading.Thread` 启动，不能自动继承执行账号和 SessionWriter 的上下文。这使按账号读取配置、写入会话诊断存在失败风险。线程异常后原实现仍标记“ready”，且主循环忽略 `wait_ready` 的返回值。

旧的错误文案没有区分以下情况：没有匹配规则、命中仅建议的规则、没有下发动作、已经下发但验证失败。因此，它不能证明“唤醒动作曾经执行并失败”。

## 4. 最近 Scout / Nexus 改动的判断

- 已核对 Scout `0.1.85`（`ef74754`）到 `0.1.86`（`8e470e9`）：`adb_executor.py`、`core.py`、`low_level.py` 没有差异。现有证据不支持本次 Scout 发布改变了 Android 点击逻辑。
- Nexus 已提交基线中也存在固定 recovery/取证编号。这是原有缺陷，不能全部归因于最近里程碑需求。
- 当前 Nexus 的前台截图准入和规划/执行分离，会把旧前台缓存放大为“执行模型没有图”；执行入口又缺少无有效观察时的拦截，最终形成错误点击。
- 因而修复应落在 Nexus 的取证、恢复和观察准入，而不是关闭 Scout 幂等机制或关闭里程碑校验。

## 7. 建议

把“传输成功”“输入注入成功”“恢复验证通过”“业务目标达成”分别呈现。ADB成功只能说明执行器接受并完成输入指令，不能直接显示业务步骤通过。

恢复最好显示一个可展开的诊断过程：当前屏幕事实 → 匹配规则 → 下发动作 → 新证据验证。这样用户可以确认到底是没匹配、没下发，还是执行后仍无效果。

接下来真机若仍停在协议页，应先核对前置流程是否明确处理协议、它是否属于系统/应用阻塞层，再调整中断流程。不要继续复用业务点击坐标，也不要为了通过用例静默接受协议。
