## 是不是 V5 改动改出来的
**是"暴露"，不是"制造"。** 底层是一个早就存在的项目归属错位，旧代码恰好把它掩盖了；V5 在 `control_registry.py` 里的未提交改动让它浮出来。

## 事实
- 步骤 1 的编译计划里 `control_id=ctl_0cdb1c36`，`target_desc=首条帖子`。
- 库里该控件的 `project_id` 是 **`_project`**（编译时没有项目 id 的兜底键），`locator_value.vlm_text="首条帖子"` 其实**已经写好**，`publish_state=draft`。
- 运行时 `agent_loop._locator_blocks_action` 传的是 `ctx.project_id or ctx.app_id`（`3d2b9799-…`）。
- `get_control(3d2b…, ctl_0cdb1c36)` 按 `(project_id, control_id)` 查 → **None** → `read_locator` 为空；`fill_locator` 同样 `row is None` 直接 `return cell`，什么都没写。

## 为什么以前没报、现在报了
- 旧 `locator_stop_reason`：`fill_locator(...)` 之后**无条件 `return ""`**。查不到控件时 fill 是空操作，但函数仍放行 → 错位被吞。
- 本次工作树改动：`fill_locator` 后新增 `if read_locator(get_control(...)): return ""`，读不到就落到末尾的"还没有写上"。**这个"写后复核"本身是对的**（V5 要求不能假装写成功），它第一次让查不到变成了可见失败。

## 修复
`services/control_registry.py`
- 新增 `_find_control_row(db, pid, cid)`：先按运行项目查，查不到退到 `_project`（`control_id` 是随机全局唯一，不会串）。
- `get_control` 与 `fill_locator` 都改用它。
- `locator_stop_reason`：控件在两处都不存在时，返回明确原因（"控件 X 在项目 Y 下不存在（含 _project），需重新导入/编译"），不再复用"定位还没写上"这句误导性文案。

1. **项目键不一致是根问题**：导入/编译时 `ensure_control` 用了 `_project`，运行用 `app_id`。V5 的"编译产物冻结、运行只读"要求控件身份在编译期就带正确项目；建议在 `stamp_compiled_plans/ensure_control` 调用处保证传入真实 project_id，并在发布前做一次迁移（把 `_project` 行归到项目）。本次仅做运行侧回退，**没有迁移数据**。
2. 当前库里 `_project` 74 行、真实项目 42/40/14 行；回退对旧数据有效，但同一 `desc_key` 在两个键下可能各有一份，后续迁移需去重。
3. V5 只读运行时（`registry_runtime("v5")`）下 `fill_locator` 会抛 `ControlRegistryReadOnlyError`，本次这条路径不受影响（vlm_text 已有值）。
