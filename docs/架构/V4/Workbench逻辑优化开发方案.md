# Workbench 逻辑优化开发方案

范围：注册登录、应用下的用例 / 任务列表加载、移除助手默认值、修复 LangBot 状态展示，以及账号隔离。Workbench 是唯一用户入口，普通用户与管理员均通过其权限控制后的页面操作。本方案覆盖旧 V4 文档中“我的默认值”的设计。

## 1. 登录与注册

**现状**：`LoginPage.tsx` 只有登录；Nexus 已有 `/auth/register`，`auth_store.register()` 已经只校验邮箱格式和重复注册，不消费验证码。

**改法**：

- 登录页增加“注册账号”，注册页只保留邮箱、密码、确认密码。前后端校验邮箱格式，不发邮件、不做邮箱验证码验证；保留密码至少 8 位及邮箱唯一约束。
- 复用现有注册接口，补前端 API、路由和表单；注册成功返回登录页并回填邮箱，登录后沿用现有 token、会话刷新和 WebSocket 初始化流程。
- 不提供忘记密码入口、找回页及找回流程；注册不调用 `/auth/send-code`，停用注册发码用途，移除相关页面和调用，不为已停用的入口保留产品流程。
- 当前注册写入 `email_verified=True`，应改为未验证语义，但不阻止登录；“格式有效”不等于“证明邮箱归属”。邮箱去重在规范化后由数据库唯一约束兜底，普通注册不能选择管理员角色。

**UI**：`登录 / 注册账号` 两个简洁入口；错误直接显示在对应字段旁，不出现验证码倒计时和忘记密码。

## 2. 用例 / 任务列表性能

**已确认的代码路径**：面板采用 lazy import；用例查询依赖 URL 中的 `projectId`，另查最近 20 个任务反推上次结果；任务列表每 15 秒刷新，运行中的详情每 5 秒刷新。实际耗时瓶颈尚未测量，不能直接归因于后端或 React。

| 优先级 | 实施项 |
| --- | --- |
| P0 测量 | 从左导航点击开始计时，到正确列表首屏完成绘制且可交互结束；空数据以真实空态完成为终点，骨架屏不算成功。分别记录路由 / JS 加载、接口、渲染耗时及失败率。 |
| P1 请求链 | 用例的 `projectId` 优先取已有应用上下文，直达链接缺失时由应用详情补齐，不再静默禁用查询。校验项目与应用对应关系；任务列表可直接按 `appId` 请求，不等任务详情。 |
| P1 首屏 | 导航悬停 / 聚焦时预加载对应面板和列表数据；列表先显示，设备、上次结果、统计与详情独立加载，失败不拖垮主列表。 |
| P1 缓存 | 复用 React Query，同账号、应用、筛选、分页共用缓存；切回立即显示缓存并后台刷新。切账号清理缓存，切应用不能闪现上一个应用的列表。写操作只失效相关查询。 |
| P2 接口 | 按测量结果增加服务端分页与筛选，列表只返回摘要，详情点击后加载。用例上次结果改为按当前页用例批量查询，不能长期靠拉任务详情反推；索引根据实际 SQL 查询计划补。 |
| P2 渲染 | 大列表使用分页或虚拟滚动，重型编辑器与任务轨迹按需加载；隐藏页面停止轮询，实时事件到达时局部更新，保留断线兜底。 |

**建议验收目标（不是现有实测值）**：约定同一机器、网络和数据集（例如 1 万用例 / 1 千任务，每页 50 条），分别覆盖两个页面的冷进入和缓存切回，各采集至少 30 次；P95 冷进入 ≤ 1.5 秒、缓存切回 ≤ 300 毫秒。失败单独计入成功率，不能用延后计时或提前显示骨架屏达标。

## 3. 我的助手：移除默认值

- 删除 `DefaultsSection.tsx` 中默认应用、默认设备及其候选查询；页面“接入与默认值”改为“接入”。“启用助手”是独立开关，移到状态区保留，避免删除整个组件时误删控制能力。
- 前后端不再读写 `default_app_id`、`default_sn` 及衍生名称字段；同步清理 `rAssistant.py`、`assistant_store.py`、`assistant_agent.py`、`assistant_gateway.py`、`assistant_tools.py` 中的提示词注入和 `_fill_default_sn` 调用。
- 参数改为“本次明确输入 → 当前会话已经确认的上下文”；仍缺失或存在歧义就询问，不静默取用户历史默认设备。执行前仍检查权限和节点在线状态。
- 数据库旧列本期保留但停止使用，接口对历史字段明确忽略或返回弃用提示；不保留对应用户流程，不为删 UI 直接破坏旧数据。其他助手功能保持原职责。

## 4. LangBot 已配置却显示未连接

**已确认的字段不匹配**：Scout `plugins/langbot_host.py::channel_status()` 把各平台的连接状态放在 `platforms[平台].connected`；Nexus `rAssistant.py::_im_nodes()` 只读顶层 `status.connected`，缺失即转成 false。Workbench `heldChannels()` 也有同样判断。上线前用实际节点快照核实中间链路是否完整保留 `platforms`。

**修复方法**：

1. Nexus 统一解析节点快照：LangBot 拆成 `langbot:<平台>` 渠道，读取对应平台的 `connected / holding / error / last_message_at`；微信沿用已有适配。两页使用同一规范化状态，普通通知机器人不计作助手对话入口。
2. 分开展示“已安装”“进程运行”“渠道连接”“当前用户绑定”。安装成功或配置齐全不能直接推断渠道在线；Scout 目前的 `connected` 也主要基于进程和配置，需接入适配器真实连接 / 认证状态，无法确认时显示“待确认”。
3. 助手状态按当前用户可访问节点、渠道持有关系和 IM 身份绑定聚合；`_im_nodes()` 当前遍历全部节点，必须补权限过滤，不能借其他用户的在线节点判定本人助手在线。
4. 心跳超时显示“节点离线”，字段缺失显示“状态未上报”，渠道连接但用户未绑定显示“待绑定账号”。不要把 IM 离线等同于 MCP 不可用，二者单独展示。
5. 安装、绑定、重启后主动刷新相关快照和助手查询，辅以实时通知 / 轮询；节点接入页配置机器人，助手页只管理当前用户的绑定，不要求重复安装或重新填平台密钥。

**UI 草图**：参考 OpenClaw 的渠道状态组织方式，采用轻量工作台卡片；Muse 未指定版本，不假定其具体页面和接口。

```text
我的助手                              启用助手 [开]
飞书 · Mac mini     渠道已连接    我的账号已绑定
企微 · Windows PC   渠道已连接    我的账号待绑定 [绑定]
钉钉 · Linux 主机   节点离线      [查看节点]
MCP                 可用          [接入说明]
[接入] [会话与轨迹] [订阅]
```

## 5. 账号隔离（需求 2.4）

**边界**：Scout 节点、我的助手、模型密钥三页的数据均属于当前登录账号，不同账号不互通。微信、飞书等绑定仅服务绑定它的当前用户；管理员在这三页也不能默认查看或使用其他用户配置。公共服务商名称等无敏感预设可以共用，用户填写的配置、绑定和密钥不能共用。

| 页面 / 数据 | 实施方式 |
| --- | --- |
| Scout 节点 | `owner_user_id` 来自服务端会话与安装凭证；列表、详情、设备、插件配置、日志、远程操作、接入结果和实时通知全部校验归属。更换账号后不得因同一浏览器、同一电脑或旧客户端标识继续看见原账号节点。 |
| 我的助手 | 档案、启用状态、社交绑定、绑定码、渠道状态、会话 / 轨迹、订阅和 MCP token 均按 `user_id` 存取。只聚合本人节点及本人渠道；不能用全局在线机器人判定本人助手可用。 |
| 模型密钥 | provider 配置、API Key、base URL、模型选择、默认项和用途开关统一按用户命名空间存储，例如 `(user_id, provider_id)`。列表、保存、删除、连通性验证和实际模型调用都带服务端用户上下文。新账号看到未配置状态，不能沿用全局或其他账号的 Key。 |

**社交绑定与消息路由**：

- 区分“节点上安装 / 配置机器人”和“登录用户绑定自己的社交身份”。绑定码关联当前 `user_id`，一次性且有有效期；确认绑定时校验节点、机器人实例与该用户归属。
- 身份按渠道、机器人 / 租户实例、平台发送者 ID 识别，不能只按昵称或渠道名匹配。收到回调后验证来源，再由已绑定身份解析用户；群聊按实际发送者查绑定，不让整群继承绑定者权限。
- 同一精确社交身份不得同时归属两个账号；其他账号不能覆盖绑定。解绑或换绑后旧映射失效，后续消息、工具调用和模型费用都归新确认的用户；重复回调须去重。
- Scout 本地插件配置和密钥也要守住归属边界；本轮不隐式共享节点。若后续允许节点转移账号，先撤销旧凭证及渠道持有关系，再隔离旧配置并重新绑定，不能让新账号继承原账号社交凭据。

**后端与前端一起改**：

1. 当前 `rSettings.py` 的模型配置接口虽要求登录，但调用 `settings_store` 时没有传用户；仅在页面过滤不成立。模型配置读写、`settings.py` 转发、`llm_client`、助手和后台任务都要贯穿明确的执行用户。后台任务创建时固化 owner，不能取最近登录用户或共享可变全局变量；缺归属就拒绝执行。线上用户任务不回退使用其他用户、管理员或共享环境 Key。
2. 请求体中的 `user_id` 不能决定归属；服务端从登录会话、受验证的渠道绑定或任务 owner 取值，读取和变更都加入归属条件。越权资源统一拒绝且不泄露其名称、配置或存在情况；密钥只返回脱敏状态，不进日志。
3. Workbench 查询缓存带用户范围；退出 / 切账号时取消请求、清空三页缓存和敏感本地状态、关闭旧实时连接。旧请求迟到和旧 WebSocket 消息不得写入新账号页面；服务端推送也按用户过滤，不能只靠前端隐藏。
4. 存量有可信归属的数据保留原 owner；全局模型密钥、无归属节点和绑定不自动复制给所有用户。迁移到待认领 / 停用状态，由有权限的维护流程确认归属后启用。先备份后迁移，业务状态仍在 SQLite，不新增 JSON 真源。

**双账号验收**：A 配好节点、助手、微信 / 飞书和模型 Key 后，B 的三页仍是自己的独立数据；B 猜 A 的资源 ID、改请求体、监听旧连接或使用旧绑定码都拿不到 A 的数据。A/B 后台任务分别使用自己的模型配置；B 无 Key 时明确报未配置。切账号不闪现 A 的内容，解绑后消息不再进入 A 的会话，群内未绑定成员不能借用 A 的权限。

## 6. 交付顺序与验收

账号隔离作为 P0，先明确归属与迁移，再贯通三页、后台执行和社交回调；同时补注册、移除默认值、修复状态字段和权限。同时记录列表性能基线，再按耗时占比优化请求与渲染。跨 Scout / Nexus 的上报变化同步协议文档和 golden fixtures。

验收覆盖：无验证码注册并登录；无忘记密码入口；缺 `projectId` 的直达用例页可恢复；用例 / 任务正确显示且达成约定耗时；旧默认值不再影响执行；已连接渠道正确显示、未绑定可识别、节点离线不误报在线、不同用户互不串状态。按仓库规范做实际 UI / 接口联调，执行链路查 `session_events` 与 `session_meta`，不新增或运行 pytest。
