# 登录页「协议未勾选」被跳过 + 耗时复盘（cr-a278a45ce22c）

> 日期 2026-10-14。会话 `cr-a278a45ce22c::case-b1d321c8::5fda2f6d`，`fail`，wall=404s（6 分 49 秒，预算 405s，**不是超时失败**）。
> 失败文案：「submit_login 只能点 登录、Log in…不要点 Send…重做之后画面仍未达成，已停止」。

## 先说好消息：前几轮修复在这次生效了
- 手机号框、验证码框都 `input_text` pass；验证码框第一次仍报「焦点点击引用失效」（seq 800），**恢复一次后第二次 pass**（seq 887），说明恢复链路已可用（根因仍有残余，见下）。
- 取到验证码、发码、回看均通过，流程一路走到「提交登录」。

## 新问题 1：登录按钮不可用，因为协议复选框没勾 —— 里程碑被错误跳过
| seq | 事实 |
|---|---|
| 516/519 | 里程碑含 `legal_consent`（同意协议，optional hook `accept_legal_consent`） |
| 933 | `milestone/skip_applied legal_consent reason=absent_ui source=hierarchy` |
| 975-979 | 点「登录」(500,645) pass |
| 1014 | 模型：「登录页提示需先同意协议，底部协议勾选框未选中，登录按钮不可用」→ 回看 fail（seq 1018） |
| 1021 | 重做点勾选框 (170,930) pass |
| 1055/1059 | 该点击被当作 **submit_login 的重做**回看，期望是「登录提交后的画面」→ 再 fail → `redo_already_sent` → 停止 |

**根因**：`milestones.maybe_skip_ui_absent_milestones` 用层级节点 `find_consent_control(nodes)` 判断"界面有没有协议框"。**纯视觉方案没有层级（hierarchy_text 为空），nodes=[]，必然"找不到"，于是把 optional 的协议里程碑判成 absent_ui 跳过。** `accept_legal_consent` 本身也只靠层级找控件，视觉模式下无法执行。
连锁：协议没勾 → 登录按钮灰 → 点登录无效 → 回看 fail；模型虽然看懂了要先勾选，但勾选动作被挂在 submit_login 名下，既受 `submit_login 只能点登录` 的限制提示约束，又按"登录提交后画面"回看，注定再 fail。

**修复**（`loop/milestones.py`、`loop/visual_review.py`）
- 无层级（`nodes` 为空）时，不再把 `legal_consent` 判为 absent_ui 跳过，而是**转成 visual_tap 里程碑**（`device_cap=tap_element`，去掉 hook_cap，标题"勾选同意协议（仅当复选框未勾选时点击；已勾选则无需操作）"），写 `milestone/consent_visual` 事件，交给看图模型点勾选框；有层级且确实没控件才仍然跳过。
- 回看期望新增 `legal_consent`：「协议复选框已处于勾选状态，登录按钮变为可点」。
**风险**：已勾选时模型若误点会取消勾选，靠标题里"已勾选则无需操作"约束，回看会兜底；这是对 optional 里程碑的保守处理，未重跑验证。

## 新问题 2（耗时）：6 分 49 秒从哪来
`perf/summary`：wall 404s，**llm 429s**，tool 5.5s。设备几乎不占时间。
| 项 | 数据 |
|---|---|
| LLM 调用 | 44 次（exec 32、plan 6、assert 2…），29 个回合 |
| 空 tool_calls | **16 次，36%**（上次 8/26=31%），**全部发生在流式第一次调用** |
| 时延对比 | 流式成功 4.9–7.6s；空返回白打 5–11s；随后非流式重试 10–19s（均≈13.5s） |
| 抵扣 | `budget/credit` 累计达 111s（有效封顶 90s；日志里的累计值未封顶，仅显示） |
| 登录流 | 3 步用例里第 3 步含 10 个里程碑（入口/聚焦/填写/发码/取码/聚焦/填写/协议/提交/确认），每个至少 1 次模型调用 + 回看 |

结论：**耗时的结构性来源是"登录流每个里程碑都走一次看图模型"，叠加 provider 的流式空 tool_calls**。上一轮的减负（取证去重、预算 405s、工具集缩小）使这次没有被墙钟打断，但没有改变调用次数。

## 可继续做的（本次未改）
1. **流式空 tool_calls 是 provider 缺陷**：每次首个流式调用约 1/3 概率空；重试非流式虽 100% 成功但比流式慢一倍。选项：(a) 重试仍用流式（需 A/B，未测）；(b) 对该模型直接非流式（期望值 ≈ 持平，不值得）；(c) 向火山反馈 `finish_reason=tool_calls` 流式无 tool delta（附 `provider_request_id`，如本次 seq 145 等）。建议 (c) + 记录率。
2. **减少模型调用次数**：登录流里"聚焦输入框"和"填写"可合并为"点击后同回合输入"（tap 后无需独立回看即可 input_text，仅在输入后回看一次）；`otp_field`+`otp_fill`、`account_field`+`account_fill` 各省 1 次决策+1 次回看，约 40–60s。涉及回看语义，需另行评审。
3. `plan` 调用 6 次（约 55s）：`orchestrator/plan_gate` 已有 skip，可评估对确定性登录流整体跳过规划。
4. **验证码框首次「焦点点击引用失效」已定位并修复（Scout）**：`focus_diag` 显示 `ref_sent == ref_recorded`（编号对），`focused_count=1`，验证码框确实 focused，只是 **bounds 从记录的 [332,1435,945,1498] 变成 [332,1435,963,1498]**——框右侧倒计时文字变化让输入框变宽。Scout 要求 (package, resource_id, bounds) 全等，所以误判。这也是前几次"第二个框失败"的真正原因（推翻我当时"旧框残留 focused"的推测，那次推断没有证据）。
   修复：`adb_executor._same_input_field`——比较 package + resource_id + 左上角（±8px），右/下边界允许漂移；`_focused_input(expect=…)` 与 input 校验共用。**需发布新版 Scout 并重启节点**；未重跑。
