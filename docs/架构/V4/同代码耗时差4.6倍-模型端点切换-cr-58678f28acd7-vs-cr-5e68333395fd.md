# 代码几乎没变，耗时 428s → 92s：差异来自模型端点，不是代码

> 日期 2026-10-14。对比 `cr-58678f28acd7`（13:30，428s）与 `cr-5e68333395fd`（13:43，92s）。两次都在同一台设备、同一 Scout 0.1.90、同一 prompt_version 17、同一条登录用例（case-b1d321c8 / case-bc8b51cf，步骤文字完全相同）。

## 结论
**唯一发生变化的是 LLM 调用的 model：`doubao-seed-2-1-turbo-260628`（按模型名）→ `ep-20261012170415-674wv`（火山推理接入点 ID）。** 耗时和空 tool_calls 的差别全部落在这里。代码没有"变快"，是换了更快、没有该缺陷的后端。

## 数据
| 指标 | cr-58678f28acd7 | cr-5e68333395fd |
|---|---|---|
| model | doubao-seed-2-1-turbo-260628 | **ep-20261012170415-674wv** |
| wall | 428.6s | **92.3s** |
| LLM 调用 | 40 | 25 |
| 空 tool_calls（status=error） | **15**（exec 33 次里 45%） | **0** |

| 首个流式调用 | 常 `error` 后被迫非流式 `auto` 重试 | 全部流式 `required` 一次成功 |
| 回合数 | 26 | 26 |

- 回合数相同（26），说明**业务流程没变**，LLM 调用从 40 降到 25 全是因为没有重试（15 次空返回 + 重试 = 额外 15 次）。
- 单次调用从 13.4s 降到 1.9s：同样的 ~5–7k prompt tokens、~100 completion tokens，说明不是输出量问题，是端点侧排队/延迟差异（按模型名走共享路径，接入点 ID 走专属/独立配额的可能性大——这是推断，没有火山侧数据）。
- 今天 11:13 起所有使用 `doubao-seed-2-1-turbo-260628` 的运行（8 个会话）exec 均值 7.5–13.4s、空 tool_calls 率 30–50%；使用 `ep-…` 的仅此一次样本（25 次 llm/response 全部成功）。样本小，但差异量级（7×）不像噪声。

## 对之前分析的修正
- 前几轮把"空 tool_calls"当成 provider 流式缺陷并加了重试放宽、预算抵扣（`wasted_ms`/90s 封顶）。**这些在新端点下不会被触发，不会有副作用，但也说明 6–7 分钟的耗时主因是端点而非用例/代码。** 之前建议的"减少回合数/合并回看"收益在这个端点下大幅缩小（92s 已远低于 405s 预算）。
- 预算公式放宽（405s）是对慢端点的保险；若今后固定用快端点，可再收紧，避免真卡住的用例晚失败 ~135s。
