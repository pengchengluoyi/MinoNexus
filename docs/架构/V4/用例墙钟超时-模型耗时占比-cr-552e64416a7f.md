# 「超过 270 秒仍未完成」：耗时几乎全在大模型（cr-552e64416a7f）

> 日期 2026-10-14。会话 `cr-552e64416a7f::case-b1d321c8::5fda2f6d`，`fail`，wall=278.5s，预算 270s（3 步用例 = (前置3+操作3+校验3)×30）。
> 用户假设：执行耗时长 / 卡死 / 模型返回事件过长。逐项核对结果如下。

## 结论
**不是设备执行慢，也不是卡死，也不是模型输出过长；是模型调用次数多 + 每次慢 + 近三分之一调用是空 tool_calls 白打。**
设备并没有走到用例失败：到超时时第 3 步刚完成点击，进度正常，只是预算被模型延迟吃完。

## 数据（session_events）
| 项 | 数值 | 判断 |
|---|---|---|
| `perf/summary` | wall 278.5s，**llm 303.8s**，tool 2.7s | 工具仅 1%；llm_ms 大于 wall 是因为部分 LLM 调用与取证并发重叠 |
| 设备动作 | tap 6 次均 ~540ms；`probe_device_state` 106 次均 544ms、`get_foreground_app` 26 次均 122ms | 单次都快，**不是卡死**；但取证 106 次是噪音（见下） |
| LLM 调用 | 26 次：exec 16、plan 6、assert 2…；**8 次 `error`（空 tool_calls）** | 31% 白打 |
| 空 tool_calls 浪费 | 每次 5.3–28s（均≈9s），随后重试一轮又 10–33s（重试用非流式 + tool_choice=auto，更慢） | 一对调用共 ≈20–60s |
| 输出长度 | completion_tokens 59–145（assert 443）；max_tokens 768 | **不是输出过长**；慢在首包/排队，不在生成 |
| 单次 LLM 延迟 | 正常 4–17s，尖峰 27.6s（plan）、28s/33.5s（exec，seq 636/641） | 火山端抖动 |
| 回合结构 | 19 回合里 `tap_element` 6、`confirm_action_result` 4、`assert_visual` 2、plan 6 | 每个点击至少 2 次 LLM（点 + 回看确认）+ 常有 plan |

回合时间线：turn 11-14（第 1 步 tap）27.7s，turn 320（第 2 步）34s，turn 648（回看确认）36s——最长的几个回合正是"空 tool_calls + 重试"叠加的回合。

## 与前几次的关系
- 上一轮为解决空 tool_calls 加的重试放宽（`tool_choice→auto`、温度 0.4、max_tokens 1536）**确实把每次都救回来了**（8 次错误后 8 次成功），但代价是**每遇一次空返回就多一整轮 LLM**。
- 同一用例近 8 次运行 wall 全在 271–376s，其中 5 次触顶 270；失败原因看似各异（聚焦、定位、超时），耗时底子是同一个。`cr-b04cab3e2313` 376s 超出预算也说明预算检查只在回合边界，一回合内多次模型重试可越界。

## 为什么预算不够
预算 = 单元数×30s 是按"每步 30s"拍的，而现实里一个操作步 = tap（LLM 5–17s）+ 回看确认（LLM 10–18s）+ 偶发 plan（6–27s）+ 空 tool_calls 重试（~20s）≈ 40–90s。3 步用例理论最低 ≈ 3×(2 次 LLM)+ 校验，没有故障也接近 150–200s，一遇 provider 抖动就越界。

## 已做的修复（降低误伤，不放宽真超时）
1. `llm_client.call_chat_text`：重试轮累计 `wasted_ms`（失败轮耗时）并写入 meta（`empty_tool_calls_retry`、`wasted_ms`）。
2. `agent_loop`：每个决策后把 `wasted_ms` 记入 `ctx.case_budget_credit_sec`（**封顶 90s**），墙钟判定改为 `elapsed - credit >= budget`，同步 `case_deadline_ts`；写 `budget/credit` 事件，超时 summary 注明已抵扣多少秒。
   理由：空 tool_calls 是 provider 缺陷，不应算在用例慢上；封顶避免 provider 持续异常时无限续命。

## 未做 / 建议（按收益排序）
1. **治本：降低空 tool_calls 率**。8/26 次（上次 3/… 同量级）。可试：缩小 tools 集合（当前 10 个，vision-exec 只给当前里程碑相关的）、对该模型开 `thinking`、或换模型做 A/B；每降 1 次省 ~20s。
2. **合并回看与下一步决策**：`confirm_action_result` 单独占一次 LLM（10–36s），代码里已有"同回合回看"机制（`review/same_turn`），但 tap 后仍需独立确认回合；可评估在下一张决策图里同回合完成回看以省一半调用。
3. **取证噪音**：`probe_device_state` 106 次/用例（平均 5.6 次/回合，每次 ~0.5s，约 55s 设备时间，虽与 LLM 并发但占 ADB 通道），可按"动作后一次"去重。与上轮 focus_ref 被取证清掉的问题同源，减少取证也减少副作用面。
4. **预算公式**：按实测中位数改为"每个操作步 ≥60s"或用例级 `wall_budget_sec` 覆盖；现有覆盖字段 `case.wall_budget_sec` 已支持。
5. 超预算检查只在回合边界；单回合内的重试/等待无硬上限（`cr-b04cab3e2313` 376s）。可把 `case_deadline_ts` 传入 LLM 调用作超时上限（`local_executors` 已用它，LLM 路径未用）。

## 验证
重跑后看：`budget/credit` 事件出现、`session/end` 在抵扣后是否通过；对比 `llm/response` 中 `status=error` 占比。未重跑、未跑 pytest。
