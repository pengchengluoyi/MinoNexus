# Web 邮箱登录取不到验证码：Send 没点中，重试被吞，get_otp 被守卫拒绝（cr-4f6712f54491）

> 日期 2026-10-13。会话 `cr-4f6712f54491::case-ed53e597::webe22615fbbb917111`（Mino Web，邮箱验证码登录）。
> `fail`：get_otp 连续 4 次被 `flow_block:require_sms_send_before_otp` 拒绝，必要里程碑无进展。

## 结论
**验证码没拿到，是因为"发送验证码"根本没发出去**——守卫拒绝 get_otp 是对的（没发码就取码没意义）。
真正的问题是：第一次点 Send 落点偏了；回看正确判了 fail；但重做那一下被"重复点击＝已满足"机制**当成成功吞掉**，里程碑被记 pass，流程直接跳到 get_otp。

## 证据
| seq | 事实 |
|---|---|
| 142/162 | 邮箱已填写成功（account_fill 达成） |
| 170/171 | tap Send：模型坐标 (763,488) → 视口 (977,390)，pass |
| 177（截图 t8） | 画面上 Send 是「6-Digit Code」输入框最右端的小图标（视口约 x≈986,y≈390）；无倒计时、无提示——点偏了 |
| 195/197/198 | 回看 `prior_status=fail`，`review/fail redo_already_sent=false`，模型要"重新点击发送按钮" |
| 200 | `milestone/already_satisfied`：`skip_repeat_tap`「已拒绝重复点击「6-Digit Code」：同位置已点过且界面未变」→ **send_code 被标 pass** |
| 216/218 | otp_fetch → get_otp，守卫：未发码 → 拒绝；之后同样 3 次 |

## 根因
`focus_turn.try_satisfy_focus_instead_of_repeat` 把一批 `skip_repeat_*` 守卫当作"已满足"：命中就对当前里程碑 `complete_in_progress_on_tool(ok=True)`。
对"launch_app / clear_cache"这类幂等动作成立；对 **视觉点击** 不成立——"同一位置已点过且界面没变"恰恰说明**上一次没生效**，尤其在回看刚判 fail 之后。
于是：回看（正确）→ 重做（同位置）→ 重复守卫（误当成功）→ 里程碑假通过 → 下游守卫（正确）拦下 → 任务失败，且失败原因描述的是下游症状。

## 修复
- `visual_review.apply_same_turn_prior`：回看判 fail 时记 `cursor.visual_failed_milestone = mid`，里程碑回看通过时清除。
- `focus_turn.try_satisfy_focus_instead_of_repeat`：`tap_element` 且当前里程碑正是 `visual_failed_milestone` 时**不再记 pass**，交还给守卫，向模型返回"同位置已点过，请换元素/坐标"，里程碑保持 in_progress。

## 仍存在 / 建议
1. 点中的概率问题：Send 是输入框内小图标，模型坐标偏约 9px。可在 `agent-vision-exec` 提示或 hint 里补"发送按钮常是验证码输入框右端的小图标/文字"，并让 redo 的 correction_hint 带上"上次落点 (x,y) 未生效，向…偏移"。目前 hint 只有"画面上上一步还没完成"。
2. 回看 fail 后若模型给出完全相同的坐标，现在会一直被守卫拒绝直到 fuse 熔断，信息量仍不够；应让 hint 明确列出上次坐标。
3. 其它 `SATISFY_GUARD_IDS` 中带"视觉点击语义"的条目（`skip_repeat_swipe_stuck`、`skip_repeat_satisfied_step_action`）可能有同类误判，未逐一核对。
4. 与 get_otp 无关：邮箱收码通道本身（gmail alias）本次没走到，未验证。
