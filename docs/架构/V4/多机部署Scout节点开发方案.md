# 多机部署 Scout 节点开发方案

> **2026-10-12 规范关系**：本目录的现行约束及文档覆盖关系见 [V4 索引](README.md)。方案描述目标，开发记录描述已实现及验收边界；早期段落不得覆盖后续明确修订。代码修改通过隔离验收不等于真实模型、IM 或桌面实机验收。

目标：一个账号可以绑定多台电脑；Workbench 是唯一用户入口，其 Web 页面始终能复制安装命令，不依赖本机是否安装 Mino / Scout。节点安装、管理及管理员认领都在 Workbench 完成。新增需求 1.2：节点需显示宿主 PC（macOS / Windows / Linux），具备相应执行能力后可在任务中选择其桌面设备。新增需求 1.3：每台 Scout 的设备列表仅显示该节点当前连接的设备，账号内多节点之间仍须隔离。

## 1. 现状与问题

### 1.1 多机安装与归属

- 已有 `POST /runtime/nodes/install-token`，签发当前账号的 15 分钟安装凭证；已有独立节点凭证、节点归属和多节点登记，优先复用。
- 当前 Workbench 的 `NodesPage.tsx` 已有“添加节点”入口；此入口解决安装接入，不会自动补齐 PC 桌面设备和执行通道。
- 浏览器不能可靠判断本机是否安装 Scout，也不能把“账号下有在线节点”等同于“当前电脑已安装”。
- 多机及新增 PC 设备统一按登录账号归属和服务端授权隔离；节点可见性不能替代设备列表、详情与派单接口的归属校验。

### 1.2 缺少 PC 设备，任务无法选择节点上的 Mac

**需求表述**：Scout 接入后，Workbench 节点页应展示这台电脑及其 macOS / Windows / Linux 系统信息；当其桌面会话与执行器就绪，应用任务可以选择该 PC 桌面执行测试。未就绪时仍能看到原因和处理入口。

**当前代码确认（2026-10-12）**：

- Scout `core.py::_discover_devices()` 只发现 ADB 设备和 Web 虚拟槽，没有为宿主 PC 登记 Desktop 设备。节点的操作系统元信息不是 `devices[]` 中的执行目标，这是当前缺失的直接原因。
- Workbench `useRunDevices()` 默认请求 `/case-runner/devices?only_online=true`；不可用目标会被隐藏。`isExecutable()` 主要检查状态和 `sn`，不足以判断桌面权限、会话、能力和任务兼容性。
- Nexus `executors_for_platform()` 当前对非 Web / iOS 平台回落到 ADB / remote；仅新增 `platform=macos` 或一条设备记录，仍可能走错执行通道。

因此这是 **设备发现 → 登记 → 状态 → 选择 → 派单** 的端到端缺口，不是单纯前端少一个选项。Mac 上已经存在的 Web 槽只能说明可以跑浏览器任务，不能代表可以操作原生 Mac 应用。

### 1.3 Scout 节点之间隔离设备（2026-10-12）

**需求表述**：选择 Scout A 时只显示 A 当前连接的设备；即使 Scout B 属于同一个账号，也不能将 B 的设备补进 A 的列表。

- 服务端节点行的 `devices[]` 以 Registry 当前 `node_id` 为准，不用 `first_scout_id`、历史数据库位置或账号相同作为兜底。实时 `current_scout_id` 与 `node_id` 保持一致。
- 节点页不补回已断开的历史手机；离线节点的实时设备列表和计数为零。全局任务选择器可以继续展示本人历史设备及不可用原因，历史记录不删除。
- 当前节点上报的宿主 Desktop / Web 槽保留，用于解释桌面权限、会话或执行器阻塞；不得用数据库历史槽补回。宿主与执行能力分别展示。
- 设备从 A 移到 B 后，只出现在 B；A 迟到的断开心跳或重新注册中的离线设备不能抢回设备位置。跨账号迁移仍拒绝。
- Workbench 以当前节点 ID、通道和节点状态做防御性筛选，可执行数量与设备列表共用同一口径。空态说明只显示当前节点的连接设备。

**兼容处理**：旧的无归属 Scout 本机插件文件不作为新账号的配置。首次验证归属后建立按服务地址与账号隔离的空插件存储、IM 库和钥匙串条目；旧文件保留原位，不再阻塞新配置。已经确认归属的配置沿用原路径，账号或服务不匹配仍拒绝继承。数据库清理仅针对明确无归属的记录，不能删除已归属节点、账号插件、模型密钥或助手绑定。

**验收**：同账号两节点列表互不混入；迁移后仅新节点出现设备；迟到断开不回迁；断开手机不显示；Desktop 权限不足仍能看到处理原因；离线节点无实时设备；新账号遇到旧本机文件仍能保存新插件，且不能读取旧配置、消息和密钥。

## 2. 怎么做

### 2.1 多机安装

| 部分 | 改法 |
| --- | --- |
| 安装入口 | 节点页标题旁常驻“添加节点”；无节点、已有节点、节点全部离线、列表读取失败时均可打开。命令获取失败单独提示和重试。 |
| 平台选择 | 默认按浏览器平台提示选择 macOS / Windows / Linux，可手动切换。识别失败要求选择，不猜 Linux；这里只判断操作系统，不识别具体机型。 |
| 命令生成 | 复用安装凭证接口和 Scout `packaging/install.sh`、`install.ps1`，按发布地址及真实脚本参数生成命令。macOS / Linux 标明终端，Windows 标明 PowerShell；CPU 架构由目标机器上的脚本检测。 |
| 账号绑定 | 安装凭证的用户只能取服务端登录会话。首次注册将节点绑定该用户，换取独立 `node_token`；凭证过期或已使用，页面重新生成。每新增一台电脑使用新凭证。 |
| 身份与重装 | 不同电脑生成不同 `node_id`；同机重跑优先复用本地身份和配置，避免重复节点。已绑定其他账号时明确提示，不静默转移归属。 |
| 多机列表 | 以 `owner_user_id` 查询该账号全部节点，显示名称、系统、在线状态、设备数、最后心跳。更换浏览器或电脑登录，看到同一份列表。 |
| 接入反馈 | 复制只提示“已复制”，不当作安装成功。通过注册事件关联本次安装凭证与新节点；在线后显示“已接入：节点名”，支持稍后回来查看。 |

安装凭证应在成功注册时原子消费，防止同一凭证并发绑定两台机器；响应丢失的重试只允许恢复同一次节点登记，不签发第二个节点。长期节点凭证支持单节点吊销，不影响其他节点。命令不包含网页登录长期 token，安装凭证不写入普通日志或埋点。

Nexus 地址须是目标电脑可访问的服务地址：复用现有部署配置，正确处理可信反向代理；不能把当前浏览器的 localhost 带到另一台电脑。`mino.local` 只适用于可解析它的局域网，跨网络需要可达域名或 VPN，不新增浏览器扫描或局域网 IP 选择器。

### 2.2 PC 设备登记与任务选择

| 环节 | 改法 |
| --- | --- |
| 宿主识别 | 由 Scout 上报实际宿主 OS、架构、名称和桌面探测状态，不能用登录 Workbench 的浏览器系统代替远端节点系统。统一展示 macOS / Windows / Linux，内部保留平台映射。 |
| 主机与设备 | 节点页始终显示已登记节点的宿主电脑卡片；真正可操作的桌面另有设备槽。宿主无图形会话时显示“无桌面会话”，不伪造可运行设备。 |
| 设备身份 | 沿用 PC 方案的 Desktop 家族：`platform=desktop`，另带 `os=macos|windows|linux`；字段为拟新增契约。设备 `sn` 可用 `desktop:<node_id>:<session_key>`，其中 key 是持久逻辑桌面槽标识，OS 会话代次单独记录。Scout 重启不新增重复设备；窗口 / 显示器不是独立槽。 |
| 注册与状态 | 扩展 REGISTER / HEARTBEAT 的设备信息、Desktop 通道、能力与不可用原因，Nexus 持久化归属并随心跳更新。切换系统登录会话使旧动作引用失效；掉线保留记录并标离线。历史节点缺字段显示“未上报桌面能力 / 需升级”，不能猜测支持。 |
| 执行能力 | 复用 [PC 端 UI 自动化方案](PC端UI自动化方案.md) 的 Cua Driver / SDK 路线。探测插件、权限、图形会话、锁屏、截图与输入能力，按实际实现声明。安装了 Scout 或 Cua，不等于已可运行；系统支持还受实际发布包 / 架构约束。 |
| 任务选择 | 用例运行栏和新建任务弹窗共用一份按账号过滤的设备数据；按节点分组，区分“PC 桌面”“Web 浏览器”“移动设备”。列表可显示当前任务相关但不可用的本人目标，置灰并显示具体原因；查询不能继续只取在线设备。 |
| 可执行判断 | 服务端返回当前任务的可选状态和阻塞原因（拟新增），综合 owner、节点连接、桌面会话、能力、OS / 应用兼容性和占用情况。前端消费服务端判定，不再只依据 `sn` 或 online 放行。能力不足与繁忙不是同一种状态。 |
| 派单 | 提交仍以设备 `sn` 为执行目标；服务端重新解析归属、平台、能力并获取互斥锁，不能信任前端提交的 platform。Desktop 只路由到对应执行器；未知平台显式拒绝。用户选中的窗口由设备执行阶段解析，不作为独立节点派单。 |
| 独占与隔离 | 一个交互桌面首版只运行一个 PC 任务，与同桌面的 headed Web 共享锁；独立 headless Web 按既有并发规则运行。所有列表、错误详情、日志、操作和实时推送都按当前账号隔离。 |

任务的匹配规则要明确：原生 macOS 应用匹配可执行的 macOS 桌面；Windows 原生应用不能直接派到 Mac 桌面。测试普通网站继续选择该节点的 Web 槽；只有涉及桌面交互的测试才选择 Desktop。缺少应用目标平台或必要执行能力时提示补全 / 不兼容，不能自动挑另一台设备。

分两步交付：① 宿主及桌面状态可见，不可运行时解释原因；② Desktop 执行链路完成并验证后开放任务选择。第一步完成不能宣称“PC 自动化已可用”，第二步应与 PC 插件方案联动验收。

## 4. 合理与不合理的设计

| 判断 | 做法 | 原因 / 调整建议 |
| --- | --- | --- |
| 合理 | 在 Scout 节点下显示其宿主 PC，并让就绪桌面成为任务执行目标 | 用户能理解“在哪台电脑跑”，且与已有节点 → 设备 → 任务模型一致。 |
| 合理 | 支持 macOS / Windows / Linux 的统一展示和分类 | 设备模型统一；具体驱动、架构、权限和发行包覆盖仍逐平台确认。 |
| 合理 | 不可用目标仍可见并给出原因 | 比单纯空列表更好排障；可见不等于允许提交。账号范围之外的目标仍不可见。 |
| 合理 | 复用现有任务、用例、报告和 Cua 执行插件 | 避免为了 PC 再建一套调度与用例流程，保留统一证据链。 |
| 不合理 | 只加一个 Mac / Windows / Linux 下拉选项就允许跑任务 | 缺少设备、能力和路由仍然无法执行，甚至落到 Android 通道；必须打通端到端链路。 |
| 不合理 | 将“Scout 在线”当成“桌面可操作” | 节点可能在无 GUI 的 Linux、Windows 后台服务或锁屏会话运行；需要分别探测。 |
| 不合理 | 一台 Mac 节点同时生成 macOS、Windows、Linux 三个可运行设备 | OS 标签不创造虚拟机。只有实际存在、单独登记并有执行通道的 VM / 会话才可作为目标。 |
| 不合理 | 把 Mac 上的 Web 槽改名为 Mac 桌面，或删除 Web 槽 | 浏览器与原生桌面的能力、隔离和并发不同，应并存并按测试类型匹配。 |
| 不合理 | 每个窗口 / 显示器建一个设备，以此并发测试 | 它们仍共享桌面焦点、键鼠和部分系统状态；首版按桌面会话独占。 |
| 不合理 | 用前端隐藏、客户端 OS 或上传的 owner / platform 决定权限和派单 | 可被绕过或与远端实际情况不同；由服务端身份与 Scout 上报事实确定。 |

需求本身合理，需要调整的是“少显示一个设备就是全部原因”的判断：补齐可见性解决发现问题，补齐桌面执行能力才解决真正下发和运行问题。

## 5. 开发范围与验收

1. **Nexus**：改 `rRuntime.py`、`runtime_tokens.py`、`node_register.py`、`node_store.py` 及节点注册链路；复用 SQLite，列表和操作统一按账号鉴权。历史未归属节点由管理员在 Workbench 认领，旧字段不参与授权且不要求额外客户端。
2. **Scout**：补两种安装脚本的幂等安装、平台检测、绑定与失败提示；核对首次注册、凭证持久化和断线重连。
3. **Workbench**：改 `NodesPage.tsx`、`api/nodes.ts` 和查询层，新增安装弹窗及接入反馈。涉及协议字段变化时，同步两仓协议文档与 golden fixtures。

新增 PC 改动：Scout `core.py` 设备发现与状态探测；Nexus 设备登记 / `ui_devices.py`、`rCaseRunner.py`、平台路由和调度锁；Workbench `api/run.ts`、设备查询、`NodesPage.tsx`、`RunBar.tsx`、`CreateTaskDialog.tsx`。设备类型、OS 与会话元数据须完整贯穿协议、持久化和 UI；不在旧默认 Android 分支上零散打补丁。

**PC 专项验收**：

- Mac 节点登记后能看到宿主和桌面状态；插件 / 权限 / 会话就绪后，可在原生 macOS 应用任务中选择它，完成真实截图、点击、输入和结果回看。
- 缺权限、无 GUI、锁屏、离线、繁忙及旧节点缺能力各显示正确原因；绕过前端直接派单也被拒绝，且不会误用 ADB 或 Web 执行器。
- 重启不重复生成设备；窗口变化不生成设备；两个任务争抢同一桌面只有一个获准，旧会话引用不能继续输入。
- 同节点的 Web 和 Android 设备继续可用；A 能看到自己的 Mac，B 无法查看、选择或通过资源 ID 操作 A 的桌面。
- Windows / Linux 按真实支持矩阵逐项验证；无安装包、不支持架构或无图形会话时如实标注，不写成“已支持全部 PC”。

原有多机验收：同账号在三种系统的受支持环境各接一台；未安装 Mino 的浏览器和已有节点的浏览器均能复制；同机重跑不重复登记；更换浏览器不丢节点；过期凭证不可用；其他账号不能查看或操作节点；一个节点离线不影响其他节点。按项目规范用实际联调记录验收，不新增或运行 pytest。

参考：现有 `docs/基础框架/NODE_REGISTRY.md`、V3 Scout 方案仅复用后端机制；产品入口以本文的 Workbench 单入口为准。旧节点文档中的 JSON 存储描述已落后于当前 SQLite 实现，以现有代码为准。

## 8. 2026-10-12 租约、迁移与验收边界补充

节点归属、设备当前位置、桌面任务准入和机器人持有应分别描述。设备离线迟到报告已有防护，不代表旧节点迟到的“仍在线”报告已有 generation/fencing 防护；后者仍待协议设计及两仓实现，不能靠 device_lost 的分支宣称完成迁移一致性。当前设备准入复用数据库 reservation/lease，不退化为仅进程锁。

后续持有协议必须包含 holder、epoch、lease_until、来源会话、失联续租/过期、切换确认和旧代回调拒绝，并提供双仓相同 golden fixture。现阶段 IM 新稳定入站键不含 node_id，可抑制相同机器人搬家后重放消息，但不能代替持有 fencing；节点 WebSocket/机器人快照只证明某一时刻状态，在线、连接、执行就绪、身份绑定和积压仍分别展示。

桌面任务正常完成、取消、异常和服务重启都需审计释放 reservation/lease；失联的任务先进入可解释的 blocked，再凭租约/执行结果回收。只实现 UI 列表不作为此故障生命周期的验收。Scope 不扩展到共享节点/账号转移，也不移除当前账号隔离。

### 8.1 桌面租约与停止确认目标契约（2026-10-13，待实现 / 联调）

| 场景 | 必须做到 |
| --- | --- |
| 准入与续租 | Nexus 原子取得数据库租约，按稳定逻辑桌面锁定，与 headed Web 共用。拟新增 `lease_id / owner / task_id / epoch / lease_until / node_session_generation`；每次动作由 Scout 校验当前授权代次及有效期，不只比较 task ID |
| 掉线或超期 | Scout 自身可判定的截止时间到了就停止新动作；Nexus 显示失联 / 待核查，不能因 WS 断开立即将同一桌面派给新任务。重连验证代次，旧授权、动作及续租全部拒绝 |
| 停止或超时 | 先持久化停止意图，再通知 Scout 关闭该任务的动作准入；回执关联停止请求、租约代次和最后在途动作，区分已停止、停止中及结果未知，不能请求一发出就显示“桌面已释放” |
| 在途动作 | 能取消则取消并确认；不能取消则等待结果或按受控 worker 终止流程隔离。晚到结果仅补审计，不推进终止任务，不自动重放提交、输入等未知动作 |
| 回收与恢复 | 已确认停止且无在途输入，或完成可证明旧执行已失效的隔离后，才释放 / 发新代租约。服务重启从库恢复并与 Scout 对账；仅靠 TTL 到期不足以证明原生在途动作已结束 |
| 暂停与接管 | 确认动作停止后才准许用户接管。继续需重新取得授权并重采窗口、截图和焦点；不得恢复旧 capture / focus 引用。本机急停也必须阻止新动作，并上报当前执行状态 |

机器人连接使用独立持有租约，复用 epoch 拒绝旧代的思路，但不与桌面锁共用状态。切换只发生在本人节点间；无法确认原持有者已断开时显示“切换待确认”，不把数据库改指向新节点当作连接切换完成。

字段为拟新增契约，协议文档、两仓实现及 golden fixtures 同步后再启用。验收覆盖断网、续租失败、停止时输入在途、Scout / Nexus 重启、旧 worker 恢复、headed Web 冲突和本机急停；必须证明旧代不能继续输入，并记录 Session 与租约代次，未通过则保持能力不可用。
