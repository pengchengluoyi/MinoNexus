# 用例导入编译 × 大模型校验：预期原句被分类名替换（cr-46fb7b919617）

> 日期 2026-10-13。会话 `cr-46fb7b919617::case-b1d321c8::5fda2f6d`，`fail`：
> 「步骤 2 预期未成立：拉起登录页。……校验点 ck_s2_0 的预期值为「导航」，实际屏幕为登录页……不匹配」
> 与 [回看失败排查](回看失败排查-cr-6a8bf8bc1694/README.md) 同一条用例，上次修了 do 回看，这次是 check 阶段。

## 结论
导入/编译没有把预期解析错——用例原文「拉起登录页」被正确归到"导航"类（`expected.screen_reached`）。
问题是**编译产物只留下了分类名，运行时把分类名当成预期交给视觉模型**。模型看到登录页，诚实地说"登录页 ≠ 导航"。页面其实是对的。

## 证据
- `project_cases`：expected 第 2 条 = 「拉起登录页」；步骤 2 点赞。
- seq 481/484：`ck_s2_0`，`title="导航"`，`assert={"mode":"vlm","element":{},"rules":{}}`，`key_ref=expected.screen_reached`。
- seq 494 `assert/vision`：`passed=false`，evidence 明确描述"造物相机登录页（手机号/验证码/登录按钮）"，即画面正是用例想要的。
- seq 495 `check/retry`：summary 复述"必选校验点预期值为「导航」"。

## 根因链
1. `case_step_key_compiler._step_from_hit`：check 行 `title = hit.event_name`（"导航"），原句只放在 `source_clause`。
2. `check_program_plan.milestones_from_check_program`：转成里程碑时**丢掉 `source_clause`**。
3. `vision_assert.checkpoints_from_milestones`：`element/rules` 都为空（导航类无结构化参数）时，`expectation = row.title` → "导航"。
4. 送给 `agent-vision-assert` 的必选项变成「预期值：导航」，原句只在上下文 goal 里出现一次，模型按必选项判。

规律：**凡是没有结构化 element/rules 的 vlm 检查点（导航、文案类兜底），都会退化成分类名**。登录页、详情页、收银台等跳转预期都会受影响，与 V5 方案要解决的"预期语义不可信"同源。

## 修复（三处，均为"保留原句"）
- `check_program_plan.py`：里程碑行携带 `source_clause`。
- `vision_assert.py`：`expectation` 取值顺序改为 `assert.expectation → source_clause → title`。
- `case_step_key_compiler.py`：新编译的 check 行，无 element/rules 时直接写 `assert.expectation = 原句`。
旧用例无需重编译：已存库的 check 行本就有 `source_clause`，运行时即生效。

## 与 V5《三端UI自动化结果可信性方案》的关系
V5 §6.1–6.3 的思路是：编译期把预期映射成原子谓词（check plan v2），映射不了的在资格检查里拦下，**不让它靠看图猜**。本次问题正好是 V5 要拦的那一类——`expected.screen_reached` 没有谓词映射，却在 v1 路径里以"分类名 + VLM"放行/误杀。
- 本次修复是 **v1 路径的止血**：让 VLM 至少拿到原句；不改变"导航类仍靠看图"的事实，可信度问题（V5 的主题）依旧存在。
- 对 V5 的输入：`expected.screen_reached` 应在 §6.2 映射表里明确——要么映射到 Nav 定位谓词（screen_id），要么标为"V5 不声明可执行"。现状 catalog 里它配置键为 `screen_id`，运行时却没有走 Nav 定位，只走 VLM。
- 另一个观察：编译期用 `compile_step_spans` 调模型归类，"拉起登录页"没有被归到更具体的类，且 title 取 `event_name` 的设计本身就会丢信息；V5 的"编译一次、人工预览、冻结"能在预览里暴露这类"title=导航"的行。
