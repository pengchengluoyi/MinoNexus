# Mino Bots：从需求开始到结束的交付与框架影响

日期：2026-10-19。规划，不代表完整开发流水线已经可用。默认自动推进，用户不承担逐阶段审批；信息缺失、资源不足和实际权限限制与人工审批分别处理。

## 1. 一条完整需求能交付什么

开始时以用户请求形成目标合同：项目/应用范围、需求来源、目标结果、完成标准、排除范围、可用环境和预算。能从项目继承的自动继承；不让用户填十页表单。完成标准在开始记录，Bot 不得临近结束偷偷缩减标准。

| 阶段 | 自动做什么 | 交付物 | 进入下一步的自动条件 | 当前能力与缺口 |
| --- | --- | --- | --- | --- |
| 需求进入 | 识别新需求/变更/缺陷，关联现有项目和资料 | 议题、范围、初始需求版本 | 作用域有效、资料可读 | 复用助手/项目服务；补议题关联 |
| 需求分析 | 目标、旅程、规则、边界、异常、验收点 | 需求规格和未决事实 | 来源和结构完整；无影响依赖工作的关键事实缺口 | analyze_req 复用；补澄清和版本上下文 |
| 交互设计 | 页面状态、输入输出、错误/空/加载态、跨端差异 | 交互说明、状态矩阵、必要流程图 | 规则对应、无明显矛盾 | 新增薄方案 job；首期不承诺 Figma/可运行原型 |
| 技术设计 | 对现有架构拟定接口、数据变更、实现范围 | 技术说明、接口草案、影响清单 | 引用实际代码/文档，假设显式 | 需新增技术 job，不凭角色名认定已实现 |
| 工作拆分 | 划分实现、测试及文档工作与依赖 | 工作项、负责 Bot、完成标准 | 无循环依赖、能力可用 | 复用任务承载，补关系；不做通用项目管理平台 |
| 开发实现 | 在指定代码基线实现、运行对应检查、记录变更 | patch/commit、日志、构建产物 | 可验证代码/构建事实且符合目标 | 后续开发适配；无适配时只能交付开发说明，明确“实现未完成” |
| 测试设计 | 更新覆盖、生成/修改用例、选回归范围 | 版本化用例与覆盖关联 | 自动结构/去重/版本校验、现有编译规则通过 | 复用 qa_cover / qa_process_assist；需补自动应用合同 |
| 测试准备 | 检查节点、目标 build、账号、前置数据 | 执行计划及资源缺口 | 真实资源满足 | 复用现有资源/Scout 事实，不能假定在线 |
| 执行与诊断 | 派发、取证、分类、给出修复工作 | session/步骤证据、缺陷与修复任务 | 原任务完成并核对实际结果 | 现有测试链复用；补议题回挂 |
| 修复复验 | 交给开发职责修复，再用正确 build/条件复验 | 修复引用、复验报告与遗留项 | 相关验收点有相匹配的真实证据 | 编码接入前只形成修复说明，不能伪造自动修复 |
| 交付结束 | 汇总范围、成果、证据、已知限制和使用说明 | 交付清单、版本说明、需求到证据追踪表 | 目标合同全部满足；未测/阻塞不能算完成 | 报告和规则 job 复用；补完成判定 |

文档交付、代码交付、测试通过、部署上线是四个不同目标。用户只要方案时不执行开发；用户要完整实现时不能拿“文档已写好”结束。生产部署若未在目标/权限范围内，不自动扩展；若已授权且工具能力已具备，不再要求重复人工确认。本次会话仍只交付方案。

## 2. 端到端示例：新增优惠券互斥规则

1. 读取项目规则和现有用例，识别优惠券/会员折扣关系。规则已有则直接采用；没有且影响金额结算则提问必要事实，先继续梳理页面状态和不依赖该规则的测试。
2. 自动形成需求 r1、验收点 AC-01～AC-06、交互状态和开发任务。确定性检查发现没有覆盖重复提交，测试职责补用例并反馈方案。
3. 方案结果自动应用为新版本，不等待“批准”。需求变化只重算受影响项；保留变化原因。
4. 已接开发能力时修改指定代码工作空间并产出 commit/build；尚未接入时形成明确的开发交接包，整体状态为等待实现，不把需求关闭。
5. 自动维护用例，经现有编译/发布合同进入已授权测试环境执行。发现接口重复扣减，保留证据并形成缺陷工作项。
6. 开发修复后对对应 build 复验；其余成功结果仅在输入/环境仍有效时复用。
7. 完成时交付：需求规格、交互/技术说明、变更引用、用例差异、测试环境/build、逐验收点证据、遗留项。没有权限或没有能力完成的部分如实列出，不用“已全部完成”包装。

## 3. 结束、暂停和失败

需求主状态保持少量：进行中、阻塞、暂停、已完成、已取消。分析/开发/测试子工作沿现有任务状态显示，不在总状态里编码所有组合。

已完成必须由规则核验目标合同、必要成果和证据；LLM 给的是解释，不能单独写完成标记。交付有缺口则显示“已交付部分成果，整体仍阻塞”。用户主动取消可以结束推进，但不是成功完成；部分失败保留成功成果。

反馈不是每天一篇总结：阶段成果和重要变化发摘要，详情链接回原对象；结束卡提供“完成了什么/哪些未完成/成果在哪/证据是什么”。继续讨论同一需求产生新版本；真正新目标可新议题并引用旧成果，不将历史结论串改。

## 4. 对当前架构的总体结论

**不需要推倒 Workbench/Nexus/Scout，但必须增加持续协作状态，并把“自动产生结果”和“安全地自动应用结果”之间的合同补齐。** 最重的变化在 Nexus 业务编排与状态，而不是换一个聊天 UI。

保持：Workbench 唯一前端；Nexus 做业务决定和非设备处理；RouterProxy→Scout 做设备执行；SQLite 是业务真源；模型配置按真实执行账号；角色/job/prompt 继续沿现有目录维护。

新增：项目 Bot 配置、议题与工作项关联、版本化产物索引/交接数据。优先扩展可复用的现有模型，缺失实体才新增表，不提前建独立机器人服务、队列集群、向量库或审批平台。

## 5. 逐层影响、风险与落点

| 层/现有位置 | 影响程度 | 必要变化 | 不这样做的后果 |
| --- | --- | --- | --- |
| Workbench 项目导航/协作视图 | 中 | 议题、Bot 管理、自动更新差异、工作状态；复用用例/证据详情 | 第二套导航、状态混淆、聊天结果找不到 |
| assistant gateway / conversation | 中至高 | 共享议题与个人 lane 分开；消息幂等、actor、scope、版本关联 | 多人消息混入私人上下文，错误归属 |
| assistant tools / 身份配置 | 中 | 工具绑定真实 owner；Bot 只是执行主体标签，调用前校验当前权限 | 用群主/管理员 Key 替别人执行 |
| qa_cover.run_llm_job / tick | 高 | 生成→校验→条件应用分离，但系统自动串联；统一收据与版本检查 | 重试重复写入，迟到结果覆盖新版本 |
| qa_cover 参考用例范围 | 中 | 改进现有 cases[:40] 限制，按范围检索/分批，明确完整性 | 自动生成导致重复用例/漏影响 |
| qa_process_assist 规则 jobs | 低至中 | 保留确定性规则，补输入版本/输出引用 | 把可预测规则改成每次随机 LLM 推断 |
| roles / job_store / prompts | 中 | Bot 引用模板版本及覆盖配置，新增少量 job 合同 | 每 Bot 复制 prompt，无法统一修复 |
| 任务恢复/编排 | 高 | 持久 owner、输入版本、领取、交接、幂等和未知结果对账 | 进程重启后重复执行或丢工作 |
| models / SQLite | 中 | 添加必要关联和修订，短事务；模型/网络调用不持写事务 | 长任务锁库、事件与业务状态分裂 |
| 用例编译/发布 | 中，须单独验证 | 校验成功自动推进既有发布合同；保持冻结版本与真实执行对应 | 删除人工步骤时误删执行有效性约束 |
| RouterProxy / Scout | 首期低 | 沿原任务派发；仅在确有缺失时补关联字段并同步协议 | 为 Bot 另开设备执行通道，破坏分工 |
| Session Log / 证据 | 低至中 | 用稳定关联把执行结果回挂议题，保留 unit/attempt/target | 不同设备和不同尝试结果互相覆盖 |
| IM / LangBot | 中、后置 | 线程绑定、成员身份和重投去重；一个渠道先做 | 群消息重复派单、权限范围扩大 |
| 开发代理适配 | 高、后续 | 代码工作空间、版本、输出合同、取消/恢复和构建来源 | 把任意 shell 暴露给 Nexus，代码与设备操作混用 |

这里的高/中/低是相对复杂度判断，不是完成工期。静态证据包括 qa_cover 的 run_llm_job、tick/_apply_* 与 cases[:40]，Workbench 的单左栏、CaseReview/CaseVersionChain，及仓库 AGENTS.md 架构约束；本轮未运行服务。

## 6. 自动化对现有发布与门禁的影响

取消的是新增业务流程中人为的“看完点通过”依赖。编译成功、用例冻结版本、账号权限、设备目标和未知写隔离等是执行正确性条件，仍由系统自动检查。现有代码若把人工动作与冻结写入耦合，需抽出业务服务供自动推进调用；不能通过直接改数据库状态伪装通过。

需要区分被测项目的用例发布、被测软件上线，以及 Mino 产品自身升级。此次自动推进设计不恢复 V7 明确取消的产品自动升级、来源周期同步、全量历史迁移等。仅在已启动需求生命周期内推进指定工作，不变成无人指定目标的全局后台自动修改。

## 7. 开源框架影响与取舍

默认复用当前编排；聊天优先 assistant-ui 组件适配既有事件。若持久交接复杂度超出现有机制，再选择 LangGraph 或 AgentScope 一个库，不同时引入多个 Agent OS。开源框架负责通用协作原语，Mino 负责版本、身份、自动应用和测试事实。

LangGraph 检查点不等于数据库业务提交；interrupt 不是必须的人类审批节点。AgentScope 团队也不能自动保证项目权限或任务幂等。新框架如果要求替换模型客户端、复制业务状态或新增一套账号，先停止扩大集成。

OpenHands 等开发适配独立于设备执行；不为它修改 Scout 的基本职责。OpenMuse 的运行后端、Dify 的工作流平台、Paperclip 的任务组织不整体一起部署，避免每层都有自己的“当前状态”。

## 8. 性能和运维变化

并发 Bot 会增加模型成本、工具调用、事件量与 SQLite 写入竞争。默认一个议题单主要负责人，独立只读分析可以有限并行；同一用例/文档的正式应用串行条件提交。限制同项目并发、每工作项轮数/时间/预算，输出大文件走现有产物引用而不是写入每条消息。

事件推送是通知，不是真源；先提交业务状态再通知，断线重连按版本/游标补读。若现有事件链不能保证投递，再增加最小持久投递记录，不预设全套事件溯源。模型和网络请求不得持有数据库事务。

新增必要排障字段：topic/work_item/bot/config_revision/input_revision/run/attempt/parent_task 与执行证据引用。日志不记录密钥和无关私人上下文。成本按真实调用记，Bot 个数不是计费次数。

## 9. 实施顺序与验收

1. 先补单议题自动链：现有需求分析→版本校验→自动写用例→既有执行链接；没有人工接受按钮。
2. 再补 Bot 增删/暂停、职责模板、工作交接和持久上下文。删 Bot 不删成果；重启不重放未知副作用。
3. 接执行事件自动回挂、缺陷工作项和复验；验证多个目标/版本不串证据。
4. 最后按真实需求接开发代理，交付范围从文档/测试扩展到代码与 build；IM 按单渠道接入。

每步保持既有手动用例/任务入口可用。新协作链可按项目启用，故障时停止新派发，保留已写数据与运行中任务，不靠回滚数据库解决。迁移仅加必要字段/表，不自动改写历史任务。

验收看真实任务/session：重复投递、基线并发变化、运行中删除 Bot、断线恢复、跨用户身份、预算耗尽、输出截断和设备未知结果。依照仓库规则不新增提交测试/mock，不跑 pytest。当前交付仅为文档，以上属于后续实施验收合同。
