## 1. 产品判断：Mino 应当成为项目里的测试协作伙伴

建议把 Mino Bots 定义为：**围绕一个软件项目，让产品、开发和测试人员与有明确职责的 Bots 持续协作，把讨论变成有版本的需求、开发说明、测试方案与真实验证证据。**

用户不需要每天重新告诉机器人项目背景，也不需要自己在几个聊天窗口间搬运结论。Mino 应当知道正在讨论哪条需求、哪些问题还没定、当前文档是哪一版、哪些结论有测试依据，并允许人随时补充、质疑和调整。

产品价值集中在四处：

1. **讨论能积累**：原始意见、已确认决定、假设和未知项分开，下一次交流接得上。
2. **协作有负责人**：Bot 可以拆解、交接、评审，但一个产物始终有明确责任人。
3. **文档可继续讨论**：文档中的某条规则可以被引用、修改、比较版本，并找到受影响的开发任务和用例。
4. **测试有证据**：最终通过与否来自 Mino 已有测试执行链，聊天总结不能替代核验。

第一阶段的用户体验应当是“拉一个项目小组，把一个需求聊清楚并形成可测试的交付包”，而不是先搭建通用 Agent 操作系统、机器人商店或自动软件公司。

## 2. 已发行产品实际服务什么场景

### 2.1 Grok Bot：给长期工作找一个有名字的负责人

官方文档中的 Bot 具有名字、职责、独立会话和持续积累的上下文；工作发生在带浏览器、文件和终端的持久电脑上。用户以自然语言交办任务，可以中途纠偏，Bot 可以联系其他 Bot 并交接工作。[G1–G4]

最有参考价值的不是“多几个聊天头像”，而是下面三种不同用法：

| 用法 | 用户具体怎样使用 | 成果 | 对 Mino 的启发 |
| --- | --- | --- | --- |
| 个人长期 Bot | 创建“Bug Reproduction”，给它一个缺陷链接、预发布环境和测试账号使用范围 | 复现步骤、预期/实际、截图、环境说明与最小复现材料 | 设立“缺陷复现 Bot”，复用项目上下文，交付标准证据包 |
| 多 Bot 群聊 | 选取 2–6 个 Bots；用户说明共同目标；研究者收集资料，撰写者整理，评审者查阻塞项 | 一个共享结果及可见交接过程 | 用于需求澄清、开发方案评审和测试设计；不要所有角色每轮都发言 |
| Team Bot | 管理者配置共享工具、文件和技能后发布；团队成员分别私聊，也可通过 Slack 使用 | 同一团队知识与工作方法，多份相互隔离的个人交流 | “团队共享测试专家”与“多人共同讨论的群”是两种产品对象 |

官方的 Bug Reproduction 案例明确要求在 staging 复现，返回步骤、截图、浏览器/OS、控制台或网络信息，并且不使用生产客户数据。Product Performance 案例要求调查发布后延迟、提供来源并区分事实和假说。这两类非常贴近 Mino；销售拓客、招聘、费用报销则不是 Mino 的首期目标。[G3]

需要特别区分：

- **个人名下的多个 Bots**可共享同一台电脑上的文件和登录态；这不意味着 Mino 中不同项目、账号和测试环境可以共享资源。
- **Team Bot**的个人会话与团队记忆分开；其官方说明也区分个人对话电脑与共享渠道电脑。不能把“团队共用一个 Bot”实现成“所有人读同一份私聊记录”。
- Grok Bot 群聊官方文档列有具体限制，例如 Bot 向群交接目前为文本形式，部分审批/秘密/登录请求不在普通 Bot 群中出现。Mino 的群内执行和凭据流程须自行按已有身份边界设计，不能假定竞品已经解决。

### 2.2 Muse：把一次问答变成持续推进的任务

Muse 官方介绍的典型用法是：用户提出目标，Agent 拆出计划，在用户关掉应用后继续工作；缺信息或遇到敏感操作时回来找人，最后交付结果。它强调消息式交互、记忆、计划、行动记录与用户接管。[M1]

对 Mino 最有价值的迁移不是旅游预订或个人财务，而是：

| Muse 的工作方式 | Mino 中的对应场景 | 必须改变的地方 |
| --- | --- | --- |
| 接受长期目标并持续推进 | “这个版本的退款需求从讨论跟到验收” | 长期目标必须绑定项目、需求版本、负责人和范围 |
| 关掉应用后仍工作 | 编译用例、执行测试、整理证据在后台继续 | 依赖 Nexus/Scout 在线与持久任务；关掉 Workbench不等于执行节点可关机 |
| 缺信息时回来问人 | “部分退款的优惠券分摊规则还未确定” | 问题绑定具体需求和版本，其他独立工作可继续 |
| 记住偏好与背景 | 记住项目名词、文档风格、测试策略 | 业务事实保留来源和有效范围；记忆不能替代当前规格 |
| 查看成果并继续修订 | 在开发说明旁说“这里要支持多次部分退款” | 生成差异和影响列表，不能悄悄覆盖已确认版本 |

Muse 是持续任务体验的参考，不是已经验证的多人测试平台，也不是 Mino 可以直接使用的开源服务。

### 2.3 OpenMuse：可读源码的持续任务应用，但不是现成团队底座

本次所指明确为 **CopilotKit/openmuse**，不是同名脑电项目，也不是 diggerhq 的同名助手。其 README 自述为 Alpha，公开使用场景包括：邮箱材料→填写 PDF→审阅回复、网页研究与浏览器接管、CSV 财务汇总、目标跟踪、任务暂停/恢复和成果卡片。[O1–O3]

可借鉴的交互非常具体：

1. 一边对话，一边看到计划、待补输入和结构化产物。
2. 任务比聊天气泡活得更久，离开页面后回来仍能找到状态和收据。
3. 后续意见排队或中断当前回复，不丢用户正在写的草稿。
4. 产物卡片回查实际任务状态，失效的文件链接重新获取。

但当前源码说明：部署是单 owner 模式；Rich Threads 依赖另行配置的 CopilotKit Intelligence，且不包含在应用 MIT 许可中；其浏览器和终端也不是 Mino 的跨平台测试执行器。因此它适合做**交互样板和模块复用来源**，不适合直接换皮后承诺多人隔离、企业私有化与测试可信性。

### 2.4 其他开源工具解决的不是同一个问题

| 工具 | 实际使用者与典型操作 | 适合 Mino 的部分 | 不适合直接承担的部分 |
| --- | --- | --- | --- |
| Munder Difflin | 开发者把现有 CLI Agents 组成有角色、邮箱、共享黑板和协调者的办公室 | 角色模板、任务交接、协作状态、停滞与预算展示 | 不是产品/开发/测试多人身份系统；文件邮箱不应替代 Nexus 业务库 |
| Orca | 开发者在独立 worktree 中运行多个编码 Agent，查看 diff、续聊、比较实现 | 后期开发任务交付与代码评审的外部工具 | 不是需求多人讨论底座，也不应变成第二个 Mino 前端 |
| ChatDev / MetaGPT | 输入目标，按角色协作生成软件相关成果 | 需求分析、角色 SOP、开发文档与评审模板 | 自动生成项目不代表对现有系统有正确需求理解，更不代表真实用例通过 |
| LangGraph / CrewAI / Microsoft Agent Framework | 开发者把角色、状态、工具与工作流组成应用 | Bots 协作执行所需的通用框架 | 本身不提供 Mino 的产品体验、项目权限或测试证据语义 |

详细许可证、依赖、成熟度及选型结论见配套调研文档。**产品应用、UI 组件、协作框架和设备执行器要分别选，不应把一个名气大的项目放到所有层。**

## 3. Mino 的适用用户和业务范围

### 3.1 优先用户

- **测试负责人/测试工程师**：需求分散、规则不完整、用例容易遗漏；希望把讨论直接连接到测试设计和复验。
- **产品经理/业务负责人**：需要开发和测试提前提出边界问题，并把回答变成可确认的规则。
- **开发负责人/工程师**：需要明确接口、状态、依赖和验收条件；修复完成后希望按原问题复验。
- **小型交付团队**：没有专职分析师，但已有真实项目和测试环境；需要一个持续跟踪上下文的伙伴。

第一批试点建议选一个 3–8 人的软件交付小组和一个真实应用；这是假设的试点规模，不是产品容量承诺。

### 3.2 场景适用等级

| 范围 | 判断 | 原因 |
| --- | --- | --- |
| 需求澄清、拆分、验收规则、测试方案、开发文档 | 首期核心 | 直接对应需求，已有文档、助手、项目和用例基础 |
| 缺陷复现、测试结果解释、需求变更影响 | 核心闭环 | 连接 Mino 现有执行和证据能力，形成差异化 |
| 开发任务分派、代码差异评审、修复交接 | 第二阶段 | 先交付任务与文档，再接已有开发链和外部编码工具 |
| 发布准出建议 | 第二阶段 | 能汇总证据、指出覆盖缺口，但不替人宣称业务风险可接受 |
| 全天候自动读取所有群、自动改需求和发布用例 | 首期不做 | 噪声大、权限与范围不清；且与已有取消决定冲突 |
| 通用办公、采购、招聘、个人生活管理 | 非目标 | 对测试产品价值有限，会引入大量连接器和运维负担 |
| 让 Bot 直接任意 shell、操纵生产环境 | 非默认能力 | 不符合 Nexus/Scout 分工与现有执行合同 |

## 4. 用户看到的产品对象

用少量对象表达工作，而不是把技术框架术语暴露给用户。

| 对象 | 用户理解 | 关键行为 |
| --- | --- | --- |
| Bot | 一位负责特定事情的伙伴 | 设名字和职责、选择项目资料、配置可用工具、私聊、加入小组 |
| 协作小组 | 人与 Bots 围绕项目工作的地方 | 邀请项目成员、开议题、@角色、查看共同结论 |
| 议题 | 一件有明确目标的事 | 例如“部分退款需求”；包含讨论、待定问题、负责人和成果 |
| 需求卡 | 已拆出的业务规则 | 来源、验收条件、依赖、状态、版本、关联用例 |
| 文档 | 团队持续评审的成果 | PRD、开发说明、测试方案、复现包；支持段落引用和版本差异 |
| 任务 | 有明确完成条件的工作 | 分给人或 Bot；可等待信息、执行、阻塞、完成、取消 |
| 证据 | 某个结论的依据 | 来源文档、决策、用例版本、运行记录、截图和核验结果 |

必须区分三种交流：个人与 Bot 私聊、团队共享 Bot 的个人咨询、多人+Bots 的共同议题。发布角色模板不会自动共享原创建者的私聊、密钥、账号或历史材料。

## 5. Mino 的主场景：从模糊想法到可测试交付

以下对话和编号都是设计示例，不是现有产品运行记录。

### 场景 A：一个想法进入需求协作小组

**人物**：产品小陈、开发小李、测试小周；Bot 为需求分析师、开发顾问、测试设计师。首期由需求分析师兼任协调者，不额外强制一个“主管 Bot”。

**触发**：小陈在“支付项目 / 退款能力”议题中说：

> 我们想支持部分退款，先帮忙把需求拆清楚，生成开发说明和测试方案。

**流程**：

1. Mino 引用现有订单、支付和退款资料，展示“我已理解的范围”和“仍缺的规则”。如果还没有资料，明确列出假设，不伪造系统现状。
2. 需求分析师把问题整理为少量会影响实现的选择：是否允许多次部分退款、金额上限、优惠券/运费如何分摊、退款中的订单能否重复提交。
3. 开发顾问指出接口和状态风险；测试设计师补充重复提交、并发、超额退款、失败重试和权限场景。三者只发自己新增的内容。
4. 小陈补充“允许多次退款，累计不能超过实付”；小李补充“现有接口没有幂等键”；Mino 把二者分别记录为业务决定与技术事实，标明来源。
5. 输出需求卡、待定问题和第一版开发/测试文档草稿。未确定的运费规则标为阻塞项，不阻塞其他已清楚内容的分析。

**交付**：有版本的需求包，清楚列出“已确定、待决定、建议、不在本期”。

**完成标准**：每条拟开发需求有业务目标、适用范围、至少一条可验证验收条件；关键未知项有负责人。不是“生成了很多文字”就结束。

**借鉴**：Grok Bot 的角色分工和群内交接；MetaGPT/ChatDev 的产物 SOP；Mino 自己提供项目来源、版本和用例关联。

### 场景 B：围绕文档继续讨论，而不是重新开一段对话

**触发**：开发在“退款开发说明 v1”的状态机段落回复：

> 回调超时不能直接视为退款失败，要保留处理中并主动查询。

**流程**：

1. 回复绑定到文档 v1 的具体段落及需求 R-退款状态，而不是只保存一段散文聊天。
2. 开发顾问提出差异；测试设计师列出“回调迟到、重复回调、查询结果相反”等受影响用例。
3. 需求分析师确认这是技术实现说明还是改变业务语义。涉及用户可见状态变化时，由业务负责人确定规则。
4. Mino 展示变更包：修改的需求、开发说明段落、新增/需重审用例，以及未受影响部分。
5. 人员接受后形成 v2；v1 和原讨论仍可追溯。已经用 v1 执行的结果仍属于 v1，不能改标签冒充新规则已通过。

**交付**：差异版本、决策记录、受影响测试清单。

**完成标准**：多人同时编辑不会互相覆盖；旧文档上的回复不会默默应用到新版本；“继续”能恢复这一议题的待办和问题。

**借鉴**：Muse/OpenMuse 的持续任务与成果交互；版本、影响追踪和测试身份由 Mino 提供。

### 场景 C：把需求转成可执行测试，保留人参与的阶段

**触发**：测试负责人说：

> 针对已确认的 v2 生成测试用例，先覆盖金额边界和重复提交，给我审阅。

**流程**：

1. 测试设计师根据验收条件形成测试矩阵：正常、边界、异常、权限、并发/重复、恢复；不适用项说明原因。
2. 每个候选用例关联需求版本、预期、前置账号/数据条件及平台。没有验证手段的断言标为能力缺口。
3. 用户审阅候选，再进入现有用例编译、审阅和发布流程；生成草稿不等于发布。
4. 用户确定环境、目标和预算后，调用 Mino 现有执行链。Bots 不自行操控浏览器或替换 Scout。
5. 完成后在议题显示覆盖、通过、失败、受阻、未核验；详细证据指向原运行记录。

**交付**：需求—验收条件—用例版本—运行证据的追踪表。

**完成标准**：无法执行的项留在范围中，不能为了“全绿”删除；模型建议通过不构成通过。

### 场景 D：群里报缺陷，Mino 帮忙把问题变得可复现

**触发**：群成员说“退款偶尔会扣两次”，附错误截图；@Mino 要求分析。

**流程**：

1. 把消息转为独立缺陷议题，收集应用/build、账号类型、环境、出现时机和期望行为。截图只作为线索。
2. 缺陷复现角色检索已授权历史运行，给出可复现计划；涉及账号/设备的准备走现有资源能力。
3. 在授权测试环境执行，交付步骤、预期/实际、session、证据及未确认的猜测。
4. 若无法复现，明确“本次条件下未复现”，保留尝试条件，不把它标为不存在。
5. 开发修复后绑定新 build，在原失败条件下复验，并补充相关回归；原失败记录不覆盖。

**交付**：可给开发直接使用的复现包及后续复验记录。

**借鉴**：Grok Bot 官方 Bug Reproduction 场景最直接；Mino 的优势在真实设备、资源控制、测试断言和版本证据。

### 场景 E：需求半途变了，准确告诉大家哪些工作要重做

**触发**：产品说“退款额度从按订单改成按商品项，还要支持组合优惠”。

**流程**：先生成变更候选，比较旧基线；按引用关系找受影响需求、文档和用例，再由角色判断关联的业务影响。引用命中是确定事实，语义推测是待复核建议。正在运行的旧版本测试继续绑定旧基线，是否停止由有权限的人决定。

**交付**：影响列表、需要重审/重编/重跑的项和新待定问题。不存在可靠映射时注明覆盖未知，不声称已经找全。

**完成标准**：只更新被接受的变更；无关文档和用例不被全量重写；用户能沿一条规则追到相关任务和证据。

### 场景 F：把开发交接做完整，随后仍在同一议题沟通

**触发**：“这版需求确定了，拆成开发任务并写开发说明。”

**交付包**至少包含：目标/非目标、现状依据、业务状态与异常、接口输入输出、数据影响、兼容与迁移考虑、任务依赖、验收条件、测试数据准备、待决定项。接口只是建议时标“拟定”，不能包装成源码已有。

Mino 把任务分给真实负责人或具备相应授权的外部编码 Agent。首期支持交付文档和任务；后期通过已有开发链或 MCP 接入编码工具。代码完成返回变更引用和构建信息，然后继续澄清、评审、测试。**“开发文档完成”“代码完成”“测试通过”是三个独立状态。**

Orca 等工具适合承接独立分支上的编码和 diff 评审，但不成为 Mino 的业务数据库或唯一界面。APK 构建仍受 V7-01 的独立范围约束。

### 场景 G：版本评审时回答“现在到底能不能交付”

用户提出“汇总这版还有哪些风险”。Mino 从已确认需求基线和固定测试范围出发，列出未决业务规则、未实现任务、无覆盖验收条件、失败/受阻/未核验项、版本不一致和资源清理问题。

结果是**证据支持的准出建议**，由指定负责人作最终决定。不能只统计执行过且成功的用例，也不能用不同 build、不同环境的成功结果拼出“整版通过”。此场景放在第二阶段，先确保前面的映射准确。

### 场景 H：让项目知识成为可复用的团队专家

新成员私聊“我们退款为什么不立即标失败”。Bot 引用已确认的状态机版本和对应决定，解释原因；不暴露其他人的私聊。发现规则过时，可以提出“需要复核”并创建候选修订。

稳定流程可以保存为“退款需求评审”团队模板，包含问题清单、输出格式和审查要点。首期人工调用；自动订阅外部变化、定时读取群消息和源文档不随模板功能自动恢复。

## 6. 角色如何设计，避免只换提示词和头像

| 角色 | 负责的结果 | 主要输入 | 可产出/调用 | 不拥有的决定权 |
| --- | --- | --- | --- | --- |
| 需求分析师（首期协调者） | 把需求说清楚并维护问题清单 | 议题、业务资料、成员回答 | 需求候选、拆分、决策摘要、角色交接 | 不替产品接受业务规则 |
| 开发顾问 | 让实现方案与当前系统边界一致 | 已确认需求、授权源码/架构材料 | 开发说明、接口建议、开发任务 | 不默认改代码、发布或操作生产 |
| 测试设计师 | 可验证的覆盖方案 | 验收规则、现有用例、能力目录 | 测试矩阵、候选用例、覆盖缺口 | 不发布用例、不修改历史 verdict |
| 缺陷复现/执行助手 | 按授权范围取得运行证据 | 复现条件、测试版本、目标资源 | 调现有编译/执行/证据工具 | 不自行解隔离、换账号、放宽断言 |
| 评审者（按需启用） | 找冲突、缺来源和未覆盖项 | 同一冻结版本的产物 | 阻塞项与具体修改建议 | 多一个模型意见不等于独立真值 |

角色配置包含：名称、职责、输入范围、知识来源、输出模板、工具白名单、模型策略、允许的项目、单次预算和可见范围。模型配置引用当前执行账号已有配置，不把密钥复制到 Bot。

“角色配置”和已经取消的旧 persona 执行能力迁移是两件事：V7 是新建协作产品角色，不恢复历史 HITL/persona 能力菜单，不因此重启旧迁移。

默认小组只有 3 个角色；执行/评审角色按任务需要使用。以下问题优先一个 Bot 直接答：查最近运行、解释一条术语、总结一份已知报告。只有需要不同专业判断或交接时才多角色协作。

## 7. 关键交互规则

### 7.1 群组不是所有人的上下文混合池

- Workbench 小组是规范协作空间；IM 群/线程是可选入口，通过明确映射关联。
- 一个议题绑定一个项目和应用范围，允许多条并行议题；“继续”优先引用的议题，无法唯一确定才追问。
- 无 @ 的群消息默认不启动全体 Bots；已明确建立的议题内，只唤醒当前负责人或被点名角色。
- 普通回答为共同结论；专家细节可展开，避免角色互相客套刷屏。
- 外部群成员不自动获得项目权限。查询权限与向整群披露结果的权限分别检查。

### 7.2 人随时可以改变方向，但已有事实不会消失

“只分析，不执行”“先暂停测试”“继续上一版”都对应具体议题/任务。停止禁止后续动作；已经派发的动作可能仍在执行，显示真实停止与对账状态。新消息不能偷偷替换已提交执行的需求版本。

### 7.3 文档与聊天互相连接

文档里每条关键规则有稳定引用；聊天可以定位规则、提出改动、查看差异和接受新版本。用户无需了解内部 JSON。内容默认生成草稿，确认需求基线和发布测试仍沿用现有业务权限；不为每个分析步骤弹审批。

### 7.4 记忆分层

| 层 | 保存什么 | 怎样使用 |
| --- | --- | --- |
| 个人偏好 | 语言、报告详略、文档风格 | 私人范围，不改变执行账号与默认设备 |
| 议题工作状态 | 当前范围、待定问题、任务进度 | 可恢复；摘要保留来源引用 |
| 项目事实 | 已确认规则、术语、架构约束 | 有负责人、版本、来源和适用 build/平台 |
| 检索线索 | 历史对话、未确认推测 | 用于找材料，不能直接当正式规则 |

## 8. 推荐的首期产品形态

仍只有 **MinoWorkbench** 一个前端。在现有项目导航增加“协作”入口，个人助手提供待办深链，避免另建一个 OpenMuse/Orca 品牌入口。

```text
左侧：项目 / 小组 / 议题
中间：讨论、@角色、问题卡、交接与任务状态
右侧：需求 / 开发说明 / 测试方案 / 证据；支持段落引用和版本差异
顶部：当前基线、范围、负责人、运行状态
```

先以列表/详情/侧栏呈现，不做像素办公室、复杂流程拖拽或机器人市场。角色和小组可使用模板一键创建；后台真实采用开源聊天组件和协作框架，而不是手写整套通用系统。

最小可交付闭环：**建议题 → 三角色澄清 → 需求与开发/测试草稿 → 人补充并接受版本 → 生成候选用例 → 现有执行链 → 回到同一议题解释证据。**

## 9. 哪些事情用开源，哪些属于 Mino 自身

| 层 | 推荐路线 | 不重复开发的能力 | 必须由 Mino 明确的内容 |
| --- | --- | --- | --- |
| 聊天 UI | assistant-ui 优先验证现有事件适配，AG-UI 按需；OpenMuse 作为交互参考 | 流式消息、输入框、工具卡片、基础会话组件 | 项目小组、需求卡、文档差异、测试证据卡 |
| 角色协作 | 现有编排优先；需要时比较 LangGraph / AgentScope | 状态图、分支/交接、中断/恢复原语 | 各角色职责、业务状态、任务幂等和版本检查 |
| IM 接入 | 沿用现有 LangBot/Scout 链路 | 渠道 SDK、消息收发 | 议题映射、成员权限、群披露策略 |
| 文档/知识 | 先复用现有文档库、FTS与检索 | 已有上传、切片与搜索 | 需求基线、文档版本、决定与证据关联 |
| 真实测试 | 现有 Nexus → RouterProxy → Scout | 已有跨平台驱动与执行能力 | 对话到既有测试任务的受控桥接 |
| 开发执行 | 后期对接已有开发能力/外部编码工具 | 编码 Agent、worktree、diff 等通用能力 | 任务交接合同与测试回流 |

这不是排斥整套开源产品：若日后目标变成独立个人助手，OpenMuse 整体 fork 会更有吸引力。但当前目标是把已有 Mino 变成多人测试协作工具，组合复用比替换前后端、数据库和身份系统的代价更小。最终依赖选择以配套选型验证为准，不能凭 README 直接承诺上线。

## 10. 产品验证方式

首轮采用三个真实案例：一个新需求、一次文档变更、一个历史缺陷的复现与复验。每个案例与现有人工流程对照，记录输入完整度、负责人投入、修改次数、输出质量和实际模型费用。

| 问题 | 评价证据 |
| --- | --- |
| 是否少重复讲背景 | 同一议题隔日继续，能正确恢复基线、未决项和引用 |
| 是否更容易发现漏项 | 人员评审确认的有效边界问题；错误/重复建议也计数 |
| 文档是否能给开发用 | 任务负责人逐项确认可实施性；拟定内容与事实分开 |
| 测试是否真正连起来 | 每条纳入范围的验收条件可查覆盖状态和真实 run/session |
| 多角色是否值得 | 与单 Bot 使用相同材料比较质量、延迟、费用；无收益则合并角色 |
| 群里是否更清楚 | 议题串线、重复任务、噪声消息和错误披露数量 |

不先承诺“节省 80% 时间”或“自动覆盖全部需求”。首期成功是团队愿意在下一条需求继续用，并且能证明讨论、文档和测试之间没有断链。

## 11. 建议的产品推进顺序

1. **先验证交互与开源适配**：同一退款案例，用拟选组件做薄原型，确认长对话、文档引用和角色交接成立。
2. **交付需求小组**：多人讨论、三角色、需求卡、开发说明、测试方案、版本和续聊。这是用户本次需求的核心。
3. **接通测试闭环**：候选用例进入现有编译/审阅/执行，结果回到议题；保留全部证据与历史。
4. **再接 IM 共享议题与缺陷复现**：逐渠道真实验收，不能从 Workbench 成功推断飞书/企微等已通过。
5. **最后扩展开发任务和准出建议**：按收益增加外部编码工具、角色模板和受控自动化；不顺带恢复已取消的源同步或自动发布。

本次新增的是 V7 Bots 方案研究与设计，不改变 V6 收尾责任，也不把 V7 原候选全部升级为承诺。
