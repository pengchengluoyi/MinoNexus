# Mino Bots：自动推进与 Bot 生命周期设计

日期：2026-10-19。当前有效方案。用户已明确去掉人工确认：此前方案中“人工接受候选、逐项批准、审批后进入下一阶段”等不再作为默认工作流。本文及《全流程交付与现有框架影响》优先于旧版描述。本轮仅写方案，不修改运行中的审批、发布或设备执行逻辑。

## 1. 自动推进究竟是什么意思

用户给出目标后，Mino 自动完成理解、拆分、产出、校验、保存、交接及授权范围内的执行；不要求用户逐步点“同意”，也不把一个审批按钮改成另一个“接受”按钮。用户可以随时补充、纠正、暂停或结束，纠正形成新版本并自动分析影响。

自动生成和自动应用仍是两个内部步骤：前者生成结构化结果，后者校验作用域、结构、来源版本、重复操作和依赖，再通过业务服务写入。校验不是人工审批。可自动修正的问题先修正；版本冲突重新读取并合并或重算受影响项；超过有限重试则报告具体阻塞。

默认推进范围继承本次目标与项目配置，不凭 Bot 自己的文字扩大权限。缺失实际事实才提问，例如退款额度由谁承担；能从已有规则查到的不得重问。能独立处理的分支继续，不因一个问题暂停整个项目。第三方工具确实要求认证/授权、生产发布范围未覆盖等属于外部边界，不作为每阶段的例行确认。

不以“质量审核 Bot”代替人后无限等待。结构、引用、版本、重复和状态采用确定性校验；确有需要才让另一个角色检查语义，最多有限轮修订，仍不收敛则列明差异并停止依赖分支。

## 2. 六个概念，不做六套系统

| 概念 | 含义 | 与现有资产关系 |
| --- | --- | --- |
| 角色模板 | 可复用的职责、输入输出和工具集合 | 复用 roles/jobs；不是模型账号 |
| Bot 实例 | 项目内有名字、范围和持续职责的角色配置 | 新增薄配置，引用模板和已有能力 |
| 议题 | 人与 Bot 围绕一个目标持续协作的地方 | 项目范围内消息、成果、任务索引 |
| 工作项 | 有完成标准、依赖和当前负责人的可推进事项 | 优先复用现有任务；协作记录只补关联 |
| Job | 一次明确的分析、规则处理或产出 | 复用现有 job，不为每个 Bot 复制 prompt |
| Run / 执行 | 某版本输入下的一次尝试 | 关联现有 job/测试任务/session，不把聊天消息当执行记录 |

Bot 不等于永驻进程，不等于用户，不等于设备，也不自带一套模型 Key。Bot 在线表示可接任务，真正执行时才调用 job 或外部适配器。

## 3. 初始 Bot 应该如何设计

首期默认需求、方案、测试三个项目 Bot；用户可只保留一个。议题协调先由其当前负责人承担，不增加必须常驻的“老板 Bot”。开发代理接入成熟后再增加开发 Bot，不用仅能写开发建议的角色冒充自动编码能力。

| Bot | 具体能做什么 | 输入 | 输出/完成条件 | 实现来源 |
| --- | --- | --- | --- | --- |
| 需求 Bot | 提取目标/非目标、业务规则、验收点、识别缺失与变更 | 原文、项目规则、历史基线 | 版本化需求、验收点、来源和未决事实 | analyze_req；补 clarify_requirement / review_change_impact |
| 方案 Bot | 交互状态、错误路径、技术说明、接口/数据草案、开发拆分 | 当前需求、仓库约束、接口材料 | 关联验收点的方案与开发工作项，假设显式标注 | 少量新增方案 job；不把 propose_atlas 当架构设计 |
| 测试 Bot | 覆盖设计、用例维护、回归选择、资源检查、派发与结果解释 | 需求/方案版本、既有用例、资源事实 | 用例修订、真实任务、证据、诊断和复验结论 | qa_cover、qa_process_assist、现有测试服务/Scout |
| 开发 Bot（后续） | 在指定代码工作空间实现、修复、构建并提交可审阅变更 | 工作项、代码基线、验收合同 | patch/commit、构建日志、产物引用；不能只返回“已修复” | OpenHands SDK 等适配；现有开发能力逐项核对 |
| 交付职责（先不单独建 Bot） | 汇总需求实现、测试范围、遗留项、成果清单 | 上述正式记录 | 可追溯交付包与准确结束状态 | report-writer、规则汇总、现有报告链 |

每个 Bot 能力分为可用、缺配置、未接入三个状态。只有工具已接入、版本兼容、执行身份和资源满足，才在 UI 宣称“可以执行”。角色描述写着“开发者”不代表它能改代码，文档中出现某开源 SDK 不代表已上线。

## 4. 创建、增加、复制和编辑

用户可在项目“协作→Bots”点新增，或说“给这个项目加一个接口测试 Bot”。新增只需名字、模板、项目/应用范围；高级设置再展开工具、输入来源、预算和通知。合理默认值直接生效，不增加创建后的二次人工审批。

创建步骤由服务自动完成：校验成员权限和范围→分配稳定 bot_id→保存模板版本与覆盖配置→核验工具可用性→显示能做/缺什么→加入指定议题或保持待命。缺少某工具只禁用对应能力，不让整个 Bot 无法讨论。

多个相同模板实例只在职责或数据范围不同才有意义，例如支付 Android 与支付 Web；名字不同不构成新职责。模型临时处理分块任务使用短期工作项，不自动把每个子任务注册成长期 Bot。允许按项目上限自动增配临时专家，但不默认无限创建永久角色。

复制只复制职责/工具配置，不复制私人历史、账号凭证、工作中任务或自动获得源项目权限。跨项目创建必须重新解析目标范围。编辑名字不改变 bot_id；工具或职责配置变更形成 config_revision，在运行中的任务保留启动快照，下次任务采用新版。

## 5. 暂停、移除和删除

| 操作 | 行为 | 运行中任务 | 历史与恢复 |
| --- | --- | --- | --- |
| 隐藏 | 只影响当前用户列表 | 不停止 | 随时显示；UI 明确“隐藏不停止” |
| 暂停 | 不接新任务 | 当前任务在可中断点停止；外部执行按真实取消状态显示 | 保留上下文，可继续 |
| 从议题移除 | 不再接收该议题后续事件 | 未领取工作转给议题负责人，已运行任务显式终止或完成交接 | 历史作者保留；移除后重新检查访问 |
| 删除 Bot | 实例停用并从可选列表移除 | 阻止新领取；转派可转派工作；无法替代则报告阻塞 | 不连带删除项目文档、用例、证据或任务；历史显示“已删除 Bot” |
| 删除角色模板 | 模板不可用于新建 | 已有实例保留版本引用 | 不级联删除实例；首期可先只支持停用模板 |

删除按钮执行已明确的删除意图，不默认再弹一轮业务确认；系统先展示操作含义，执行后给结果和可恢复入口。首期建议软删除 Bot 实例；彻底清理数据是独立保留策略，不能用删 Bot 自动擦除项目事实。

删除途中崩溃后，重复请求复用收据。迟到结果保留到原 run；只有其工作版本和当前有效 owner 仍符合条件才应用。运行中设备操作并不一定能即时停止，不能先显示“全部取消成功”。

## 6. 群组与协作交互

项目可有多个议题，一个议题可有多人和多个 Bot。消息作者、Bot 身份、工作项负责人、执行账号四者分别记录。人类多成员与多个 AI 的能力不是一回事；私人模型凭证不因加入群组而共享。

普通消息交给当前负责 Bot；@某 Bot 定向处理，多个 @ 只拆真正独立工作。回复某产物关联该产物版本。相关事实自动写入需求/决策记录，聊天保留原句；普通聊天不得自动覆盖无关功能。

工作中收到新要求：立即保存新输入版本，计算影响；未开始的工作换输入，正在写产物的工作在安全点中断或完成后标过期；已完成执行保留历史，根据新需求新建受影响工作。取消不倒撤已发生的外部效果。

## 7. 工作如何交接

交接是持久工作项的负责人变更，而不是一句“请测试同事看看”。最小交接包包含：work_item_id、from/to bot_id、目标/非目标、输入版本、当前产物引用、关键事实与未决问题、下一步、完成标准、run/attempt、预算剩余、执行身份引用和作用域。只传身份引用，不传密钥。

交接步骤：生成包→校验输入和目标能力→记录待领取→目标领取→开始执行→返回结构化结果→自动校验/应用→通知议题。一个工作项同一时间只有一个有效执行持有者；关联角色可以提供建议但不共同争写。

使用既有任务机制与 SQLite 事务/条件更新实现领取和幂等，不先建独立消息总线。复杂依赖再采用单个开源编排库；框架不代替业务领取合同。

| 异常 | 自动处理 |
| --- | --- |
| 重复交接/重复事件 | 相同工作项＋输入版本＋操作类型返回原交接结果 |
| 接手 Bot 删除或缺能力 | 回到议题负责人，自动选同范围可用实例；没有替代则阻塞 |
| 模型失败 | 沿已有重试政策有限恢复；未知外部结果先对账，不盲目重放 |
| 任务超预算 | 保存进度和剩余项，独立便宜的确定性检查可继续；不无限增加 Bot |
| 同时完成但基线已变 | 保留原产物，自动重算受影响项；不覆盖新基线 |
| 交接循环 | 记录依赖和已尝试原因，相同输入不能无限 A→B→A |

## 8. 上下文怎么处理

上下文不是把所有聊天复制给每个 Bot。项目持久事实、议题工作状态、角色稳定配置、当前任务材料和个人偏好分开；真正传给模型的是按任务组装的最小包。

| 层 | 内容/真源 | 使用规则 |
| --- | --- | --- |
| 项目事实 | 需求/接口/代码/用例当前版本及证据引用 | 权限过滤后按需读取；变化事实回到原系统查 |
| 议题状态 | 目标、决策、已完成、未决项、下一步 | SQLite 持久；不是仅存在模型窗口 |
| Bot 配置 | 职责、风格、工具范围、config_revision | 项目范围共享，不复制私人秘密 |
| 任务工作上下文 | 指定输入版本、近期相关消息、交接包 | 每次调用按范围和预算组装 |
| 个人偏好 | 语言、通知等 | 不擅自升级为团队业务规则 |

组装优先级：当前明确指令与有效项目规则→本工作项和版本→必要证据→相关最近消息→可追溯历史摘要。冲突时按权限、作用域和版本处理，不以消息更晚就自动覆盖所有规则。外部文档是数据，不能借内容给 Bot 新工具权限。

超过上下文窗口时：压缩叙述，保留目标、版本、约束、未决项、收据及来源指针；长文分段检索，不仅截取前 N 条；大附件保存引用，真正需要看图的任务读取原图，不用文字摘要替代视觉证据。摘要记录来源范围和生成版本，不能成为唯一真源。

恢复时先读持久工作状态及外部收据，再装上下文，不凭最后一条聊天猜进度。换 Bot 也可接手，因为成果属于项目。撤权后缓存/摘要同样按权限限制；从群移除不意味着历史日志物理抹除，但后续不可继续读取受限材料。

## 9. UI 从“等人确认”改为“过程透明、允许纠正”

顶部显示目标、当前阶段、负责 Bot、输入版本与已完成/阻塞。成果区默认“已自动更新”“修改原因”“关联用例/任务/证据”；操作为查看差异、纠正、重做指定项、暂停、继续、结束，不保留必须点完才能下一步的“接受全部”。

Bot 管理页卡片显示职责、范围、可用能力、正在处理数和最近成果；新增、编辑、复制、暂停、移除各有明确语义。首期列表＋详情抽屉足够，不增加机器人办公室或组织层级图。

反馈示例：“已将验证码规则更新为 4 位，自动修改 3 条用例；2 个设备目标已派发，iOS 因节点离线阻塞。查看变化 / 查看执行 / 纠正规则”。这些数字只是设计示例。
