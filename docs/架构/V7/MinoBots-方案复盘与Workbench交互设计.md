# Mino Bots：方案复盘与 Workbench 交互设计

> **2026-10-19 流程已修订：本篇保留历史分析依据，人工接受/逐项批准/人工确认后推进的工作流不再有效。当前默认自动校验、自动应用、自动交接与执行；以 [自动推进与 Bot 生命周期设计](MinoBots-自动推进与Bot生命周期设计.md) 和 [全流程交付与现有框架影响](MinoBots-全流程交付与现有框架影响.md) 为准。用户纠正及必要事实补充不是例行审批。**


日期：2026-10-18；静态源码审阅与规划，未运行前端验证。本文修订首版入口与技术组合建议。

## 1. 首版方案需要修正什么

| 问题 | 影响 | 修订 |
| --- | --- | --- |
| 把项目协作放在个人 /assistant 下 | 项目/应用作用域不明显，个人待办与团队事实混合 | 项目导航新增“协作”；个人助手只做待办聚合和跳转 |
| 三栏容易被实现成第二套侧边导航 | WorkShell 已统一单左栏，会再次拥挤 | 保留唯一全局/项目导航；议题列表作为页内容，详情按需展开 |
| 直接锁定 assistant-ui＋AG-UI＋LangGraph | 未证明需要第二套事件适配和运行时 | 先验证组件对现有事件的适配；复杂协作才比较 LangGraph / AgentScope |
| 把文档/需求能力误当现成页面 | retired docs/process/knowledge 等不能直接恢复 | 新建最小议题产物视图，不复活旧导航或全局文档平台 |
| 群组概念未区分人群与 Bot 团队 | 多 Bot 对话不等于多人权限协作 | 明确项目成员、消息作者、执行 owner、Bot 职责四种身份 |
| 结果只在聊天流展示 | 难以批量确认、比较版本和反馈 | 聊天总结＋结构化成果表＋既有详情深链 |
| “完成”含义不清 | 误把生成完成当测试通过 | 显示分析、接受、编译、发布、执行各自状态 |
| 完整场景混入首期范围 | 建出组织架构、流程引擎与知识平台 | 首期三个模板、一条闭环，不做通用机器人市场 |

## 2. 页面信息架构

现有 `WorkShell.tsx` 单左栏保留。`ProjectWorkbench.tsx` 承担项目范围，沿 `projectHref` 生成链接。拟新增 collaboration tab（名称待实施时核对），不是已存在路由。旧 docs/process 等重定向不更改。

```text
单一左侧导航      项目 / 应用范围 / 协作
                  [全部议题] [待我处理] [搜索]
                  标题          当前阶段      负责人      待处理数
                  优惠券互斥    待规则确认    产品甲        2
                  支付无响应    待复验        测试乙        1
```

议题详情默认给讨论足够宽度；不永久占用列表栏。

```text
← 议题列表   优惠券互斥   项目A / AppB   基线 r3   成员 / 更多
当前：待产品确认互斥优先级                         [查看待确认项]
──────────────────────────────────────────────────────────
讨论区                                   成果区（可收起）
产品：优先使用优惠券                       需求 r3 / 开发说明 / 测试
需求 Bot：提出 2 项修改                    新增 2 | 修改 1 | 待定 1
[规则 AC-02 的引用]                        来源 / 原文 / 建议 / 原因
[打开差异]                                [逐条接受] [退回修改]
──────────────────────────────────────────────────────────
输入框：消息、引用、@角色                  关联用例 / 任务 / 证据
```

窄屏改“讨论/成果”页签，状态条保持可见；长文档独立全宽查看，返回保留阅读位置。多成员编辑第一版采用保存时版本检查，不做实时光标和 CRDT。

## 3. 五类用户入口

| 用户与场景 | 入口 | 最短操作 | 结果位置 |
| --- | --- | --- | --- |
| 产品提交需求 | 项目协作→新议题 | 选择已有范围、粘贴需求、开始澄清 | 需求候选与待确认项 |
| 测试修改用例 | 用例详情→讨论此项 | 引用当前版本和某一步 | 同议题候选变更；接受后回原详情 |
| 开发定位失败 | 任务/Session→讨论此结果 | 引用执行单元、步骤和 build | 原证据链接＋缺陷/方案草稿 |
| 负责人处理等待 | 我的助手→待我处理 | 跳转原议题并补充 | 原任务继续，不新建重复任务 |
| 项目管理员配置角色 | 项目协作设置 | 选择模板、范围、允许工具 | 项目 Bot 实例；系统 /roles、/jobs 仍由管理角色维护 |

成员不应为了提需求先配置模型拓扑或 job YAML。默认三模板；允许只邀请一个 Bot。普通消息先由当前负责人响应，被 @ 的专家按需介入，不让三个 Bot 自动轮流发言。

## 4. 现有组件的直接复用

| 组件/机制 | 复用方式 | 不足 |
| --- | --- | --- |
| CasesPanel、CasePreview | 候选接受后链接原用例，保留过滤和分页 | 不复制第二套用例编辑器 |
| CaseVersionChain | 显示原文、理解、冻结发布、历史执行区别 | 需求文档版本需额外关联，不改变用例版本真源 |
| CaseReview | 沿用六类原因、复核和待实跑状态 | 需求评论不能混入执行诊断状态 |
| ImportConflictReview、CaseImportResult | 候选对比、冲突和部分成功交互参考/复用 | 先检查 props 和 API 合同，不假定零改动 |
| RequestsSection | 补信息、过期、范围、恢复任务交互 | 团队议题需项目授权，不能复用个人会话混存 |
| MinoCardView | 展示摘要和链接 | 非 URL 动作当前为 IM 预览，新增 Web 动作需认证回调 |
| executionLinks、V5Evidence、RunComparison | 原证据定位、版本结果比较 | 卡片摘要不复制替代证据真源 |
| React Query、useAppRealtime | 缓存、既有任务事件、局部失效 | key 保留 owner/project/app；多设备保留 execution_unit/attempt/target |
| 未保存离开保护 | 草稿离开提示 | 浏览器刷新后恢复需明确草稿保存方式 |

## 5. 交互状态与反馈

空议题给三个具体入口：“澄清需求”“分析变更”“讨论失败”，不放机器人商城。分析中显示任务范围与可取消操作；超时给已保存部分结果与续接入口。没有模型配置则跳本人设置；没有 Scout 不阻止文档分析，但执行明确不可用。

发生并发冲突时显示当前版本与自己修改，保留草稿，选择重新分析或重新提交；不自动覆盖。旧版本评论仍可阅读，但明确过期，用户重新定位后才应用。

取消分析只停止后续生成；已派发的测试展示实际取消状态。无权限的附件/证据不能靠客户端隐藏保护，所有读写都由服务端校验。撤权后刷新访问权限，不将私人讨论自动共享到项目。

通知只发送待处理、失败、完成和明确 @；结果更新合并成一条摘要。用户可以订阅议题而不接收每个工具日志。

## 6. 性能与可用性优化

长议题分页/按需加载，成果默认摘要；流式片段合并渲染，工具日志折叠，差异大文档按需获取。输入框保持独立状态，避免每个 token 重绘整张用例表。既有 query 缓存按身份隔离，收到事件只刷新关联数据，不全项目 invalidate。

上线前需要测量长消息渲染、首屏和断线恢复；这是一组设计建议，不是本轮已经测出的性能缺陷。键盘可操作、焦点返回、状态文本和非颜色提示应作为基本交付要求。

## 7. 实施边界

先不做流程画布、独立知识库、实时多人富文本、全局组织管理、机器人市场和第二个聊天产品。UI 复用现有 AntD 与 assistant-ui 候选组件；表格、审批、权限、版本比较是 Mino 自己的业务界面，不能期待通用聊天库自动提供。
