## 1. 先区分六个概念

| 概念 | 回答什么 | 例子 | 复用原则 |
| --- | --- | --- | --- |
| 人员职责 | 谁对业务决定负责 | 产品负责人、开发负责人、测试负责人 | Bot 不因为名字叫负责人就获得人的决定权 |
| 产品 Bot | 谁长期帮助我做这件事 | “退款需求顾问” | 有项目范围、长期职责、交流记录和配置版本 |
| 专业角色 | 采用什么专业视角 | `req-analyst`、`case-writer` | 优先复用已有角色，多个 Bot 可引用同一角色模板 |
| Job 定义 | 这一次具体产出什么 | `analyze_req`、`draft_cases` | 复用已有输入/输出合同，不复制 prompt 到 Bot 配置 |
| Job 实例/任务 | 这次工作做到哪了 | 某议题某版本的用例生成任务 | 带 owner、输入版本、结果、费用、状态与收据 |
| 工具/执行能力 | 真正怎样读写或操作 | 查文档、创建用例候选、跑测试 | 复用业务服务/能力目录；模型不能绕过工具授权 |

**Bot 不是 job 的别名，也不是另一个执行器。**例如一个“测试设计 Bot”可以组合脑图编写、用例编写和需求 QA 角色所对应的 jobs；界面不必同时展示三个一直说话的机器人。一个 job 也可以被多个 Bot 使用，但每次都保持具体项目、版本和执行身份。

通用协作框架负责安排节点/中断/交接；Mino 角色和 jobs 负责专业产出；Mino 服务负责接受产物、权限与副作用。不要让框架自带模型入口绕过已有模型账号选择与 `dispatch_log`。

## 2. 当前可复用能力清单

源码路径相对 MinoNexus 根目录。判断等级：A=已有明确业务调用链，适合优先包装；B=已有定义/局部服务，需补合同与接线；C=只参考职责或规划，不当作可调用服务。全部仍需面向 V7 场景验收。

| 现有角色 / job | 本次查到的事实 | V7 怎么用 | 不应误用 | 等级 |
| --- | --- | --- | --- | --- |
| `req-analyst` / `analyze_req` | JSON job，输出 `req_analysis`；`qa_cover.run_llm_job` 调用；理解 baseline/delta、journeys、平台、AC、测试点 | 需求顾问的结构化分析工具；已有产品改造时同时分析原流程和变化 | 不是完整需求池、多角色群会话或需求版本服务 | A |
| `req-analyst` / `propose_atlas` | 生成图谱调整候选；`qa_cover.tick` 保存 pending patch | 判断需求影响模块、辅助确定覆盖范围 | 不是技术架构设计；不能自动改已确认产品结构 | A |
| `mindmap-writer` / `draft_mindmap` | `mindmap` 输出；有 previous_mindmap、按端/分支修订的提示约束 | 测试设计 Bot 的覆盖分解，局部修改尽量保留 ID | job 文本支持某字段不等于所有调用入口已经传入 | A |
| `case-writer` / `draft_cases` | JSON cases 与 missing_points；服务可写入用例草稿 | 测试点展开为用例候选，并反查覆盖缺口 | 不能直接等同编译完成、发布或运行通过 | A |
| `req-qa-bm` / `map_cases`、`classify_fail`、`draft_sign` | `qa_process_assist.py` 中是规则实现；`rAppAutomation.py` 有入口 | 需求验收助手复用规则结果，再解释依据和缺口 | 不为了“Agent 化”把确定性逻辑改成 LLM；不复用未经核对的旧结果聚合来决定新版准出 | A |
| `version-qa-bm` / `pick_regression`、`draft_gate` | 同样是规则 jobs；角色对话 prompt 明说只建议 | 版本顾问选回归、形成准出草稿 | 不自动发版、不把“建议发版”记成审批完成 | A |
| `test-engineer` / `case-step-compile`、`agent-*`、断言 jobs | 角色绑定多个 runtime jobs；独立编译、执行与核验链已存在 | Bots 通过已有业务工具委托编译/执行/读证据 | 不在群聊里直接调用一步动作 job 绕过资源、模式和 RouterProxy | A，按现行执行模式使用 |
| `product-expert` | 角色目录 wired；正文用于与应用简报/产品事实对齐；本轮未完成所有生产调用路径核验 | 需求顾问/设计顾问调用的产品事实审查能力 | 不是产品经理的规则决定权，也不是凭常识生成真实产品事实 | B |
| `knowledge-reviewer` / knowledge、doc learn 相关服务 | `knowledge_situation.py`、`doc_learn.py` 有知识审阅上下文；目录标 wired | 知识候选审查，过滤冲突、无来源内容 | 旧“知识通过”不能变成需求基线批准或自动训练授权 | A/B，沿现有服务范围 |
| `im-qa-assistant` / `im-dialogue` | 存在角色定义；当前 `assistant_agent.py` 实际走 `assistant-route` 与工具循环 | 延用现有助手网关和工具编排；对外作为入口身份 | 不把历史 im-dialogue prompt 当成当前完整运行时 | A（入口服务），B（旧 job） |
| `im-defect-assistant` / `im-defect` | 目录 wired；正文给出 title/steps/expected/actual/severity；带观察沙盒说明 | 缺陷收集结构和追问模板可复用 | 未在本轮证明完整建单/复现连接器；不能声称发一句话已经建单 | B |
| `conductor` / `route` / `qa_tick` | 目录有抽象调度；`list_playbooks` 明列分析→脑图→用例；`qa_cover.tick` 为默认顺序 | 作为协作入口和确定步骤的模板来源 | 不是已经拥有群消息路由、持久多角色交接的调度器；不能每个节点额外调一次主管模型 | A（既有顺序链），B（协作扩展） |
| `report-writer` / `draft_test_report` | 角色 `called: sandbox`；job 正文仅测试/发版报告草稿 | 复用报告格式与职责；补业务输入、schema、存储和实际调用 | 不能拿来直接写所有 PRD/接口设计，也不能称为完整生产服务 | B |
| `doc-keeper` / `publish_wiki` | `called: sandbox`；负责外部同步动作建议，明确不写报告正文 | 后期经独立授权的文档发布工具设计参考 | 不是开发文档写作器；不恢复已取消的外部自动同步/写回 | C（首期） |
| `inspect-session` | 正文明确检查当前截图的登录态/账号身份，输出 session/identity/证据 | 留在测试执行登录判断链 | 名字里的 session 不是聊天会话；不承担群讨论总结、失败报告分析 | A，范围不变 |

### 2.1 复用的真实缺口

1. `qa_cover.run_llm_job(analyze_req)` 当前构造 title/source_text/human_feedback；不是已具备多人议题快照、完整产品简报、决策日志和引用权限。V7 需用适配器显式补齐，不能仅把长聊天塞进 source_text。
2. `draft_mindmap` 的 prompt 提到了 previous_branch/retry_note/human_feedback 等修订方式，但所读普通 `run_llm_job` 分支主要传 title、understanding、source_text、previous_mindmap。必须检查实际入口并补字段，才能兑现“对某条评论局部改脑图”。
3. `draft_cases` 的该调用分支只取 `(cases or [])[:40]`。大型项目不能据此宣称完成全库去重或全面覆盖；需按范围分页/检索并声明 completeness。
4. 这些分析 jobs 默认 `max_tokens: 2048`。完整需求可能被截断，应按业务分段、校验输出与记录不完整状态；不要默默把截断内容当全部分析完成。
5. `qa_cover.tick` 既分析又应用结果、写库。包装为 Bot 工具时必须区分“纯候选生成”和“接受并写入”，不能让一次讨论自动覆盖现有需求和用例。
6. 部分角色 job YAML 声明 `text_chat/chat_reply`，正文却要求 JSON，且包含“观察沙盒”前缀。角色观察体验和生产结构化作业需要分离合同；仅设置 `enabled: true` 不代表可直接当后台任务调用。
7. 规则型验收 jobs 存在不等于已符合最新多 attempt/固定分母/跨 build 比较语义。Bots 展示前应从当前报告服务取事实，不能简单复活历史聚合方式。
8. 现有 `AssistantProfile` 以 user_id 为主键，是“一个用户的助手”结构；不能直接改成多个项目 Bots 而影响旧助手身份。应新增 Bot 实例及模板绑定，旧助手入口继续兼容。

## 3. 建议的角色体系：少量常驻角色，按需专家

### 3.1 面向用户的六类职责

| 产品角色 | 核心责任 | 复用什么 | 真正新增什么 |
| --- | --- | --- | --- |
| 需求顾问 | 还原场景、澄清规则、拆需求、维护问题 | req-analyst、product-expert、analyze_req、propose_atlas | 议题内问题/决定追踪和需求基线 |
| 设计顾问 | 用户流程、页面状态、交互反馈、异常/空态/权限行为 | analyze_req 的 journeys/surfaces；已有应用资料 | 交互设计规格和方案对比；首期不宣称像素级设计或自动 Figma |
| 开发顾问 | 技术方案、API/数据、兼容、任务依赖、可测试性 | 已有文档/源码材料与 development 服务边界 | 技术设计、开发拆分的结构化 jobs；代码执行另走授权工具 |
| 测试设计师 | 风险覆盖、测试点、用例和准备条件 | mindmap-writer、case-writer、req-qa-bm | 对需求/设计版本的显式引用与变更影响 |
| 测试执行助手 | 准备、委托运行、证据整理、缺陷复验 | test-engineer、现有助手工具、资源与执行链 | 群议题与真实任务双向关联，不新造执行器 |
| 质量/版本顾问 | 验收缺口、回归范围、准出建议 | req-qa-bm、version-qa-bm、规则 jobs、报告服务 | 聚合多个议题的版本基线与风险责任 |

产品专家、知识审核员、报告编写多数作为后台能力供上述角色调用，不要求用户分别邀请三个机器人。文档维护是交付工具职责。协调者默认由议题负责人角色承担，必要时使用 conductor 路由，不再常驻一个只会转发的“CEO”。

### 3.2 首期与完整形态的关系

首期小组模板为“需求顾问 + 方案顾问 + 测试设计师”：方案顾问合并交互设计与开发分析。复杂需求可拆成设计顾问和开发顾问；真实执行通过测试设计师调用执行工具并展示独立任务，而不一定新增一个发言头像。

区分两种“设计”：

- **产品/交互设计**：用户能怎么操作、页面有哪些状态、错误怎么恢复、无障碍/多语言等。
- **技术设计**：服务和模块边界、接口/数据、并发一致性、迁移/兼容、可观测性。

不要让一个模糊“架构师”把两者混成一份看似完整的说明。可由同一 Bot 分两次 job 完成，但成果分别命名、引用同一需求基线。

### 3.3 建议最小新增 jobs（均为设计名称，当前不存在）

| 新 job | 为什么现有 job 不够 | 输入 | 输出 |
| --- | --- | --- | --- |
| `clarify_requirement` | analyze_req 擅长拆 AC/测试点，未提供持久问题和多人决策合同 | 议题快照、来源、既有问题和新消息 | 问题增量、冲突、假设、决定候选及来源 |
| `draft_interaction_spec` | journeys 是流程线索，不是交互规格 | 需求 revision、现有流程/页面、设计反馈 | 用户流程、状态/事件/反馈矩阵、异常恢复、待定项 |
| `draft_technical_spec` | propose_atlas 是产品图谱，不是技术方案 | 需求与交互 revision、授权架构/代码引用 | 技术选项、接口/数据建议、约束、风险、兼容与可测试性 |
| `split_development_work` | case-writer 拆的是测试，不是开发交付 | 已接受设计、依赖和验收规则 | 带依赖/负责人建议/完成条件的开发任务候选 |
| `review_change_impact` | 图谱变化不覆盖需求/设计/开发/用例全部依赖 | 基线差异、确定引用图、现有产物 | 确定受影响项、推测项、复核/重编/重测建议 |

PRD/开发文档的排版优先由上述结构化结果和模板生成，不为每种文档再发明一位 Agent。文字润色可按需调用现有模型层，不重复业务判断。已有 report-writer 后期补齐后继续负责测试/版本报告。

## 4. 完整生命周期的实际场景目录

每个场景都说明用户为何会来用、角色怎样协作、产物怎样进入下一步。不是要求每个项目都依次跑完全部场景。

| 阶段/场景 | 用户的实际话语与痛点 | 谁做什么 | 输出和下一步 |
| --- | --- | --- | --- |
| 01 新想法，资料少 | “给老用户增加续费优惠，规则还没定” | 需求顾问还原用户/目标、提出关键取舍；测试师指出不可验证处 | 问题清单+候选 AC；未确定项有负责人 |
| 02 老功能改造 | “保持现有退款逻辑，只增加按商品退” | 产品事实核对 baseline，需求顾问分 delta；开发看兼容，测试保留旧回归 | 新旧边界、兼容清单和测试范围 |
| 03 多份需求冲突 | PRD 写七天，群里说三天，API 文档写五天 | 需求顾问列引用和冲突；指定产品负责人决定 | 决策记录与新基线；不按最新消息自动覆盖 |
| 04 口头讨论变正式需求 | “把今天群里说的整理成能评审的需求” | 经允许选取共享议题消息，区分意见/决定；按角色补缺口 | 有来源的需求草稿，人物原意可追溯 |
| 05 范围与优先级 | “本周只能做一半，先保什么” | 需求顾问提最小闭环；开发给依赖/未知；测试给风险 | 必做/可延后/明确不做；人定优先级，估时标假设 |
| 06 用户旅程设计 | “用户从哪里进入，退款处理中怎么显示” | 设计顾问画流程/状态；产品确认规则；测试校验可观察结果 | 交互规格和状态矩阵，供开发实现 |
| 07 空态/异常设计 | “断网、重复点击、权限拒绝怎么办” | 设计列反馈与恢复；开发给系统实际能力；测试展开场景 | 每种状态的展示/操作/恢复条件，关联用例 |
| 08 跨端一致性 | App 提交后，运营后台何时可见 | 需求确认时效，开发说明一致性，测试师按 e2e 分解 | 跨端验收规则；不能只测 App 一侧 |
| 09 设计稿评审 | “这个页面改稿是否遗漏错误状态” | 设计顾问对照已上传材料；测试按状态矩阵评审 | 设计问题列表；没有接 Figma 时只支持上传/人工引用，不假造连接器 |
| 10 技术方案比较 | “同步退款还是异步回调” | 开发顾问给方案/证据/成本假设；测试询问超时和幂等；产品确认体验 | ADR 式选择记录与约束，随后形成接口规格 |
| 11 接口与数据设计 | “接口字段和退款状态怎么定义” | 开发基于授权架构材料提出 schema；测试找空值/重复/乱序 | 拟定 API/数据规格；人接受后成为开发基线 |
| 12 可测试性评审 | “后端成功了，但 UI 看不出来怎么办” | 测试师提出观测点，开发决定可提供接口/日志/标识 | 可观测性任务；无可用证据时保留能力缺口 |
| 13 开发任务拆分 | “把方案拆成前后端任务，标依赖” | 开发顾问拆数据迁移/服务/UI/观测任务，测试准备并行数据 | 每任务有输入版本、依赖、负责人和完成条件 |
| 14 开发中继续澄清 | “优惠券不能按商品分摊，怎么办” | 形成问题回送需求负责人，设计/测试分析候选方案影响 | 变更候选和受影响任务；不让开发私聊变全项目事实 |
| 15 代码交付核对 | “实现好了，帮看是否对应需求” | 外部编码工具/开发者交付 commit；开发顾问做差异与需求对照 | 实现说明、未实现点和测试建议；静态审查不等于实跑 |
| 16 测试点设计 | “根据已确认的规格补边界和异常” | analyze_req→draft_mindmap；按需开发/设计复核 | 覆盖树；可按平台/功能局部修订 |
| 17 用例复用 | “这些旧用例还能用吗，不要全重写” | map_cases 给候选，测试师查版本/预期相容性 | 复用/修改/新增/退役候选；相似标题不等于覆盖成立 |
| 18 用例编译受阻 | “自然语言用例写好了但执行不了” | 编译链给实际缺字段或能力；测试师补信息，开发说明可观察条件 | 可编译候选或明确能力缺口；不自动降低预期 |
| 19 测试资源不足 | “测这个版本，但退款账号都被占用” | 执行助手展示资源/租约状态并排队或提示 | blocked/waiting 状态；不换他人账号或解隔离 |
| 20 缺陷报备与复现 | “偶现扣两次，有截图” | im-defect 结构化追问；执行助手按批准范围复现 | 复现包，未复现也保留条件与尝试 |
| 21 失败分诊 | “是程序 bug 还是工具没点到” | 规则 classify_fail 和原 session 供事实；测试/开发分别评估 | 根因候选及证据；无证据保持未知，不能篡改 verdict |
| 22 修复复验 | “新包修好了，帮我验证原问题” | 执行助手固定原失败条件和新 build；测试师选相关回归 | 新 run/attempt、原失败对照、问题是否解决 |
| 23 中途需求变更 | “已测一半，现在规则改了” | impact job 分影响；人决定是否停旧 run；各角色仅修订相关产物 | 新旧基线并存，旧通过不转成新通过 |
| 24 非功能需求 | “要支持高并发、弱网、无障碍、多语言” | 需求定可测阈值；开发/测试分析工具和环境能力 | 测试计划与能力缺口；未接压测/安全工具就不声称已执行 |
| 25 版本准出 | “现在能不能上线，风险谁承担” | version-qa-bm 汇总固定范围和未核验；责任人决策 | 准出建议/人工决定，绝非自动发布 |
| 26 文档与新人答疑 | “为什么要这样设计，先前谁定的” | 产品事实/知识检索引用已确认规格和决定 | 可追溯回答，不泄露私人交流 |
| 27 线上问题反馈 | “上线后又出现同类失败” | 读取授权问题材料，关联既有 issue/需求/证据，测试环境复现 | 复发议题与测试补充；不直接改生产 |
| 28 重复交付模板 | “下个支付需求也按这个方式评审” | 把成功流程保存为角色/job 组合与文档模板 | 人工可调用模板；不自动开启外部监听或定时任务 |

## 5. 跨角色交接：交材料，而不是只转一句话

每次交接至少有：议题、任务、发起人、接收角色、输入产物版本、要回答的问题、期望输出、未决项、权限/预算范围、完成条件。接收者发现缺输入则返回明确问题，不静默创造业务规则。

| 交接 | 必交内容 | 接收者的检查 | 不完整时 |
| --- | --- | --- | --- |
| 需求→设计 | 目标用户、范围、业务规则、AC、未知项 | 每个核心流程是否有起点、结果和异常 | 返回具体待定项，能独立做的继续 |
| 设计→开发 | 用户流程、状态/事件矩阵、交互反馈、引用需求 | 状态转移是否可实现，后端/前端责任是否清楚 | 输出技术约束及待选方案 |
| 开发→测试 | 接口/数据、变更清单、部署 build、前置与观测点 | 环境真实可用、版本对应、预期可观察 | 缺构建或资源标阻塞，不造测试结果 |
| 测试→开发 | 复现条件、步骤、预期/实际、case/run/session、证据 | 区分工具问题、业务失败和未知 | 开发可以反问，但不能直接关闭原失败 |
| 修复→复验 | commit/build、修复说明、影响范围 | 原失败条件可重现且 build 更新 | 明示不具备复验条件 |
| 测试→版本负责人 | 固定需求/用例范围、各结果、未核验、风险 | 不混版本，分母完整，风险有责任人 | 只能给“不完整评估”，不输出假全绿 |

## 6. 多人和多 Bot 的典型冲突

### 6.1 产品说 A，开发说 B

Bot 不凭职位名替团队裁决。区分业务取舍与技术约束：业务负责人决定用户规则，开发负责人确认实现约束；测试指出哪种方案可验证。不能达成一致就保留两个方案和阻塞项，禁止把较新的回复当正式决定。

### 6.2 两个人同时改文档

修改绑定 base_revision。相同段落冲突需人工处理，不按最后写入覆盖。不同段落可以产生可审阅合并候选，仍检查跨段落矛盾。Bot 后台完成时若基线已经变更，只作为旧基线候选，不更新当前有效文档。

### 6.3 一个 Bot 工作中收到新要求

“补充背景”可以排入同一议题后续分析；“改变当前范围”生成新 revision 或明确停止/重排；“另一个问题”创建独立任务。工作被取消后保留已有产物和已发生副作用，用户可选择继续未完成项，不能从聊天断点盲目重跑外部写。

### 6.4 设计与测试互相循环提问题

每轮必须新增决定、有效问题或产物差异；相同问题不反复发。初始策略建议每任务最多两轮自动跨角色评审、单次最多三名参与角色，达到预算或无进展则给负责人一条摘要。这是可调建议，需真实案例验证，不是产品硬限制。

### 6.5 私聊有新知识，能否自动进入群

不能。用户选择“作为项目资料共享”后，将指定内容整理成候选并展示披露范围；个人敏感字段/账号材料不随总结进入项目。共享事实仍要满足来源与版本要求。

## 7. 三条推荐工作流，不把所有任务强塞一条大链

### 7.1 新需求工作流

澄清问题 → 分析 AC → 交互/技术方案（按需）→ 开发任务 → 测试点/用例 → 人审 → 编译/发布 → 授权运行 → 证据/验收建议。

需求尚不明确时可以提前出测试问题与风险，但标为探索草稿，不能把它作为已冻结测试基线。

### 7.2 变更工作流

引用现有基线 → 生成差异 → 影响追踪 → 定向修改需求/设计/开发/测试 → 接受新基线 → 仅重编/重跑必要项。已有合格产物直接复用，不全链重来。

### 7.3 缺陷工作流

问题结构化 → 缺信息追问 → 测试环境复现 → 根因候选 → 开发修复任务 → 新 build 复验 → 补充回归与知识候选。无需求变化时不强制重新写 PRD。

## 8. Job 复用适配合同

建议统一调用封装，而不是建立第二套 job 管理平台。封装的输入包括：

```text
project_id / app_id / topic_id / bot_id / actor_user_id
job_id / job_definition_version / input_artifact_revisions
source_refs / context_completeness / user_feedback
allowed_tools / execution_owner / deadline / budget
idempotency_key / base_revision
```

输出包括：结构化 payload、citations、unresolved、completeness、usage、job_run_id、输入版本、状态和候选产物 ID。框架自己产生的 checkpoint 不作为最终业务结果。

复用路径：

1. 角色模板引用现有角色 ID 和 job IDs，不复制 job 正文。
2. 从 `prompt_repo` / `prompt_render` / `job_store` 读取定义与 prompt 版本；新增 job 同样进入现有目录和启动校验。
3. 规则 job 调现有服务；模型 job 使用现有账号隔离的模型调用和追踪。
4. 先验证输出 schema、完整性、来源/项目范围和基线 revision，再创建候选。
5. 业务服务负责接受候选、形成版本与后续动作；框架 node 不直接写正式需求/发布状态。
6. 记录 `topic_id → bot_run_id → job_run_id → case_revision → run/session`，用户可以从讨论追到真实测试证据。

知识和 job 名称里有 “skills” 不代表与设备 `catalog_entries` 是同一层。业务分析 job 决定产出，能力目录声明设备/工具怎么实现；不把需求讨论的顺序塞进设备能力目录。

## 9. 源码依据与后续边界

- `mino_nexus/prompts/roles/*.yaml`：角色职责、绑定、wired/sandbox 元数据。
- `mino_nexus/prompts/jobs/{analyze_req,draft_mindmap,draft_cases,propose_atlas}/`：结构化产出合同。
- `mino_nexus/prompts/jobs/{conductor,product-expert,report-writer,doc-keeper,req-qa-bm,version-qa-bm,knowledge-reviewer,im-defect,inspect-session}/`：职责与限制。
- `mino_nexus/ai/roles_catalog.py`：角色目录、playbooks、观察对话入口。
- `mino_nexus/services/qa_cover.py`：实际分析调用、结果应用和 tick。
- `mino_nexus/services/qa_process_assist.py`、`routers/rAppAutomation.py`：规则 jobs 与接口入口。
- `mino_nexus/services/job_store.py`、`ai/prompt_repo.py`、`ai/prompt_render.py`：定义加载、别名和渲染。
- `mino_nexus/services/assistant_agent.py`：现行 assistant-route 模型/工具循环。

本轮不修改上述代码，不恢复旧 Studio 入口，不读取真实业务数据库。下一阶段验证必须分清“定义存在、服务接线、真实业务调用、上线验收”四种状态，避免以角色目录截图证明 Bots 已完整落地。
