## 0. 这一版为什么重写

第四版为了「像 Dots、像 Bot」，把一个聊天入口设计成了一整套并行的执行系统：自己的任务表、自己的派发与预检、自己的线程表、七种事件触发。落地后出现两个问题：

1. **像 IM**：对话没接到真正干活的代码上，用户说话得不到有用的回应。
2. **挡住原功能**：为了「同一用例只有一个 run」，在 `run_store` 里加了全项目闸门，手动在任务页触发也会被拦。

两个问题同一个根源：**把「工作区」当成了执行系统，而不是一个入口。**

### 0.1 过度设计清点（源码核实）

与协作相关的文件合计约 7000 行（含此前已有的议题与流水线部分）。第四版新增的部分逐项评估：

| --- | --- | --- | --- | --- |

### 0.2 第四版里一个应当撤回的判断

第四版 §2A.8 说「在工作区里让助手直接调 `case.run` 会导致 run 不挂在工作区下，所以必须用工作区自己的写工具」。**这个判断是错的**，它正是造出上面那套并行执行系统的理由。

正确做法：工作区调用的就是 `case.run`，与任务页手动触发是同一条路径。「在工作区里能看到这个 run」靠一条带 `run_id` 的消息卡片解决（§3.4），不需要另建任务表，也不需要任何前置绑定。

### 0.3 第五版又砍过头的地方（2026-10-19 更正）

第五版把多角色一起砍成了「一个说话的入口」。实际要的是**群组 + 管家**：工作区有成员，成员是后台已有角色；**管家**是统一接收人，负责按对话拆任务、按「角色 + 它的 job」分配、排先后。署名由数据决定，不能写死。见 §3.5～§3.7、§6。

## 1. 唯一原则

> **工作区是入口，不是门。** 执行只有一条路径（`case.run` → `case_runner` → `run_store`）。工作区、任务页、助手 IM 都只是触发它的方式。工作区不能是执行的前提，也不改变执行的任何规则。

推论：

- 在任务页手动跑，不需要任何工作区，行为与现在完全一致。
- 工作区里跑的 run，就是一个普通 run，`run_store` 里没有任何工作区专有字段或规则。
- 工作区只负责三件事：**记住范围**、**对话**、**把相关 run 展示出来**。

---

## 2. 概念：四个

| 名词 | 定义 | 存哪 |
| --- | --- | --- |
| **工作区** | 一个聊天，**可以**绑定一个需求或一组模块。绑定后同项目同范围只有一个 | `collab_topics`（沿用，已有 `requirement_id` / `modules` / `scope_case_ids`） |
| **成员** | 工作区是一个群，成员是后台已有的角色；其中 `conductor` 是**管家**（统一接收人）。有默认成员，可再拉入 | `collab_topic_members`（沿用，无新表） |
| **范围** | 需求 ∪ 模块 ∪ 钉住的用例。创建时可以为空，后在对话里补 | 工作区字段 |
| **执行** | 就是一个 run，不另立「任务」 | `run_store`（不动） |

创建与范围规则：

- **一键新建对话**，不要求先选需求、模块、应用或环境；缺什么在对话里问、补。
- **空范围不等于全部用例**：范围为空时不能执行，管家要先问清楚跑哪部分，**不得静默扩大到整个项目**。
- 对话里提到已有模块或需求后，管家把它写进范围；也可以由用户在页面上直接绑定。
- 明确绑定了同一范围，则复用已有工作区；未绑定范围的新对话互不去重。
- 用例页「加到工作区」只把用例钉进已有工作区，不新建单用例工作区。
- 执行时才需要确认范围、应用、环境，缺哪项就在聊天里问哪项，已经说过的信息不丢。

## 3. 对话怎么承接

### 3.1 一个入口：管家

用户的话一律先到**管家**。管家 = 以 `conductor`（分析师）为视角、以 `assistant_agent` 的工具循环为底座的处理器（新模块 `workspace_agent`）。聊天立即返回，处理走已有的持久消息队列 `collab_message_jobs`，重启后未完成的标记为中断，**已发起的写操作不重放**。

**为什么必须有这个循环**：角色本身不会调工具。运行时一个角色 = 取一个 job 的提示词 + 聊天历史，调一次模型（`ai/roles_catalog.py` 的 `chat_with_role`）。查数据、跑用例靠 `prompts/assistant/tools/*.yaml` 里的工具，驱动工具的是「模型选工具 → 执行 → 结果回灌」的循环，也就是 `assistant_agent` 里那套。

**为什么不直接调 `handle_utterance`**：它要求 IM 绑定（`check_binding`）、会话单位是 IM 的 `origin`；并且任何 `risk: write` 工具一被调用就立刻 `return submit(...)`，循环结束，只能做「一问一事」。工作区需要「同一轮里先后做几件事」。所以只复用它的底件：`render`、`_persona`、`_parse_args`、`openai_tools`、`run_tool`、墙钟预算、无进展判断，**不改 `handle_utterance`**（回归面是全部 IM 入口）。

不用正则分流，不用固定话术兜底。听不懂时基于事实反问并给可选项。

### 3.2 事实包（模型看到的东西）

代码取事实，模型只负责理解和措辞：范围与用例数、可执行/阻塞分布（现有 preflight 结果）、最近引用的 run 及其状态（读 `run_store`）、资源概况。数字只来自代码，不让模型回填。体积有上限，超出按字段裁剪，不截断 JSON。

### 3.3 工具：全部复用

| 用途 | 工具 | 状态 |
| --- | --- | --- |
| 看用例、设备 | `case.list`、`device.list`、`app.explore` | 已有 |
| 跑、重跑失败 | `case.run`、`case.retry_failed` | 已有，**与任务页同一路径** |
| 看进度、结果、取消 | `task.get`、`task.list`、`task.cancel` | 已有 |
| 看证据 | `session.list`、`session.events`、`session.screenshot`、`llm.get` | 已有 |
| 看版本/编译 | `case.version_chain`、`case.compile_job`、`case.recompile` | 已有 |
| 指派成员（问一次 / 跑规则） | `member.assign` | **新增**（§3.5），只能指派群成员的 `chat_jobs` |
| 看工作区范围、钉用例 | `collab.scope_get`、`collab.pin_cases` | **尚未实现**。范围已在事实包里；钉用例走页面「加到工作区」，需要时再补，各一份 yaml |

写类工具（`case.run`、`case.recompile` 等）沿用现有 `risk: write` 规则，不另建权限层。

### 3.4 把 run 展示在工作区里

`case.run` 返回 `task_id`（即 run）后，管家往工作区写一条**run 卡**（`card_kind=run`，`ref=run_id`）。卡片内容渲染时读 `run_store`，不冻结数字。

反向关联：`run_store.finish` 已有一个钩子（`collab_events.on_run_finished`）。run 结束时，若有消息卡片引用了该 `run_id`，就在对应工作区播报终态。没有引用就什么都不做——**手动执行的 run 完全不受影响**。

这是工作区与执行之间唯一的连接，单向、只读、可缺失。

### 3.5 群组、成员与分配

**成员**
- 工作区是一个群，**成员 = 后台「角色」页已有的角色**，不新建角色。成员存在 `collab_topic_members`（`member_kind='role'`，`member_id`=角色 id），不加新表。
- **默认成员**：`conductor`（分析师，即管家，不可移出）和 `test-engineer`（测试工程师）。新建对话时自动加入。默认成员放在设置里（`settings` 表一个 key，默认就是这两个），不按工作区单独设。
- **可再拉入**：`req-qa-bm`、`version-qa-bm`、`product-expert`。`report-writer` 当前 `called: sandbox`，补完业务输入合同前不可拉入。没被拉进群的角色不会发言。

**一个 job 能不能被「分配」，取决于它的类型**（源码核实）

| job 类型 | 例子 | 怎么执行 | 输入从哪来 |
| --- | --- | --- | --- |
| 对话型 | `conductor`、`req-qa-bm`、`version-qa-bm`、`test-engineer-chat`、`product-expert`（`text_chat` / `chat_reply`） | **角色声明了 `tools` 的，成员跑同一个工具循环（§3.5.1）；没声明的，退化为带该 job 提示词的单次模型调用** | 管家的问题 + 事实包 |
| 规则型 | `map_cases`、`classify_fail`、`draft_sign`、`draft_gate`、`pick_regression` | **代码**调 `qa_process_assist.run_job`，没有模型 | 代码从库和 `run_store` 取需求、用例、run；模型只指明「对哪个需求/哪个 run」 |
| 结构化 | `draft_test_report`（`report-writer`） | 补合同前不开放 | — |
| 设备步骤型 | `test-engineer` 名下的 `agent-*`、`case-step-compile`、`inspect-session` 等 | 属 `agent_loop`，**不可从聊天调用** | — |
| 执行 | 不是 job，是工具 `case.run` | 管家直接调，**一条消息最多一次** | 用例范围 + 测试目标 |

因为角色 YAML 里的 `jobs:` 把设备步骤型也列在内，无法据此判断「聊天里能调哪些」，所以角色上增加**一个可选字段 `chat_jobs`**，只列可从聊天调用的对话型/规则型 job id。启动时校验引用的 job 存在；没有此字段的角色不能入群。这是本方案对角色目录唯一的改动。

### 3.5.1 成员也是自主的：同一个工具循环 + 自己的工具白名单

此前把成员定为「单次对话」，导致被 `@` 的成员只会说话：问进度它不会去查，让它执行它只回「请你补充」。改为：

- 角色目录再加**一个可选字段 `tools`**（与 `chat_jobs` 并列），列该角色在群里可调用的工具 id，取自 `prompts/assistant/tools`。启动时校验：不存在、已停用或仅限管家（`workspace_only`）的工具拒绝启动。
- 现配置：`test-engineer`：`case.list`、`device.list`、`case.run`、`case.retry_failed`、`task.list`、`task.get`、`session.list`、`session.events`；`req-qa-bm`：`case.list`、`task.list`、`task.get`；`version-qa-bm`：`task.list`、`task.get`。`conductor` 不配，管家自己的工具集不变。
- 成员循环**复用管家的同一个工具执行函数**（`run_one_tool`），所以范围校验、暂停校验、应用·渠道校验、幂等收据对所有人一致。
- 成员循环有独立步数上限（5）并共用本轮的墙钟 deadline。
- 成员提示词规则（`workspace-route/system/30-member.md`）：自己用工具查事实，不把查询推回给用户；缺信息时列出缺哪几项和真实可选项；做完用 2～5 句话收尾并建议管家下一步。

**写操作计数只有一处。** 管家与成员共用同一个 `state`（`wrote` 标志），所以一条消息里无论谁提交了 `case.run`，其他人都不能再提交第二次。

**分配**：管家用工具 `member.assign`，参数 `{member, job, question?, target?}`。代码校验：`member` 必须是本群成员；`job` 必须在该角色的 `chat_jobs` 里。通过后：
- 对话型：用该 job 提示词问一次，答复作为一条消息发出，**署名是该成员**，并回灌给管家继续。
- 规则型：代码取输入、执行、把结果回灌；成员只负责解释这个结果。数字一律来自代码。

用户 `@` 某个成员，等价于直接对该成员做一次 `member.assign`。成员之间不直接对话，不为每个成员建线程，不新增任务表。

### 3.6 先后执行：成员做完交回管家

采用「**经管家转手**」：成员做完回到管家，由管家决定下一步；成员之间不直接互相调用。控制点集中在管家一处：循环风险（调用关系始终是星形）、写操作计数、停止条件都只在一处管。

- 用户 `@成员`：成员先按 §3.5.1 干活并以自己的署名发消息；**随后整轮交回管家**，管家看到 `mentioned_member_results`，决定继续执行、指派下一位成员，还是只做一句总结。此前「成员答完整轮就结束」的行为已取消。
- 用户没有 `@`：由管家拆目标，按顺序调用 `member.assign` 与 `case.run`。

后一步看得到前一步的结果：

管家把目标拆成有序的几步，**按顺序在同一轮里执行**，后一步看得到前一步的结果：

> 用户：「把登录模块回归一下，顺便看下覆盖」
> 1. `member.assign` → `req-qa-bm` / `map_cases`（规则型，看覆盖）
> 2. `case.run`（登录模块，管家直接调）→ 发出 run 卡
> 3. 回复总结

代码强制的约束：
- 只能指派群成员，只能调 `chat_jobs`。
- 一轮内 `member.assign` 有次数上限（6），`@` 的成员数也不超过 6；一轮有步数和墙钟上限；相同调用无新结果即停止。
- `case.run` 一条消息最多一次；已提交后再要求写，拒绝并让模型告诉用户结果。写工具沿用幂等收据，重复请求返回原 run。
- 任一步失败或需要补信息即停止，把原因和可选项告诉用户；不把失败说成通过。
- 上一步输出作为下一步上下文时截断到有界长度，数字不由模型回填。
- 中途重启：该消息标为中断，不重放已发起的写操作，用户再说一遍即可。
- 用户插话：发新消息，管家按最新话重新处理。没有线程。
- 上下文：事实包 + 最近 6 条消息，不拼整段历史。

每一步的产出都是聊天里的一条消息，**不另存步骤表**。

### 3.7 run 结束之后的后续步骤（P2，默认不开）

run 是异步的，同一轮里等不到结果。现有钩子在 run 结束时只做一件事：给引用了该 run 的工作区发一条终态播报。

需要「跑完自动分析失败」时，让钩子再往持久队列放一条**系统消息**交给管家，由管家照常指派（例如 `classify_fail`）。约束：系统消息触发的这一轮**禁止调用写工具**，防止「失败 → 自动重跑 → 再失败」循环。默认关闭，已实现显式开关；自动复跑是另一个受限系统动作，不由只读分析触发。

### 3.8 成本与风险

| 工作 | 难度 | 说明 |
| --- | --- | --- |
| 署名由后端算（§6） | 小 | 一个函数 + 前端显示字段 |
| `chat_jobs` 字段 + 启动校验 | 小 | 只涉及约 6 个角色 YAML |
| `member.assign` 工具与校验 | 中 | 一份 yaml + 一个函数；对话型复用 `chat_with_role`，规则型调 `run_job` |
| 群成员（默认成员、拉入/移出、抽屉成员页） | 中 | 表已存在，主要是接口与界面 |
| run 后的后续步骤（§3.7） | 中 | 默认不做 |

主要风险：对话型成员会「编」。缓解：事实包和规则结果一并作为输入，要求答复引用依据；数字只来自代码。
