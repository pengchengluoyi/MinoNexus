# V7 用例执行链路收敛设计

日期：2026-10-20。状态：设计方案，未实施。本文不代表任何代码已改动或已验收。

承接：[去旧兼容与执行合同统一整改方案](去旧兼容与执行合同统一整改方案-20261020.md)（V7-ST01～ST08）、[第一批实施记录](去旧兼容与字段合同整改实施记录-20261020.md)。本文使用独立编号 `V7-EX01`～`V7-EX06`，不占用既有编号。

## 0. 结论

1. **去旧兼容整改对本计划有实质帮助，但只解决了"入口侧"**。它把平台、渠道、环境、模式、能力的"多种表达"收敛为"一种表达 + 明确拒绝"，这是重做执行链路的前提条件。
2. **它没有触及问题的另一半：循环内部**。`agent_loop._run_loop` 仍是一个巨型函数，隐式状态仍散落在 `ctx` 动态属性里。去兼容后，这部分的复杂度一分都没减少。
3. 因此建议在 ST 批次之上增加 EX 批次：**入口一次性解析成不可变的执行合同（`ResolvedCase`），循环内只读它；循环内状态收敛为显式的 `CaseSession`；场景分支改为拦截器**。不推倒重写，按绞杀者方式逐步迁移，每步用 `session_events` 前后对照。

| `return` / `continue·break` | 110 / 59 | `_run_loop` |
| `loop/` 总规模 | 约 3.3 万行，80+ 文件 | |

说明：这些是行文本统计，不是语义分析；"局部变量名"是赋值左值去重计数，包含循环内的临时变量。结论只用于说明量级，不用于精确断言。

三个结构性事实：

- **状态在 `ctx` 上动态挂载**：`setattr(ctx, "_step_cursor", cursor)` 这类写法使任何模块都能读写任何状态，没有声明、没有变更日志。这是"改一处，别处坏"的直接机制。
- **阶段（prep/do/check）是循环里的 `if cursor.phase` 分支**，而不是独立阶段。`step_pointer.py` 的提示词模板直接编码了阶段纪律（"前置只做三件事…"），即阶段约束靠 prompt 约束 LLM，而不是靠程序约束执行。
- **入口有两套模式且名字误导**：`case_runner.py:158` 把空值和 `agent` 归一成 `legacy`，另有 `v5`（要求已发布用例 + 固定 Web 槽 + headless）。`legacy` 承载普通 Agent 执行，不是可删除的旧功能（审计清单 §二已指出）。

未核实项（实施前必须核实，不能按本文推断）：`flow_block_runner.py` 与 `flow_block_runner_v2.py` 是否仍同时被调用——grep 到的引用文件为 `agent_loop`、`milestone_orchestrator`、`login_evidence_navigation`，但子串匹配无法区分 v1/v2。

## 2. 去旧兼容整改对本计划的价值评估

### 2.1 有帮助的部分

| ST 批次 | 对执行链路重做的价值 |
|---|---|
| ST02 平台/渠道/站点身份 | 使"目标平台、渠道、环境"成为**可一次解析、之后不再变化**的事实。这是 `ResolvedCase` 能成立的前提；原先循环内到处存在的"平台不对就改一下"的补丁理由消失。 |
| ST03 去旧数据真源 | 循环读到的配置只有一个来源，排查时不再需要判断"这次读的是哪份"。 |
| ST04 能力目录统一 | 能力的 caller/phases/platforms 完整声明，是**拦截器与阶段门禁数据驱动**的前提。目前阶段限制写在 prompt 里，目录声明完整后可由程序强制。 |
| ST05 协议当前化 | `EXECUTE` 载荷合同固定，`RouterProxy` 才能成为真正稳定的边界（CLAUDE.md §2.2）。 |
| ST06 资源准入 | 设备/账号租约在准入阶段事务化后，循环不再需要处理"没租到怎么办"。 |
| 已落地 `dispatch_pending` 缺 NavFSM 返回 `blocked / navigation_configuration_required` | 方向正确：**问题在准入/预检暴露，而不是循环里偷偷换路径**。 |

### 2.2 不能解决的部分（本文要补的缺口）

1. 循环内部状态的所有权问题（见 §1 前两点）。
2. 场景处理（登录、弹窗、恢复、导航）与主循环的耦合方式。
3. 执行阶段的程序级约束。
4. ST05 要求把 `legacy` 改名 `agent`，但**改名不改变结构**；若不同时拆分内部，改名只是增加一次全链路改动面。

### 2.3 风险

- 工作树目前有数十个未提交文件（含 `agent_loop.py`、`case_exec.py`、`navigation_policy.py` 等执行核心），ST 与 EX 若并行改同一批文件会互相覆盖。**EX 必须排在 ST02/ST04 合入之后**，或明确文件级分工。
- ST 批次仍在方案阶段；本文的 `ResolvedCase` 字段依赖 ST02 的最终合同，字段名在 ST02 落定前只能视为草案。

## 3. 目标设计

### 3.1 分层与所有权

```
Run（批次）            调度 · 并发 · 设备/账号租约 · 聚合       ← 不进入用例内部
 └─ ResolvedCase       入口一次解析，之后不可变                ← 合同
     └─ CaseSession    唯一的可变状态持有者 + 事件日志          ← 状态
         └─ Phase      Prepare → Do → Check → Finalize        ← 阶段
             └─ Turn   observe → intercept → decide → act → verify
```

每层只允许向下依赖，`loop` 代码不感知网络（延续 CLAUDE.md §2.2：只依赖 `router.dispatch`）。

### 3.2 `ResolvedCase`：入口一次解析的不可变合同

在 `case_runner.run_cases` 的准入阶段（现在已有幂等摘要、设备归属校验、环境解析）末尾**一次产出**，字段全部来自 ST02 统一后的合同：

- 身份：`run_id / case_id / sn / node_id`
- 目标：`platform`（mac/win/android/web）、`surface_id`、`app_id`、`env_profile`
- 模式：`mode`（`agent`/`strict`——对应现 legacy/v5，名称随 ST05 落定）
- 预算：`max_steps`、`wall_budget_sec`、阶段预算
- 能力快照：本次允许的 capability 集合及其 `executor_order / low_level / selected_impl`（即 CLAUDE.md §2.1 要求"Nexus 算完塞进 EXECUTE"的部分，在此处预先算好，循环里只查表）
- 资源：设备租约 id、账号租约 id
- 策略：导航缺图策略（降级/阻断）、视觉降级策略

规则：循环内**读不到原始 case dict / project env / 平台字符串**，只读 `ResolvedCase`。任何"循环里再判断一次平台"的代码都视为缺陷。缺失必填信息在准入阶段 `needs_input`，不进入循环。

### 3.3 `CaseSession`：显式状态

把 `ctx` 动态属性与 `_run_loop` 的 317 个局部变量**分类**后收敛为几组 dataclass（分类须在 EX01 用真实读写统计产出，下面是按现有命名归纳的草案）：

| 状态组 | 内容（草案） | 现在散落在 |
|---|---|---|
| `Cursor` | 阶段、当前步骤、已完成步骤 | `StepCursor` / `ExploreCursor` / `step_pointer` |
| `Screen` | 最近观测、指纹、前台应用 | `screen_capture` / `channel_observation` / ctx |
| `Auth` | 登录态、账号租约、验证码流程 | `login_*` 9 个文件 |
| `Nav` | 当前页面、导航计划、目标作用域 | `nav_runtime` / `navigation_policy` |
| `Budget` | 步数、墙钟、各类重试计数 | 循环局部变量 + `fuse/` |
| `Recovery` | 恢复次数、最近障碍 | `recovery` / `interrupt_recovery` |

变更规则：

- 只能通过 `session.apply(event)` 修改；`apply` 同时追加一条 `session_events`。
- 禁止新增 `setattr(ctx, …)`；存量 128 处按状态组迁移，迁完后 `ctx` 只保留不可变的 `ResolvedCase` 引用。
- 与现有 `session_events + session_meta` 排查体系兼容：事件名沿用，增量只是"状态变更必有事件"。

### 3.4 阶段：程序强制，不靠 prompt

- `Prepare`：租账号、清缓存、装包、启动、登录到前置状态。产出**起点快照**；失败即整条用例终态失败，**不进入 Do**。
- `Do`：逐步执行。
- `Check`：只允许 `check` 类能力（`catalog_entries.kind`），由能力目录的 `phases` 声明在派发前强制，而不是在提示词里劝 LLM"禁止点击"。
- `Finalize`：释放租约、收集证据、终态落库——**唯一一处**释放资源。

前置条件：ST04 要求能力的 `phases` 必须完整声明，这里才有数据可强制。`step_pointer` 的纪律提示词保留，但降为"辅助 LLM 理解"，不再是唯一约束。

### 3.5 拦截器：场景处理脱离主循环

一个 `Turn` 内，observe 之后、decide 之前，按优先级运行拦截器链：

```
Interceptor.match(session, observation) -> bool
Interceptor.handle(session, observation) -> TurnOutcome   # 消费本轮并给出动作/状态变更
```

迁移候选（来自现有文件，逐个迁，不一次性）：

| 拦截器 | 现有来源 |
|---|---|
| 系统弹窗 / 权限 | `system_dialog_recovery` / `recovery_permission` |
| 登录链（含邮箱/OTP） | `login_*`、`email_login_auto`、`sms_auto`、`flow_block_runner*` |
| 同意/协议弹窗 | `ui_consent` |
| 中断恢复 | `interrupt_recovery` |
| 导航拦截 | `nav_runtime` / `guard_gate` |

约束：拦截器**读 `ResolvedCase`、写 `CaseSession`（经 apply）**，不得互相调用；需要协作就通过 session 状态与事件。新增场景 = 新增一个拦截器 + 一条声明，不改主循环。

### 3.6 决策只有一个入口

`decide(session_snapshot) -> Intent`：

- 脚本化步骤与探索（`StepCursor` / `ExploreCursor`）作为两种 `StepSource` 注入，**同一个 `CaseSession`**。
- LLM 只在 `decide` 被调用，输入是只读快照；其余动作（登录、导航、等待、已知弹窗）由程序确定性处理。
- 派发统一经 `router.dispatch(event, ctx, …)`；四类本地 executor（hitl/vlm/ai_persona/internal）仍在本仓本地执行，规则不变。

### 3.7 与"不用 pytest"约束的配合

CLAUDE.md §1 约束 5 禁止新增/运行单元测试。因此验证手段只能是**事件回放对照**：

- 迁移前后对同一批真实用例各产出 `session_events`，比对"事件类型序列、终态、资源终态"，容忍文本差异；
- `CaseSession` 的 `apply` 是纯状态转换，可以用已落库的 `session_events` 离线重建状态，作为一致性检查**脚本**（放 `scripts/`，不进 `tests/`，不提交为测试）。
- 单个迁移步骤的验收仍必须由真实 session 给出，与 ST08 同口径：源码改动、已加载、局部通过、真实验收四种状态分别记录。

## 5. 不做的事

- 不推倒重写：循环中的登录、弹窗、导航处理含大量真实踩坑的业务知识，逐个迁移而非重写。
- 不引入新的执行引擎或工作流框架；沿用现有 `RouterProxy`、`session_events`、能力目录。
- 不为 EX 增加兼容层：与 ST 同口径，旧形态直接替换，不保留双路径（EX03 的临时双写仅限对照期，期末必须删）。
- 不扩大范围到 Scout 侧循环；Scout 只通过协议消费 `EXECUTE`，协议改动按 CLAUDE.md §5 两仓同步。
- 不替代 Mino Bots / 协作工作区方案：工作区仍只是 `case.run` 的入口。
