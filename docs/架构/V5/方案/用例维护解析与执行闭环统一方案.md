## 1. 两个版本的边界

| 事项 | V5：MVP，先上线可用 | V6：在MVP上完善 |
| --- | --- | --- |
| 输入 | 本地XLSX上传；手动修改/重新上传 | 飞书Sheets、文件持续更新、增量维护 |
| 飞书 | 独立技术探测（spike），提交读取样本与结论，不阻塞MVP | 通过读取验证后正式接入，不能把正文读取冒充Sheets |
| 需求 | 用例列表的分组字段、筛选器与轻量归组；可未分组 | 只有实际有收益时再做独立分组详情，不作为必交大模块 |
| 解析 | 复用编译器，修真实误判；收据→revision→持久job→固化 | 依赖失效、跨次复用、并发更新/预算维护 |
| 界面 | 现有用例列表＋一个理解侧栏＋可筛选问题清单 | 来源页、完整版本/趋势与维护交互 |
| 执行 | 已支持路线上的固定版本、预检、实际执行与证据 | 扩大已验证动作/核验覆盖，强化节点和恢复能力 |
| 问题分析 | 阶段×六类根因×复核状态，能定位原句与证据 | 经复核的应用识别资料、趋势、复发和修复收益 |
| 清理/恢复 | attempt内明确开始/清理责任；异常停止、标未核验、必要隔离 | 自动接管剩余项、复杂组合资源和精细恢复 |
| 写回/训练 | 不做 | 仍非默认目标，只有独立收益和约束明确后才立项 |

本文件的“V5”是产品交付版本，不等于代码枚举`execution_mode=v5`。现有严格Web与移动/PC编译辅助执行可以在MVP中分别按真实支持范围使用，保证等级显式展示，不能换标签冒充同等能力。

## 2. “所有用例跑起来”的操作口径

一个指定应用和当前目标平台的全量用例先逐条解析、预检，形成可执行集合和受阻清单：

- 语义清楚、处于已承诺支持范围的用例，不能被编译器、错误映射、模式接线、版本混用等工具问题挡住。这类问题由平台修，不能让用户删预期来迎合工具。
- 用例缺信息、互相矛盾、验收标准模糊，给完整原句、具体缺什么、如何修正；不把所有失败写成“无法UI自动化”。
- 缺资源/测试环境、当前能力未支持、需要外部证据分别标明；不能伪装成用户写错。
- 已执行但断言不成立是测试发现，不自动算用例错误或平台错误；保留证据再归因。
- 无法判断先待复核。静态受阻不能算执行失败，也不能从原请求分母删除。

首个用例只验证链路贯通；上线验收还必须处理首个应用/平台选定范围内的全部用例。范围及真实数量在验收前固定，不能事后剔除失败项。对当前明确不支持的能力如实给出边界，不承诺任意场景均可UI自动化。

## 3. 唯一主流程

```text
上传XLSX → 预览 → 持久收据 + case_revision + queued编译job
→ 系统理解/未解决项 → 修实际原因 → 新job与固化产物
→ 发布或冻结兼容计划 → 预检 → 按固定版本执行
→ 原句/动作/检查证据 → 解决或确认仍有问题
```

需求分组只影响列表筛选，不进入编译构建键、执行资格、账号选择、核验结论。没有分组一样可完成上述流程。

### 3.1 来源与编辑简化

首版XLSX是一次性上传，不绑定持续外部真源。用户选工作表和列映射，平台保存映射到用例的原文副本；以后在平台修改生成新revision，或明确重新上传更新。不自动写回原文件，不提供假“自动监听”。

新文件有稳定用例编号就按已确认映射更新；没有编号可首次导入并生成case_id。无编号再次上传不得按名称猜覆盖，须明确对应关系或按新增预览。同一提交重试与用户上传另一份新文件是两件事。

已有其他输入能力不删除，但不作为MVP的新开发、兼容或验收承诺。飞书spike仅验证一张真实Sheets的工作表/范围、编号、多行字段、读取完整性与错误返回；失败保留结论，不改用docx方案充数。

## 4. 后端最小改动

### 4.1 收据、修订和解析任务

复用现有数据库、导入预览和编译器；下面是需要保证的逻辑记录，不要求为了名称再造一套存储框架。

| 数据 | 必须保存的内容 |
| --- | --- |
| 导入收据/行 | client_request_id、输入摘要、行ID、冲突决定、状态、实际case/revision、错误 |
| case_revision | 不可变原文、前置/操作/预期、平台、来源行、内容摘要 |
| compile_job | revision、job_id、构建输入、状态、产物/诊断、实际模型/目录版本与dispatch引用 |
| 固化/运行快照 | 选定revision、artifact/发布版本、资源/核验依赖、实际模式与目标 |

**行级事务同时写case_revision、提交收据和queued编译job；事务内不调模型。** 同请求键同输入返回原收据，不同输入拒绝。committed不重做，未提交项可补交；目标revision变了须重新核对覆盖决定。预览可过期，收据不会一起消失。

worker复用现有后台机制领取数据库作业，不引入消息中间件。最小状态为queued/running/succeeded/failed/interrupted/cancelled；中断任务可见，不盲目重复已不确定的模型调用。逐行编译失败不阻塞其他case解析。

每case显示“最新原文/最新解析任务/当前有效产物/已发布版本”。晚返回的旧job只入历史，不覆盖新revision。修改或重编产生新候选，不能混用新文字与旧计划；最新失败不能被旧成功隐藏。

### 4.2 理解结构与拍摄页样本

复用已有do/check/resource结果，补齐可展示且可定位的字段：原句及区间、系统理解、操作、页面识别线索、业务断言、未解决项。保存完整预期，不以“导航”等分类名替代。

首个样本：`进入拍摄页（页面底部有几个圆形按钮）即可`，位于预期栏时应理解为：

- 业务断言：当前处于拍摄页。
- 页面识别线索：底部、圆形按钮、原文未指定精确数量；不编造count=3。
- 句末语气“即可”不制造未覆盖问题；不能全局删除单字或整个括号。
- 若原文是“必须显示3个圆形按钮”，数量、形状/位置是业务要求，不能降为可忽略线索。
- 能理解但当前核验器做不到，归平台能力缺口；不是用例语义错误。仅出现圆按钮不足以判拍摄页，相似页面是必测反例。

只补该真实用例所需的已确认页面/核验配置，复用已有视觉或结构化能力。MVP不建完整页面知识库、不训练模型。对应路线若缺必要核验能力，先做有限且可验证的实现或明确阻塞，不能为了演示使用更弱断言。

### 4.3 六类根因，而不是六个新子系统

在现有诊断/用例元数据与session投影中收口，问题清单不另建复杂工单系统。`phase`为前置/操作/预期/清理；根因待确认时可为空，`review_status`表达待复核，不增设第七个含糊大类。

| 类别 | 判定与例子 | 默认处理方向 |
| --- | --- | --- |
| 1 用例定义问题 | 信息缺失、要求矛盾、验收标准无法确定 | 指出具体原句与缺项，用户修原文；需要证据确认，不能模型一句话定责 |
| 2 语义解析/应用识别问题 | 括号误拦、错分事件、导航原句丢失、页面认错 | 平台修编译/识别或补应用解释资料，不让用户删业务要求 |
| 3 动作/核验能力缺口 | 现有平台或合同尚无所需动作/视频核验等 | 平台补能力或明确当前边界，不说用例写错 |
| 4 配置/环境/资源问题 | 测试账号、支付沙箱、节点、OTP来源缺失或临时不可用 | 区分配置缺失与临时争用，指向配置/等待；责任按事实判断 |
| 5 执行工具链问题 | 焦点/合同/版本错位、重复写、状态污染、落库或回执错误 | 平台修复；不能算产品断言失败或推给用例 |
| 6 纯UI证据边界/人工前置 | 实际到账需账本接口，实体操作/人工生物识别 | 明确所需外部证据或人工步骤，经复核确认范围，不下永久不可自动化结论 |

支付不是天然不能UI操作，特效也不是天然不能核验。`verified_fail`是结果，不是第七类根因；是否产品缺陷、用例错误或环境问题另行复核。

最低复核状态：待复核、已确认、修复后待实跑、已验证解决。记录诊断来源、确认人/理由、revision与证据引用；编译恢复不等于执行通过，复发重新打开。模型仅建议，不能修改verdict、删必选项或解除资源隔离。

### 4.4 发布、预检和固定版本执行

选一条真实失败用例完成“原文→修复→发布/冻结→预检→执行→证据”；不是另找容易通过的样例替代。严格Web复用已有publication；其他支持路线也必须冻结原文/计划/资源/核验输入，并在UI展示其实际保证，不能伪称已支持严格模式。

预检只读，区分静态不可执行和临时资源不可用；能跑的自动继续、全部静态受阻不建执行任务。三个旧入口不各写一套模式与版本选择，新分组筛选仍落同一个入口。

保留requested_total和受阻清单。每个执行单元用独立身份更新，多设备同case不串结果。运行不得现场重新拆业务原文以绕过已固化计划，动作回执不等于业务检查通过，check不允许误映射成点击。

### 4.5 attempt内的最小状态与清理责任

首版不建自动接管/组合资源大系统，但这些底线不可后移：

- 计划明确start_state及验证办法、cleanup_policy；Nexus控制准备/执行/清理，Scout操作并返回事实，沿用已有账号和节点准入。
- attempt记录阶段、核验结论、停止/清理结果。下一独立用例不能默认继承前一条登录态；关闭App不证明后端数据复位。
- 业务断言失败且清理通过，其余独立case继续；清理失败或写效果未知时停止相关资源上的新写，沿用现有隔离/禁用标记，其他资源继续。
- 无法确认停止，终结为未核验并保留隔离，不重放未知写、不因租约到期自动释放。取消也不等于已停止。
- 等待、单案和停止/清理使用已有有界配置并写入attempt；缺相关配置先补一个有版本的简单配置，不设计多层预算平台。到期明确终结，不无限等待或让模型续期。
- 重启后旧在途执行可标中断并交维护者检查；MVP不承诺自动续跑旧动作。新任务要重新检查停止/清理与资源就绪，不能仅重启便认为安全。

输出事实继续写session，不新增另一套执行事实真源。人工结论另记复核，不覆盖自动证据。V6再完善自动恢复和组合租约，首版不得放宽已有更严格的V5合同。

## 5. 前端只改现有工作台

**不建独立需求页，不建来源管理大页面。** 只在现有用例列表增加分组字段/筛选器，以及XLSX入口、解析状态、问题入口。

| 部位 | MVP内容 |
| --- | --- |
| 列表 | 名称/编号、分组、最新解析状态、可运行版本、最近结果；轻量归组，未分组合法 |
| 理解侧栏 | 原句、系统理解、线索、断言、未解决项、修复入口；完整显示括号/否定/数量，链接来源行与证据 |
| 修复入口 | 编辑原文、新revision重编、补现有配置、登记工具缺陷；按根因给动作，不只有“重试” |
| 发布/执行 | 展示实际revision与执行路线；新原文未固化时不能悄悄运行旧发布；旧版本回归需明确选择 |
| 最小问题清单 | 当前应用/平台过滤，阶段×六类根因×复核状态；列表可点进原句和session证据，少量计数即可 |
| 执行结果 | 原请求X/N已核验、未核验/未执行原因；首次失败与复跑并列，资源隔离可见 |

没有数据、加载失败和零问题分开显示。问题计数按case去重并显示已评估分母；一条多根因不能加总冒充case数。无需趋势图、复杂自定义看板、工单指派或多角色审批。

示例文案：“预期第2步已识别为到达拍摄页，但当前页面核验实现不支持该识别方式。原文无需删除，待平台补齐核验。”与“预期要求精确验证按钮数量，但原文只写‘几个’，请明确验收数量”必须区分。

## 6. 实施顺序与验收

本版按已确认路线 B 交付：以下产品闭环与主修订方案 N0–N5、P-A–P-D 同时纳入完成口径。平台内部被测平台统一 mac/win/android/web，包含三仓消费者、SN/引用迁移与新合同切换；不是延期到 V6。现合同 D08 后须复验新合同受影响用例，旧 pass 不能充抵新合同证据。

首批“刷新后不再弹窗”按刷新完成、页面就绪后的一个明确检查点判定：有效观察未发现即通过，观察失败或未就绪不能当不存在。无需连续监测、闪现捕捉、延迟复现或时间窗口编辑器；后续业务持续性需求独立规划，不扩大本版 N3。

1. **选定真实失败用例与应用范围**：记录正确业务含义、当前失败证据、平台/构建和已授权测试资源；拍摄页句子作为首个语义验收样本。
2. **补持久链路并修真实工具卡点**：收据/revision/job同事务、原文保真、check不点击、版本一致；复用现有模块，不重写编译器。
3. **接理解侧栏和六类问题清单**：能从问题到原句、修改/配置、重编，不以建页面替代修复。
4. **同一用例真实闭环**：实际模型编译，发布/冻结，目标设备执行，留检查证据。不能以缓存、手工造计划或局部函数检查冒充。
5. **推广到首个应用的全量选定用例**：逐条评估，执行支持范围内的case，修工具缺陷，再确认用例侧缺项；独立case不被单例失败拖停。

飞书spike可作为独立工作包同期开展，不是上述1—5的依赖，不要求为并行工作引入多Agent系统。

### 6.1 必过验收

| 验收 | 明确标准 |
| --- | --- |
| 导入与补交 | 重复提交不重复创建；提交中断可查收据并补未提交行；preview过期不丢结果 |
| 原句理解 | 拍摄页线索与独立断言分开；相似页面不误通过；不因“即可”误拦；原必选要求不减少 |
| 新旧版本 | 修改原文产生新job；旧job不覆盖；运行消费同一revision的计划和资源 |
| 问题归因 | 编译不理解不能直接归用例错误；每个确认问题有原句/证据；不确定显示待复核 |
| 真实执行 | 选定失败用例完成修复闭环；单独有真实产品断言失败也允许，必须有有效证据而非工具失败 |
| 整批与清理 | 能跑的全部实际执行，受阻有明细；失败不阻断独立case；污染资源不续用；未知写不重放 |
| 平台与新合同 | 路线 B 的 N0–N5 完成；四值校验、存量歧义处理、共享资源锁不分裂、历史证据可读；切换后完成受影响用例复验 |
| 弹窗单次检查 | 明确检查点存在/不存在正确判定；旧证据、采集失败和未就绪不能判不存在；不要求持续取证 |
| 前端 | 真实HTTP+浏览器操作验证导入、修复、发布、执行、证据链接；本轮文档未做这些验收 |

验收报告必须列原范围总数、已解析/待解析、已执行/未执行、工具阻塞、用例问题、环境/边界、待复核和核验结果。分类可交叉时说明去重口径。

**上线门槛：固定验收范围内，已承诺支持且语义明确的用例，因已确认的工具缺陷而未执行或无法给结论的数量为0；工具阻塞未清零就不能宣布MVP完成。** 这不是对未知缺陷的“永远零故障”承诺，也不能靠重新分类为用例问题或缩小验收范围达标。

确认的用例问题要有可操作建议；环境/能力边界单列，不算用例写错。对尚不支持的端或场景明确保留待办，不能从一条Web通过宣称三端全支持。

## 7. V5不做与后续入口

不做飞书正式同步、文件监听、独立需求页、完整来源维护页、全量页面知识库、趋势分析、复杂自动接管、组合租约重构、训练/微调、写回来源、与本版无关的全库重构、消息中间件；不做持续弹窗监测。路线 B 必需的平台、SN、环境渠道及事件引用迁移属于本版 N4，不能以“全库迁移不做”排除。

V6按实测阻塞收益扩展，见[V6方案](../../V6/持续维护与执行可靠性方案.md)。已有写安全和证据要求继续参考[结果可信性合同](三端UI自动化结果可信性方案.md)、[验收清单](执行侧交付与验收清单.md)；[开发记录](../执行开发与验收记录.md#record-v5)只证明其明示范围，不自动算本MVP已验收。

本轮只是确定两个产品版本的落地边界，不启动开发、模型调用或真实设备测试。后续遵守仓库：隔离数据目录、真实接口/session证据，不跑pytest、不向业务库灌入复现数据。
