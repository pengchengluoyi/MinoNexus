## 2. 现状事实基线

### 2.1 三套目录并存，各自带平台字段

| 目录 | 位置 | 内容 | 平台字段 |
| --- | --- | --- | --- |
| 能力目录 | `catalog_entries`（93 条，kind=base/check/generic/recovery） | 能力 + 驱动 + 守卫 + 恢复规则 | `platforms_json` |
| 用例事件目录 | `services/case_resource_key_catalog.py`（代码常量，23 个 `key_ref`） | 编译器识别的操作/预期句式 | 条目内 `platforms`，目前只有 `operation.reload_page=[web]` |
| 逻辑块目录 | `nav_flow_block_catalog`（`fb.global.login`、`fb.global.system_dialog`） | 步骤序列，步骤用 `hook_cap` / `cap` 引用能力 | 块级无；步骤级 `platforms`、`optional` |

引用关系是 `key_ref → cap / block → implementation → executor`。三处各自判断平台，没有统一入口。

### 2.2 `catalog_entries` 的构成（不是 93 个事件）

| kind | 条数 | 实际是什么 |
| --- | --- | --- |
| base | 37 | 驱动描述（adb / playwright / ios_wda / remote，均 deprecated）、底层通道、**13 条 guard 规则** |
| generic | 42 | 设备事件 + 工具事件 + 登录业务混合 |
| check | 1 | `assert_visual` |
| recovery | 13 | 恢复规则（match/actions/verify），部分与 generic 同名重复 |

guard 与驱动不是事件，不应参与"事件在哪个平台可用"的判断；现在 guard 标 `[android, ios, web]`，反而排除了桌面。

### 2.3 平台标注与实现的差异（只读审计）

执行器→平台映射取自 Scout：`adb→android`、`playwright→web`、`desktop→mac | win`。`ios_wda`、`remote` 在 Scout 没有可用实现（`screen.py` 注明"未搬"）。`vlm / internal / hitl / ai_persona` 在 Nexus 本地执行，与设备平台无关。

| --- | --- | --- | --- |
| tap_element、input_text、swipe_*、long_press_element、multi_tap、launch_app、close_app | android、ios、web | android、web | 去 ios；补 mac / win 实现行 |
| **press_key** | android | android、web | **放开**（标注过窄） |
| get_foreground_app | android | android（目录）；Scout playwright / desktop 声明也支持 | **放开**，补目录实现行 |
| clear_app_cache、kill_app、get_app_version、probe_device_state、dismiss_keyguard、wake_screen、exec_script | android | android | 保留（真限制） |
| install_apk | android、ios | android | 去 ios |
| set_clipboard、read_device_data | android、ios | android | 去 ios；其他平台是"未实现" |
| read_web_auth | web | web | 保留（真限制） |
| wait_ms、human_*、hitl | 五平台全标 | 本地执行 | 改为全平台（不设限制） |
| wait_screen_ready、assert_visual | android、ios、web | 本地 vlm | 改为全平台 |

**两条重要观察：**

1. 整个目录没有任何一条能力的 `implementations` 指向 `desktop` 执行器，而 Scout 的 `DESKTOP_CAPS` 有 7 项（screenshot、tap_xy、tap_element、input_text、press_key、launch_app、get_foreground_app）。mac / win 路径"在目录里没有实现"是缺数据，不是不能做。
2. 目录实现与 Scout 实际声明不一致（playwright 实际支持 `get_foreground_app`，目录只写了 adb、remote）。"目录推导"与"Scout 运行时声明"必须对账。

### 2.4 现有运行机制

- `skill_channel.channel_platforms_for`：先读目录 `platforms`，为空才回落代码常量 `CHANNEL_PLATFORMS`。已入库条目改代码默认值不生效。
- `skill_channel.apply_channel_skip`：平台不符→`status=skipped, skip_reason=channel_absent`，无事件、无报错。
- `case_clause_events.platform_block`：编译期按事件 `platforms` 阻断，向用户展示"只在 Web 执行"。
- Scout `REGISTER` 已携带 `executors: [ExecutorManifest]` 与 `runtime_capabilities`，节点自述能力的通道已存在。

## 3. 设计原则

1. **平台属于实现，不属于能力名。** 由该平台是否有可用实现决定；人工标注只能收窄，且必须写原因。
2. **"没有实现"和"不适用"是两件事。** 前者阻断，后者需显式声明。
3. **事件只描述一个原子动作或一个原子观察。** 带业务流程语义的属于逻辑块。
4. **阶段分离。** 编译只固定语义需求；具体平台实现由预检/开跑的统一绑定入口解析。运行只校验快照与事实，不临场删必选步骤。
5. **运行时以 Scout 自述为准，静态推导用于编译与展示。** 两者不一致报"目录与节点不符"。
6. **同一概念只有一个词、一个字段、一个入口。** 不留兼容分支（K7）。

## 4. 平台词表与字段统一

### 4.1 现状：七种写法、至少五处各自归一化

| 位置 | 实际使用的取值 |

| `runtime/platform_gate.py` | `desktop / macos / windows / linux`，别名含 `mac`、`darwin`、`osx`、`pc`、`win`、`win32`、`桌面` |
| `services/device_targets.py` | `_NATIVE_OS = {mac→macos, pc→windows, linux}`；设备行 `platform == "desktop"` + `os` |
| `services/project_env.py` | 渠道 id / 平台用 `pc`、`mac`；`CHANNEL_PLATFORMS` 另含 `macos`、`windows`、`linux`、`server` |
| `catalog/skill_channel.py` | `normalize_platform` 只处理 web、ios，桌面不归一 |
| `catalog_entries.platforms_json` | `mac`、`windows`（各 10 条）、`ios`（51 条） |
| `loop/case_runner.py` | `{"macos":"mac","windows":"pc","linux":"linux"}`（`plat_for_pkg`） |
| Scout `desktop.py` / `core.py` | 设备 `platform="desktop"`，`os ∈ {macos, windows, linux}`；`sn` 为 `desktop:{node}:console`；`core.py` 里还有 `ios`、`iphone`、`ipad` 映射 |

词频（引号内字面量，不含 prompts）：Nexus 中 `desktop` 74、`macos` 28、`windows` 27、`linux` 23、`mac` 14、`pc` 14、`win` 3；Scout 中 `desktop` 27、`macos` 12、`windows` 8。同一台设备同时是 `platform=desktop` 与 `os=macos`，一个概念占了两个字段。

### 4.2 词表（唯一合法取值）

| 规范值 | 含义 | 显示名 | 执行器 |
| --- | --- | --- | --- |
| `android` | Android 设备 | Android | adb |
| `web` | 浏览器 | Web | playwright |
| `mac` | macOS 桌面应用 | macOS | desktop |
| `win` | Windows 桌面应用 | Windows | desktop |

- 词表之外的值（含 `ios`、`linux`、`desktop`、`pc`、`macos`、`windows`）一律视为非法：边界校验处拒绝并给出"不支持的平台 {值}，目前支持 android / web / mac / win"，**不做映射、不做回退**。
- `desktop` 允许出现在非平台上下文：执行器 id（`desktop_executor`、`executor_used="desktop"`）和驱动状态字段（`desktop_state`、`desktop_unreported`）。以及桌面证据命名空间、共享桌面资源键；它们不是被测平台。
- `server` 不是平台（K10）：`project_env` 中 `kind=server` 的渠道删除 `platform` 取值，不再出现在 `CHANNEL_PLATFORMS`；该渠道是否保留及如何表达，由 `project_env` 按"非设备渠道"单独处理，不借用平台字段。

### 4.3 字段统一

| 概念 | 唯一字段 | 取值 | 删除 / 收敛 |
| --- | --- | --- | --- |
| 设备平台 | `platform` | android / web / mac / win | 删除 `device_platform`（`platform_gate` 里恒为 `"desktop"`）、`target_platform`、`native_os`；设备记录里的 `os` 字段整体删除 |
| 用例平台 | `platform` | 单值四选一；多值用 platforms 数组，all 用 platform_scope | `parse_case_platforms` 词表换成 §4.2 |
| 渠道平台 | 渠道条目 `platform` | 同上 | 平台值 pc 经 Windows 专用 schema 确认后迁 win；渠道 ID 是引用，整体迁移引用后才能改；ios 受控归档 |
| 能力平台 | `platforms_json` | 同上，推导结果 | 由实现推导（§6），不再手填 |
| 执行器 | `executor` | adb / playwright / desktop / vlm / internal / hitl | 不是平台；`desktop` 在此合法 |
| 硬件信息 | `arch`、`hostname` | 原样 | 保留，不参与平台判断 |

**必须区分"被测平台"与"宿主 OS"。** 下列用法判断的是 Scout / Nexus 进程自己跑在什么系统上，不属于本词表，**不得改动**：

- Scout `power.py`（`_engage_linux`）、`service.py`（`sys.platform.startswith("linux")`）、`self_update.py`（`darwin / win32 / linux` 打包平台）、`plugins/secret_store.py`（`_linux_put`）、`desktop_windows.py`、`desktop_focus.py`（`platform.system()`）；
- Nexus `routers/rReleases.py` 的 `_norm_os` / `_norm_arch`（发布包宿主系统，K12）：只管发布包，本方案不动。

`desktop.py:46` 里 `platform.system()` 对 Linux 宿主的处理：Scout 在 Linux 宿主上不注册桌面设备，返回"当前系统不支持桌面执行"，不得注册成 `linux` 平台。

- `PLATFORMS = ("android", "web", "mac", "win")`
- `validate(value) -> str`：在词表内返回原值，否则抛出带原因的 `ValueError`

- `executor_platforms(executor) -> tuple[str, ...]`

## 5A. 事件能力的唯一来源：注册（K13）

### 5A.1 问题

版本不同，事件集合不同：旧 Scout 没有的执行器或能力，新 Scout 有；Nexus 新增的本地工具同理。任何"在库里人工维护一张全局事件平台表"的做法，一旦版本错位就与实际不符，这正是 P1–P4 的根因。

### 5A.2 两个注册面

| 注册面 | 谁注册 | 回答的问题 | 现状 |
| --- | --- | --- | --- |
| Scout 注册 | 每个 Scout 节点在 `REGISTER` / `HEARTBEAT` 上报 | 这个节点、这个平台、这个版本**能执行**哪些设备事件 | 已有 `executors[].provides`（由各 executor 自报，Scout `core.manifest()`），但只是能力 id 列表，**没有平台与版本维度**；`runtime_capabilities` 只覆盖输入契约 |
| Nexus 注册 | Nexus 进程启动时自注册 | Nexus **本地能直接执行**哪些事件（`tier=tool`：get_otp、wait_ms、assert_visual、hitl 等）及所属 `runs_on` | 无；现在这些散落在 `local_executors` 与目录 `implementations` 中 |

两个面都是**运行时注册结果**，不是库里手填数据。

### 5A.3 Scout 注册载荷要补的字段

在现有 `ExecutorManifest` 之上升级合同（provides 条目化是破坏性变更，不称 additive；沿用两仓协议同步流程，详见修订方案 C01）：

| 字段 | 含义 |
| --- | --- |
| `platforms` | 该 executor 在本节点覆盖的平台，取值只能是词表（§4.2）。adb→`android`，playwright→`web`，desktop→本机的 `mac` 或 `win` |
| `provides[]` | 由现在的字符串 id 升级为条目：`{id, platforms?, params_schema_version}`；条目缺省继承 executor 的 `platforms` |
| `scout_version` | 已有，作为能力版本依据 |
| `reason` | 不可用原因，已有，保留 |

事件 id 由 executor 自报，**Scout 不读目录**（CLAUDE.md §2.1），与现有"core 不硬编码能力表"的原则一致。

### 5A.4 Nexus 注册

新增 Nexus 本地事件注册表，由 `loop/local_executors.py` 中各本地 executor 自报（hitl / vlm / ai_persona / internal 与 `get_otp` 等程序工具），字段同上，`runs_on=nexus`。不进库，进程内维护。

### 5A.5 事件能力视图（用例执行时获取）

```
capability_view(node_id | sn, platform) =
    Scout 注册面 ∩ 该设备所在节点 ∩ platform
  ∪ Nexus 注册面（仅表示已注册；可执行性还需核验依赖与调用规则）
```

- 视图是**运行时计算**，不落库。
- 此视图仅表达当前实现事实；语义编译不依赖节点在线。预检/开跑的 `resolve_execution_binding` 结合视图、调用规则和目标生成绑定；菜单/派发消费其投影，运行不改写冻结计划。
- 同一语义计划可在不同节点得到不同预检结论；实际消费的绑定须落到 session，不用实时视图覆盖历史。

### 5A.6 目录页改为只读

| 现状 | 目标 |
| --- | --- |
| Workbench 目录页可编辑 `platforms`、`enabled` 等事件字段 | **只读**：展示"各节点/Nexus 当前注册的事件、平台、版本、来源" |
| `catalog_entries.platforms_json` 人工填写 | 删除作为判定依据；不再读写 |
| 能力显示信息 | 显示名、说明可作为展示元数据；参数合同/装配及 caller、phases、enabled/lifecycle 仍有执行语义，按修订方案 R01 保留或迁到明确的新权威 |

事件页只读；程序注册不自动解除既有停用、deprecated 或授权限制。平台推导缓存不写库；调用规则与装配迁移完成前仍保留其原权威。

### 5A.7 与 `not_applicable` 的关系

"不适用"（如 `dismiss_ime` 在 web/mac/win）同样由执行器**注册时声明**（`not_applicable_on`），不由人工目录维护。

## 5. 事件来源分层

每个事件只属于一层。**`tier` 不存库、不人工填写**，按事件语义由程序声明；runs_on 按实际执行位置声明，两者正交。Scout 可提供 device 或 tool，不按注册来源强行归层。下表“推导依据”列为历史目录数据的对照，仅用于生成差异表：

| tier | 谁执行 | 推导依据 | 平台是否受限 | 现库例子 |
| --- | --- | --- | --- | --- |
| `device` 设备事件 | 大模型经 Scout 操作被测设备 | `kind ∈ {generic, check}` 且至少一条有效实现指向 adb / playwright / desktop | **受限，按实现推导** | tap_element、input_text、press_key、launch_app、clear_app_cache |
| `tool` 工具事件 | Nexus 或 Scout 工具侧程序 | `kind=generic` 且实现只指向 vlm / internal / hitl，或无实现且 `caller` 为程序 | 默认不限；绑定设备执行器时按该执行器 | get_otp、lease_account、wait_ms、assert_visual、read_web_auth |
| `block` 逻辑块 | FSM 拼接 device + tool 步骤 | 在 `nav_flow_block_catalog` 中 | 由成员推导（§6.3） | fb.global.login |
| `policy` 规则 | 循环内的守卫与恢复规则 | `category=guard`，或 `kind=recovery` 且有 `match/actions` | 不适用"事件平台"概念 | 13 条 guard.*、system_permission_dialog |
| `driver` 驱动 | 平台推导的依据，不是事件 | `kind=base` 且有 `provides/probe` | 本身即平台来源 | adb、playwright、desktop |

`tool` 另有只读属性 `runs_on: nexus | scout`。对应需求 3.2.1 的三种来源：设备可执行、scout/nexus 工具侧、FSM 逻辑块。tier 在 Workbench 只读页展示；不提供手工覆盖。

## 6. 注册面归并规则（取代原"人工目录推导"）

> 以下规则只在内存中计算 capability_view，不写 `platforms_json`，不回写目录。

### 6.1 单事件推导

```
registered_presence(event, node, platform) =
    event ∈ Scout 注册面(node) 且 platform ∈ 该条目的 platforms
  或 event ∈ Nexus 注册面（tier=tool；不等于依赖已满足）
```

- 条目的 `platforms` 由执行器注册时自报（adb→`android`、playwright→`web`、desktop→本机 `mac` 或 `win`），Nexus 不从目录推断。
- 结果**不落库**。`platform_override` 取消（目录只读，K13），例外情形只能通过执行器自己的注册声明表达。
- 未注册的执行器（`ios_wda`、`remote`）天然不出现在视图中，无需特别排除。

### 6.2 三方一致性

| 来源 | 角色 |
| --- | --- |
| 目录 `implementations` | 当前装配适配来源；迁移后由版本化事件适配合同承接，不能提前停读 |
| Scout `REGISTER.executors / runtime_capabilities` | 运行期真相 |
| Scout `_SUPPORTED_CAPS`（adb / playwright 执行器）与 `DESKTOP_CAPS` | 实现自身的声明 |

注册面是实际实现存在性的依据；调用资格仍受权限/阶段/停用和依赖约束。目录 implementations 中 low_level/参数映射在替代合同完成前继续参与装配；完成迁移后才将旧描述降为展示，完整绑定见修订方案 §14。

### 6.3 逻辑块推导

块可用性按必需步骤、条件必需及其适用性探测、真正可选分别计算；不能仅用 optional 排除依赖。明确不适用可跳过，适用性未知需有界取证，详见修订方案 R03。这条规则取代"块里有 `confirm_login_state`，其平台标 web，所以 Android 上这一步被跳"。

## 7. 区分"真事件"与"检查"：以 confirm_login_state 为例

`confirm_login_state` 是一个**检查**，不是设备事件。同一语义在不同平台有不同实现：

| 平台 | 实现 | 来源 |
| --- | --- | --- |
| web | `read_web_auth` 提供凭据线索，并结合业务认可的页面/身份/上下文证据；Cookie 存在不单独证明登录成功 | tool，绑定 playwright |
| android / mac / win | `inspect_session`（看图/结构判登录态） | tool，nexus 本地 |

它是 tool 层检查事件，平台差异收在实现与依赖里；本地函数存在不代表截图/目标/模型配置已满足，按绑定结果判断。

> 受限 = 某平台没有任何可用实现；有差异 ≠ 受限。

### 7.1 `dismiss_ime` 的归类

收起软键盘属于设备事件。Web 无软键盘，mac / win 通常没有；它在这些平台的语义是**不适用**，不是缺口。事件上声明 `not_applicable_on: [web, mac, win]` 并附原因。执行到这里时跳过并记录，不当作失败。

## 8. 业务逻辑迁出事件（需求 3.3）

原则：事件表只保留"一个动作或一个观察"；带"先后、条件、业务含义"的下沉到逻辑块或项目 FSM。

| 现有条目 | 实际是什么 | 处理 |
| --- | --- | --- |
| `request_sms_code`（generic + recovery 各一份） | 登录块 `send_code` 步骤：点击带"发送验证码"文案的控件 | 迁入 `fb.global.login`；两处事件条目退役 |
| `accept_legal_consent`（generic + recovery 各一份） | 登录块 `legal_consent` 可选步骤：勾选协议框 | 迁入登录块；底层复用通用勾选事件（`operation.check_box`） |
| `relogin` | 整个登录流程 | 由 `fb.global.login` 整体承担，事件退役 |
| `confirm_login_state` | 检查 | 改为 tool 层检查事件（§7），块里的 `login_state` 步骤引用它 |
| `open_app`、`open_url` | `launch_app` 的参数变体（包名 / URL） | 合并为 `launch_app`，目标由参数给出；**旧 id 删除，同时迁移引用它们的用例与块**，不留别名 |
| `get_otp`、`get_phone`、`lease_account`、`release_account` | 工具侧程序 | 保留，`tier=tool`；不人为写平台限制，但按具体资源/插件/权限依赖准入 |

## 9. 缺少事件时的运行语义（需求 3.2.3）

**核心改动：把 skip 从运行时的隐式行为，变成计划阶段的显式结论。**

对"步骤 S 引用事件 E，目标平台 P"，编译/预检时解析为下列三种结果之一，写入计划：

| 结果 | 条件 | 运行时行为 |
| --- | --- | --- |
| `native` | E 在 P 上有可用实现 | 正常执行 |
| `not_applicable` | E 声明 `not_applicable_on` 含 P，且原因成立 | 跳过，记录原因，**不计入通过证据** |
| `unavailable` | 必填步骤，E 在 P 上无可用实现 | **预检阻断**，状态 `blocked`，必须写明原因（§9.2） |

约束：

1. **"找不到实现"永远不能得到 skip。** 只有显式声明的 `not_applicable` 能跳过。
2. 只有不承担作者要求的真正可选步骤可 unavailable_optional。协议等条件必需步骤不能因旧 optional 标记缺实现跳过；适用性未知有界观察，仍未知则未核验。
3. `not_applicable` 的跳过要留证据（事件声明 + 平台），不能用"空树""没看到"推断（沿用 DOM 优先方案 §8.3）。
4. 运行中节点自述与计划不符（节点掉了某执行器）：该步骤转为 `blocked`，原因"节点缺能力"，不重试成 skip。
5. 一条用例只要有任一必填步骤为 `unavailable`，该用例整体 `blocked`，在预检阶段给出，不创建任务、不租资源（与 `case_preflight` 的"提交前只读检查"一致）。

### 9.1 登录块逐步解析（Android 为例）

| 步骤 | 事件 | 解析 |
| --- | --- | --- |
| login_entry、account_field、otp_field | tap_element | native（adb） |
| account_fill、otp_fill | input_text | native（adb） |
| send_code | 点击"发送验证码"（块内步骤） | native（tap_element） |
| otp_fetch | get_otp | native（tool, nexus） |
| legal_consent（条件必需） | 勾选（`operation.check_box`） | native；运行时没找到协议框属于观察结果，按“适用性未知→有界取证→仍未知则阻断/未核验”处理，不得靠空树判定不存在 |
| submit_login | tap_element | native |
| login_state | confirm_login_state（检查） | native（tool，看图实现）→ **不再被 skip** |

### 9.2 阻断原因必须标注清楚

`blocked` 不允许只写"无法执行"。每条阻断带结构化原因码和一句人话，在 IM、Workbench、`session_meta` 中一致显示：

| 原因码 | 含义 | 人话模板 | 谁来解决 |
| --- | --- | --- | --- |
| `no_impl_on_platform` | 事件在该平台没有任何有效实现 | 「{事件}」在 {平台} 上还没有实现（目前支持 {已有平台}） | 补实现 / 改用例 |
| `node_missing_capability` | 其他节点/版本有该事件，但目标设备所在节点此刻没有注册 | 当前节点 {sn} 不支持「{事件}」，可换节点或升级 Scout | 换节点 / 升级 |
| `event_not_in_catalog` | 用例引用的事件不在目录 | 「{原句}」没有对应事件 | 改用例 / 新增事件 |
| `platform_invalid` | 目标平台不在词表 | 「{平台}」暂不支持（目前支持 android / web / mac / win） | 改平台 / 等待支持 |

必须同时给出：用例 id、步骤号、原句、事件 id、目标平台、缺失项。字段与现有 `blocked_by` 结构对齐，不新增用户可见参数。

现有 `blocked_by[].reason` 取值（`uncovered / unmapped / platform_unsupported / missing_slot / ambiguous_clause / layer_mismatch`）不被替换；本方案把其中的 `platform_unsupported` 细分为上表各项。

## 10. 统一消费点

## 11. 数据迁移（一次性，不留兼容）

| `uploads/session-thumbs/` 目录名 | 形如 `cr-…__case-…__desktop_{node}_console` |

这些是**只读证据**，按 `session_id` 精确查找，磁盘缩略图目录名也由它派生。**不重写**，理由：重写要同步改磁盘目录与全部引用，风险远大于收益。

这条与 K7 不冲突，前提是：**代码不得解析 sn 前缀推断平台**（§4.5 已要求）。旧行里的 `desktop:…` 只是不透明的 id 字符串，不需要任何兼容分支。代价：历史记录里的 sn 与新设备记录的 sn 不再相等，Workbench 展示历史证据时原样显示旧 sn，不做跨表 join。

**实施前须核对**：是否有代码用"某次运行的 `sn`"去**重新拼装** `session_id`。若有，`app_regression_runs.sn` 不改写即可保持一致；若某处用 `m_device.sn` 去查历史 session，会在改名后查不到，需要逐处处理。

## 12. 任务拆分与上线方式

## 14. 待决策与未核实项

**待验收**：修订方案 R4 的绑定结构、存储、人审和切片边界；本期弹窗按明确检查点单次观察，不再等待持续时间窗决策。既有产品方向已确认，但不能把未细化合同称为全部无待定项。原记录：原 O1（server）、O2（migration 例外）、O3（rReleases）已按 K10–K12 决定。

**风险**

- **注册协议是破坏性扩展**：旧 Scout 不报 `platforms`/条目化 `provides`，按 K7 不做兼容推断，直接拒绝注册并提示升级；须确认现网 Scout 均可同步升级。
- **"只来自注册"意味着节点离线时视图为空**：此时预检按 `node_missing_capability` 阻断，需在文案中区分"节点离线"与"节点不支持"。

- **协议改动面大**：设备 `platform` 取值变化同时影响 Scout、Nexus、Workbench 与 golden fixture，必须一个周期内同版本发布（CLAUDE.md §5）。
- **仓库当前有大量未提交改动**（含 `core/protocol.py`）：实施前必须先确认其归属，避免在其上叠加协议改动。
- 删 ios 渠道会丢用户配置，必须先导出（§11.2）。
- `open_app / open_url` 合并会影响已有用例的 `key_ref`，迁移时必须回放现库用例确认引用已迁移。

**本轮没有核实**

- R4 当时未核对 Workbench；R3 已补应用创建、环境、API、设备选择和证据展示消费面，见主方案 §21 与审计 CSV。未执行浏览器运行验收。
- `mino_nexus/prompts/` 中 4 个文件含相关字样（`assistant/tools/case.run.yaml`、`device.list.yaml`、`assistant-route/system/20-rules.md`、`jobs/analyze_req/system/10-main.md`），需逐个确认是平台文案还是别的含义；库内 `knowledge_entries`、`skills`、`llm_jobs`、`prompt_evidence` 各有零星命中，同样需逐个确认。
- `open_url` 在 Web 的真实实现路径（playwright 声明集不含它，可能走 `launch_app` 带 URL）。
- `set_clipboard` 在 Playwright / desktop 上的可行性，当前只能说"目录无实现"。
- 事件目录 `operation.dynamic_visual` 的业务含义与是否含硬编码。
- `REGISTER.runtime_capabilities` 的字段内容是否足以逐事件对账（需读 `websocket/node.py`）。
- 现有 Nexus 是否有 Scout 版本门禁；没有则 E07 需要新增"平台不在词表即拒绝注册"的明确错误。
- 本文未重编译用例，也未运行任何会话；差异表是静态审计，不是运行验证。
