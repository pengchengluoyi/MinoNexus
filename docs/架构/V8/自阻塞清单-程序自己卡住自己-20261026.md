# 自阻塞清单：程序自己卡住自己的地方（2026-10-26）

> 这份清单只回答一个问题：**我们自己的哪一行，让本来能跑通的用例跑不通？**
> 每一条都附现场症状（session 事件或 reason_code）和出处（file:line），
> 便于逐条判断「该留着」还是「该删掉」。
>
> 触发这一轮梳理的两条真实事故：
> 1. `cr-9f7f478af02c` 21 条用例 3 秒判死 —— 系统弹窗块只有 `match` 候选文案，DOM 无锚点，
>    Scout 回「不用坐标兜底」，Nexus 直接记账成 `system_dialog_block_failed`。
> 2. `cr-2a8474bd82ca` 的 `case-50b5e242` —— 准入已经写出 `dependency_blocked`，
>    循环照旧跑，最后报成 `observation_missing` + `binding_not_committed`。

---

## 0. 一句话结论

| 层 | 自己卡自己的方式 | 现在最疼的症状 |
|----|------------------|----------------|
| Nexus 派发口 | 目录里没有行 = 不许派；`lifecycle != active` = 不许派 | `能力未启用或当前不可覆盖: hierarchy`（意图 `order.pay` 整条判死） |
| Nexus 参数口 | DOM 方案把坐标抹掉；视觉方案没坐标不许派 | `缺少完整坐标，未派发到节点`、`tap_target_unresolved` |
| Nexus 记账口 | 一次参数退化被记成用例失败 | `milestone_plan_incomplete`、`program_hook_failed` |
| Nexus 准入 | 依赖没满足也继续跑 | `observation_missing`（真因是账号/登录块 blocked） |
| Nexus↔Scout 契约 | 协议版本只允许完全相等；DOM/视觉二选一互不放行 | Scout 拒绝执行 Nexus 已经算好的指令 |
| 三段式用例 | prep/do/check 各自的门、断言必须先被消费 | `required_assertions_consumed`、prep 反复重入 |
| Workbench | caller/visible_to 决定条目对作者不可见；revision 乐观锁 | `prep_lease_account` → `event_not_registered` |

下面逐条展开。

## 1. 派发口：目录状态 = 派发权限

### 1.1 目录里没有这一行就派不出去

`mino_nexus/catalog/skill_channel.py:125`（改动前）：

```python
row = get_capability(cap)
if row is None:
    return False
```

而函数自己的注释写的是「目录没有这一行时不拦」。观察类能力（`hierarchy` / `screenshot`）
走 `device/probe` 通道，`catalog_entries` 里**没有它们的行**（`select count(*) from catalog_entries
where id='hierarchy'` → 0）。于是任何意图/逻辑块只要 `caps` 里带上它们，就被判
「能力未启用或当前不可覆盖」。

**现场**：`cr-2a8474bd82ca` 的 `api-1-216`，意图 `order.pay` 直接失败，
`tool/result` 写着「意图 order.pay：能力未启用或当前不可覆盖: hierarchy」。

**已改**：缺行不再拦（`skill_channel.py:125` 起）。是否要保留「白名单外一律拒」由你定 ——
我倾向「不拦，让 Scout/绑定报真正的不支持」。

### 1.2 `lifecycle != active` 与 V5 排除表

`skill_channel.py:10` 的 `V5_EXCLUDED_IDS`（`hitl`、`ai_persona`、`signal_ask_human` 等）
与 `:127` 的 `lifecycle == "active"` 是硬门。这两条本身合理（废弃能力不该还能派），
但它们和「程序直接派发的系统能力由程序自己注册」是两套机制，
系统能力一旦被人在 Workbench 改过生命周期，就会静默失效。

**建议**：系统能力（`caller=system`）不读 `lifecycle`，只读代码声明的版本合同。

### 1.3 块/意图的可派发判断

`local_executors.py` 的 `is_block_dispatchable`：`enabled` 为假或 `steps_json` 为空即拒。
这一条在 `fb.global.system_dialog` 那种「步骤只有 `match` 没有 `params`」的块上没问题，
问题出在下一步：**参数退化**。

## 2. 参数口：把「能做的事」判成「不能做」

### 2.1 DOM 方案把坐标抹掉

`mino_nexus/action_space/dom.py`（改动前）把 `x/y/fallback_xy/from_*/to_*` 全部 `pop`，
只留 `point_policy=node`。于是一旦锚点解析失败，**整条指令没有任何可执行信息**。

**现场**：`cr-9f7f478af02c` 的 21 条 `system_dialog_block_failed`：
`execution.reason_code=tap_target_unresolved`、`execution_started=no`。

**已改**：坐标保留为 `fallback_xy`，`point_policy` 仍是 `node`。

### 2.2 视觉方案没有坐标就判失败

`mino_nexus/action_space/assemble.py:60` 的 `visual_point_missing()`：
`tap_element/long_press_element/multi_tap` 缺 `x/y` 即视为「缺参数」。

**现场**：`api-1-211` / `api-1-212` 的 `do_s*_hook`「当前视觉操作缺少完整坐标，未派发到节点」。

**已改**：`xy_from_bounds()` 现在能按 `match` / `target.name` / `selector_text`
在当前层级里找唯一节点，用它的 `bounds` 中心点补坐标（`assemble.py:74`）。

**还要不要更狠**：完全去掉「缺坐标即失败」，改为「缺坐标就交给模型看一眼再点」。
目前是补不出来才退化（见 3.1）。

### 2.3 结构锚点必须唯一

`mino_nexus/action_space/scheme.py:114` `structure_target_available()`：节点命中数必须 `== 1`，
否则 DOM 视为不可用。列表页、重复文案（「确定」「删除」）天然命中多个 → 永远走视觉。

**这条我认为该保留**：命中多个时按第一个点才是真的在猜，是产品级错误源。

### 2.4 输入只认当前焦点

`assemble.py` 里 Android 的 `input_text` 被强制改成 `current_focus + append`，
`target_mode=node` 的输入在原生端直接不成立（`input_contract v2`）。
这是协议事实，不是门 —— 但它依赖「先有一次成功点击」，于是 2.2 的失败会连锁成输入失败。

## 3. 记账口：一次参数退化 = 一条用例失败

### 3.1 块失败 → `program_hook_failed` → 里程碑 failed → `milestone_plan_incomplete`

`flow_block_executor.py:588` 把 `not ok` 一律记成 `program_hook_failed`；
hook 路径有 `_target_unresolved` 的例外（`:543` 起，三次机会转看图），
但**意图路径**与 `run_flow_block` 早期版本没有，于是：

- `api-1-211` 第 37 回合：`run_flow_block → general.navigate`，`skipped`「缺少完整坐标」
- `api-1-212`：`do_s2_0_hook` → `milestone_plan_incomplete`
- `api-1-216`：`intent_handoff_do` → `milestone_plan_incomplete`

**已改**：`local_executors.py` 新增 `degrade_program_block_to_visual()`，
命中「缺少完整坐标 / 未派发到节点 / 锚点未命中 / tap_target_unresolved」时，
把当前里程碑改成 `visual_tap`、写 `program/handoff`、`use_visual_fallback`，
并给模型一句 `correction_hint`；同一块连续 3 次才真正记账失败。

### 3.2 回看太严（已在前几轮放宽）

`visual_review.py` 曾经「未列出的元素 = 没达成」直接回滚；现在是软 miss + 阈值 3。
这条列出来是因为它同类：**证据不足 ≠ 失败**。

### 3.3 断言必须先被消费

`agent_loop.py:671/1166/1220/2497`：`required_assertions_consumed` 作为 pass 的理由出现，
反过来，check 阶段若断言未被消费，会挡住 exit。

**现场**：`cr-9f7f478af02c` 有 1 条以 `required_assertions_consumed` 结束（正常终点），
但如果 do→check 的推进条件没满足，就会卡在 check 里反复观察。

## 4. 准入：依赖没满足也照样跑

`agent_loop.py` 的 `except BindingAdmissionError` 分支（改动前）：

```python
writer.append("execution/blocked", {...})
execution_admitted = True      # 然后照常进 _run_loop
```

于是「账号没租到」「登录块 blocked」的用例照样进循环，烧掉 4 个恢复动作
（`wake_screen` + `dismiss_keyguard` 各两轮）后报 `observation_missing`。

**现场**：`cr-2a8474bd82ca` 的 `case-50b5e242`：
seq 4 `dependency_blocked`（`block:fb.global.login`）→ 2 秒后
`session/end reason_code=observation_missing, summary=binding_not_committed`。

**已改**：认 `dependency_blocked / dependency_unknown`（缺 `resource:account`、
缺 `block:*`、或 `dependency_facts` 全非 ready）即 `env_blocked` 收口，
理由写进 `execution/dependency_blocked`。

**同类未改**：`binding_not_committed` 仍走「先记账再进循环」。
它本身是「绑定没提交」，属于真错误，但现在会被后面的循环覆盖成别的 reason。

## 5. Nexus ↔ Scout 的相互限制

### 5.1 协议版本只许完全相等

`mino_nexus/api/ws/node.py:171` 与 `:260`：

```python
if env.v != P.PROTOCOL_VERSION:
    raise RuntimeError(f"Scout 用了协议 v{env.v}，本 Nexus 是 v{P.PROTOCOL_VERSION}")
```

`core/protocol.py:11` 是 `PROTOCOL_VERSION = 2`，**不做降级协商**（注释里写明按协议 §7）。
后果：Scout 与 Nexus 必须同版本部署，任何一边单独升级都连不上。
这是「自阻塞」里最硬的一条 —— 但它有安全理由（载荷语义变化），建议保留，
只把错误提示做成「请同步升级到 vX」。

### 5.2 Scout 拒绝执行 Nexus 的指令（已放宽）

`MinoScout/mino_scout/executors/adb_executor.py` 的 `_tap_element` / `_multi_tap` /`input_text`：
锚点没命中时，即使 payload 里带坐标也直接 `_fail`：

- `:848`「DOM 点击锚点未命中，不用坐标兜底」
- `:895`「DOM 连点锚点未命中，不用坐标兜底」
- `:1029`「DOM 输入锚点未命中，不用坐标兜底」

**已改**（`adb_executor.py:1092` 起）：`point_policy=node` 且锚点未命中时，
按 `fallback_xy` → `x/y` 顺序兜底执行，`audit.point_policy` 记成 `anchor_fallback`。
原则按你说的定了：**Nexus 给了指令就执行，Scout 不替 Nexus 做策略判断**。

> 注意：Scout 侧还有 `executor_order` / `low_level` / `selected_impl` / `device_hint`
> 四个字段必须由 Nexus 算完塞进 `EXECUTE`，缺一个 Scout 就走默认路径（AGENTS.md §2.1）。
> 这不是 Scout 的拦截，是 Nexus 的漏塞。

### 5.3 三条渠道/方案二选一

`action_space/scheme.py:21-31`：`action_scheme` 与 `observation_mode` 决定 dom / visual。
现在两个方案互不放行（dom 不带坐标、visual 不带锚点），任何一边失效就整条死。
2.1 的 `fallback_xy` 是把两边接上的最小改动。

## 6. 三段式用例自身的限制

`session/start.payload.sop_orchestration`（每条用例都写）：

```json
{"phases": [
  {"id": "prep",  "job": "agent-vision-plan", "exec_job": "agent-vision-exec", "advance_on": "milestones"},
  {"id": "do",    "job": "agent-vision-plan", "exec_job": "agent-vision-exec", "advance_on": "milestones"},
  {"id": "check", "job": "agent-vision-plan", "exec_job": "agent-vision-assert", "advance_on": "milestones"}
]}
```

### 6.1 阶段推进只认 milestones

`advance_on: milestones` 意味着：里程碑没变成 pass，阶段不动。
而 3.1 里的「参数退化」会把里程碑变成 failed —— 一次点不中就卡住整个 do 阶段。

### 6.2 prep 的重入

prep 里的 `prep_lease_account` / `prep_launch_app` / `prep_device_session` 是程序种子，
`milestone/program_seed` 每次进 prep 都会重置 pending（`agent_loop.py` 的 `prep_claim`）。
复跑会话里能看到同一个 `milestone/focus` 连写 4 次（`cr-9f7f478af02c` seq 270/274/278/279），
这就是 6.4 去重要处理的东西。

### 6.3 check 不能碰业务动作

`prompts` 与 `check_phase.py` 都把 check 限制成只观测；`agent_loop` 里 check 结束必须
`required_assertions_consumed`。这条是对的（结果可信），但它把「do 里没做完的事」
永久留在 do —— 3.1 的退化机制是唯一出口。

### 6.4 墙钟预算与等待窗口

| 项 | 值 | 出处 |
|----|----|------|
| 单条用例墙钟 | `prep×30 + do步号×60 + check步数×45` 秒（`cr-…` 的 214 是 405 s） | `contract/step_pointer.py:118` |
| 资源等待 | 300 s（`execution_policy.resource_wait_seconds`） | `loop/case_runner.py:276` |
| 回合上限 | 500 | `loop/agent_loop.py:108` |

`api-1-214` 在 `cr-1af0a562d726` 里以 `execution_deadline_exceeded` 结束 ——
它其实跑得很深，是预算不够，不是逻辑错。这条要你定：加预算还是压缩观察开销。

## 7. Workbench 侧的相互限制

| 现象 | 机制 | 出处 |
|------|------|------|
| 用例作者看不到 `prep_lease_account`，报 `event_not_registered` | 目录行 `lease_account` 是 `caller=system`、`visible_to=["system"]` | `catalog_entries`（无代码强制，靠 `menu_caller_ok` 过滤） |
| 块/用例编辑冲突 | `expected_revision` 乐观锁，冲突后必须重读 | `case_recompile` / `case_version_chain` |
| 编译产物与原文绑定 | `source_revision` + `latest_compile_job_id`，最新版没就绪不能借旧产物跑 | `case_version_chain` |
| 会话看板「一步两条」 | 一个动作写 `tool/call` + `device/action` + `tool/result` + `stream/emit` + `review/dispatched` | 见 8.1（已加去重） |
