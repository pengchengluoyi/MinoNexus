## 1. 已落地范围

### 1.1 数据与迁移

新增 8 张表，全部在 `mino_nexus/models/work_*.py`：

| 表 | 用途 |
|---|---|
| `work_items` | 工作项主表：目标、计划、验收、预算、状态、owner |
| `work_steps` | 可领取步骤：计划、角色回合、工具、等待、审批、验收 |
| `work_events` | 追加事件流，`(work_id, seq)` 唯一 |
| `work_approvals` | 计划/工具/回合审批 |
| `work_artifacts` | run、session、报告、回复等证据 |
| `work_links` | 工作项到 run/session/用例的引用，不复制 run 状态 |
| `work_agent_sessions` | 按工作项/角色 upsert 的会话摘要 |
| `work_agent_memory` | 工作项内的决策、事实、教训记忆 |

`mino_nexus/core/schema_migrations.py` 在严格 schema 校验前执行 additive migration：
- 只 `CREATE TABLE IF NOT EXISTS` 缺失的 `work_*` 表；
- 不 ALTER / DROP 旧表；
- `PRAGMA user_version=1`；
- 发现数据库版本高于代码版本直接拒绝启动；
- 空库仍由 `metadata.create_all` 建全表，再补版本。

### 1.2 状态机与存储

`mino_nexus/assistant/work/work_store.py`：

- 所有 `work_*` 写操作走 `work_session()`：`BEGIN IMMEDIATE`，commit 后才发 WS 事件；
- `create_work` 按 `(owner_user_id, create_key)` 幂等；
- `claim_step` 带租约、到期时间、attempt；`run.wait` 的轮询不增加 attempt；
- `finish_step_in_db` 供 handler 在同一个事务里完成父/子步骤；
- `resume_parent_in_db` 避免在 handler 事务里嵌套开新事务；
- 计划审批通过后把 `work.status` 从 `waiting_human` 拉回 `running`，否则审批步骤永远领不到；
- `pause_work` / `resume_work` / `cancel_work` / `block_work`；
- `recover_stale_work` 启动恢复：`agent.plan`、`agent.turn`、`job.call`、`run.wait`、`work.review` 可重试；
- `tool.call` 崩溃恢复只允许两种情况：已有子步骤则补父步骤完成；否则标记 `unknown` 并阻塞，绝不重放；
- `reserve_budget` 在领取后扣预算，超限直接把步骤置 `cancelled` 并阻塞工作项；
- `run.wait` 最多轮询 1200 次（约 1 小时），超时阻塞，避免无限事件风暴。

### 1.3 执行器

`mino_nexus/assistant/work/work_runner.py`：

- 单 worker 循环；`app.py` lifespan 启动，shutdown 停止；
- 每个 handler 在 `execution_user(owner)` 下执行，工具/模型都按工作项 owner 取配置；
- 启动时先 `recover_stale_work()`；
- `tool.call` 抛异常一律 `unknown` + `blocked write_result_unknown`，不自动重试；
- 其他步骤最多 `max_attempts` 次，指数退避。

`mino_nexus/assistant/work/work_handlers.py` 已实现的 handler：

| kind | 行为 |
|---|---|
| `agent.plan` | 调 `work-plan`，写计划、验收、计划审批；审批步骤用 `human.approval` |
| `human.approval` | 计划批准后创建第一个 turn；工具批准后按**已批准的具体 args**创建 `tool.call`；驳回则阻塞 |
| `agent.turn` | 五选一：`tool` / `reply` / `delegate` / `approval` / `complete` |
| `tool.call` | 角色工具白名单；`client_request_id=step_key`；写工具结果落 artifact/link；`case.run` 创建 `run.wait` |
| `run.wait` | 只读 `run_store`；终态才写 run/session 证据并唤醒父 turn；非终态 3 秒后再看 |
| `job.call` | 用角色的 `chat_jobs` 调 `chat_with_role`，结果落 note artifact |
| `work.review` | 逐条验收；模型说 done 不算，run/session/artifact 必须本地可验证并已链接 |

### 2.2 收口联调（2026-10-23）

在 2026-10-22 的链路上继续修了四个会直接毁掉“事情能做完”的问题，并用
真实 `case.run` 复验：

- **`run.wait` 轮询耗尽 step 预算**：`reserve_budget` 原来每次轮询都加
  `spent.steps`，3 秒轮询约 1 分钟就把 `max_steps=24` 打满，工作项
  `budget_exhausted:steps`，而 run 还在跑。现在 `run.wait` 不计入 step 预算。
- **run 终态后父回合继续起第二个 run**：`run.wait` 读到了终态，却把父
  `agent.turn` 唤醒，模型又调一次 `case.run`。现在 run 终态时直接收口父回合
  并进入 `work.review`，不再让父回合有机会重复启动。
- **用例 id 被填进 `search`**：模型把 `api-1-218` 填进“名称关键字”`search`，
  `case.run` 返回“这个范围没有用例”。现在工作层对 `X-N-N` 形态的
  `search` 做确定性纠正为 `case_ids=[...]`，prompt 也明确 id 必须放
  `case_ids`。
- **验收证据引用 artifact id**：验收模型把 `wa_...`（run artifact）填进
  `type="run"` 的 `ref`，被 `evidence_run_not_found` 误杀。现在
  `validate_review` 先把 artifact id 解析成其 `ref_id`（run/session），再校验
  本地记录、终态和 link。

本轮最终工作项 `wk_731edc9b042749afa4c4`（绑定“4.0”工作区）：
`work-plan → 审批 → case.run → run.wait → work.review` 全部完成，
状态 `done`，6/6 步 100%；真实 run `cr-beee95c04cb7` 终态为 `done`，
关联 session `cr-beee95c04cb7::api-1-218::5fda2f6d`，工作项写入
run/session artifact 与 link。**注意**：run 的终态是 `done`，但该用例本身
仍是 `unverified`（`required_operation_unverified`），没有一条“用例通过”的
结论；工作项的完成含义是“执行并取证完成”，不是“测试通过”。

## 3. 边界与未完成

- **审批策略**：默认 `plan`；`policy_json.write_approval="always"` 时，所有 `risk=write` 工具在 `run_tool` 之前生成 `tool` 审批，批准后才以冻结参数执行。不是所有工作都默认逐次审批。
- **L4 设备接管**：`takeover_step` 只暂停自动推进并记录控制权，不向 Scout 发设备动作；设备操作仍由 Scout/人工在 Scout 侧完成。
- **`work_agent_sessions` / `work_agent_memory`**：`work-turn` / `work-plan` / `work-review` 都注入记忆；后台每 6 小时清理过期记忆。记忆只作辅助上下文，验收仍看 run/session/artifact 证据。
