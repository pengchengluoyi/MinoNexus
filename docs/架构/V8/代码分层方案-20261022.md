# MinoNexus 代码分层方案（V8 草案）

日期：2026-10-22。状态：**设计方案，未实施**。本文不代表任何代码已改动或已验收。
承接：[V7 用例执行链路收敛设计](../V7/用例执行链路收敛设计-20261020.md)（EX 批次）、[ARCHITECTURE.md](../../基础框架/ARCHITECTURE.md)。

本文只回答三件事：

1. 你提的 9 层**是否合理**；
2. 按真实业务逻辑**应该怎么拆**；
3. 迁移后的**1/2/3 级目录**分别放什么。

---

## 0. 结论

### 0.1 一句话

**9 层里 3 层边界成立、可直接保留（assistant / resource / plugin）；4 层要拆或换位置（loop 过宽、FSM 混了编译期与运行期、llm 放错 ctx/job、session 混了三种记录）；1 层要改名（service）；另有一个空号，正好是缺的 `contract`（纯契约层）。**
但没有这一层，无论目录怎么改，循环 import 和"改一处坏多处"都会原地复活。原因见 §1.3。

### 0.2 逐层判决

| # | 你的层 | 判决 | 处理 |
|---|---|---|---|
| 1 | loop 执行层（编译/预检/触发执行） | **过宽，且混了 3 种生命周期** | 拆成 `casework`（编译/预检）、`execution/schedule`（触发/派单）、`execution/`（循环本体） |
| 2 | FSM 层（页面/路线/逻辑块/登录） | **半对：混了"编译期图"和"运行期状态机"** | `navigation/`（图与布局，主要是编译期）+ `execution/{auth,nav,program}`（运行期） |
| 3 | llm 层（job/角色/上下文/ctx） | **半对：`ctx` 和 `job` 放错了** | `intelligence/` 只留模型、提示词、决策；`ctx` → 执行态，`job` → `records/tasks` |
| 4 | plugin 层（与 Scout 插件交互） | **对，但要正名为适配器并引入端口** | `connectors/scout/` + `contract/ports.py` |
| 5 | assistant 层（IM/工作区） | **对，但必须切断 ASGI 自调用** | `assistant/{im,conversation,agent,workspace,qa}` |
| 6 | resource 层（账号/设备状态） | **对，但设备"状态"有双真源风险** | `resources/` + 明确 `node_registry` 是在线状态唯一真源 |
| 7 | session 层（全部调度记录） | **半对：三种记录混在一起** | `records/{eventlog,runs,tasks,evidence}`，其中 `eventlog` 是叶子 |
| 8 | （空号） | **恰好是缺的那层** | `contract/`：协议、五态、ResolvedCase、事件契约、端口 |
| 9 | service 层（model/router/websocket） | **名字冲突，且 model 不该在这** | `api/`（http/ws/请求模型）+ `models/` 独立保留 |

### 0.3 总判断

你用的是**两套切法混在一起**：

- `loop` / `llm` / `plugin` / `service` 是**技术角色**（谁在跑、谁在调模型、谁在联网、谁是入口）；
- `assistant` / `resource` / `session` 是**业务能力**（IM、租号、记录）。

这两种切法不能同级并列 —— 技术角色会在每个业务能力里重复出现（每个域都要调模型、都要写事件、都要联网），
一旦并列，任何"跨角色"的调用都会变成跨包循环。

**正确做法：外层按业务能力分包，技术角色降级为包内二级目录；再用 4 个环（基座 / 能力域 / 执行 / 入口）钉死依赖方向。**

以下全部是当前工作树的实测值，不是估计。

| `doc_*` / `knowledge_*` | 13 | 2,813 | 文档知识 |
| 其余散件 | 13 | 1,500 | 无归属 |

### 1.2 依赖不是分层，是几乎全环

按 AST 统计包间 import（含函数内 import）：

```
services -> loop        272 条    loop -> services        54 条   ← 双向
services -> routers       2 条    ← 业务反向依赖 HTTP
core     -> services      4 条    ← 基础设施反向依赖业务
ai       -> services 18 条 + loop 4 条（6 个模块）
catalog  -> services 8 条 + loop 5 条
```

被引用最多的模块里，有一半是"本该在底层"的东西：

| 模块 | 被多少模块 import | 问题 |
|---|---:|---|
| `core.database` | 154 | 正常 |
| `services`（整个包） | 117 | **包名当命名空间用，等于没有边界** |
| `core.execution_user` | 66 | 正常 |
| `loop.milestones` | 30 | **纯状态函数埋在 loop 里，服务层被迫 import loop** |
| `loop.hierarchy_slots` | 27 | 同上（且它还反过来 import `services.nav_layout`） |
| `loop.observe.session_log` | 26 | 事件日志埋在 loop 里，导致 10 个 services 模块 import loop |

这就是 `services <-> loop` 双向环的直接成因：不是谁写错了，而是**类型和函数放错了楼层**。

### 1.3 最致命的一条：78% 的 import 写在函数体内

```
from mino_nexus ... 共 4205 处
  顶层 import       926 处（22%）
  函数内 import    3279 处（78%）
```

这些函数内 import 绝大多数是为了**绕过循环 import**。后果不是"能跑了"，而是：

- 结构错误在启动时**不再报错**，只在某条执行路径上才炸；
- 任何静态分析（IDE 跳转、grep、本文的依赖图）看到的都是残缺的；
- 你"改一处"，另一条路径炸，因为那条路径的依赖从来没被显式声明过。

**这是"连续改错、问题反复"的机制本身。** 只改目录不动这条，等于把地雷换个房间埋。

### 1.4 状态没有主人

```
setattr(...)        229 处，分布在 46 个文件
setattr(ctx, ...)   114 处
agent_loop.py        72 处   visual_review.py  47 处
```

`ctx` 是动态挂属性的对象，任何模块都能读写任何键（V7 实测 77 个 `ctx` 键）。
于是"谁改坏了"无法从代码回答 —— 只能翻 `session_events` 反推。这正是排查慢的根因。

### 1.5 助手层通过 ASGI 自调用回灌自己的 HTTP

`services/assistant_tools.py`：

```python
def _asgi_request(method, url, rest, headers):
    transport = httpx.ASGITransport(app=_app())   # 直接打进自己的 FastAPI
    ...
```

`_app()` 在未 bind 时还会 `create_app()` 再建一个应用。
所以**真实的依赖图比 import 图更糟**：`assistant -> api -> 所有域`，而且绕过了类型检查、绕过了事务边界，
还额外复制了一次 `execution_user` contextvar 到新线程。IM 报错时，你无法判断错在 IM、ASGI 传输、鉴权还是目标路由。

### 1.6 一个函数 4,924 行

`loop/agent_loop.py` 6,050 行，`_run_loop` 约 4,924 行、317 个局部变量、626 个 `if/elif`（V7 实测）。
目录分层对它**一分帮助都没有** —— 它必须先按阶段切开（见 §6 第 8 步）。

### 1.7 小结

> 目录分层能降低"改错连带率"，但**排查速度**取决于三件事：单向链路、状态有主、事件日志完整。
> 因此本方案的验收标准不是"目录长得对"，而是 §3 的三条规则能被脚本检查、且 §6 每步都能用 `session_events` 前后对照。

## 2. 对 9 层的逐条评估

### 2.1 边界成立的（5 层）

- **assistant**：真实边界。35 个文件、7,620 行、独立表（`assistant*` / `collab_*`），入口是 IM/工作区，出口是"调工具"。
- **resource**：真实边界。42 个文件、10,351 行、独立表（`pool_account` / `device*` / `resource_ops` / `execution_resource`）。
- **plugin（改名 connectors）**：真实边界。它是 Nexus 唯一"出网到 Scout"的地方，`node_plugin_call.py` 的 `_ALLOWED` 清单已经是隐式端口。
- **llm（缩小为 intelligence）**：真实边界，但要剔掉 `ctx` 和 `job`（见 2.2）。
- **FSM（拆成 navigation + execution 内三块）**：边界真实，但不能只做一层（见 2.2）。

### 2.2 必须修正的（4 层 + 1 处命名）

#### ① `loop` 装了三件生命周期完全不同的事

你的描述是"编译、预检、触发事件执行等"。这三件事的触发者、耗时、失败语义都不同：

| 事 | 谁触发 | 何时 | 失败意味着 |
|---|---|---|---|
| 编译（case → 可执行计划） | 用户在 Workbench 编辑用例 | 编辑期，可分钟级 | 用例不可执行，与设备无关 |
| 预检（准入：平台/环境/账号/设备/用例） | 点击"运行" | 运行前，秒级 | 拒绝执行，**不进入循环** |
| 触发执行（建 run、派单、并发、租约） | 点击"运行" / IM / 定时 | 运行期 | 调度失败，与单用例无关 |

把它们都叫 loop，等于让"编辑用例"和"跑用例"共享一个包 —— 改编译的人会碰到执行代码。
**拆法**：编译 → `casework/compile`；预检 → `casework/preflight` + `execution/schedule/admission`；触发 → `execution/schedule`；循环本体 → `execution/`。

#### ② `FSM` 混了"编译期图"和"运行期状态机"

现状能证明这一点：`services/nav_*` 39 个文件里，`nav_compiler` / `nav_synthesis` / `nav_candidate_compiler` / `nav_screen_layout`
是**离线把页面图算出来**（编译期）；而 `loop/nav_runtime.py` / `navigation_policy.py` 是**运行时按图走**。
两者放同一层，依赖方向必然相反：编译器要读全量图，运行时只读当前页。

另外"逻辑块（登录）"其实是三样东西：

| 东西 | 现状位置 | 应放 |
|---|---|---|
| 逻辑块**定义**（DB 配置：步骤、守卫、key 引用） | `services/nav_flow_blocks.py`(1633 行) / `nav_flow_block_catalog.py` | `navigation/blocks/` |
| 逻辑块**运行时执行** | `loop/flow_block_executor.py`(1028 行) / `runner` / `guards` / `exit` | `execution/program/` |
| 登录**状态机** | `loop/login_*.py` 9 个文件 | `execution/auth/` |

**拆法**：`navigation/`（图、布局、块定义）+ `execution/{nav,auth,program}`（运行期）。

#### ③ `llm` 里的 `ctx` 和 `job` 会制造反向依赖

- `ctx`（`RunContext` + 77 个动态键）是**执行态**。放进 llm 层，等于让 `execution` 为了拿状态去依赖 `intelligence` —— 方向反了。
- `job`（`job_store.py`）是**任务记录**，和 `run_store` / `task_store` 同族，属于 `records/tasks`。
- "角色"是提示词资产（`ai/roles_catalog.py`）→ `intelligence/prompts/`。
- "上下文"要分三种，现状被一个词盖住了：**提示词上下文**（intelligence）、**运行上下文**（contract + execution）、**会话记录**（records）。

**拆法**：`intelligence/` 只保留 `llm/`（provider 客户端、dispatch_log、用量）、`prompts/`（渲染、角色、层级栈）、`decide/`（planner、action space、语义）。

#### ④ `session` 把三种记录混成一层

| 记录 | 特点 | 归属 |
|---|---|---|
| `session_events`（`session_store` / `SessionWriter`） | 只追加、按 run 排障的**唯一证据链** | `records/eventlog` |
| `app_regression_runs`（`run_store`，1001 行） | 可变、有状态机（running/finish/cancel） | `records/runs` |
| IM 会话（`assistant_conversation` / `collab_*`） | 对话态、按人/群 | `assistant/`（它自己的表，不进 records） |

如果合成一个 `session` 层，它会变成第二个 `services`：谁都能写，谁都能改。
**关键约束**：`records/eventlog` 必须是**叶子** —— 只依赖 `core/contract/models`，任何层都能写它，它不写任何层。
现状恰好相反：`loop/observe/session_log.py` import `services.session_store`，而 10 个 services 又 import `session_log` —— 环。

#### ⑤ `service` 这个名字不能用，`model` 也不能放进去

- 仓库现有约定是「新业务进 `services/`」（AGENTS.md §3）。再来一个 `service` 层，两个词永远分不清。
- `model`（ORM，51 个文件）现在**只依赖 core**，是全仓最干净的一层。塞进 HTTP 层会立刻被 routers 的请求模型污染。
- 两个 websocket 方向相反，不能同层：`websocket/node.py`（Scout 连进来）= 适配器；`websocket/observers.py`（UI 推送）= 入口。

**拆法**：`api/`（`http/` + `ws/` + `schemas/`）+ `models/` 独立保留 + `connectors/scout/ws.py`。

### 2.3 缺的那一层：`contract`（你编号里的 8）

循环 import 的根源不是"文件放错了目录"，而是**共享类型被埋在了实现包里**：

- `loop/milestones.py`（纯函数 + 状态字典）被 30 个模块引用；
- `loop/hierarchy_slots.py`（457 行，纯数据操作）被 27 个模块引用，其中 9 个是 `services/nav_*`；
- `loop/resolved_case.py` / `loop/business_contract.py` / `loop/llm_step_context.py` / `loop/ui_channel.py` 是契约候选，但**并不"零依赖"**（见下表，第一版判断错误已修正）；
- `core/schemas.py` 里放着 `EventResult` / `PlanEvent` —— 协议类型住在基础设施里。

**修正（2026-10-22 实测）**：第一版说这 4 个"零内部依赖"，是只扫了顶层 import。
按 AST 扫完全部函数内 import 后，真实依赖是：

| 模块 | 顶层依赖 | 函数内依赖（真实耦合） | 能否直接搬 |
|---|---|---|---|
| `resolved_case` | dataclass / json / math | 15 处：`case_semantic_integrity`、`execution_binding`、`step_pointer`、`catalog.registry`、`session_atomic`、`resource_preflight`、`session_gate`、`login_evidence`、`milestones`… | **否**，需先抽端口 |
| `business_contract` | 无 | `knowledge_match`、`milestones` | **否** |
| `llm_step_context` | json | `milestones`、`ui_channel`、`session_ensure`、`session_persist`、`session_match`、`project_env`、`login_verification` | **否** |
| `ui_channel` | enum | 仅 `runtime.run_context.is_web_slot` | **可以**：先把纯谓词抽进 contract |
| `hierarchy_slots ↔ nav_layout ↔ nav_screen_layout` | 三者互成三角 | **无外部依赖** | **可以**，已实施（§6.0） |

> 这正好是 §1.3 的现场演示：顶层扫描认定"零依赖"，函数内 import 才是真实依赖。
> 所以第 1 步不是搬文件，而是**先抽纯函数/端口，再搬**。

第 1 步的**实际收益**（已按 §6.0 完成几何三角）：`services -> loop` 从 **54 条降到 39 条**（-15），
`loop -> services` 从 **272 条降到 267 条**（-5）。剩下的 `services -> loop` 边要按第 2、3 步逐条处理。

### 2.4 一个必须承认的事实

**这 9 层解决不了"agent_loop 6,050 行"和"ctx 114 处 setattr"。**
那两件事是 V7 EX 批次的范围。本方案的价值是：**在切循环之前，先把它的依赖抽干净**，否则切的时候会同时移动 30 个引用方。

## 3. 目标架构：4 环 15 包

### 3.1 环与包

**一个包一行**（上一版把多个包写在一行，容易被读成"同级两个目录"，这里改清楚）：

```
环 4  入口        api/            HTTP / WS / 请求模型
环 3  应用        assistant/     人机交互（IM、工作区、群）
环 2  执行        execution/      单用例循环 + 调度 + 派单
环 2  执行        connectors/     Scout 适配器、外部系统适配器
环 1  能力域      records/        记录（eventlog 是叶子）
环 1  能力域      catalog/        能力目录
环 1  能力域      navigation/     页面图与几何
环 1  能力域      casework/       用例生命周期
环 1  能力域      resources/      账号 / 设备 / 租约 / 环境
环 1  能力域      intelligence/   模型、提示词、决策
环 1  能力域      knowledge/      文档 / 知识条 / 设计稿
环 1  能力域      platform/       身份 / 配置 / 插件策略
环 0  基座        contract/       纯契约（无 I/O / 无 ORM / 无网络）
环 0  基座        core/           基础设施
环 0  基座        models/         ORM（只依赖 core）
装配             app.py / cli.py / prompts/（数据）
```

> 注意层级关系：`execution/vision/` 是 **execution 的子目录**，`navigation/controls/` 是 **navigation 的子目录**，
> 它们都不是与 `mino_nexus/` 平级的顶层包。§4 的树里靠缩进表示层级。

依赖方向**只准向下**：

```
api ──► assistant ──► execution ──► {resources, casework, navigation, intelligence, catalog, knowledge, platform}
                            │
                            ├──► records（任何层都可写，records 不反向 import）
                            └──► contract（端口）◄── connectors（实现端口）
```

### 3.2 可脚本校验的 8 条规则

| # | 规则 | 现状违反 |
|---|---|---|
| R1 | `core` / `contract` / `models` 只能向下 import（models 可 import core/contract） | `core.bootstrap` import 8 个业务模块 |
| R2 | `records` 是叶子：只 import core/contract/models | `run_store` 函数内 import `agent_stream`/`web_env` |
| R3 | 任何域不得 import `api/` | `services.development` → `routers.rRuntime`；`scout_install` → `rReleases` |
| R4 | 任何域不得 import `assistant/` | 无（靠 #7 保持） |
| R5 | `execution` 不得 import `connectors`，除 `execution/schedule/wiring.py` 一个文件 | `services.node_plugin_call` → `loop.router_proxy` |
| R6 | `connectors` 不得 import `execution` | 当前无，但 `router_proxy` 在 loop 里，等于没边界 |
| R7 | `assistant` 不得 import `api`（**禁止 ASGI 自调用**） | `assistant_tools._asgi_request` |
| R8 | 能力域之间只允许白名单边（迁移第 1 步用脚本生成，不从文档手抄） | `execution_policy` → `loop.step_pointer` 等 |

> 关于"不另设守门脚本"（CONVENTIONS §4）：建议改为**一个只读的 `tools/arch_report.py`**，

> 因为现在这套环，正是上一次"没有检查"的结果。

### 3.3 端口与适配器（本方案最重要的一处结构改动）

现在 `loop/router_proxy.py`（1,254 行）既是**端口**（循环只认 `dispatch(event, ctx)` 这个签名）又是**适配器**（序列化 `EXECUTE`、等 `RESULT`、超时重发）。
所以循环虽然"不感知网络"，但**包依赖上仍然 import 了网络实现**，CLAUDE.md §2.2 只能靠自觉。

拆成两个文件：

```python
# contract/ports.py —— 循环唯一认识的东西
class DeviceRouter(Protocol):
    def dispatch(self, event, ctx, **kw) -> EventResult: ...
    def observe(self, kind: str, ctx, **kw) -> Any: ...

# connectors/scout/router_proxy.py —— 唯一实现
class RouterProxy:  # 结构兼容 DeviceRouter
    ...
```

注入点只有一个：`execution/schedule/wiring.py`（装配 `RunDeps(router=RouterProxy(...), notifier=...)`）。
收益：`execution` 的 import 闭包里再也没有 `websockets` / `protocol` 的序列化细节；R5 变成可机器校验的一条规则。

### 3.4 状态所有权

| 状态 | 唯一主人 | 形态 |
|---|---|---|
| 批次调度（run / 并发 / 取消） | `records/runs` | 表 + 显式状态机 |
| 单用例执行态（阶段、游标、预算、登录态、导航态） | `execution/turn/session.py` | `CaseSession` dataclass（替代 114 处 `setattr(ctx, ...)`） |
| 不可变执行合同（平台/环境/能力快照/租约） | `contract/execution/resolved.py` | `ResolvedCase`（V7 §3.2） |
| 设备在线状态 | `connectors/scout/node_registry` | 内存 + 落库快照，**唯一真源** |
| 设备台账/租约 | `resources/devices`、`resources/lease` | 表 |
| 登录证据 | `resources/otp` | 表 + 策略函数 |

⚠️ 双真源风险：`services/device_store.py` 与 `services/node_registry.py` 都能回答"这台设备能不能用"。
迁移时必须写死：**能不能派 = node_registry；归谁/租给谁 = resources**，不允许第三处判断。

### 3.5 通知与回调（防止 assistant ↔ execution 成环）

运行结束要通知 IM，但 `execution` 不能 import `assistant`。用 `contract/ports.py` 的 `Notifier` 端口：

```
records/runs.finish() ──► notifier.on_run_finished(run_id)   # 端口在 contract，实现注册在 app 装配
assistant 启动时注册实现；execution 不知道 assistant 存在
```

## 10. 附：三个新问题的核实结论（2026-10-22）

### 10.1 登录逻辑到底在几处（对应"页面上把登录放进项目配置"）

**结论：不是重复实现，是三个不同的问题被放在三个地方。** 但它们之间有两条真实分叉路径。

| 面 | 存储 | 决定什么 | 写入口 | 读入口 |
|---|---|---|---|---|
| `fb.global.login` 逻辑块 | `nav_flow_block_catalog`（全局 v13，10 步） | **页面步骤序列** | `catalog/flow_block_seed.py` 播种；`PUT /flow-blocks/apps/{id}/overrides` | `flow_block_executor`、`login_block_steps` |
| 项目环境 `channel_secrets[渠道][环境].login` | `project.env` JSON | **取号策略**（auto/pool/hitl）与**账号类型**（phone/email） | Workbench 环境页 / `rSettings` | `account_lease`、`otp_resolve`、`login_block_steps.send_code` |
| 应用 playbook `login_evidence_policy` | app playbook | **登录成功的证据口径**（`ui_identity` / `submitted_account` + 环境渠道白名单） | `PUT /apps/{id}/login-evidence-policy` | `login_evidence`、`milestones`、`flow_block_executor` |

所以"步骤 / 取号 / 证据"各一处，本身是对的。**两个真实风险**：

1. **两种覆盖都会打穿硬编码 step id**：`resolve_effective_steps()` 支持 `skip_step_ids`（跳过若干步）
   和 `steps`（整表替换）两种 override；而 `login_block_steps._web_tap_send_code()` 硬编码查 `id == 'send_code'`。
   跳过或改名该步 → 该路径返回 `BLOCKED`，不报错、不提示"配置写错了"。
   override 存放在 `nav_fsm.meta.flow_block_overrides`（`nav_flow_block_catalog.py:82/134` → `calib.save_draft`）。
2. **两个"登录成功"判据**：`login_evidence_policy.mode=submitted_account` 把"已提交账号"视为已登录，
   而 `fb.global.login.login_state` 仍会跑 `confirm_login_state`；`milestones.py` 与 `visual_review.py` 各自调用
   `note_submit_result`，两边可能给出不同结论。

**当前开发库实测**（只读）：`nav_flow_block_catalog` 4 行、`nav_fsm` **0 行**（即没有任何 override）、
`projects.env.channel_secrets` 为 `{}`（即全部走默认 `auto`/`phone`）。**今天三者一致，没有已经坏掉**；
风险是机制性的，一旦有人在页面上改就会触发。

#### 10.1.1 归属调整（2026-10-22 已确认）

`login_evidence_policy` **归 `navigation/`**，因为"登录成功的口径"是页面事实，不是执行细节。但整个文件不能原样搬：

| 部分 | 函数 | 依赖 | 去处 |
|---|---|---|---|
| 纯策略 | `normalize_policy`、`DEFAULT_POLICY`、`policy_for_context`、`submitted_account_enabled`、`configured_session_knowledge` | 只读 `ctx` / dict | `navigation/login/policy.py` |
| 证据落库 | `_now_valid`、`confirm_account_fill`、`note_submit_result`、`submission_current`、`clear_submission` | `services.login_evidence`、`login_evidence.scope` | `records/evidence/login.py`（与 `login_evidence` 合并） |

为什么必须拆：`login_evidence_policy ↔ login_evidence` 现在是**双向 import 的环**，
而 `login_evidence` 又依赖 `loop.login_transition`（`session_persist`、`vision_assert`、`channel_observation`）。
整文件搬进 `navigation/` 会立刻产生 `navigation -> execution` 的反向边。
按上表拆开后：`navigation/login/policy.py` 只依赖 `contract`；`records/evidence/login.py` 只依赖 `records/eventlog`。

**执行顺序**：先做 `records/eventlog` 叶子化（第 2 步），再搬这两块；否则 `navigation` 会被迫在函数体内 import `loop`。

**建议的收敛**（下一步可做，不在本次搬迁范围内）：
- 定义 `LOGIN_STEP_IDS` 合同；写 override 时校验 step id 必须属于合同，缺必需步直接拒绝；
- 把"登录成功"收敛为一个函数（`login_verdict(ctx)`），`login_state`、milestones、visual_review 都只读它；
- 项目环境只保留 `mode/kind`（取号），**不允许**在项目配置里写步骤 —— 步骤只有逻辑块一个真源。

### 10.2 RAG / 知识条放哪
