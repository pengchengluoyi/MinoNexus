# 多 Agent 协作与任务工作层方案（V8 补充方案，草案）

日期：2026-10-22
状态：**方案，待评审**。本文不含实施代码，不代表已经改造完成。
承接：[V7 MinoBots 方案](../V7/MinoBots-方案.md)、[V8 代码分层方案](代码分层方案-20261022.md)、仓库 `AGENTS.md` / `CLAUDE.md`。

本文回答以下问题：

1. 为什么现在“复用角色 + job”做不出 Grok Bot / OpenAI Dots 那种体验；
2. OpenDots、DeepSeek-Bot、Prometheus 等开源项目哪些能接、怎么接、接到哪一层；
3. 我们真正要补的那一层是什么，数据、运行时、UI 怎么设计；
4. 现有 18 个角色、38 个 job、prompt 资产怎么处理，分几期上线；
5. “放到本机”是否等于放到 Scout、是否还走 Nexus 逻辑；
6. 如果不考虑许可证，哪个开源项目最合适；
7. 为什么现有 prompt 撑不起“任务看得见、卡住能接管、事情能做完”，应怎么分层。

## 0. 结论

### 0.1 一句话

**不要整体接入 OpenDots，也不要 fork DeepSeek-Bot 当核心；Prometheus（AethraIntelligence）是目前最接近目标的参考实现，但它是单机/无认证的独立平台，不能直接当 Nexus 后端。主路线是：把它的 `Objective/Task/Plan/Approval/Verifier/EmployeeDefinition` 核心移植进 Nexus，配上 AG-UI 事件、MCP 工具；协作语义可选参考 DS Bot，交互范式参考 OpenDots。执行仍然只走现有 `case.run → case_runner → run_store → Scout` 一条路。**

### 0.2 四个判断

| # | 判断 | 依据 |
|---|---|---|
| 1 | 现在缺的不是“更强的角色 prompt”，而是**持久的工作对象**：目标、验收、计划、步骤、事件、审批、会话、记忆 | 当前工作区只有消息 + run 卡；`MAX_STEPS=8`、`total_timeout_sec=300`；成员完成即回交，没有 step 级状态 |
| 2 | **有现成参考，但没有现成答案**：Prometheus 已把任务/计划/审批/验收做出来了，但它是单用户、localhost、无认证、独立数据库；OpenDots/DS Bot 则偏通用 coworker/群聊 | 见 §3.5：Prometheus 31 张表、42 个 migration、`127.0.0.1` 无认证；OpenDots 是 TS 模板；DS Bot 是 DSH 插件 |
| 3 | **整体 fork 仍不划算，但“移植核心”能显著降风险** | 直接跑 Prometheus = 第二套身份/数据/前端/依赖；移植核心 = 复用它的状态机/审批/验收，保留 Nexus 单一真源 |
| 4 | **现有 prompt 不能靠加长解决**：它们是 run 内角色提示，缺目标、状态、权限、验收 | `workspace-route` 只有 persona/facts/recent_turns/utterance；`MAX_STEPS=8`；成员完成即回交；见 §6.9 |

### 0.3 推荐路线：借四样，移植一层，缓三样

| 策略 | 对象 | 怎么用 |
|---|---|---|
| **采用** | AG-UI | 工作事件流的标准事件名与 HITL 交互；Workbench 只做渲染 |
| **采用** | MCP | 已有 `/mcp` 端点；外部 agent / DS Bot 试点统一走工具协议 |
| **移植核心** | **Prometheus（Aethra）** | `Objective/Task/Plan/Approval/Verifier/EmployeeDefinition` + `EmployeeRuntime`/`WorkflowEngine` 的模式；存储/LLM/工具/UI 换成 Nexus 的 |
| **借用语义（可选）** | DeepSeek-Bot | 长驻 Bot、群聊管理员、@交接、每成员独立会话、三档记忆、checkpoint、权限、用量；与 Prometheus spike 二选一 |
| **借用范式** | OpenDots | Dots/Spaces 信息架构、Computer 面板、Approve & run 卡、工具权限、任务/自动化 |
| **自建** | Work Layer 适配层 | `work_items / work_steps / work_events / work_approvals / agent_sessions / agent_memory` + `WorkRunner`；只做 Nexus 特有部分 |
| **暂缓** | Temporal | 等出现多节点/HA/万级工作流再换；现在只借它的语义，不背它的运维 |
| **暂缓** | LangGraph | 不再引入第二套编排模型；`pyproject.toml` 里遗留的 langgraph/langchain/agentscope 应先清理 |
| **只做运维** | `prometheus/prometheus`（监控） | 指标与告警；不承担“任务看得见” |

### 0.4 工期判断

| 阶段 | 时间 | 产出 |
|---|---|---|
| Phase 0 | 3 周 | 第 1 周 Prometheus headless spike + MCP 桥；第 2–3 周迁移机制 + 核心移植骨架 + WorkRunner + 可演示切片 |
| Phase 1 | 4 周 | v0.5：移植核心状态机/审批/验收；单团队、4 个 agent；真实设备闭环“回归 → 失败归类 → 报告” |
| Phase 2 | 6 周 | v1：多 agent 交接、记忆、接管、并发与成本；工作流/定时可选 |
| Phase 3 | 6 周 | 生产硬化：故障注入、可观测、安全、可选 Temporal |

**v1 约 11–13 周（2 名后端 + 1 名前端 + 1 名 QA/Agent 工程师）。** 有 Prometheus 参考，设计风险显著降低，但适配存储/身份/工具/UI 仍是完整工程；按 14 周排期更稳。不是 2–3 年，但也不是 2 周。

## 1. 现状：为什么“角色 + job”不够

### 1.1 现在真实有的东西

| 能力 | 位置 | 现状 |
|---|---|---|
| 执行链 | `case.run → case_runner → run_store → Scout` | 完整、可信，是最大资产 |
| 工具层 | `assistant_tools.py` + `prompts/assistant/tools/*.yaml` | 已有 case/device/task/session/evidence 等工具 |
| 工作区 | `assistant/workspace/*` | 群聊、成员、@、run 卡、范围、自动化、审阅 |
| 持久消息队列 | `collab_message_jobs` | 串行消费；重启把未完成标 interrupted，不重放 |
| 事件证据 | `session_events` / `session_meta` | 跑批/登录问题的事实来源 |
| 模型调用日志 | `dispatch_log` / `model_usage` | 可按 job/role/trace 查 |
| 外部工具协议 | `api/rMcp.py` | 已支持 MCP tools/list、tools/call |
| 角色/job 资产 | `prompts/roles/*.yaml`（18 个）、`prompts/jobs/*`（38 个） | 提示词与引擎已成型 |

### 1.2 缺的东西

| 能力 | 现在 | 缺口 | 直接后果 |
|---|---|---|---|
| 工作对象 | 一条用户消息 + 一张 run 卡 | 没有“目标 / 验收标准 / 计划 / 步骤” | 用户只看到“在跑”，不知道“在做什么、还差几步” |
| 持久会话 | 每条消息重新拼 facts，最近 6 条 | 没有 agent session、没有长期记忆 | 同一个问题要反复解释；成员之间不共享上下文 |
| 长任务 | 单轮 300 秒、8 步；成员 5 步 | 不能跨消息继续，不能在等待 run 时释放线程 | 回归跑 20 分钟，聊天早已超时；只能靠 run 卡事后看 |
| 接管 | 工作区暂停（只挡写）、取消 run | 不能在某一步暂停、改指令、接管完成、跳过、重试 | “卡住”只能取消重来，或者人去任务页手动操作 |
| 多 Agent | `member.assign` 单次调用，成员做完回交 | 没有 handoff 合同、没有 specialist session、没有并发/深度控制 | 成员像“一次性问答”，不像“同事” |
| 完成定义 | 模型说“已完成”/run 结束 | 没有 acceptance + evidence 合同 | “回复了”被当成“做完了”；报告可能没有证据 |
| 可见性 | 聊天 + run 卡 | 没有工作列表、时间线、当前动作、阻塞原因 | 无法回答“现在谁在做什么、为什么卡住” |
| 恢复 | 消息级 interrupted；run 级 reconcile | 没有 step 级 checkpoint / lease / unknown 状态 | 重启后只能重发；写操作不敢重试 |

### 1.3 V7 的教训不能丢

V7 砍掉的是**第二套执行系统**：`collab_tasks`、`collab_batches`、`collab_agent_runs`、七种触发。它们复制了 `run_store` 的状态、预检和派发，导致两套行为分叉。

这次不能重犯：

- 不复制 run 状态；Work Step 只存 `run_id` 引用，状态实时读 `run_store`。
- 不复制派发/预检；要跑用例就调现有 `case.run` 工具。
- 不建 per-agent 线程表；一个 Work Item 一个事件流，agent 会话是上下文，不是执行线程。
- 不新增执行引擎；Work Layer 只做协调、记录、接管。
- 不把“计划卡”做成不可编辑的表演；计划必须是可修改、可失败的持久对象。

一句话：**V7 说“工作区是入口，不是门”；本方案补的是“入口后面的工作台”，不是第二扇门。**

## 2. 目标与边界

### 2.1 三个目标的可验收定义

#### A. 任务看得见

- 用户提出一个需要多步完成的目标后，**5 秒内**出现工作卡：目标、验收标准、步骤计划、当前状态。
- 每一步都有：序号、类型、负责 agent、意图、状态、开始/结束时间、产出/证据链接。
- 页面刷新、服务重启、换设备打开，看到的是同一份工作状态，不靠聊天记录拼接。
- 当前动作可读：正在调哪个工具、跑哪个 run、等什么审批、缺什么资源。
- 阻塞有结构化原因：`waiting_approval / missing_resource / model_error / repeated_failure / timeout / unknown_write`，并给出可执行选项。

#### B. 卡住能接管

- 任何 `running` 的工作可以“暂停”，暂停发生在**步骤边界**；正在执行的设备动作按现有停止/确认语义处理，不硬杀。
- 人可以：改指令、改剩余计划、批准/拒绝、重试当前步、跳过当前步、接管完成当前步、取消整个工作。
- 接管后恢复，从 checkpoint 继续；已完成的写操作不重放；未知写操作必须先对账。
- 所有接管动作有审计：谁、何时、改了什么、为什么。

#### C. 事情能做完

- 每个工作有明确的 `acceptance`（验收标准），来自计划或用户确认。
- `done` 必须满足：验收标准逐条有证据；证据是 `run_id / session_id / screenshot / report artifact` 之一。
- 没有证据只能 `blocked`，不能 `done`；模型说“完成”不算。
- 失败/阻塞时，工作不会静默消失；它留在列表里，带原因和下一步建议。

### 2.2 不做什么

- 不做 Jira / 项目管理：工时、排期、看板拖拽、跨团队依赖图，v1 都不做。
- 不做第二套执行、派发、预检、设备控制。
- 不做 Agent 市场、角色市场、Bot 商店。
- 不做实时设备远控（v1 只做“暂停 + 查看证据 + 改指令 + 接管步骤”；L4 远控后置）。
- 不做跨项目共享记忆；不做全局自动学习。
- 不整体 fork OpenDots / DeepSeek-Bot；不把 Prometheus（Aethra）服务当生产后端；不新增第二个产品前端。

### 2.3 八条设计原则

1. **单一执行路径**：所有设备动作仍然只经 `case.run` / `case_retry_failed` 等既有工具。
2. **单一状态真源**：run 的状态只信 `run_store`；工作的状态只信 `work_events`（投影到 `work_items/work_steps`）。
3. **事件先行**：先追加事件，再更新投影；UI 断线用 `seq` 续传。
4. **写操作幂等 + 未知不重放**：每步有 `idempotency_key`；崩溃后可能已发生的写，标 `unknown`，人对账后再继续。
5. **Prompt 只做判断与表达**：权限、预算、范围、写次数、完成校验都在代码里。
6. **一工作项一 manager，星形委派，深度 ≤ 2**：成员之间不自由对话，控制点集中。
7. **聊天快、工作慢**：聊天队列和工作队列分离；工作步骤不阻塞用户继续提问。
8. **参考实现优先**：状态机、审批、验收先移植 Prometheus 已验证的语义，再写 Nexus 适配；不重新发明。

## 3. 开源项目评估

### 3.1 总表

| 项目 | 它是什么 | 栈 / 许可 | 对本目标的价值 | 结论 |
|---|---|---|---|---|
| [OpenDots](https://github.com/CopilotKit/OpenDots) | 自托管 AI coworker 模板：Dots、Spaces、Computer、HITL 审批、Slack | React 19 + Node 24 + SQLite；模板 MIT；会话依赖 CopilotKit Intelligence（托管/商业自托管） | 交互范式、AG-UI 用法、审批卡、Computer 面板 | **借范式，不整体接** |
| [DeepSeek-Bot](https://github.com/Fei2411/DeepSeek-Bot) | DSH 的 Bot 插件：长驻 Bot、群聊、@交接、记忆、checkpoint、权限、定时任务、用量 | Node/TS；Apache-2.0；peer 依赖 DSH | 最接近“AI 同事团队”的协作语义 | **借语义 + 2 周影子试点，不 fork 核心** |
| [Prometheus（AethraIntelligence）](https://github.com/AethraIntelligence/Prometheus) | 本地优先的 AI 管理者 + 数字员工平台：目标、计划、委派、验收、审批、审计、记忆、工作流 | Python 3.12 + FastAPI + SQLAlchemy + Alembic；SQLite/Postgres；MIT | **最接近本目标的参考实现**：Objective/Task/Plan/Approval/Verifier 都有 | **移植核心，不作为生产后端** |

| [AG-UI](https://github.com/ag-ui-protocol/ag-ui) | Agent-User 交互事件协议 | 协议/SDK；MIT | 事件流、状态同步、HITL、生成式 UI | **采用** |
| [MCP](https://modelcontextprotocol.io) | Agent 工具协议 | 协议/SDK；开放 | 工具边界、外部 agent 接入 | **已有，继续用** |
| [Temporal](https://github.com/temporalio/temporal) | 持久执行平台 | Go server + SDK；MIT | 工作流、重试、信号、定时器、可见性 | **暂缓，借语义** |
| [LangGraph](https://github.com/langchain-ai/langgraph) | Agent 图编排 + checkpoint/interrupt | Python；MIT | 图、断点、人工中断 | **不引入核心** |
| [invisible_dots](https://github.com/feder-cr/invisible_dots) | 自托管 Dots 替代：每 Dot 一台 VM、Playwright、任务/自动化 | Node/Go/QEMU；MIT | 证明“always-on + computer + tasks”是品类共识 | **只作参考** |

### 3.2 先看清 Grok Bot / OpenAI Dots 到底是什么

这类产品（以及 Claude Cowork、Manus Cue 等）的共同点不是“更会聊天”，而是：

- **always-on**：agent 常驻，不是一问一答；
- **每个 agent 有独立工作环境**：浏览器/文件/终端/设备，状态可持久；
- **任务与例行**：任务队列、优先级、开始时间、定时/触发；
- **记忆与技能**：跨会话记住偏好/事实，能把步骤写成可复用技能；
- **审批与接管**：危险动作要人批，卡住能人接管，执行过程可见；
- **多入口**：Web、手机、IM，同一个 agent 连续工作。

这正好对应我们要补的 Work Layer + Session/Memory + Approval/Takeover，而不是“再加几个角色”。

Grok Bot / OpenAI Dots 本身是闭源产品，没有可直接接入的源码；开源替代里 OpenDots、DeepSeek-Bot、invisible_dots 各覆盖一部分，但没有一个覆盖“UI 自动化 + 设备执行 + 证据”。所以只能借语义/协议/交互，不能整体替换。

### 3.3 OpenDots：值得学，不值得整体接

**核实到的能力**（README / SETUP）：

- Specialist Dots：每个 Dot 有名字、角色、指令、允许的工具。
- Dot computers：每 Dot 一个隔离浏览器/工作区，Computer 面板有 browser、human takeover、files、terminal、activity。
- Review before saving：HITL 卡暂停工具调用，Approve & save / Decline，批准后继续。
- Connections：任意 MCP server；只读工具直接跑，其他工具必须 Approve & run。
- Spaces：工作文档的持久空间；对话用 CopilotKit Threads。
- AG-UI 承担消息、工具调用、agent state 的流式传输。

**为什么不能整体接**：

1. **栈不同**：Next/Vite + Node 24 + React 19；Nexus 是 Python/FastAPI/SQLite，Workbench 是另一个 React 应用。接进来就是第三个前端。
2. **会话有商业依赖**：README 明确“Conversations require CopilotKit Intelligence”，本地 Docker 评估也要 CopilotKit 账号、30 天许可、4 CPU/12 GB/40 GB；生产自托管需要商业授权。核心对话不能押在这上面。
3. **数据/身份重复**：它有自己的 SQLite（pages/spaces/dots/work metadata）、OWNER_ID、OWNER_TOKEN；和 Nexus 的项目、成员、执行账号、模型 Key 是两套。
4. **不懂领域**：没有项目、用例、run、session、证据、Scout、设备租约、账号池。
5. **约束冲突**：仓库硬约束是“只有 MinoWorkbench 一个前端”。

**正确用法**：

- 把它的 **Dots/Spaces 信息架构、Computer 面板、Approve & run 卡、工具权限模型** 作为 Workbench 的交互参考。
- 用它的 **AG-UI 事件映射** 作为协议参考；React 组件如果复用，保留 MIT 归属，不引入它的 server/runtime。
- 如果要做 demo，只在沙箱 fork，不接生产数据。

### 3.4 DeepSeek-Bot：最像目标，但它是 DSH 的插件

**核实到的能力**（README / package.json）：

- 长驻 Bot：每个 Bot 是一个 DSH Session，有名字、角色、指令、模型。
- 主 Bot（Chief）：管理其他 Bot 和群聊。
- 群聊：管理员默认应答；可 @ 指定 Bot；任何 Bot 可用 @ 把工作交给另一个 Bot；被交办的 Bot 自己干活并在群里更新。
- 每个成员在群里有一个**隐藏 Session**，群不会读到 Bot 的私聊。
- 记忆三档：Bot 自己、群、团队；Markdown 文件；`remember/forget/recall`；记忆审查；敏感信息拒绝。
- 长上下文：context steward 在检查线决定“原地压缩成 checkpoint”还是“写交接条并开新 part”。
- 权限预设：Read only / Workspace / Full access；只有人能改。
- `message_bot`、`ask_user`、`show_view`（text/metrics/table/progress/choices/confirmations/forms）。
- Capabilities：共享的 MCP server、skills、packs；Bot 添加本地 MCP 命令需要人批准。
- 定时任务、用量统计、密钥卡（Bot 看不到明文）。

**为什么不能 fork 进核心**：

1. **它是 DSH 插件**：`peerDependencies` 是 `@deepseek-ai/cordis`、`dsh-llm`、`dsh-tools`、`dsh-web`；离开 DSH 运行时要重写一大半。
2. **数据在 DSH home**：`bot/` 和 `sessions/`；和 `mino.db` 是两套真源。
3. **身份/权限不同**：它只有 DSH 的 owner/team，没有 Nexus 的项目成员、执行账号、模型 Key 隔离。
4. **不懂 UI 自动化**：它的“computer”是 DSH 的文件/终端/浏览器工具，不是 Scout 的设备执行、用例、证据。
5. **fork 即分叉**：上游 v0.2 preview，格式还会变；每年合并成本高于自研薄层。

**正确用法**：

- 把它当**协作语义的参考实现**：群聊管理员、@交接、每成员独立 session、三档记忆、checkpoint、权限、用量。这些语义直接映射到我们的 Work Layer。
- 做 **2 周影子试点**（与 Prometheus spike 二选一，避免重复验证）：DSH + DS Bot，加一个 Nexus MCP capability，建 3 个 Bot（管家/测试工程师/需求分析），只调用 Nexus 的只读工具和受控 `case.run`。目的不是上线，是让团队快速体验“任务被交办、被更新、被接管”的交互，收集哪些语义值得移植。
- 试点不接客户数据，不作为产品前端，不改变 Workbench 唯一前端约束。

### 3.5 Prometheus（AethraIntelligence）：最接近的参考实现

#### 先澄清同名

公开检索里有两个 Prometheus：

- **`AethraIntelligence/Prometheus`**：本地优先的 AI 管理者 + 数字员工平台，Python 3.12 + FastAPI + SQLAlchemy + Alembic，MIT，Tauri/React 桌面壳。**这个才是与“任务看得见、卡住能接管、事情能做完”直接相关的项目。**
- **`prometheus/prometheus`**：监控与时序数据库，Apache-2.0。它只做指标/告警，不提供任务、计划、步骤、接管。

下面评估的是第一个。仓库地址：<https://github.com/AethraIntelligence/Prometheus>。

#### 它已经有的东西（已读源码/README/ADR 核实）

| 能力 | 实现 | 对本方案的价值 |
|---|---|---|
| **目标 / 验收标准** | `domain/workforce/protocols.py` 的 `Objective`：`acceptance_criteria` 在任何工作开始前写入；`ObjectiveStatus` 有 RECEIVED/PLANNING/RUNNING/PAUSED/DONE/FAILED/ESCALATED/CANCELLED | 直接对应 WorkItem + acceptance；解决“完成标准事后改” |
| **任务 / 计划 / 依赖** | `Plan` 把一个 objective 拆成多个 `Task`，带 `dependencies`、`revision`、`superseded`；`TaskPlan` 是单个任务内部的步骤 | 直接对应 WorkStep + 依赖；replan 保留历史 |
| **任务状态机** | `TaskStatus`：CREATED/PLANNING/RUNNING/WAITING_FOR_TOOL/WAITING_FOR_APPROVAL/PAUSED/VERIFYING/COMPLETED/FAILED/CANCELLED；`Execution` 持久化 step 游标 | 直接对应我们的 Work/Step 状态；resume 语义成熟 |
| **管理者 / 员工** | `PrometheusManager` 只做“读请求 → 规划 → 委派 → 监督 → 验收 → 回答”，从不执行；`EmployeeDefinition` 是 YAML 声明：`allowed_tools`、`capabilities`、`policies`、`limits`、`contract`、`memory_scope`、`model_profile` | 直接对应 manager/specialist 与角色/job 元数据 |
| **执行循环** | `EmployeeRuntime` + `executor.py`：think → act → observe；每步后有显式 `Observation`；预算在每步前检查；工具调用先权限、再审批、再计费 | 直接对应 WorkRunner 的 step handler；比“单轮 8 步”成熟 |
| **审批 / 风险** | `ApprovalGate`：风险跟效果走；不可逆操作必须人批；`ApprovalScope` 精确到 subject/action/resource；`ApprovalGrant` 支持 ONCE/TASK/PERSISTENT；`CapabilityLease` 可撤销、可过期 | 直接对应工作层审批；比“一个布尔写预算”细 |
| **验收 / 防自证** | `Verifier` 用独立模型调用判断结果；`domain/workforce/acceptance.py` 用“记录到的成功工具调用/写入文件”判断是否真的发生；全被拒绝/全失败会拒绝“成功” | 直接对应完成合同；这是最值得抄的部分 |
| **审计 / 刹车** | 所有动作（包括被拒绝的）进 audit；`prometheus stop` 是全局刹车，跨重启；审批在刹车后再次检查 | 直接对应接管/安全 |
| **记忆 / 线程** | 记忆带 provenance、可搜索/删除/过期；线程有 brief、最近轮次、compaction | 直接对应 AgentSession/Memory |
| **工作流 / 定时** | `WorkflowEngine`：YAML 声明步骤、依赖、`on_failure`、每步重试、预算；`Scheduler` 定时/触发 | 对应 Phase 3 的 routines；可提前 |
| **接口 / 事件** | FastAPI：`/api/tasks`、`/api/approvals`、`/api/objectives`、`/api/events` SSE；`ActivityEvent` 推送；Tauri/React 桌面壳 | 对应 `/work` + AG-UI/SSE；可参考事件字段 |
| **MCP** | `infrastructure/tools/mcp.py` + `infrastructure/mcp/*`：MCP 工具与本地工具同构；效果由本地记录决定；返回内容按不可信内容包裹 | 对应 Nexus `/mcp` 接入；但传输只有 stdio |

#### 它没有的（正是我们要补的）

- **没有 step 级接管**：有 objective 级 pause/resume、task 级 cancel/retry/handoff，但没有“暂停在第 N 步、改指令、跳过、接管完成、从下一步继续”。
- **没有移动端 UI 自动化**：工具是 filesystem/browser/desktop/code，没有设备、用例、Scout、session 证据。
- **没有多用户/认证/租户**：单机 localhost；团队/项目/执行账号要重建。
- **没有 HTTP MCP**：只有 stdio；Nexus `/mcp` 需要桥接或新增 transport。
- **没有 Workbench 集成**：它的 Tauri/React UI 不能作为我们的唯一前端。

#### 规模与成熟度

- 407 个 Python 文件，178 个测试文件，31 个 ADR，42 个 Alembic migration，31 张表，18 个 validation scenario。
- README 说“Nineteen phases complete”；版本 `0.1.0`；最后一次提交 `2026-09-21`。
- 代码风格是 DDD 分层 + dataclass + Protocol，和 V8 的分层思路接近；`import-linter` 强制 `app → application → domain`、`infrastructure → domain`。
- 这不是 demo，但也还不是经过大规模生产验证的 1.0。

#### 为什么不能直接把它的服务当 Nexus 后端

1. **单用户、本地、无认证**：`app/ui/server.py` 明确写“binds to 127.0.0.1 and has no authentication”；ADR 0006 把“同进程 + 仅回环 + 无密码”作为一个决定。Nexus 是多用户/项目/执行账号模型，直接接会缺认证、租户隔离、成员权限、按用户模型 Key。
2. **数据真源重复**：它有自己的 SQLite/Postgres、31 张表、42 个 migration、自己的 workspace/employee/model/secret 表；和 `mino.db` 的项目、用例、run、Scout、账号池是两套。把工作状态放过去，就违反“业务状态进 `mino.db`”。
3. **不懂 UI 自动化**：它的工具是 filesystem/browser/desktop/code；没有移动端设备执行、用例、Scout、设备租约、session 证据。要接 Nexus，只能把 Nexus 工具当 MCP 暴露给它。
4. **MCP 只有 stdio**：`infrastructure/mcp/transport.py` 是 `StdioTransport`，启动子进程；Nexus `/mcp` 是 HTTP。需要一个 stdio↔HTTP 桥或新增 HTTP transport；不是“填个 URL”就能接。
5. **依赖与硬约束冲突**：`pyproject.toml` 依赖 `playwright`、`pyautogui`；Nexus 硬约束禁止 import 这些。它只能作为**独立进程**，不能被 Nexus 进程内 import。
6. **第二前端**：它有 Tauri/React 桌面壳和自带 Web 页；仓库硬约束是只有 MinoWorkbench 一个前端。直接用它就是第二个产品。
7. **还年轻**：0.1.0，API/ schema 还可能变；fork 后要跟上游合并。

#### 正确用法：四种，按目标选

| 用法 | 适合 | 代价 | 判断 |
|---|---|---|---|
| **A. 1 周 spike**：只跑 `prometheus serve` 的 Web/API（不启 Tauri 桌面壳），加一个 stdio↔HTTP MCP 桥接 Nexus `/mcp`，建 3 个 employee，跑一次真实回归 | 快速验证“任务/审批/验收”交互，统一团队认知 | 1 周；独立数据、独立 UI、不接客户数据 | ✅ 建议先做 |
| **B. 移植核心到 Nexus**（推荐）：把 `Objective/Task/Plan/Approval/Verifier/EmployeeDefinition` 的领域模型与运行时模式移植进 `assistant/work/`，存储/LLM/工具/UI 换成 Nexus 的 | 要把能力做进 MinoNexus 产品 | 核心 4–6 周 + 适配/UI 4–6 周；v1 约 11–13 周 | ✅ **主路线** |
| **C. 独立产品 fork**：把 Prometheus 作为单机版“AI QA 同事”独立产品，保留它的 UI/数据/单用户模型，用 Nexus MCP 做工具后端 | 目标是单机/个人版，不是团队工作区 | 6–8 周出 MVP；长期维护 fork | ⚠️ 另立项目，不混进 Nexus |
| **D. 直接把它当 Nexus 生产后端** | 想省掉工作层 | 认证/租户/双库/双前端/依赖冲突 | ❌ 不建议 |

#### Spike 最小步骤（1 周）

1. `git clone` + `uv sync`；`uv run prometheus serve --host 127.0.0.1 --port 8765`，用独立 `PROMETHEUS_DATA_DIR` 和测试模型 Key。
2. 写一个 ~100 行的 `nexus_mcp_bridge.py`：stdin/stdout 的 JSON-RPC ↔ `POST http://<nexus>/mcp`，带测试 token；在 Prometheus 里作为 stdio MCP server 注册。
3. 建 3 个 `employee.yaml`：manager（只读 + 规划）、test-engineer（`case.list/device.list/case.run/task.get/session.events`）、req-qa（`case.list/task.get`）；工具只给只读 + 受控 `case.run`。
4. 提交一个真实 objective：“登录模块回归，失败归类，给报告”；观察 plan、approval、SSE、verifier、stop。
5. 记录：哪些语义可移植、哪些字段 Nexus 没有、哪些交互 Workbench 必须补、MCP 桥的延迟/错误。
6. 结束即销毁数据；不接客户数据，不把这个实例当产品。

#### 结论

**Prometheus 是目前最接近“任务看得见、卡住能接管、事情能做完”的开源实现，值得作为第一参考，甚至作为单机产品的 fork 基座；但它不是 MinoNexus 可以直接接上的后端。** 对我们的主路线，正确姿势是 **B：移植核心，不搬服务**。

### 3.6 AG-UI：建议直接采用的事件协议

- MIT；约 16 种标准事件；传输无关（SSE / WebSocket / webhook 均可）。
- 覆盖：run 开始/结束、文本流、工具调用开始/参数/结束/结果、状态快照/增量、自定义事件、错误。
- 它解决“agent 怎么把过程讲给 UI 听”，不解决“工作怎么持久化/调度/接管”；后者正是 Work Layer。

**接入方式**：

- 在 `contract/` 增加 `agui.py`：把 `work_events` 映射成 AG-UI 事件。
- 在现有 `/ws` 上增加 `work:{work_id}` 订阅；或加 `/agui` SSE 端点，保留 `/ws` 兼容。
- Workbench 用 `@ag-ui/client`（MIT）或自写 parser；用 Ant Design X 渲染，不引入 CopilotKit 整套 UI。
- 保留 `event_id/seq`，断线重连先发 `STATE_SNAPSHOT`，再发增量。

### 3.7 MCP：已经有，直接作为工具边界

`api/rMcp.py` 已支持 `initialize / tools/list / tools/call`，工具来自 `assistant_tools`，以 token 主人身份经 `run_tool` 执行。这意味着：

- 外部 agent（DS Bot 试点、未来的 IDE/IM）可以用统一工具协议调用 Nexus。
- 不需要为每个外部壳子写一套 REST。
- 但 MCP 只是“一次工具调用”，没有工作状态、审批、重试、完成合同；不能拿它当多 Agent 协作协议。

### 3.8 Temporal / LangGraph：现在不接，但要留接口

**Temporal**

- 成熟、MIT、Python SDK、durable timer、signal（人工审批）、query、重试、版本化、可见性。
- 代价：Go server + 数据库 + worker + 运维；对当前“单机/私有化 + SQLite”的产品形态过重。
- 建议：Work Layer 的 `WorkRunner` 定义成可替换接口；当出现多节点、HA、万级工作流、跨天定时需求时，再把 step handler 包成 Temporal activity，不重写领域工具。

**LangGraph**

- checkpoint / interrupt / time travel 很合适 agent 图，但会引入第二套编排模型；仓库历史上已经移除过 LangGraph/AgentScope/OpenHands，文档也明确不再用。
- `pyproject.toml` 仍保留 `langgraph>=0.2.60,<0.4`、`langchain-core`、`agentscope`，属于遗留依赖，应先清理，避免有人误用。
- 建议：不引入核心；如果某个团队坚持用图 DSL，只能作为 Work Layer 内部的“计划编译器”，不能成为状态真源。

### 3.9 四种接入方式，选 B

**先看适配度**（针对“UI 自动化 + 团队工作区”）：

| 维度 | OpenDots | DeepSeek-Bot | Prometheus（Aethra） | 自建 |
|---|---|---|---|---|
| 运行时 | TS/Node | DSH 插件（Node） | Python/FastAPI | Python/Nexus |
| 任务 / 计划 | 弱（偏对话） | 中（群聊/任务） | **强**（Objective/Plan/Task） | 需建 |
| 审批 / 接管 | **强**（HITL） | 中（ask_user） | **强**（Approval/Stop） | 需建 |
| 验收 / 证据 | 弱 | 弱 | **强**（Verifier/Acceptance/Audit） | 需建 |
| 多用户 / 权限 | 自有 auth | DSH team | **无**（单机 localhost） | Nexus 现有 |
| UI 自动化 | 浏览器/桌面 | 无 | 浏览器/桌面，无移动 | **现有 Scout** |
| 接入成本 | 高（商用依赖） | 中（插件） | **中**（Python/MIT，但需适配） | 高（全建） |
| 推荐用法 | 借 UX | 借协作语义 | **移植核心** | 只建适配层 |

**结论：没有一个项目能直接覆盖“UI 自动化执行层”；Prometheus 最适合做工作层参考，OpenDots 最适合做交互参考，DS Bot 最适合做协作语义参考。**

| 方式 | 做法 | 工期 | 风险 | 建议 |
|---|---|---|---|---|
| **A. 协议接入** | AG-UI 事件 + MCP 工具；不引入对方运行时 | 1–2 周 | 低；只依赖协议 | ✅ 先做 |
| **B. 移植 Prometheus 核心** | 把 `Objective/Task/Plan/Approval/Verifier/EmployeeDefinition` 的模型与运行时模式移植进 `assistant/work/`；存储/LLM/工具/UI 全部换 Nexus 的 | 核心 4–6 周；含适配/UI 的 v1 约 11–13 周 | 中；要改适配层，不能整包复制 | ✅ **主路线** |
| **C. 独立产品 fork** | 把 Prometheus 作为单机版“AI QA 同事”独立产品，保留它的 UI/单用户模型，用 Nexus MCP 做工具后端 | 6–8 周出 MVP | 中高；长期维护 fork；不是团队工作区 | ⚠️ 另立项目，可做 |
| **D. 当 Nexus 生产后端 / 运行时 fork** | 直接跑 Prometheus server，把 Nexus 工具接进去，Workbench 调它的 API | 6–8 周起 | 高；无认证/双库/双前端/依赖冲突 | ❌ 不建议 |

**结论**：**Prometheus 是“最好的参考实现”，不是“可以直接接上的后端”。** 主路线是 B：移植它的领域模型和运行时模式，适配 Nexus 的 `mino.db`、执行账号、`assistant_tools`、Scout、Workbench。这样既复用已经踩过的坑，又不产生第二个大脑。

**例外**：如果目标是单机/个人版“AI QA 同事”，不是 MinoNexus 团队工作区，C 是成立的；但它必须独立产品、独立身份、独立数据、独立前端，不能和 Workbench 共库。

### 3.12 在“允许二开商用”的许可证下，选哪个

先纠正一个常见误解：**MIT 不是“非商业许可”。** MIT 明确允许使用、复制、修改、合并、发布、分发、再许可和**销售**，只要求保留版权与许可声明。Prometheus（Aethra）、AG-UI、OpenDots 都是 MIT，**可以二开、可以商用、可以闭源分发**。如果你要的是“禁止商用”，那不是 MIT，也不适合做产品基础。

在“许可证允许二开商用”的前提下，选型只看架构匹配。**并且执行层不再选型：Scout 已经是唯一的 UI/浏览器/桌面/移动执行层，Nexus 不再引入第二套执行器。**

| 你的首要目标 | 最合适的开源项目 | 它能给你什么 | 它不给你什么 |
|---|---|---|---|
| **任务/计划/审批/验收** | **Prometheus（Aethra，MIT）** | Objective/Task/Plan/Approval/Verifier/Audit/Workflow | 多用户、移动设备执行、HTTP MCP、Workbench |
| **持久执行/HA/长任务** | **Temporal** | durable workflow、signal、timer、retry、visibility | Agent/任务/审批/验收/UI |
| **多 Agent 对话/编排语义** | **AutoGen/AG2、CrewAI、LangGraph** | 角色、图、handoff、checkpoint | 工作项/审批/证据/完成合同 |
| **Agent ↔ UI 事件协议** | **AG-UI（MIT）** | 标准事件、HITL、前端渲染约定 | 任务状态、审批、执行 |
| **Agent ↔ 工具协议** | **MCP（本仓已有）** | 工具发现/调用、权限边界 | 工作层、验收 |
| **工作台交互范式** | **OpenDots（MIT）** | Dots/Spaces、Computer 面板、Approve 卡 | 任务状态、执行、后端 |
| **群聊/交接/记忆语义** | **DeepSeek-Bot（Apache-2.0）** | 长驻 Bot、@交接、独立 session、记忆、checkpoint | 设备执行、Nexus 工作层 |

**明确不纳入 Nexus 的执行类项目**：OpenHands、Browser Use、Stagehand、Midscene.js、UI-TARS、OmniParser、Mobile-Agent、AppAgent、AutoDroid、MaaFramework、Appium 等。它们解决的是“怎么点/怎么看”，而 Scout 已经解决；放到 Nexus 会违反单一执行路径和设备边界。它们最多作为 **Scout 内部实现参考**，不作为 Nexus 依赖。

**综合结论**：

1. **Prometheus 仍是第一**。它的缺口（多用户、设备执行、证据、Workbench）正好是 Nexus 已有的；其他项目的缺口（工作层、审批、验收）是 Nexus 没有的。**选“缺的那块你正好有”的项目，而不是选“看起来更火”的项目。**
2. 如果目标是**多节点/HA/万级长任务**：**Temporal 做执行底座 + 自建工作层**，比 fork 任何 Agent 框架都稳；现阶段不部署。
3. 多 Agent 框架只借**协作语义**（handoff、session、checkpoint），不引入第二套运行时；工作项/审批/验收仍由 Nexus Work Layer 拥有。
4. 如果**完全 greenfield、不管 Nexus/Scout 约束**：**fork Prometheus 单机版最快**；但只要还要 Scout 执行设备，就必须保留 Nexus 的 brain 位置。
5. 许可证不是分水岭：**MIT/Apache-2.0 已足够二开商用；架构缺口是否互补才是。**

**移植原则**：纯领域（dataclass/Protocol）可以靠近原样移植；存储、LLM、工具、HTTP、UI 全部写 Nexus 适配层。不要把 Prometheus 的 SQLAlchemy 模型、FastAPI 路由、Tauri/React 壳搬进来。

**不是 git fork 整个仓库**：vendor 固定 upstream commit 的纯领域子集到 `assistant/work/core/`，加 `THIRD_PARTY_NOTICES`；适配层把上游接口挡住，未来升级只动 `core/` 和适配器，不动业务代码。这样既拿到 MIT 的成熟实现，又不会被 407 个文件绑死。

### 4.3 状态机

**WorkItem**

```
draft → planning → running → waiting_human → running → done
                         ↘ blocked → running
                         ↘ paused → running
                         ↘ failed
                         ↘ cancelled
```

| 状态 | 含义 | 允许的动作 |
|---|---|---|
| `draft` | 刚创建，未生成计划 | 编辑目标、删除 |
| `planning` | 正在生成/修订计划 | 取消、改目标 |
| `running` | 有步骤在执行/等待外部结果 | 暂停、取消、查看 |
| `waiting_human` | 等审批/补充信息/接管 | 批准、拒绝、改指令、接管 |
| `blocked` | 缺资源/重复失败/未知写 | 重试、跳过、改计划、取消 |
| `paused` | 人主动暂停 | 继续、改计划、取消 |
| `done` | 验收通过且有证据 | 查看、导出 |
| `failed` | 不可恢复失败 | 重试、克隆为新工作 |
| `cancelled` | 人取消 | 查看 |

**WorkStep**

```
pending → ready → running → waiting → done
                    ↘ failed → ready（可重试）
                    ↘ unknown（写结果未知）
                    ↘ skipped
                    ↘ cancelled
```

`unknown` 是安全阀：任何“可能已经发生”的写操作，宁可停下对账，不自动重放。

### 4.6 WorkRunner：运行时

**职责**：领取可执行步骤、执行、写事件、checkpoint、处理超时/重试/崩溃恢复。

参考 Prometheus 的 `TaskRunner`（提交/恢复/重试）和 `Runs`（后台任务、取消、刹车）；但 **claim/lease 用我们的 SQLite**，不搬它的 in-process `asyncio` 运行表。

```
loop:
  claim one ready step (BEGIN IMMEDIATE, lease 60s)
  → execute handler in thread (no DB transaction held)
  → heartbeat every 10s (lease renew)
  → on success: write step.done + event, enqueue next
  → on failure: classify, retry or block
  → on shutdown: release lease / mark interrupted
```

**Step handler 类型**：

| kind | 做什么 | 幂等 |
|---|---|---|
| `agent.plan` | 调 `work-plan` job，生成/修订计划 | 是（同输入可重算） |
| `agent.turn` | 调 `work-turn` job，决定下一步/说话 | 是（不产生外部写） |
| `tool.call` | 调 `assistant_tools.run_tool`，如 `case.run` | 用 `idempotency_key` + 工具收据 |
| `rule.call` | 调 `qa_process_assist.run_job`（map_cases/classify_fail） | 是 |
| `run.wait` | 轮询 `run_store`，直到终态/超时 | 是 |
| `human.approval` | 建审批，状态 `waiting_human` | 是 |
| `timer` | 到期再继续 | 是 |
| `artifact.create` | 写报告/引用 | 是 |
| `work.review` | 校验 acceptance + evidence | 是 |

**并发**：

- 同一 WorkItem 内**串行**（一步完成再下一步），避免状态竞态。
- 不同 WorkItem 可并行；全局默认 2–4 个 worker，按项目/用户配额。
- 聊天队列（`collab_message_jobs`）与工作队列分离；聊天不被长任务阻塞。
- 每个 step 捕获 `owner_user_id`，执行时 `execution_user(owner)`，模型 Key 仍按账号隔离。

**崩溃恢复**：

- 启动时扫描 `running` 且 lease 过期的 step：
  - 只读/agent turn：回到 `ready`，最多重试 `max_attempts`。
  - 可能产生外部写的 `tool.call`：查 `run_store` / 工具收据 / `idempotency_key`；能确认已发生→`done` 并补引用；能确认未发生→`ready`；不能确认→`unknown`，建审批让人对账。
- 绝不因为“重启”自动重放 `case.run`。
- 所有恢复动作写 `work_events`，UI 可见。

**为什么不用 Temporal 现在**：

- 当前是单机/私有化 + SQLite，Temporal 的 server/DB/worker 运维成本大于收益。
- WorkRunner 的接口按“可替换”设计；未来把 `claim/execute/heartbeat` 换成 Temporal activity 即可，领域 handler 不变。

### 4.7 接管模型 L0–L4

| 级别 | 能力 | v1 | 说明 |
|---|---|---|---|
| L0 观察 | 看计划、步骤、当前动作、证据 | ✅ | 默认 |
| L1 指令 | 暂停后补充/修改指令，agent 重规划 | ✅ | 不直接改状态 |
| L2 审批 | 批准/拒绝写操作、重试、完成 | ✅ | 所有写默认过审批 |
| L3 接管步骤 | 人直接标记某步完成/失败/跳过，附证据 | ✅ | agent 从下一步继续 |
| L4 接管设备 | 实时看屏/操作设备，再交回 | ❌ 后置 | 需要 Scout 侧支持；先不做承诺 |

接管交互必须回答三个问题：**现在在做什么、为什么停、你有哪些选项。** 不能只给一个“失败”红点。

### 4.8 UI 自动化场景怎么落到 Work Layer

| 场景 | Work Step | 复用的现有能力 |
|---|---|---|
| 单条用例执行 | `tool.call(case.run)` → `run.wait` | `case.run` / `case_runner` / `run_store` |
| 模块回归 | `agent.plan` → `tool.call(case.run)` → `run.wait` | 预检、设备/账号准入、run 卡 |
| 失败归因 | `agent.turn` + `tool.call(session.events/screenshot)` + `rule.call(classify_fail)` | session 证据、失败归类 |
| 覆盖分析 | `rule.call(map_cases)` → `agent.turn` | `qa_process_assist` |
| 测试报告 | `agent.turn(report-writer)` → `artifact.create` | 报告 job、事实包 |
| 设备离线 | `blocked(missing_resource)` → 等上线/取消 | 现有资源检查、排队 |
| 编译未就绪 | `blocked(compile_not_ready)` → 重试/取消 | 编译链、`case.compile_job` |
| 登录/验证码/授权 | `human.approval` 或 `human.takeover_step` | `hitl_executor` 语义、截图 |
| 失败重跑 | `tool.call(case.retry_failed)` + 审批 | 安全复跑资格、原执行单元 |
| 多平台（Web/移动/PC） | 同上；平台差异在 Scout/工具内部 | 三端统一执行链 |

要点：

- **Work Layer 不感知平台**；平台差异留在 Scout/能力目录。
- **长等待用 `run.wait` + `timer`**，不占用 LLM 线程。
- **失败先取证再归类**，不让模型凭印象判断。
- **人接管优先复用 `hitl_executor` 的语义**，但工作层的接管是“步骤级”的，不是单次工具调用。
- **写操作的安全规则沿用现有执行链**：未知写不重放、原执行单元重试、设备/账号租约。

| `GET` | `/work/{work_id}` | 详情：计划、步骤、当前动作、产出、审批 |
| `GET` | `/work/{work_id}/events?after_seq=` | 事件增量（AG-UI 重放） |
| `POST` | `/work/{work_id}/pause` | 暂停（步骤边界） |
| `POST` | `/work/{work_id}/resume` | 继续 |
| `POST` | `/work/{work_id}/cancel` | 取消（含 run 取消/资源释放） |
| `POST` | `/work/{work_id}/plan` | 修改剩余计划（版本化） |
| `POST` | `/work/{work_id}/steps/{step_id}/retry` | 重试当前步 |
| `POST` | `/work/{work_id}/steps/{step_id}/skip` | 跳过当前步 |
| `POST` | `/work/{work_id}/steps/{step_id}/takeover` | 接管完成/失败，附证据 |
| `POST` | `/work/{work_id}/approvals/{approval_id}` | 批准/拒绝/选择 |
| `GET` | `/work/{work_id}/artifacts` | 报告/证据列表 |

规则：

- 所有写接口校验项目成员/维护者、owner、工作状态；跨项目拒绝。
- 写接口带 `client_request_id` / `Idempotency-Key`，重复请求返回原结果。
- 事件接口支持 `after_seq` 与 `snapshot=1`；断线重连不丢事件。
- 不用 `collab_messages` 的状态字段表达工作状态；工作状态只读 `work_items/work_steps`。
- 形状可参考 Prometheus 的 `/api/tasks`、`/api/approvals`、`/api/events`（SSE）；但身份、项目、执行账号一律用 Nexus 的，**不要复用它的 localhost 无认证模型**。

### 4.10 部署拓扑：本机、Nexus、Scout 到底谁在哪

先把三个角色分开：

| 角色 | 职责 | 不应该做什么 |
|---|---|---|
| **MinoWorkbench** | 人看工作、批审批、接管、看证据 | 不直接碰设备/不存业务状态 |
| **MinoNexus** | 工作层、计划、状态、审批、验收、模型 Key、审计 | 不 import 设备库、不直接 adb/playwright |
| **MinoScout** | 设备/桌面执行、截图、session 上报 | 不做计划、不存工作状态、不接第二套审批 |

“放到本机”有四种含义，答案不同：

| 场景 | 工作层放哪 | 执行放哪 | 结论 |
|---|---|---|---|
| **A. Nexus 部署在用户本机**（local-first） | Nexus（本机进程） | Scout（本机或远端） | ✅ 仍然走 Nexus 逻辑；只是部署位置在本机 |
| **B. 被测对象是本机 PC/桌面/浏览器** | Nexus（服务端或本机） | 本机的 Scout/桌面执行器 | ✅ 规划/状态仍在 Nexus；设备侧在 Scout |
| **C. 把整个 Agent Runtime 放到 Scout 上** | Scout | Scout | ❌ Scout 变成第二个大脑；破坏单一执行路径、多节点、证据、权限 |
| **D. 单机独立产品（Prometheus 路线）** | Prometheus 自己的 DB/进程 | Prometheus 自己的 browser/desktop | ⚠️ 可以，但这是另一个产品，不是 MinoNexus |

**推荐拓扑**：

```
团队/云端：
Workbench（浏览器） → Nexus（Work Layer + DB + Auth） → Scout 节点 → 设备/浏览器/PC

本机 local-first：
Workbench + Nexus + Scout 同机（localhost），边界不变

单机独立产品（可选）：
Prometheus（planner + runtime + UI + DB） → MCP → Nexus/Scout（可选）
```

**一条规则**：**“本机”只改变进程部署位置，不改变状态归属。** 只要产品还是 MinoNexus，Nexus 就是 brain，Scout 就是 hands；把 brain 放到 Scout 上，等于把多节点/多用户/证据链一起放弃。

如果只是想把**工具**放本机：MCP server 可以在本机，但 MCP 只解决“怎么调工具”，不解决“谁规划、谁批、谁验收”。不要用 MCP 代替 Work Layer。

如果只是想让**被测 PC/桌面**被自动化，正确做法是给 Scout 增加桌面执行能力（或在被测机跑一个 Scout 执行器），不是把工作层搬过去。如果 Scout 目前只覆盖 Android，本机 PC 自动化需要在 Scout 侧新增执行器；**不能在 Nexus 里 import playwright/pyautogui**。v1 仍建议只做设备/浏览器，L4 桌面远控后置。

## 5. 多 Agent 协作语义

### 5.1 三类角色，不要混

| 类型 | 例子 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **Manager** | conductor | 规划、委派、监控、汇总、请求审批 | 不直接做设备细节；不绕过写预算 |
| **Specialist** | req-qa-bm、version-qa-bm、test-engineer、report-writer、product-expert、knowledge-reviewer | 在自己的职责内查事实、调受限工具、产出结论/证据 | 不自由对话其他 specialist；不越权写 |
| **Executor** | `agent-decide`、`agent-vision-*`、`case-step-compile`、`inspect-*` | 设备循环内的决策/观察 | 不是“同事”，不进入群聊、不接工作 |

关键判断：**不是所有角色都变成 agent。** 设备执行/视觉判断仍然是 `loop/` 的内部 prompt；把它们拉进群聊只会增加成本和不确定性。

### 5.2 Handoff 合同

Manager 委派 Specialist 时，不传一段自由文本，而是一个结构化信封：

```json
{
  "work_id": "w_...",
  "step_id": "s_...",
  "from": "conductor",
  "to": "req-qa-bm",
  "goal": "分析登录模块的测试点覆盖缺口",
  "context": {
    "project_id": "p_...",
    "topic_id": "t_...",
    "case_ids": ["c1", "c2"],
    "run_ids": ["r_..."],
    "facts_digest": "..."
  },
  "constraints": {
    "read_only": true,
    "max_steps": 4,
    "deadline": "2026-10-22T12:00:00Z",
    "write_budget": 0
  },
  "expected_output": {
    "schema": "coverage_result_v1",
    "evidence_required": true
  },
  "prior_results": []
}
```

返回：

```json
{
  "status": "ok | needs_input | blocked | failed",
  "summary": "2-5 句结论",
  "artifacts": [{"kind": "coverage", "ref": "..."}],
  "evidence": [{"kind": "run", "ref": "r_..."}],
  "next": ["建议 manager 下一步"],
  "needs": ["缺什么"]
}
```

规则：

- 返回必须符合 schema；不符合让模型修复一次，仍不符合则 `blocked`，不把自由文本当结果。
- `needs_input` 必须列出缺项和真实可选项；不能只说“请补充”。
- Specialist 的结果进入 `work_artifacts`，不是只发一条聊天消息。
- Manager 看到的是结构化结果 + 有界摘要，不是整段对话。

### 5.3 Session 与 Memory

**Session**

- 粒度：`(project_id, topic_id, agent_id)` 一个持久会话；`work_id` 作为当前工作上下文。
- 存什么：滚动摘要、最近关键轮次、当前工作引用、模型/prompt 版本。
- 不存什么：完整聊天记录（消息仍在 `collab_messages`）、原始大 JSON（放 artifact/ref）。
- 生命周期：项目/话题删除时归档；工作结束不删除 session，下一次继续用。

**Memory 三档**（对齐 DS Bot 的 Bot/群/团队，映射到我们的域）：

| scope | 例子 | 谁写 | 谁读 |
|---|---|---|---|
| `agent` | “报告先给结论，再给证据” | 该 agent / 人 | 该 agent |
| `project` | “登录模块的测试账号在账号池 A” | manager / 人审批 | 项目内 agent |
| `topic` | “本次回归只看 P0” | manager / 人 | 当前工作区 |
| `work` | “这次已确认跳过 2 条环境失败” | 当前工作 | 当前工作，结束即归档 |

规则：

- 记忆是数据，不是指令；不能因为网页/用例文本里写了“记住 X”就写记忆。
- 密钥、token、身份证号等敏感信息拒绝写入。
- 全局/项目记忆写入需要人审批；`work` 级可自动。
- 注入 prompt 时有字符上限（建议 2000–3000 字），按相关度取 top-k，不整库塞入。
- 记忆带 `source` 和 `created_at`，可查、可删、可过期。

### 5.4 写预算与审批

| 动作 | 默认 | 说明 |
|---|---|---|
| 只读工具（case.list/task.get/session.events） | 自动 | 不需要审批 |
| `case.run` / `case.retry_failed` | 需要审批或计划已批准 | 一个 WorkItem 默认 1 次执行；重跑需要明确批准 |
| `collab.scope_update` / `pin_cases` | 自动（计划内） | 非执行写，仍记事件 |
| 记忆写项目级 | 需要审批 | 防止污染 |
| 完成 `done` | 需要 review 通过 | 证据不足则 blocked |

写预算放在 WorkItem 上：`max_runs`、`max_retries`、`max_tokens`、`max_wall_clock`。默认值建议：

- `max_runs=1`（一个工作一次正式执行；重跑是显式新步骤）
- `max_retries_per_step=2`（只对安全失败）
- `max_steps=12`
- `max_tokens=200k`（按项目配置）
- `max_wall_clock=2h`（长回归可配）

预算耗尽 → `blocked`，给出“继续需要批准”的选项；不静默加预算。

### 5.5 完成合同

每个 WorkItem 的 `acceptance` 是计划的一部分，例如：

```json
[
  {"id": "a1", "text": "登录模块 P0 用例全部执行", "evidence": "run"},
  {"id": "a2", "text": "失败用例有归类与原因", "evidence": "artifact"},
  {"id": "a3", "text": "输出测试报告", "evidence": "artifact"},
  {"id": "a4", "text": "未执行/阻塞项已列出", "evidence": "note"}
]
```

`work.review` 步骤：

1. 读 `run_store`、`session_events`、`work_artifacts`；
2. 逐条检查 acceptance 是否有证据；
3. 全部满足 → `done`；否则 `blocked`，列出缺哪条、缺什么证据、可选下一步。

禁止：模型在 `reply` 里说“已完成”就直接 `done`；`run_store.status=done` 不等于验收通过；报告存在不等于报告有证据。

### 5.6 协作拓扑

- **星形**：用户 → Manager → Specialist → Manager → 用户。Specialist 之间不直接对话。
- **深度 ≤ 2**：Manager 可以委派 Specialist；Specialist 不再委派另一个 Specialist（v1）。需要链式时，由 Manager 分步。
- **并发**：同一 WorkItem 串行；不同 WorkItem 可并行；每个用户/项目有并发上限。
- **群聊**：保留现有工作区群聊，用于人和 agent 的协作；群聊消息可以创建 WorkItem，但群聊本身不是执行状态机。
- **@ 提及**：`@测试工程师` 等价于一次 `work.delegate`；成员回复署名仍由后端计算。

## 6. Prompt / 角色 / Job 怎么处理

### 6.1 先把概念分开

现在 `role` 和 `job` 都把“身份、提示词、引擎、输出、工具”混在一起。建议明确：

| 概念 | 定义 | 存在哪 |
|---|---|---|
| **Role** | 是谁：身份、边界、默认工具、记忆范围、可委派对象 | `prompts/roles/*.yaml` |
| **Job** | 能做什么：一次可调用能力的输入/输出合同、引擎、预算 | `prompts/jobs/*/job.yaml` |
| **Step** | 这次做什么：WorkItem 里的一个执行实例，绑定 role+job+输入 | `work_steps` |
| **Skill** | 怎么做：可复用的方法/检查清单/模板 | `prompts/skills/*.yaml` |
| **Work** | 为什么做：目标、验收、预算、状态 | `work_items` |

一句话：**Role 回答“谁”，Job 回答“做什么”，Step 回答“这次做哪一步”，Work 回答“为什么、做到什么算完”。**

### 6.2 现在的问题

先明确：**现有 prompt 不是“工作层 prompt”，而是“一次 run 内部的角色提示”。** 这不是把 prompt 写得更长能解决的；错的是层级，不是字数。

1. **角色 = 一次性问答**：`chat_with_role` 取一个 job 的 prompt + 历史，调一次模型；没有 session、没有工具循环（除非声明了 `tools`）。
2. **job 没有输入/输出合同**：`output_schema` 只是字符串，运行时不校验；成员返回自由文本也能结束。
3. **prompt 混了策略与状态**：`workspace-route/system/20-rules.md` 很长，既有权限、范围、写次数，又有业务话术；状态变化就要改 prompt。
4. **工具白名单是角色级的，不是步骤级的**：成员只要在 `tools` 里，就能在任意步骤调用；没有“这一步只能读”的约束。
5. **没有长期记忆**：`collab_topics.memory` 字段存在，但工作区代码没有读写路径；每条消息重新拼 facts。
6. **单轮上限**：`MAX_STEPS=8`、`total_timeout_sec=300`、成员 5 步；长任务只能靠 run 卡。
7. **写次数按消息算**：`state['wrote']` 一条消息一次；跨消息/跨步骤没有统一预算。
8. **成员分配是一次调用**：`member.assign` 没有 handoff 合同、没有 specialist session、没有结果 artifact。

### 6.3 18 个角色怎么处置

| 角色 | 类型 | 进工作区？ | Work Layer 中的定位 | 处理 |
|---|---|---|---|---|
| `conductor` | Manager | 是（固定） | Manager：规划、委派、汇总、审批 | 保留；重写 prompt 为 manager；新增 `work-plan/work-turn` 绑定 |
| `req-qa-bm` | Specialist（分析） | 是 | 覆盖分析、失败归类 | 保留；`map_cases/classify_fail` 作为 rule step |
| `version-qa-bm` | Specialist（分析） | 是 | 回归选择、准入判断、失败归类 | 保留；`pick_regression/draft_gate` 作为 rule step |
| `test-engineer` | Specialist（执行） | 是 | 发起 run、看证据、判断失败 | 保留；工具收窄到 case/device/task/session |
| `product-expert` | Specialist（顾问） | 是 | 需求/产品判断，只读 | 保留；禁止写工具 |
| `knowledge-reviewer` | Specialist（顾问） | 是 | 知识/文档审阅，只读 | 保留；禁止写工具 |
| `report-writer` | Specialist（报告） | 是 | 基于事实产出报告 artifact | 保留；必须引用事实，不能编数字 |
| `im-qa-assistant` | Specialist（IM） | 否（IM 表面） | 后续复用 agent core | 保留；先不动 IM 路径 |
| `im-defect-assistant` | Specialist（IM） | 否（IM 表面） | 后续复用 agent core | 保留；先不动 IM 路径 |
| `req-analyst` | Producer | 否 | 一次性需求分析 job | 保留为 job；需要时可作为 step |
| `mindmap-writer` | Producer | 否 | 一次性脑图 job | 保留为 job |
| `case-writer` | Producer | 否 | 一次性用例草稿 job | 保留为 job |
| `doc-keeper` | Producer | 否 | 文档整理 job | 保留为 job |
| `propose_atlas` | Producer | 否 | 导航图建议 job | 保留为 job |
| `agent-decide` | Executor | 否 | 设备循环决策 | 保留在 `loop/`；不接工作区 |
| `agent-vision-assert` | Executor | 否 | 视觉断言 | 保留在 `loop/` |
| `agent-vision-exec` | Executor | 否 | 视觉执行 | 保留在 `loop/` |
| `agent-vision-plan` | Executor | 否 | 视觉规划 | 保留在 `loop/` |

原则：**角色文件不删、不批量改名。** 先加元数据、分表面、收工具；等新路径稳定后再标 deprecated。

**Prometheus 的 `employee.yaml` 是最合适的模板**。我们的 role YAML 已经有 `tools` / `jobs` / `chat_jobs`，把它扩成下面这样即可，不需要新角色格式：

```yaml
# prompts/roles/test-engineer.yaml（增量）
name: test-engineer
role: 测试工程师
role_description: 在设备上执行用例，读证据，判断失败。
allowed_tools:            # 对应现有 tools
  - case.list
  - device.list
  - case.run
  - case.retry_failed
  - task.list
  - task.get
  - session.list
  - session.events
capabilities: [TEST_EXECUTION, EVIDENCE_READ]
policies: [no_delete, no_sending]
limits: {max_steps: 8, max_cost_usd: 0.80, max_wall_time_seconds: 900}
memory_scope: project
contract:
  accepts: [REGRESSION_REQUEST, FAILURE_QUESTION]
  produces: [RUN_RESULT, FAILURE_CLASSIFICATION]
  evidence: [RUN, SESSION]
```

映射规则：

- `tools` → `allowed_tools`（只保留 Nexus 工具名；设备/视觉内部 job 不放进来）。
- `kind: conversational|json` → `agent.kind: specialist|manager|executor`。
- `chat_jobs` → `surface: chat` 的 job；不进工作层。
- `jobs` 里的规则 job → `rule.call` step；设备 job 留在 `loop/`。
- 新增 `limits` / `contract` / `memory_scope` / `policies`，缺省不报错；有声明才校验。

### 6.4 38 个 job 怎么处置

按“表面（surface）”分五类：

| 类别 | job | 处理 |
|---|---|---|
| **Chat/Agent**（10） | `conductor`, `test-engineer-chat`, `req-qa-bm`, `version-qa-bm`, `product-expert`, `knowledge-reviewer`, `im-dialogue`, `im-defect`, `report-writer`, `draft_test_report` | 保留；标 `surface: chat`；工作层的 `work-turn` 通过 `job_id` 复用其 system prompt，不直接复用其单次聊天引擎 |
| **Rule**（5） | `map_cases`, `classify_fail`, `pick_regression`, `draft_sign`, `draft_gate` | 保留；标 `surface: work`、`engine: rule`；由 `rule.call` step 调用 |
| **Device/Vision/Observe**（15） | `agent-decide`, `agent-text-assert`, `agent-vision-assert/exec/plan`, `assert-vision`, `case-step-compile`, `inspect-checkbox-state`, `inspect-login-consent-scope`, `inspect-session`, `account-facet-commit/schema`, `nav-atlas-morph`, `nav-widget-state`, `app-intel-ask` | 保留；标 `surface: internal`；不进工作区、不可从聊天调用 |
| **Content/Knowledge**（8） | `analyze_req`, `draft_cases`, `draft_mindmap`, `propose_atlas`, `doc-keeper`, `doc-learn`, `knowledge-extract`, `knowledge-extract-batch` | 保留；标 `surface: job`；可作为一次性 step，不默认进群 |
| **新增 Work**（4） | `work-intent`, `work-plan`, `work-turn`, `work-review` | 新增；严格 schema；`surface: work` |

> 数量说明：现有 `prompts/jobs/*/job.yaml` 共 38 个；新增 4 个后 42 个。`workspace-route` 是 assistant job（不在 `prompts/jobs/` 下），单独处理。

**具体规则**：

- `conductor` job：保留给边缘路由/`qa_tick`；新工作层用 `work-plan/work-turn`，不把它改成万能 prompt。
- `workspace-route`：保留给“简单问答/单步操作”；多步/长任务走 `work-intent` → WorkItem。不要让它继续承担计划与执行。
- 规则 job：只读或确定性计算；不产生设备写；输入由代码取，模型只解释结果。
- 设备 job：不暴露给工作区；工作层通过 `case.run` 工具发起，不直接调 `agent-vision-exec`。
- 内容 job：保留现有入口；需要时由工作层作为 `agent.turn` 的一个 job 调用，输出 artifact。

### 6.5 新增 4 个 job 与 schema

下面的 YAML 只列**关键字段**，不是可直接启动的完整文件；实际要按现有 `job.yaml` 格式补齐 `system` 块、slot heading 等，启动时 `startup_health` 会校验渲染。

这四个 job 与 Prometheus 的 `IntentReader` / `ObjectivePlanner` / `EmployeeRuntime` / `Verifier` 一一对应；prompt 可以借鉴它的 `prompts/`，但 schema、工具白名单、证据字段必须用 Nexus 的。

#### `work-intent`（可选，轻量分类）

```yaml
id: work-intent
label: 判断是问答还是工作
engine: json_chat
```

### 6.6 Prompt 文件改造

**拆分原则**：稳定策略进文件，动态状态进 slot；代码校验优先于 prompt 叮嘱。

建议目录：

```
prompts/assistant/jobs/work-plan/
  job.yaml
  system/00-role.md          # 你是谁：manager
  system/10-planning.md      # 怎么拆步、什么算好计划
  system/20-schema.md        # 输出 schema 与禁止项
prompts/assistant/jobs/work-turn/
  job.yaml
  system/00-role.md
  system/10-execution.md     # 工具/委派/停止规则
  system/20-handoff.md       # 交接合同
prompts/assistant/jobs/work-review/
  job.yaml
  system/00-role.md
  system/10-acceptance.md
```

**放在 `prompts/assistant/jobs/` 而不是 `prompts/jobs/`**：work-* 要复用 assistant 的工具渲染、`openai_tools` 和成员/范围校验；两处同名会覆盖。建议启动时增加“job id 重复”校验，避免静默覆盖。

**现有 `workspace-route` 的处理**：

- 保留，作为“聊天/单步”入口；`20-rules.md` 只留聊天规则（事实、范围、语气、拒绝编造）。
- 把“计划、委派、写预算、完成校验”移出 prompt，进 Work Layer 代码与 work-* job。
- `30-member.md` 保留给旧成员循环；新工作层用 `20-handoff.md`，两者并存一个版本周期。

**Role YAML 增量**（向后兼容，缺省不报错）：

```yaml
agent:
  kind: manager | specialist | executor
  model: inherit
  max_steps: 6
  write_budget: 1
  memory: [agent, project, topic]
  can_delegate: [req-qa-bm, version-qa-bm, test-engineer, report-writer]
  handoff_schema: work_handoff_v1
  surfaces: [workspace, work]
```

**Job YAML 增量**：

```yaml
surface: chat | work | internal | job
input_schema: work_step_input_v1
output_schema: work_plan_v1
idempotent: true
budget: {max_tokens: 2000, timeout_sec: 60}
```

**校验**：

- 启动时 `startup_health` 已校验每个 job 能渲染；新增 schema 校验（JSON Schema 或 Pydantic）。
- 计划/动作输出不合法：让模型修复 1 次；仍不合法 → `blocked`，不执行。
- `prompt_version` / `agent_version` 写入 `work_steps`，便于回放“当时用的哪版提示词”。

### 6.7 兼容与迁移顺序

| 阶段 | 动作 | 兼容性 |
|---|---|---|
| P0 | 只加 `agent`/`surface` 元数据，加载器缺省兼容 | 旧 YAML 不改也能跑 |
| P1 | 新增 `work-*` job；`workspace-route` 保留；Work Layer 开关默认关 | 旧工作区行为不变 |
| P2 | 新工作流默认走 Work Layer；`member.assign` 保留为 `work.delegate` 别名 | 旧对话可继续 |
| P3 | 旧成员循环标 `legacy`，只读保留；提示词资产不删 | 可回滚 |

不要在 P1 就删 `chat_with_role`、`member_loop`、`workspace-route`；它们是回滚面。

### 6.8 不要做的事

- 不要为每个新任务新建一个角色；先加 job 或 skill。
- 不要把任务状态写进 prompt；状态放 `work_state` slot。
- 不要让角色自由调用所有工具；工具白名单 + step 级允许集合。
- 不要为每个 agent 建任务表；一个 WorkItem 一个事件流。
- 不要把聊天记录当状态；聊天是投影，状态在 `work_events`。
- 不要让模型自己宣布 `done`；完成校验在代码。
- 不要把 `run_store` 的状态复制进 `work_steps`；只存 `run_id` 并实时读。

### 6.9 为什么现有 prompt 撑不起这套逻辑

**你的判断是对的。** 现有 prompt 解决的是“一次 run 中间，哪个角色、看什么、怎么决策/断言”，不是“一件工作从提出到验收”的合同。

| 现有 prompt | 它实际负责 | 它看不到 / 管不了 |
|---|---|---|
| `workspace-route` | 聊天路由、facts、成员委派、自动化 | 没有 WorkItem/计划/验收；只有单轮；无 step 状态 |
| `conductor`（role/job） | 抽象调度、这一步该调谁 | 没有目标/验收；不持久；不拥有工作 |
| `test-engineer-chat` / `req-qa-bm` / `version-qa-bm` | 单次问答、分析、归类 | 没有 session/step 预算/证据校验；返回自由文本 |
| `report-writer` / `draft_test_report` | 基于给定事实写报告 | 不验证事实是否发生；不拥有 acceptance |
| `agent-decide` / `agent-vision-*` | run 内设备循环的决策/视觉断言 | 不跨 run；不管审批/接管/工作状态 |
| `case-step-compile` / `inspect-*` | 编译/观察/检查 | 不参与工作状态机；不是“同事” |

#### 三个错位

1. **目标错位**：prompt 只有 `utterance`、`workspace_facts`、`recent_turns`；没有 `goal`、`acceptance`、`plan`、`current_step`。
2. **状态错位**：每条消息重新拼 facts；没有 `work_id`、`step_id`、`prior_results`、`budget`、`approval_state`，所以模型不知道“现在第几步、还剩多少预算、上一步发生了什么”。
3. **权责错位**：prompt 里写“不要重复执行”“必须给证据”“完成前要确认”，但模型可以违反；没有代码强制，也没有持久对象记录。

#### 再加一段 prompt 不会解决

- 模型说 `done` ≠ 完成；需要 `acceptance` + 证据校验。
- 模型说 `paused` ≠ 暂停；需要状态机 + pause API + step 边界。
- 模型说“已委派” ≠ handoff；需要持久 `work_step` + specialist session + 结果 artifact。
- 模型说“没有重复跑” ≠ 幂等；需要 `idempotency_key` + 收据 + `unknown` 状态。

#### 四层模型：Prompt 只做判断与表达

| 层 | 谁拥有 | 内容 | 变化频率 |
|---|---|---|---|
| **1. Work contract（代码）** | `work_items/work_steps` + 校验器 | 目标、验收、预算、权限、状态机、证据、幂等 | 稳定 |
| **2. Work-level prompt** | `work-plan` / `work-turn` / `work-review` / `handoff` | 计划、当前步决策、验收建议、交接信封 | 中 |
| **3. Role prompt** | 现有 18 个角色 | 领域身份、判断口径、话术、工具偏好 | 低 |
| **4. Run-internal prompt** | `agent-decide` / `agent-vision-*` / `case-step-compile` | 设备循环内的决策/观察 | 低 |

**不是用第 2 层替代第 3/4 层，而是把第 3/4 层包进第 1/2 层的工作信封里。** 角色 prompt 仍然负责“测试工程师怎么判断登录失败”，但它不再负责“这件工作做到哪、能不能算完、谁能批”。

#### `work-turn` 应该看到什么

```json
{
  "goal": "登录模块回归，失败归类，给报告",
  "acceptance": [
    {"id": "a1", "text": "P0 用例执行完成", "evidence": "run"},
    {"id": "a2", "text": "失败有归类", "evidence": "artifact"}
  ],
  "current_step": {"seq": 2, "kind": "tool.call", "intent": "执行回归"},
  "prior_results": [
    {"step": 1, "status": "done", "summary": "范围已确认：P0 共 12 条"}
  ],
  "available_tools": ["case.list", "device.list", "case.run", "task.get", "session.events"],
  "budget": {"steps_left": 4, "runs_left": 1, "tokens_left": 120000},
  "approval_state": "none",
  "memory": "本项目登录模块使用账号池 A；环境失败不重跑",
  "constraints": "只读优先；写操作需审批；不得跨项目"
}
```

输出只允许一个动作：

```json
{
  "action": "tool | delegate | reply | request_input | complete",
  "tool": "case.run",
  "args": {},
  "text": "",
  "evidence": []
}
```

#### 三个目标分别靠什么

| 目标 | 靠什么 | Prompt 的角色 |
|---|---|---|
| **任务看得见** | `work_events` + `work_steps` + UI 时间线 | 产出计划/步骤意图，不负责“可见” |
| **卡住能接管** | pause/resume/approve/takeover API + step 边界 | 只负责提出“需要人决定什么” |
| **事情能做完** | `acceptance` + evidence validator + `work-review` | 只给建议 verdict；最终判定在代码 |

#### 改造顺序

1. **P0**：只加 `surface`/`agent` 元数据；现有 prompt 不动，先让加载器兼容。
2. **P1**：新增 `work-plan/work-turn/work-review`；拆 `workspace-route`，只留聊天规则；把写预算/范围/完成校验移进代码。
3. **P2**：角色 prompt 作为 step 的第 3 层复用；旧 `member_loop` 标 legacy；不删 18 个角色/38 个 job。
4. **P3**：按数据决定是否合并/淘汰旧 job；不在没有证据前删资产。

#### 反模式

- 一个巨型 prompt 同时做路由、计划、执行、验收。
- 让模型自己宣布 `done`。
- 让模型自己决定权限/预算。
- 把状态塞进 prompt 文本，而不是 `work_steps`。
- 把角色 prompt 直接当工作层 prompt。
- 用自由文本当 handoff 结果。

## 7. UI / 交互

### 7.1 信息架构

保持 Workbench 唯一前端，不新增产品。建议在现有 Bots/工作区页面内加“工作”视图：

```
项目
└─ Bots / 工作区
   ├─ 左栏：对话列表（现有）
   ├─ 中栏：聊天（现有）+ 工作卡（新）
   └─ 右栏抽屉：
       ├─ 成员（现有）
       ├─ 测试目标（现有）
       ├─ 工作（新）：列表 + 详情
       └─ 运行/证据（现有任务页）
```

也可以把“工作”做成独立 tab，但不要做成第二个应用、不要做拖拽看板。

### 7.2 工作列表

字段：

- 标题、目标一句话
- 状态 chip：计划中 / 执行中 / 等你决定 / 阻塞 / 暂停 / 已完成 / 失败
- 进度：已完成步骤 / 总步骤；当前步骤名
- 负责 agent 头像/名字
- 开始时间、最近活动
- 阻塞原因（如有）
- 成本（tokens）可选

排序：等你决定 > 执行中 > 阻塞 > 最近完成。

### 7.3 工作详情

从上到下：

1. **Header**：标题、状态、目标、验收标准（可折叠）、预算使用。
2. **计划**：步骤列表，每步显示序号、类型、agent、意图、状态、耗时；可展开看输入/输出摘要。
3. **当前动作**：正在调用的工具/正在跑的 run/正在等的审批；实时更新；附 run 卡和证据链接。
4. **时间线**：事件流（创建、计划、每步开始/结束、审批、接管、完成），默认折叠技术细节。
5. **产出**：报告、截图、run/session 链接。
6. **控制**：暂停/继续、改指令、改计划、重试、跳过、接管、取消。
7. **审计**：谁在何时做了什么（接管/审批/修改）。

### 7.4 接管交互

| 场景 | 交互 |
|---|---|
| 执行中 | “暂停”按钮；暂停后显示“已暂停在步骤 N，未提交的写操作不会发生” |
| 等你决定 | 顶部大卡：“需要你决定：是否重跑 3 条环境类失败？[批准] [拒绝] [只分析]” |
| 阻塞 | 显示原因 + 选项：“设备离线，已排队；上线后自动开始 / 取消” |
| 改指令 | 文本框 + “保存并重新规划”；只影响未完成步骤 |
| 接管步骤 | “我来完成这一步” → 填结果/附证据/标记完成或失败 → 从下一步继续 |
| 未知写 | 黄色警告：“上一步可能已提交，不能自动重试”；[已执行，继续] [未执行，重试] [查看 run] |
| 取消 | 二次确认；取消 run + 释放资源；工作保留为 cancelled |

原则：**任何“危险/不可逆”的动作都要明确说明后果，并留下审计。** 不要用“智能重试”掩盖未知写。

### 7.5 聊天与工作的关系

- 一条用户消息可以创建一个 WorkItem；聊天里出现一张工作卡（不是把计划塞进消息正文）。
- 工作有独立详情；聊天继续用于追问、补充、接管指令。
- 工作的事件可以回写成聊天消息（重要节点），但聊天消息不是状态真源。
- `@成员`：等价于一次委派；如果只是问一句，仍走聊天，不建工作项。
- 现有 run 卡保留；工作卡与 run 卡通过 `work_links` 关联，不重复展示同一 run。

### 7.6 不做的 UI

- 不做节点图/流程图编辑器（v1）。
- 不做拖拽看板、工时、排期。
- 不默认展示原始 JSON / 全量日志；提供“查看详情”入口。
- 不做第二个前端、不做 OpenDots 外壳、不做手机端新 App。
- 不把预算、重试次数、设备 SN 等配置塞进主界面；放设置/高级。

## 8. 分期与里程碑

### Phase 0：参考验证 + 地基 + 可演示切片（3 周）

**目标**：先用 Prometheus 验证交互，再把工作层骨架落进 Nexus；不追求多 agent。

| 工作 | 产出 |
|---|---|
| **Prometheus spike（第 1 周）** | 只跑 `prometheus serve` 的 Web/API；stdio↔HTTP MCP 桥接 Nexus `/mcp`；3 个 employee；跑一次真实回归；记录“哪些语义值得移植、哪些不能” |
| 迁移机制 | `schema_contract` 增加只增不减的迁移注册（建议用 `PRAGMA user_version` + 迁移列表，只 `CREATE TABLE/INDEX`，不删不改列）；`work_*` 表可安全加到老库 |
| 核心移植 | `assistant/work/core/`：Objective/Task/Plan/Approval/Verifier/EmployeeDefinition 的纯领域模型（先不接完整执行） |
| 数据模型 | `work_items/steps/events/approvals/links` + ORM + 索引 |
| WorkRunner | claim/lease/heartbeat/execute/事件；崩溃恢复；参考 `TaskRunner`/`Runs` |
| AG-UI 映射 | `contract/agui.py` + `/ws` 订阅 + 断线重放 |
| 最小 UI | 工作列表 + 详情时间线 + 暂停/继续 |
| 单任务 | “登录模块回归”：plan → case.run → run.wait → 完成 |

**退出标准**：

- 真实设备跑一个回归；页面能看到计划、步骤、当前 run、结果。
- 暂停后恢复不重复提交 run；重启后步骤不丢、不重放。
- 老库升级可启动；旧工作区聊天不受影响。

### Phase 1：v0.5 垂直闭环（4 周）

**场景**：“把登录模块回归一下，失败的看下原因，给我报告。”

| 工作 | 产出 |
|---|---|
| Manager/Specialist | conductor + req-qa-bm + test-engineer + report-writer 接入工作层；employee 声明式权限 |
| 计划/执行/复核 | `work-plan/work-turn/work-review` + schema 校验；对齐 Prometheus `ObjectivePlanner`/`EmployeeRuntime`/`Verifier` |
| 完成校验 | `Verifier` + `acceptance`：记录到的成功工具/证据，不以模型自述为准 |
| 审批 | 执行前批准、失败重跑批准、完成验收 |
| 接管 | 暂停、改指令、重试、跳过、接管完成 |
| 报告 | 基于 `run_store/session_events` 的报告 artifact |
| UI | 工作列表、详情、审批卡、接管面板、证据链接 |

**退出标准**：

- 5 个真实工作项端到端完成；每个都有 acceptance + evidence。
- 失败场景能归类并给出选项；不把失败说成通过。
- 一条消息最多一次 `case.run`；崩溃/重启 0 重复执行。

### Phase 2：v1 多 Agent（6 周）

| 工作 | 产出 |
|---|---|
| Handoff | 信封 schema、深度/次数限制、结果 artifact |
| Session/Memory | 三档记忆、注入上限、审批、审计；参考 Prometheus memory provenance + thread brief |
| Workflow | 参考 `WorkflowEngine`：YAML 步骤/依赖/重试/预算；先只读接入，不替换现有 automation |
| 多 Agent | 5 个 specialist、并发、配额、成本 |
| 接管 L3 | 接管步骤、改计划、跳过/重试 |
| 自动化 | 定时/触发创建 WorkItem（复用现有 automation） |
| 观测 | 工作指标、dispatch 关联、成本面板 |

**退出标准**：

- 3 类工作（回归/覆盖/失败分析）、6 个 agent（1 manager + 5 specialist）稳定运行 2 周。
- 接管率、阻塞时长、完成率可统计。
- 单工作成本可上限；超预算会停。

### Phase 3：生产硬化（6 周）

| 工作 | 产出 |
|---|---|
| 可靠性 | 故障注入、lease 竞争、断线重连、数据库锁 |
| 规模 | 并发/队列/公平性、长工作（小时级） |
| 安全 | prompt injection、权限审计、记忆隔离 |
| 可选 | Temporal adapter、`prometheus/prometheus` 指标、L4 设备远控 |
| 交付 | 升级/回滚、运维手册、容量评估 |

### 人员与排期

| 角色 | 投入 |
|---|---|
| 后端 A（Work Layer/Runner） | 全程 |
| 后端 B（Agent/tools/prompt） | 全程 |
| 前端（Workbench） | Phase 0 后半–Phase 3 |
| QA/Agent 工程师 | Phase 1 起 |
| 产品/设计 | Phase 0–1 重点 |

如果只有 1 后端 + 1 前端：v1 约 6–8 个月；仍然远少于 2–3 年，但不要承诺 10 周。

### 成功画面（v1）

> 用户说：“把登录模块回归一下，失败的看下原因，给我一份报告。”
>
> 5 秒内出现工作卡：目标、4 条验收标准、5 步计划。
> 第 2 步运行中，显示当前用例、设备、已用时、实时截图入口。
> 失败后自动归类：3 条失败，2 条像环境问题，1 条像真实缺陷；卡片问“是否只重跑环境类？”
> 用户点“只重跑环境类”，agent 执行；仍失败则转人工，保留证据。
> 完成后报告卡：结论、失败分类、run/session/截图链接；验收标准逐条打勾。
> 全程可暂停、改指令、接管、继续；重启不丢步骤、不重复跑。

## 9. 验收与指标

### 9.1 功能验收（真实场景，不写 pytest）

按仓库约束，以 `work_events` + `dispatch_log` + `run_store` + `session_events` 为证，不以单测/构建通过代替。Prometheus 自己的 178 个测试只在它自己的仓库/CI 里跑；**不把它们搬进 Nexus，也不在 Nexus 跑 pytest**。

| # | 场景 | 通过标准 |
|---|---|---|
| 1 | 单步问答 | 不建 WorkItem；聊天延迟不明显变差；旧路径不变 |
| 2 | 回归执行 | 计划可见；run 卡与 `run_store` 一致；一条消息最多一次 run |
| 3 | 失败分析 | 失败原因来自 session 证据；不编数字；给出可执行选项 |
| 4 | 暂停/恢复 | 暂停在步骤边界；恢复不重复写；审计可见 |
| 5 | 崩溃恢复 | `running` 步骤按安全规则回到 ready/unknown；0 重复 run |
| 6 | 接管 | 人能改指令/重试/跳过/接管完成；后续步骤继续 |
| 7 | 完成验收 | 无证据不能 done；有证据才 done；报告可追溯 |
| 8 | 权限 | 非本群/非本项目的 agent 不能执行；写工具需审批 |
| 9 | 记忆 | 记忆可查/可删；不写密钥；不跨项目 |
| 10 | 旧库升级 | 迁移后启动；旧工作区/旧 run 不受影响 |
| 11 | Prometheus spike | 3 个 employee 走通一次受控回归；审批/验收/暂停可演示；不接客户数据；不改变 Nexus 生产库 |

### 9.2 指标

| 指标 | 目标 |
|---|---|
| 首次计划可见时间 p95 | < 5s |
| 步骤事件完整率 | 100% |
| 崩溃后重复执行率 | 0 |
| 完成且有证据比例 | > 90% |
| 阻塞暴露时间 p95 | < 10 min |
| 接管率 | 10–30%（有门是正常的，不是 0） |
| 聊天 p95 延迟 | 不明显劣化（简单问答 < 2s） |
| 单工作成本 | 在预算内；超预算停止 |
| 工作完成率 | 按场景统计，不以“回复了”计 |
| 验收拒绝率 | 按 `acceptance` 原因分类：全拒绝/全失败/缺证据；不是越低越好，0 拒绝要怀疑没校验 |
| 审批等待 p95 | 记录从 `approval.requested` 到决定；用于发现“卡在等人” |
| 停止正确率 | 刹车后不再发起新工具调用；已在执行的写按现有停止语义处理 |

### 9.3 证据存放

- 每个 step 记 `dispatch_id`、`run_id`、`session_id`、`prompt_version`。
- `work_events` 是工作审计；`session_events` 是设备证据；两者用 `work_links` 关联。
- 报告 artifact 只存引用 + 摘要；原文在文档/报告存储。
- 不用“截图存在”代替“结论正确”；结论必须指向具体 run/session。

## 10. 风险与对策

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| 1 | 又造一套执行系统 | 两套状态分叉，重演 V7 | Work Layer 只协调；run 状态实时读 `run_store`；不建派发表 |
| 2 | 老库加表启动失败 | 升级即炸 | Phase 0 先做只增不减迁移；CI/启动自检 |
| 3 | 未知写重复执行 | 重复跑用例/重复操作 | `idempotency_key` + 收据 + `unknown` 状态 + 人工对账 |
| 4 | Agent 无限循环/烧钱 | 成本失控 | 步数/墙钟/token/重试上限；无进展检测；预算耗尽即停 |
| 5 | 多 Agent 互相甩锅 | 责任不清 | 星形拓扑、深度 ≤2、结构化 handoff、每步一个 owner |
| 6 | Prompt 膨胀/漂移 | 行为不可预测 | 策略进代码；prompt 分块；schema 校验；版本记录 |
| 7 | UI 变成项目管理 | 偏离目标 | v1 只做工作列表/详情/接管；不做看板/排期 |
| 8 | 接管变成“人肉重跑” | 没省事 | 接管要能“从下一步继续”，不是取消重来 |
| 9 | 第二前端/双真源 | 维护爆炸 | 不引入 OpenDots/DS Bot 作为产品壳；只借范式 |
| 10 | 权限/注入 | 越权/数据泄露 | 工具白名单、审批、用户隔离、prompt injection 防护 |
| 11 | 迁移/回滚 | 上线失败难退 | feature flag；旧路径保留一个版本；数据只增不删 |
| 12 | 团队不熟 | 延期 | 先做垂直切片；不先造通用平台；Prometheus spike 做交互学习 |
| 13 | **把 Prometheus 当后端**：单用户/无认证/双库 | 安全与数据真源崩 | 只移植核心；不跑它的生产服务；不接客户数据 |
| 14 | **移植漂移**：上游 0.1.0 还在变 | 合并困难/行为分叉 | 只移植纯领域，适配层自己写；记录 upstream commit；不逐行同步 |
| 15 | **许可/归属** | 合规问题 | MIT 允许，但保留版权声明/NOTICE；派生文件标注来源 |

## 11. 需要确认的决策

1. **确认 Prometheus 指 `AethraIntelligence/Prometheus`？** 如果你说的是另一个项目，请给链接；本文按 Aethra 这个评估。
2. **主路线选 B（移植核心）还是 C（独立产品 fork）？** 建议 B；如果目标是单机个人版，C 才成立。
3. **是否批准 1 周 Prometheus headless spike？** 只内部、独立数据、不接客户数据、不作为产品前端；用来验证交互和工具桥，不承诺上线。
4. **v1 是否必须“实时接管设备”？** 建议 v1 只做 L0–L3（观察/指令/审批/接管步骤），L4 远控后置；否则 Scout 侧要另开项目。
5. **是否批准新增 `work_*` 表与只增不减迁移机制？** 这是 Phase 0 的前置；不做就只能复用旧表/JSON，后面更难。
6. **前端投入能否保证 1 人 11–13 周？** 工作列表/详情/时间线/审批/接管是半边产品。
7. **是否允许把 MIT 代码/模式移植进 Nexus 并保留 NOTICE？** 这是 B 的前置；法务/合规需要确认。
8. **单工作预算上限多少？** 建议先按项目配置：`max_runs=1`、`max_retries=2`、`max_tokens=200k`、`max_wall_clock=2h`。
