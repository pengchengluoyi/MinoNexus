## 0. 结论先行

这份设计解决的不是"再做一个页面列表"，而是让系统在**进入某个页面之前**，先回答四个问题：

1. **这个页面是谁？**  
   用 DOM/层级结构指纹 + 语义别名识别，不依赖看图、不依赖 OCR、不依赖图像模型。
2. **有哪些逻辑可以进入这个页面？**  
   把"运行观察、用例步骤、常识规则、需求/技术/设计文档、人工补录"统一记成**入口证据**，每条都带来源、触发方式、先决条件和置信度。
3. **现在该走哪条入口？**  
   已发布路由优先；没有路由时，只允许执行**有证据、可校验、有预算**的入口探针，不允许模型自由乱点。
4. **如果进不去怎么办？**  
   明确产出一个**入口缺口（Gap）**，在 Workbench 里可解释、可补录、可验证；下一轮不会重复同样的乱碰。

四个问题的答案分别落在四个平面：

| 平面 | 负责 | 不负责 |
|---|---|---|
| 页面身份平面 | 页面是谁、结构指纹、别名、页面角色 | 不负责"怎么去" |
| 入口证据平面 | 从哪来、点什么、什么先决条件、证据是什么 | 不直接改已发布导航图 |
| 运行时决策平面 | 当前步骤该走路由、探针，还是报缺口 | 不发明页面、不发明入口 |
| 治理/UI 平面 | 入口档案、冲突、失效、覆盖度、会话回放 | 不直接操作设备；本版不做人工审核 |

**一句话：页面身份用结构，入口用证据，运行时有边界，失败有缺口。**

## 1. 现场与根因

### 1.1 现在的链路

用例执行到"进入某页"时，当前链路大致是：

```text
case step
  └─ casework/case_step_key_compiler.py
       └─ nav_target（目标页，可能只是自然语言）
  └─ loop/step_nav_plan.py: build_step_nav_plan_hint()
       └─ navigation/atlas/nav_state_resolve.py: plan_route_resolved()
            └─ navigation/atlas/nav_route.py: plan_route()
                 ├─ 有路径 → fsm_navigate
                 └─ 无路径 → error="路线图无路径：{src} → {dst}。目标页在图中无入边，需跑一条「进入该页」的用例补采集。"
  └─ loop/navigation_policy.py: plan_and_dispatch_next()
       └─ 无路径/无 FSM → _degrade(local_reason="fsm_degraded")
            └─ loop/nav_onboarding_open_loop.py
                 └─ 模型按当前屏幕自由点按，直到"碰"到目标页或耗尽预算
```

`nav_route.plan_route()` 已经写出了正确的诊断："目标页在图中无入边，需跑一条「进入该页」的用例补采集。"  
问题是：**这句话只是错误文案，没有变成可执行的补采集动作，也没有变成可追踪的缺口。** 运行时随后进入 open-loop，模型开始乱碰。

### 1.2 四个具体断点

| 断点 | 代码事实 | 后果 |
|---|---|---|
| 只有"已发布边"，没有"入口证据" | `nav_fsm_edges` 只存已审核的边；`nav_candidate_compiler` 主要从重复采集转迁中生成候选，且"登录页不与主流程自动连边" | 用例里明明写了"点击 X 进入 Y"，但这条知识进不了图 |
| 页面身份没有显式结构合同 | `nav_localize` 已有 `skeleton_wireframe`、`layout_framework`、`text_landmarks`、`phash_delta` 等信号；`nav_screen_registry` 也有聚类指纹，但 `nav_fsm_states` 没有一个可审核、可复用的结构指纹字段 | 同壳页面（列表/详情、不同 Tab 子页）容易靠文案硬猜；换构建后无法解释为什么匹配/不匹配 |
| 缺口没有落库 | `plan_route()` 返回错误字符串；`navigation_policy` 降级后没有 `nav_page_gaps` 之类的记录 | 同一个缺口每次跑都重新乱碰，Workbench 看不到"哪些页面进不去" |
| 常识没有页面级声明 | 首次启动协议、登录门禁、系统权限弹窗等顺序知识主要靠 flow block/prompt；没有可查询、可配置、可解释的页面级 prior | 换个模型/换条用例就忘；不同应用无法配置 |

### 1.3 "FSM 缺失"要分四种，不要混为一谈

用户说的"FSM 缺失"在代码里至少对应四种不同状态，处理方式必须不同：

| 类型 | 判定 | 正确处理 |
|---|---|---|
| `no_fsm` | 整个应用没有可用的 `nav_fsm` | 仍可用页面指纹/采集页工作；入口缺口照记；不要假装有全图 |
| `no_target_state` | 图存在，但目标页不在 `states` 里 | 目标未绑定；允许建"临时目标"，到达后走页面候选审核，不静默建页 |
| `no_incoming_edge` | 目标页存在，但没有任何入边 | 入口档案的主战场：从用例/文档/常识/人工找入口 |
| `no_path` | 目标页有入边，但从当前页不可达（断图/守卫挡住） | 先找桥接入口；找不到就报 `no_path`/`guard_blocked`，不要自由点 |

这四类都会落到统一的 `nav_page_gaps.reason`，但 UI 文案和补录动作不同。

### 1.4 目标与非目标

**目标**

- 任一"进入页面"的用例步骤，要么走可信路由，要么走有证据的入口探针，要么明确报缺口；**不存在第四种"模型随便点"**。
- 每条入口可回答：从哪来、触发什么、什么先决条件、证据是什么、成功过几次、是否随构建失效。
- 页面身份可回答：结构是什么、和哪一页像、为什么不是另一页。
- Workbench 能在一个页面里完成：看缺口 → 看入口 → 从用例/采集重建 → 回用例验证。
- 不引入图像识别/OCR/本地 CV；不碰设备；不 import Scout；业务状态进 `mino.db`。

**非目标**

- 不追求"全自动探索出所有页面"。
- 不替换 NavFSM；入口档案是 NavFSM 的**证据层和工作层**，不是第二套页面目录。
- 不把用例/文档提取结果直接写进已发布导航图。
- 不保证每个页面都可达；**不可达是一等公民**，必须有缺口记录。
- 不在本轮改 Scout 协议；所有设备动作仍走现有能力与 `EXECUTE` 载荷。

## 2. 设计总览

### 2.1 四个平面与一条闭环

```text
┌─────────────────────────────────────────────────────────────────────┐
│  治理/UI：页面地图 · 入口档案 · 缺口收件箱 · 指纹对照 · 会话回放      │
└───────────────▲───────────────────────────────────────┬─────────────┘
                │ 只读查看/重建（无人工审核）             │ 发起重建/运行验证
┌───────────────┴───────────────────────────────────────▼─────────────┐
│  入口证据平面：nav_page_entries + evidence + priors + gaps           │
│  来源：capture / case / prior（无 doc/figma/导入）                    │
│  状态：active；连续失败/换构建 → stale；冲突 → rejected              │
└───────────────▲───────────────────────────────────────┬─────────────┘
                │ 只读证据                               │ 有效图 overlay
┌───────────────┴───────────────────────────────────────▼─────────────┐
│  运行时决策平面：EntryRuntime                                        │
│  LOCATE → RESOLVE_TARGET → PLAN（route / probe / block）             │
│        → EXECUTE_HOP → VERIFY_ARRIVAL → RECORD                      │
└───────────────▲───────────────────────────────────────┬─────────────┘
                │ 当前页/指纹                           │ 一次有界动作
┌───────────────┴───────────────────────────────────────▼─────────────┐
│  页面身份平面：nav_fsm_states.meta.page_fingerprint + nav_localize   │
│  DOM 结构路径 / 区域 / 树形 / 语义别名；截图与 pHash 只做辅助         │
└─────────────────────────────────────────────────────────────────────┘
```

闭环的关键是最后一步：**每次探针的结果回写入口证据**。成功会提高置信度，失败会降级/失效，缺口会自动关闭或重新打开。这样系统不是"每次从零猜"，而是"越跑越有据"。

### 2.2 五个关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 入口存哪里 | 独立 `nav_page_*` 表，不塞 `nav_fsm_edges.meta` | 边表没有证据/状态字段；`nav_fsm_store._edge_public()` 目前也不回传 `meta`，塞进去会丢；入口需要按来源、状态、目标查询 |
| 入口和已发布图的关系 | 已发布边是"合同"，入口是"运行时证据层"；active 入口直接可用，但不回写边表 | 不膨胀导航图合同，也不让入口等待审核 |
| 页面身份主信号 | DOM/层级结构指纹 + 语义别名 | 用户明确要求；也符合现有 `nav_localize` 的无图像路线 |
| 用例提取结果 | 直接 active，带 `rule_id`/原文证据；不直接改图 | 用例是当前最便宜的入口知识；保留证据便于回查，失败自动降级 |
| 运行时无入口时 | 一次有界探针，失败即缺口；禁止 open-loop 乱点 | 直接解决"整个任务开始乱碰" |

## 3. 页面身份：DOM 结构指纹 v2

### 3.1 为什么不是"看图识别"

页面身份必须满足三个条件：**可解释、可版本化、可在无 GPU/无图像依赖的服务端计算**。

- 截图/pHash 适合判断"屏幕有没有变"，不适合回答"这是哪一页"；同壳页面（列表/详情、不同 Tab）视觉可能极近。
- 文案适合做语义补充，但文案会变、会重复、会国际化；不能当唯一主键。
- DOM/层级结构包含上下级、兄弟顺序、区域角色、可点击性，正好是"页面骨架"的稳定部分。

因此：

- **主信号**：结构指纹（stable paths + regions + tree shape）+ 语义别名（标题、Tab、稳定 chrome 文案）。
- **辅助信号**：布局框架（`layout_framework`）、文本地标（`text_landmarks`）、历史（`history`）。
- **仅辅助**：`phash_delta` 继续保留 0.2 权重，用于"屏幕变了"与探索进度，不作为页面身份。
- **禁止**：引入 `cv2`/`torch`/`paddleocr`/`open_clip` 或任何本地图像识别；不在 Nexus 里做 OCR。

### 3.2 指纹的组成

对 Android 层级（Web 用 DOM 节点做同构映射）：

```json
{
  "version": 2,
  "platform": "android",
  "layout_role": "form",
  "tree_shape": "root>FrameLayout>LinearLayout[3]>ScrollView[*]",
  "depth": 9,
  "branching": 2.4,
  "regions": [
    {"slot": "top_bar", "classes": ["Toolbar"], "child_count": 2, "bounds": [0, 0, 1, 0.08]},
    {"slot": "content", "classes": ["ScrollView", "LinearLayout"], "child_count": 7, "bounds": [0, 0.08, 1, 0.84]},
    {"slot": "bottom_bar", "classes": ["BottomNavigationView"], "child_count": 4, "bounds": [0, 0.9, 1, 1]}
  ],
  "stable_paths": [
    "content/ScrollView/LinearLayout[0]/TextView|title",
    "content/ScrollView/LinearLayout[1]/EditText|input",
    "content/ScrollView/LinearLayout[3]/Button|submit",
    "bottom_bar/BottomNavigationView/Item[*]|tab"
  ],
  "semantics": {
    "title": "提单页",
    "tab": "我的",
    "chrome_texts": ["提单", "提交订单"],
    "aliases": ["提单页", "提交订单页"]
  },
  "exclusions": {
    "volatile_text": true,
    "dynamic_children": ["RecyclerView item count", "WebView content"],
    "resource_id_patterns": [":id/.*_count$", ":id/.*_time$"]
  },
  "stats": {"samples": 8, "builds": ["1.2.3"], "stability": 0.91}
}
```

现有的 `navigation/geometry/hierarchy_slots.py: dom_structure_fingerprint(nodes)` 是对 class+bounds 的 SHA1，适合"同/不同"的一致性校验，但不提供可解释相似度；本设计的 `stable_paths/regions/tree_shape` 是它的升级，复用节点规范化，不把 SHA1 直接当匹配分数。

#### 3.2.1 稳定路径 `stable_paths`

不是把整棵树哈希，而是抽取"有结构意义"的锚点：

- 路径由**语义容器 + 角色 + 相对层级**组成，例如 `content/ScrollView/LinearLayout[1]/EditText|input`。
- 类名只取 simple name；`resource_id` 去掉包名前缀、去掉纯数字/随机后缀，保留语义后缀（`_submit`、`_title`、`_tab`）。
- 列表项折叠：`RecyclerView/Item[*]` 表示"任意数量、同一结构"，不把 item 数量写进指纹。
- 文本不进入 `stable_paths`；文本只进入 `semantics`，且只取跨样本稳定的 chrome 文案。
- 动态区域（WebView、广告位、倒计时）通过 `exclusions` 排除。

#### 3.2.2 区域 `regions`

把屏幕按相对坐标分成 top/content/bottom 等槽位，记录每个槽位的类名族、子节点数量、相对 bounds。  
它解决"两页都有标题栏 + 列表，但一个是详情、一个是表单"的区分。

#### 3.2.3 树形 `tree_shape`

深度、分支度、子节点数量直方图，折叠重复列表项。  
它解决"同一业务页在空态/有数据态"的稳定性：列表 item 数量变化不影响树形。

#### 3.2.4 语义 `semantics`

- `title`：页面标题，优先从 `meta.display_name` / `page_title` / 稳定标题栏文本取。
- `tab`：所属 Tab（如果有）。
- `chrome_texts`：跨样本稳定、且不是列表内容的文案；沿用 `stable_chrome_texts` 的思路。
- `aliases`：来自 `meta.aliases`、用例目标名、文档标题、设计稿 frame 名；**别名不参与结构主键**，只用于目标解析和歧义消解。

### 3.3 相似度与判定

对当前观察 `fp_obs` 与页面 `fp_page`：

```text
J = IDF 加权 Jaccard(stable_paths_obs, stable_paths_page)
R = 区域槽位/类名族/子节点数的相似度
T = 树形（depth、branching、child_count 直方图）相似度
M = 语义匹配（title、alias、tab、chrome_texts）

S = 0.40*J + 0.20*R + 0.20*T + 0.20*M
```

- `J` 的 IDF：`FrameLayout`、`ViewGroup` 这类常见节点权重低，`EditText`、`Button`、`Toolbar`、`Tab` 等角色权重高，避免"大家都是 LinearLayout"导致误配。
- `M` 只做加分，不允许单独把页面顶到高分；避免"文案碰巧一样"。
- 没有结构指纹时，退化为现有 `identify.required` 信号，`degraded=true`，并在会话里标注 `identity_source="legacy"`。

**阈值（可配置，先给默认）**

| 分数 | 判定 | 运行时行为 |
|---|---|---|
| `>= 0.80` | 高置信匹配 | 可直接作为到达依据（仍需 `effect_assert` 或下一次观察确认） |
| `0.62 – 0.80` | 中置信 | 允许一次"再看一帧"；不允许直接当作到达 |
| `< 0.62` | 低置信 | 不匹配；若在目标页附近，报 `fingerprint_ambiguous` |
| top1 - top2 `< 0.06` | 歧义 | 不自动选；报歧义，UI 提示补别名/锚点 |

`nav_fsm_states.meta.page_fingerprint` 只存**规范摘要**；每次观察的原始层级和样本放 `data_dir()/nav/fingerprints/...` 或 `nav_page_fingerprint_samples`（P1），避免数据库膨胀。

### 3.4 与 `nav_localize` 的接入

`nav_localize.localize()` 已经有权重表：

```text
session 1.0, skeleton_wireframe .88, tab_bar .9, layout_framework .85,
text_landmarks .7, vlm_landmarks .78, history .6, phash_delta .2
```

新增信号，不改已有语义：

```text
structure_fingerprint: 0.90
```

规则：

1. 如果 `state.meta.page_fingerprint` 存在，自动计算 `structure_fingerprint`，参与加权。
2. `identify.required` 可显式要求：
   ```json
   {"signal": "structure_fingerprint", "match": {"ref": "meta.page_fingerprint", "min_score": 0.78}}
   ```
3. 结构指纹命中但语义不命中：降低 `M`，仍可匹配，但 `degraded=true`，提示"结构像、文案不像"。
4. 语义命中但结构不命中：不直接判为同页；最多作为候选，等待下一次观察。
5. `phash_delta` 不升级为主信号；继续只做"屏幕是否变化"的辅助。

### 3.5 指纹的生成、审核、失效

**生成**

- 每次 `NavRuntime.observe()` 采到可用层级后，对已定位/候选页面计算指纹。
- 同一 `state_id` 累计样本；`samples >= 3` 且 `stability >= 0.80` 才生成"可审核指纹"。
- 生成后写入 `nav_fsm_states.meta.page_fingerprint`，状态 `candidate`，不自动当作可信身份；UI 可审核。
- 已有 `nav_screen_registry` 的聚类结果可复用，但**不另建页面目录**；页面主键仍是 `nav_fsm_states.state_id`。

**审核**

- Workbench "指纹对照"展示：结构树、区域、稳定路径、样本数、构建、稳定性。
- 维护者可"批准为规范指纹"、"合并到另一页"、"拆分为新页"、"拒绝"。
- 批准后 `meta.page_fingerprint.review_status="approved"`，并记录 `reviewed_by/at`。

**失效**

- 构建变化时，计算旧指纹对新样本的 `S`；`S < 0.65` 标记 `stale`，不参与高置信匹配。
- 连续 2 次定位失败或人工标记"不是这页" → `stale`，并在 `nav_page_gaps` 里生成"指纹漂移"缺口。
- 失效不等于删除；保留历史，UI 可对比新旧结构。

## 4. 页面入口：入口档案（Entry Ledger）

### 4.1 一条入口记录是什么

```json
{
  "entry_id": "entry.7f3a9c2d",
  "app_id": "app.xxx",
  "from_state_id": "page.home",
  "target_state_id": "page.submit",
  "target_label": "提单页",
  "platform": "android",
  "build_scope": "1.2.3",
  "source_kind": "case",
  "status": "candidate",
  "confidence": 0.72,
  "trigger": {
    "kind": "tap",
    "selector": {"text": "做成真的", "match": "exact", "role": "button"},
    "scroll": {"direction": "up", "max_swipes": 3},
    "wait_ms": 800
  },
  "preconditions": {
    "session": "logged_in",
    "first_launch": false,
    "consent": "accepted"
  },
  "expect": {
    "state_id": "page.submit",
    "fingerprint_min": 0.80,
    "landmarks_any": ["提单", "提交订单"]
  },
  "evidence": [
    {
      "source_kind": "case",
      "source_ref": "case.123#step.3",
      "relation": "leads_to",
      "quote": "点击「做成真的」进入提单页",
      "weight": 0.72
    }
  ]
}
```

字段语义：

| 字段 | 说明 |
|---|---|
| `from_state_id` | 已知来源页；`""` 表示任意页（通常用于 deeplink/启动入口） |
| `target_state_id` | 目标页；未知时为空，用 `target_label` 暂存 |
| `target_label` | 用例/文档里的目标名，用于未绑定目标和 UI 展示 |
| `source_kind` | `capture` / `case` / `doc` / `figma` / `prior` / `manual` |
| `status` | `candidate` / `verified` / `published` / `rejected` / `stale` |
| `trigger` | 单跳触发；多跳用 `steps`，见 4.1.1 |
| `preconditions` | 登录态、首次启动、协议、权限、账号 facet；不存凭据 |
| `expect` | 到达校验：目标页 + 指纹阈值 + 地标；不把"点击成功"当到达 |
| `confidence` | 0–1；来源先验 + 成功历史 + 构建匹配 - 风险惩罚 |
| `conflict` | 同一 `from + trigger` 指向多个目标时为真；UI 标冲突，运行时不自动选 |
| `published_edge_id` | 发布到 `nav_fsm_edges` 后的回链 |

#### 4.1.1 多跳入口

文档/用例可能给的是"首页 → 我的 → 我的订单 → 提单页"。不要把它当成一条"点一下就到"的边，而是：

```json
{
  "trigger": {
    "kind": "path",
    "steps": [
      {"cap": "tap_element", "params": {"selector_text": "我的"}},
      {"cap": "tap_element", "params": {"selector_text": "我的订单"}},
      {"cap": "tap_element", "params": {"selector_text": "提单"}}
    ],
    "expect_after_each": ["page.mine", "page.orders", "page.submit"]
  }
}
```

运行时**一次只执行一步、每步后观察/校验**；不允许把整段脚本一次性丢给设备。中间页未知时，`expect_after_each` 可为空，但仍要求最终到达校验；中途页面变化不符合预期就中止并记失败，不继续盲走。

#### 4.1.2 触发方式

| `kind` | 用途 | 示例 |
|---|---|---|
| `tap` | 点击控件 | `selector.text="做成真的"` |
| `path` | 多跳点击 | 文档里的路径 |
| `back` | 返回父页 | 子页回列表 |
| `deeplink` | 直接打开 | `app://order/submit` / Web URL |
| `launch` | 冷启动/热启动 | `launch_app` 后到首页 |
| `swipe` | 滚动后出现 | 列表底部入口 |
| `system` | 系统弹窗/权限 | 权限允许/拒绝 |
| `wait` | 启动页/加载 | 等待首页出现 |

`deeplink` 是高价值入口：技术文档里的路由表、Web URL、Android scheme 都可以直接变成入口；但它必须走现有 `open_url` 能力，并校验最终页面，不能假设"URL 打开成功 = 到达"。

### 4.2 入口的五个来源

以下示例里的页面名、按钮文案、包名只用于说明；实施时全部来自数据库/配置，不得写进代码常量。

#### 4.2.1 运行观察（capture）

**做什么**

- 从 `nav_capture_store` 的每次 turn 中提取 `(from_page, action, to_page)`。
- 已有 `nav_candidate_compiler` 会把重复转迁编译成候选边；本设计复用其数据，但增加：
  - 每次转迁都写 `nav_page_entries` 的 `capture` 证据，即使只出现一次；
  - 记录触发控件的文本/资源 id/位置/是否滚动后出现；
  - 记录到达时的目标指纹分数。
- 对"只出现一次"的转迁：`confidence` 低，状态 `candidate`，不自动发布；但可以在探针模式使用。

**为什么**

- 运行观察是唯一"真实发生过"的证据，优先级应高于文档推断。
- 现有编译器只保留重复转迁，会丢掉"只跑过一次但确实能进"的入口；入口档案保留它，但用置信度区分。

**不做什么**

- 不把每次转迁都自动变成已发布边；仍走 `candidate → verified → published`。
- 不因为一次成功就认为永久有效；构建/账号变化会衰减。

#### 4.2.2 用例推导（case）

这是用户第 2、4 点"路径用例没写清楚 / 从用例获取先后层级关系"的落点。

**输入**

- 用例原始步骤 `steps` / `steps_raw`。
- 编译后的步骤 bundle、`nav_target`、`operation`、`expected`。
- 用例的 `precondition` / `case_scene`（登录态、平台、环境）。

**抽取规则**

1. **显式单句**
   - `点击「做成真的」进入提单页`
   - `在首页点击「我的」打开个人中心`
   - `通过「订单」进入提单页`
   - 输出 `from`（若句中有）、`trigger.text`、`target`，置信 0.85。
2. **相邻两步**
   - 第 i 步：`点击「做成真的」`
   - 第 i+1 步：`进入提单页`
   - 输出 `from=第 i 步所在页`、`trigger=第 i 步动作`、`target=第 i+1 步目标`，置信 0.70。
3. **面包屑/层级**
   - `首页 > 我的 > 我的订单 > 提单页`
   - 输出 `parent_of` / `precedes` 证据，不直接生成"点击"入口；用于页面层级、返回路径、排序。
4. **只有目标、没有动作**
   - `进入提单页`
   - **不生成入口**；生成 `target_only` 缺口，UI 显示"用例只写了目标，没有写怎么进"。
5. **动作歧义**
   - `点击按钮进入提单页`（没有具体控件）
   - 生成低置信候选（0.35），标记 `trigger_too_generic`，必须人工补控件或运行观察补齐。

**`from` 怎么推**

按优先级：

1. 当前步骤显式写了"在 X 页"；
2. 上一步的 `nav_target` / 期望页；
3. 上一步动作后观察到的页面（如果有会话）；
4. 用例的 `precondition` 指定页；
5. 推不出就 `from=""`（任意页），置信减 0.10，UI 标"来源页未知"。

**`to` 怎么解析**

1. 精确 `state_id`；
2. `nav_fsm_states.meta.display_name/aliases`；
3. `nav_state_resolve.resolve_state_fuzzy`；
4. 文档/设计稿别名；
5. 仍解析不了 → `target_state_id=""`，保留 `target_label`，进入"未绑定目标"桶。

**输出**

- `nav_page_entries` 的 `candidate` + `nav_page_entry_evidence`（case_id、step_index、quote）。
- 不写 `nav_fsm_edges`；不覆盖已有人工入口。
- 同一 `(from, trigger, target)` 去重；多条证据累加，不重复建行。

**"先后层级关系"不只是顺序，要分四种关系用**

用例里的"第 1 步首页、第 2 步登录、第 3 步提单页"既包含顺序，也可能包含父子、前置条件。统一存成 `relation`，但只有 `leads_to` 能生成入口：

| 关系 | 从用例里怎么来 | 用途 | 能不能生成入口 |
|---|---|---|---|
| `leads_to` | `点击「做成真的」进入提单页`；相邻"动作 → 目标" | 入口候选 | 能（带触发） |
| `precedes` | 相邻步骤的页面顺序；`先…再…` | 候选排序、缺口优先级、页面时间线 | 不能，只做顺序证据 |
| `parent_of` | `首页 > 我的 > 订单`；缩进/编号层级 | 返回路径、页面树、判断子页归属 | 不能，只做层级证据 |
| `contains` | "首页包含推荐/分类两个 Tab" | Tab 结构、同壳页面区分 | 不能，只做结构证据 |
| `requires` | "登录后才能进入"；`precondition` | 先决条件、登录门禁 | 不能，只做条件 |

这样处理的好处：

- 用例只写了"先首页后提单页"，不会误生成"首页直接跳提单页"；
- 用例写了"点击 X 进入 Y"，才会生成可执行入口；
- 用例只写了目标没写动作，进入 `target_only` 缺口，而不是硬编一条假入口；
- 页面顺序可以用来排序候选：同一用例里先出现的来源页，优先于跨用例的远距离入口。

**"用例路径"在 UI 里怎么呈现**

- 左侧用例步骤时间线，右侧页面节点。
- 每步标注：识别到的页面、动作、目标、抽取结果（入口/仅目标/歧义）。
- 未匹配的页面用红色虚线；点击可"绑定到已有页面"或"建临时目标"。
- 提供"生成入口候选"按钮，生成前可逐条勾选；不静默全量写入。

#### 4.2.3 常识规则（prior）

用户第 5 点"首次启动的协议弹窗在登录页面前面"属于**生命周期顺序知识**，不应写死在 prompt，也不应写死 App 文案。

**规则表 `nav_page_priors`**

```json
{
  "rule_id": "prior.first_launch.consent_before_login",
  "priority": 20,
  "enabled": true,
  "when": {
    "first_launch": true,
    "target_page_role": ["login", "home", "protected"],
    "visible_overlay_kind": ["consent", "privacy", "agreement"]
  },
  "then": {
    "action": "handle_overlay",
    "block": "fb.global.consent",
    "params": {"decision": "accept"},
    "before": "target_page"
  },
  "source": "seed"
}
```

**首批通用规则（不写任何 App 文案/包名）**

| rule_id | 何时 | 做什么 | 目的 |
|---|---|---|---|
| `prior.cold_start.splash` | 启动页/闪屏 | 等待或跳过，观察首页 | 避免在闪屏上乱点 |
| `prior.first_launch.consent` | 首次启动 + 协议/隐私浮层 | 先处理协议，再进入目标 | 用户明确提到的场景 |
| `prior.system.permission` | 系统权限弹窗 | 按用例策略允许/拒绝 | 系统弹窗不是 App 页面 |
| `prior.login.gate` | 目标页 `role=protected` 且未登录 | 先走登录链/登录页 | 不能直接点受保护页 |
| `prior.onboarding.coach` | 新手引导/蒙层 | 跳过/关闭后再导航 | 避免引导层吞点击 |
| `prior.update.dialog` | 升级弹窗 | 关闭/稍后 | 避免更新弹窗阻断 |
| `prior.child.back_to_parent` | 目标父页、当前子页 | 先返回父页 | 提供返回路径 |
| `prior.tab.root` | 目标是 Tab 根页 | 直接点 Tab | 比逐级进入稳定 |
| `prior.deeplink.preferred` | 目标有已验证 deeplink | 优先 open_url | 技术文档路由表的价值 |

**规则边界**

- `when` 只匹配通用角色/浮层种类/已有 block id，不匹配具体 App 文案。
- `first_launch` 由现有会话/应用数据状态判定，不由入口表自行推断；入口表只消费这个事实。
- App 特有覆盖写在 `app_id` 维度的同表记录里，由维护者在 UI 编辑；代码只保留通用 seed。
- 规则只决定**顺序、先决条件和本次 run 的临时动作**，不凭空产生"从 A 点 B"的常驻入口；入口仍来自 capture/case/doc/manual。
- prior 的临时动作即使成功，也只先记成 `capture` 证据；要变成入口档案仍需人工确认或探针验证。
- 规则命中/未命中都要写会话事件，便于解释"为什么先弹了协议"。

#### 4.2.4 文档与设计稿（doc / figma）

**需求文档（PRD）**

- 典型句："用户在首页点击‘我的’进入个人中心"、"提交订单后进入提单页"。
- 抽取为 `PageEntryClaim`，必须带 `doc_source_id`、`chunk_id`、原文引用、字符偏移。
- 只有句子同时有"动作/控件"和"目标页"才产出 `relation=leads_to`；只描述页面先后的产出 `precedes`，只描述包含关系的产出 `contains`/`parent_of`，不生成可点击入口。
- 有路由表的文档优先**确定性表格解析**（列：页面/路由/入口/参数/备注），正文再用 LLM 结构化。
- LLM 输出严格 JSON；解析失败不落库；不确定就留空，不允许编造 `from`。

**技术文档**

- 路由表、deeplink scheme、Web URL、页面栈说明 → `trigger.kind=deeplink` 或 `path`。
- 这类入口置信度可以较高（0.75），但仍需到达校验；技术文档经常过期。

**UI 设计稿（Figma）**

- `resources/figma_service.py` 已能解析 frames/texts；`figma_logic.py` 写 `playbook.figma_pages` / `app_atlas`。
- 本设计只取三样：
  1. 页面/frame 名 → `display_name` / `aliases`；
  2. frame 内文本 → `chrome_texts` 候选；
  3. 页面层级（frame 嵌套/分组）→ `parent_of` / `precedes` 证据。
- **设计稿不证明"可点击跳转"**；如果 frame 内有按钮文案，最多生成 `figma` 低置信入口（0.40），并明确标注"设计稿提示，待运行验证"。
- 不把设计稿图片拿去做视觉识别；只读结构化文本/层级。

**审核**

- 文档提取结果进入 `candidate`，Workbench 显示原文高亮 + 抽取卡片。
- 必须"目标页已绑定 + 来源引用存在 + 无冲突"才允许批量批准。
- 批准只把状态改为 `verified`；发布到导航图仍需单独动作（可批量）。

#### 4.2.5 人工补录（manual）

- 维护者在 Workbench 直接填：从哪页、点什么、什么先决条件、期望到哪页。
- 支持"从会话挑一跳"：选一个 session/turn，把已观察到的 `(from, action, to)` 预填，减少手填。
- 人工入口默认 `verified`（人明确声明），但仍建议跑一次验证；`verified` 可直接用于正常路由 overlay。
- 人工可以标记"仅本构建有效"或"所有构建"。

### 4.3 证据、置信度、状态机

#### 4.3.1 来源先验

| 来源 | 基础分 | 说明 |
|---|---:|---|
| `manual` | 0.90 | 人明确声明，但可能配错 |
| `capture` | 0.85 | 真实发生过；单次也降权 |
| `case` | 0.70 | 用例可能写得含糊/过期 |
| `doc` | 0.60 | 文档可能过期/抽象 |
| `figma` | 0.40 | 只证明设计存在，不证明可跳 |
| `prior` | 0.55 | 只证明顺序，不证明具体控件 |

最终 `confidence` 不是固定值，而是：

```text
confidence = clamp(
  base
  + 0.10 * same_build
  + 0.08 * same_case
  + 0.12 * success_rate_laplace
  - 0.10 * hops_penalty
  - 0.10 * precondition_risk
  - 0.15 * recent_fail_penalty,
  0.05, 0.98
)

success_rate_laplace = (success_count + 1) / (success_count + fail_count + 2)
```

具体系数实施时可调；关键不是精确，而是**来源、历史、构建、先决条件都进入分数**，UI 能解释。

#### 4.3.2 状态机

```text
                 ┌───────────┐
   新证据 ──────►│ candidate │
                 └─────┬─────┘
       人工批准 /       │      2 次独立成功探针
       1 次成功+批准    │      + 目标指纹 >= 0.80
                       ▼
                 ┌───────────┐
                 │ verified  │──── 人工发布 ───► published
                 └─────┬─────┘
     连续失败/换构建    │
     指纹 < 0.65        ▼
                 ┌───────────┐
                 │  stale    │──── 重新验证成功 ──► verified
                 └───────────┘
```

- `candidate`：可用于**探针**，不可用于普通路由。
- `verified`：可用于**运行时 overlay**（正常路由），但还没有写进 `nav_fsm_edges`。
- `published`：已写入 `nav_fsm_edges`，是长期合同；`published_edge_id` 回链。
- `rejected`：人工拒绝或连续失败；保留证据，不再使用。
- `stale`：构建/指纹漂移或近期失败；只在没有更好候选时允许一次探针。

`published` 行只用于证据展示和回链；规划时以 `nav_fsm_edges` 为准，不把同一条边在 overlay 里算两次。

**自动提升**

- `candidate → verified`：2 次独立成功探针（不同 session 或不同 turn），且目标指纹 >= 0.80，最近 3 次无失败。
- 或人工批准。
- 自动提升写 `nav/entry_promote` 事件；默认**不自动 publish**。

**自动降级**

- `verified → stale`：构建变化且指纹相似度 < 0.65；或连续 2 次失败。
- `candidate → rejected`：连续 2 次失败且无新证据；或人工拒绝。
- 降级不删除；UI 显示原因和时间。

### 4.4 冲突、去重、失效

**去重键**

```text
entry_hash = sha1(
  app_id | from_state_id | target_state_id | target_label |
  normalized(trigger.kind) | normalized(trigger.selector) |
  normalized(preconditions)
)
```

- 同一入口多条证据 → 合并到一条，证据表多行。
- 同一触发但目标不同 → 不合并，标 `conflict`；按构建/平台/先决条件拆分。
- 同一目标但多个入口 → 正常，运行时排序选择。
- `entry_hash` 即使目标未绑定也用 `target_label` 参与计算；空 hash 不进唯一索引（见 §7.1 的部分索引）。
- 目标从未绑定改为已绑定时，重算同 `app_id + target_label` 下 `target_state_id=""` 的入口 hash，并合并重复行；证据不丢，缺口同步指向新 `state_id`。

**冲突处理**

- UI 在页面详情显示"入口冲突"：同一 `from + trigger` 指向多个目标。
- 运行时只选置信度最高的一条；如果 top1-top2 < 0.08，不自动选，报 `entry_conflict`，让 UI/人处理。
- 冲突不自动删除任何一方；保留证据，等构建/账号信息补全。

**失效**

- 构建变化、目标页指纹漂移、触发控件消失、连续失败 → `stale`。
- 触发控件消失的判定：探针执行前在层级中找不到 selector；记 `trigger_not_visible`，不点。
- 失效入口在 UI 变灰，保留"曾经可用"的历史。

**没有 FSM 时也必须工作。** `EntryRuntime` 不以 `NavRuntime.active`（即 `fsm` 是否存在）为开关；只要 hierarchy 观察开启就创建。没有 FSM 时：

- `published` 边为空，仍可从 `nav_capture_store`/页面候选里解析当前页和目标页；
- 入口候选仍可来自用例、文档、人工和采集；
- 目标页解析不到 → 直接 `target_unbound` 缺口；
- 页面身份仍可用结构指纹/采集页聚类。

换句话说，**"FSM 缺失"只影响"已发布路由"这一层，不应把入口决策一起关掉。** 入口层是 NavFSM 的前置/补充，不是它的子功能。

### 6.2 每步生命周期

```text
STEP_START
  │
  ├─ 1. 解析目标页
  │     nav_target / expected / 用例目标名 / 文档目标
  │     → target_state_id 或 target_label（未绑定）
  │
  ├─ 2. 已在目标页？
  │     指纹 >= 0.80 → STEP_DONE（不再导航）
  │
  ├─ 3. 构建有效图
  │     published edges + verified entries（overlay）
  │     + 当前用例强相关的 candidate（仅探针层）
  │
  ├─ 4. 最短路径
  │     有路径 → ROUTE（正常 fsm_navigate）
  │     无路径 → 找“桥接入口”
  │
  ├─ 5. 入口规划
  │     先应用 priors 的顺序/先决条件
  │     candidates = entries(target, from=current, build, platform)
  │     + case_hypotheses(current step)
  │     + prior 的本次 run 临时动作
  │     → 排序、去重、冲突检查
  │
  ├─ 6. 有候选 → PROBE（一次一个 hop）
  │     无候选 → GAP（记录 + 阻断）
  │
  └─ 7. 注入提示/动作
        ROUTE: 【路由】...
        PROBE: 【入口】只允许点...
        GAP:   【入口缺口】禁止盲点...
```

### 6.3 规划算法（伪代码）

```python
def plan_entry(ctx, step, localized, nav):
    target = resolve_target(step, localized)
    if not target:
        return NoNavIntent()

    current = localized.chosen or ""
    if arrived(current, target):
        return AlreadyThere(target)

    graph = EffectiveGraph(
        published=nav.fsm.edges,
        verified=entry_store.verified(target.app_id, build=ctx.app_version),
    )

    # 1) 正常路由：只用 published + verified
    route = shortest_path(graph, current, target.state_id)
    if route:
        return RoutePlan(route, mode="trusted")

    # 2) 桥接：允许最多 1 条 candidate（探针），其余必须是 trusted
    candidates = entry_store.candidates(
        app_id=target.app_id,
        to_state=target.state_id,
        from_state=current,
        platform=ctx.platform,
        build=ctx.app_version,
    )
    candidates += case_hypotheses(step, current, target)
    candidates += prior_bridges(target, current, ctx)  # 仅本次 run 的临时动作，不写入口表
    candidates = rank(candidates, ctx, step)
    candidates = drop_conflicts(candidates)

    if candidates:
        return ProbePlan(candidates[0], max_attempts=2, expected=target)

    gap = entry_store.record_gap(
        target=target,
        from_state=current,
        reason=classify_gap(nav, current, target),
        case_id=step.case_id,
        step_index=step.index,
    )
    return BlockedPlan(gap, message=gap.user_message())


def rank(candidates, ctx, step):
    for c in candidates:
        c.score = (
            0.45 * source_weight(c.source_kind)
            + 0.25 * c.success_rate
            + 0.15 * context_match(c, ctx, step)   # same case/build/session
            + 0.10 * recency(c)
            + 0.05 * (1.0 / max(1, c.hops))
            - 0.10 * c.precondition_risk
        )
    return sorted(candidates, key=lambda c: c.score, reverse=True)
```

**关键约束**

- `trusted` 路径上不允许混入 `candidate`；`probe` 路径最多 1 条 `candidate`，其余必须是 `published/verified`。
- 如果桥接入口的 `from` 是"任意页"，但当前页不是它的来源，不允许直接用；必须先走 trusted 路由到它的 `from`，再探针。
- 如果目标页未绑定（`target_state_id=""`），探针仍可执行，但到达校验只能用 `target_label + 语义/结构`；成功后进入"页面候选绑定"，不自动建页。
- 如果 `graph` 里没有当前页（localize 失败），不允许从"任意页"猜；先走 `localize/recover`，再规划。

### 6.4 执行与到达校验

**执行前**

- 校验触发控件在当前层级可见；不可见时按 `trigger.scroll` 滚动后再找，最多 N 次。
- 校验先决条件：登录态、首次启动、协议、权限；不满足时交给 prior/登录链，不直接点目标。
- 校验预算：每步最多 2 次入口尝试；每次只执行 1 个 hop；同一入口同一 run 不重复试。

**执行**

- 通过现有 `navigation_policy` 派发 `tap_element` / `open_url` / `press_back`，不新增设备通道。
- 入口动作带 `params.entry_id`、`expect_state`、`expect_fingerprint`，供 `after_execute` 使用。
- 不允许 `multi_tap` 整段路径；多跳入口逐跳执行、逐跳观察。

**到达校验**

```python
def verify_arrival(target, before_fp, after_localized, after_nodes):
    if not after_nodes:
        return Pending("no_observation")

    changed = dom_fingerprint(after_nodes) != before_fp
    score = page_identity.match(target, after_nodes)

    if score >= 0.80 and changed:
        return Pass(score)
    if 0.62 <= score < 0.80:
        return RetryObserve("fingerprint_ambiguous", max_extra=1)
    if target.landmarks_any and any_in(after_nodes, target.landmarks_any) and changed:
        return Pass(score, via="landmark")
    if not changed:
        return Fail("no_transition")
    return Fail("wrong_destination", actual=after_localized.chosen)
```

- **"点击成功"不算到达**；必须看到页面变化 + 目标身份匹配（或明确地标）。
- `no_transition` 先等待/再观察一帧，不立刻重复点；超过 1 次等待仍无变化才失败。
- `wrong_destination` 记录实际页面，供 UI 解释；下一次候选排序会降低该入口。
- `fingerprint_ambiguous` 允许一次额外观察，不允许连续点不同控件。

### 6.5 防乱碰约束

对 `nav_intent` 步骤（有 `nav_target` / 期望页 / 指令明确"进入/打开/跳转"）：

`nav_intent` 由 `step_nav_plan.step_needs_nav_plan()` 和步骤目标判定，**不依赖 FSM 是否存在**；没有 FSM 时同样适用，否则"FSM 缺失"又会退回开放探索。

**允许的动作**

- `ROUTE` 指定的边；
- `PROBE` 指定的一个触发；
- prior/登录链的明确块；
- `press_back` 仅当路由/入口明确要求返回；
- `signal_ask_human` / `signal_give_up`；
- `wait` / `observe`（不改变页面）。

**禁止的动作**

- 任何不在计划里的 `tap_element` / `multi_tap` / `swipe` / `input_text`；
- "先点一下看看"的探索；
- 连续尝试不同控件超过预算；
- 在 `GAP` 状态下继续派发设备动作。

**执行方式**

- `navigation_policy.dispatch_pending()` 在原有逻辑前调用 `entry_runtime.next_action()`：
  - 返回 `RouteAction`：走现有 `fsm_navigate`；
  - 返回 `ProbeAction`：直接派发一条 `tap_element`/`open_url`；
  - 返回 `BlockedAction`：不派发，写 `nav/entry_gap`，注入 `signal_ask_human/give_up` 提示；
  - 返回 `None`：回退现有逻辑（非 nav_intent 步骤）。
- `GuardGate` / `nav_compiler` 增加一行硬约束：`GAP` 状态下禁止未列出的 tap。
- 如果模型仍然尝试乱点，先 `steer` 一次，再 `block`；block 原因写 `entry_gap`，不写"模型不听话"。

**为什么不是完全禁止所有探索**

- 普通业务步骤（非 nav_intent）仍需正常操作；
- 入口探针本身是"有边界的探索"，但必须有目标、有触发、有到达校验、有预算；
- 这样既解决乱碰，又不把整个 agent 变成只会走固定脚本。

### 6.6 前置条件与常识规则

**先决条件来源**

- 用例 `case_scene`：`required_session`、`platform`、`device_need`；
- 运行上下文：`picked_account`、登录态、`app_version`、`env_profile/surface`；
- 入口记录 `preconditions`；
- 页面 `role`：`protected`、`login`、`consent` 等。

**求值顺序**

```text
1. 系统浮层（权限/安装/选择器）
2. 首次启动协议/隐私
3. 启动页/闪屏
4. 登录门禁
5. 新手引导/升级弹窗
6. 目标页正常路由/入口
```

- 这个顺序是**默认 prior**，可按应用覆盖；但"系统浮层优先"不应被应用覆盖掉。
- 每一步只处理一个先决条件，处理完重新观察/重新规划；不把多个先决条件串成一个盲脚本。
- prior 命中但处理失败 → 记 `precondition_blocked` 缺口，不继续点目标页。

### 6.7 预算、重试、回滚

| 项 | 默认 | 说明 |
|---|---|---|
| 每步入口尝试 | 2 次 | 第 1 次失败后可换第 2 个候选；不无限试 |
| 每步额外观察 | 1 次 | 用于 `fingerprint_ambiguous` / `no_transition` |
| 多跳入口 | 最多 5 跳 | 超过则不建议作为入口，改用文档/人工拆解 |
| 同一入口同 run | 1 次 | 防止重复点 |
| 连续失败降级 | 2 次 | `candidate → rejected` / `verified → stale` |
| 缺口阻断 | 立即 | 本步不再派发设备动作；本 case 可继续非导航步骤或按策略停止 |

**回滚**

- 探针失败后，如果当前页已偏离来源页，优先 `press_back` 回来源页（仅当路由/入口明确），否则重新 localize 后再规划。
- 不回滚已经成功的业务步骤；入口探针只影响导航，不撤销用户输入/提交。
- 探针产生的页面跳转要写会话，不能"静默恢复"。

**探针 API 的边界**

- `POST /entries/{id}/probe` 只创建一次真实 run，参数含 `sn`/`env_profile`/`env_surface`；
- 不在 API 里直接操作设备；仍由 `case_runner` 走 Scout；
- 探针 run 标记 `run_type="manual"`、`source="entry_probe"`，在会话里可识别；
- 返回 `run_id`，UI 轮询/订阅结果；不阻塞 HTTP。

**抽取 API 的边界**

- 文档抽取可能耗时，走后台 job（复用现有 job 机制），返回 `job_id`；
- 抽取结果只写 `candidate`；不直接 publish；
- 目标未绑定的 claim 也保存，但 `target_state_id=""`，UI 显示"待绑定"。

## 8. 覆盖度与验收

### 8.1 指标

| 指标 | 定义 | 目标 |
|---|---|---|
| `entry_coverage` | 有至少 1 条 `verified/published` 入口的页面 / 页面总数 | 逐迭代上升 |
| `reachable_rate` | 从启动页/首页经 trusted 图可达的页面 / 页面总数 | 逐迭代上升 |
| `gap_count` | 打开的缺口数（按目标页去重） | 下降；新增页面允许短期上升 |
| `median_gap_age` | 缺口从首次发现到关闭的中位时长 | 下降 |
| `probe_success_rate` | `nav/entry_attempt` 成功 / 总尝试 | 上升 |
| `nav_blocked_by_gap_rate` | 因入口缺口阻断的导航步骤 / 导航步骤 | 先升后降（先暴露问题） |
| `random_nav_tap_rate` | 未绑定 route/entry/step 的点击 / 导航步骤 | 接近 0 |
| `wrong_destination_rate` | 到达了非目标页 / 探针次数 | 下降 |
| `fingerprint_precision` | 人工审核为"确实是该页"的匹配 / 审核样本 | >= 0.95 |
| `case_target_resolution_rate` | 用例目标名解析到页面的比例 | 上升 |

### 8.2 验收场景（用真实会话，不写 pytest）

**A. 无入边，但用例给了入口**

- 用例：`首页点击「做成真的」进入提单页`；图中无 `首页 → 提单页`。
- 期望：
  - `nav/entry_plan` 显示 `mode=probe`，候选来源 `case`；
  - 只点击 `做成真的`，不点其他控件；
  - `nav/entry_attempt` `result=pass`，目标指纹 >= 0.80；
  - 工作台该入口状态 `candidate`，成功次数 +1。

**B. 完全没证据**

- 用例只写 `进入提单页`，没有动作，图中无路径。
- 期望：
  - 第一轮导航就写 `nav/entry_gap`，`reason=target_only`；
  - 不产生任何未绑定点击；
  - 工作台"入口缺口"出现该页，可手工补录；
  - case 结果明确说明"缺入口"，不是"模型没找到"。

**C. 首次启动协议在登录前**

- 首次启动，目标登录页，当前协议弹窗。
- 期望：
  - prior `first_launch.consent` 命中；
  - 先处理协议，再进入登录；
  - `nav/entry_plan` 显示 `priors=["prior.first_launch.consent"]`；
  - 不把协议弹窗当登录页。

**D. 文档抽取**

- 上传 PRD，含"首页点击‘我的’进入个人中心"。
- 期望：
  - 抽取卡片带原文引用；
  - 目标 `个人中心` 未绑定时不能批准；
  - 绑定后批准为 `verified`；
  - 下一次正常运行可用，不要求先发布。

**E. 指纹区分同壳页面**

- 两个页面都有底栏和标题栏，但结构不同（一个表单、一个列表）。
- 期望：
  - `fingerprints/test` 对正确页 >= 0.80，对另一页 < 0.62；
  - 若 top1-top2 < 0.06，返回歧义，不自动选。

**F. 构建漂移**

- 入口属于 1.2.2，当前 1.2.3，指纹相似度 0.55。
- 期望：
  - 入口标 `stale`，不进入 trusted 路由；
  - 缺口 `fingerprint_low` 出现；
  - 可用一次探针验证；成功则恢复 `verified`，失败保持 `stale`。

**G. 不影响普通步骤**

- 非导航步骤（填写、断言、滚动）不受入口 gate 影响。
- 期望：原有能力照常；只有 `nav_intent` 步骤被约束。

### 8.3 观测方式

- 查 `session_events`：`nav/entry_plan`、`nav/entry_attempt`、`nav/entry_gap`、`nav/entry_promote`。
- 查 `session_meta`：run 状态、失败摘要。
- 查 Workbench：页面地图、缺口、入口详情、会话"导航决策"。
- 不新增 `tests/test_*.py`；不以 pytest 作为验收。

## 10. 风险与开放问题

### 10.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 结构指纹误配同壳页面 | 到达错误页 | 语义/地标二次校验；歧义不自动选；人工审核 |
| 指纹随构建漂移 | 入口失效 | build scope + stale + 探针恢复 |
| 用例推导错 from | 探针点错入口 | `from` 不确定时降权；探针仅在有界范围；失败回写 |
| 文档抽取幻觉 | 假入口 | 强制引用；目标绑定；人工审核；不直接发布 |
| 过度阻断 | 普通步骤被误伤 | 只约束 `nav_intent`；非导航步骤保留原能力 |
| 探针本身乱点 | 仍是乱碰 | 一次一个 hop、触发可见、到达校验、每步 2 次预算 |
| 入口表膨胀 | 查询/UI 卡 | 去重、索引、分页、按 app/build 过滤 |
| 多账号状态 | 入口只在某账号可用 | `preconditions` + 账号 facet；scope 校验；不存凭据 |
| 迁移风险 | 旧库启动失败 | 加性迁移、CREATE IF NOT EXISTS、启动前严格校验 |
| 证据隐私 | 泄露页面文案/账号 | 只存必要字段；会话证据鉴权；不存密码 |

### 10.2 开放问题（建议默认）

1. **页面地图放顶级 tab 还是"应用逻辑"子页？**  
   建议顶级 `页面地图`：它跨用例、跨页面，和"应用逻辑"的控件编辑不是同一任务。
2. **用例抽取在编译期自动跑，还是用户点"从用例生成"？**  
   建议编译期生成 `candidate`（不阻塞编译），UI 默认展示待审数量；用户可手动触发重跑。
3. **文档抽取用 LLM 还是纯规则？**  
   建议"路由表/表格优先规则，正文用 LLM + 强制引用"；没有引用的结果直接丢弃。
4. **verified 入口是否自动 publish 到 nav_fsm？**  
   建议默认不自动；verified 已可用于运行时 overlay，publish 是维护者的显式动作，避免图膨胀。
5. **常识规则是否允许应用覆盖？**  
   建议允许应用级覆盖，但"系统浮层优先"不可覆盖；所有覆盖留审计。
6. **指纹按构建还是按应用存？**  
   建议 `meta.page_fingerprint` 存最新稳定规范；样本表按 `platform + build` 存历史；运行时按当前构建降权。

## 附：一页纸时序（给实现者）

```text
refresh_step_navigation(step)
  ├─ target = resolve_target(step)
  ├─ entry.bind(target, current_page)
  │    ├─ known route?  → RoutePlan
  │    ├─ candidates?   → ProbePlan(one hop, expected fingerprint)
  │    └─ none?         → record_gap + BlockedPlan
  └─ inject 【导航】/【入口】/【入口缺口】

each turn:
  nav.observe()
    ├─ localize with structure_fingerprint
    ├─ entry.on_observe()
    └─ if probe pending: verify_arrival()
  decide:
    ├─ RoutePlan  → fsm_navigate
    ├─ ProbePlan  → tap the one trigger
    └─ Blocked    → signal_ask_human / signal_give_up
  after_execute:
    ├─ pass → entry success_count++
    ├─ fail → entry fail_count++, maybe stale
    └─ gap  → close if entry verified
```

**最重要的验收标准：** 当目标页没有可信入口时，会话里出现的是 `nav/entry_gap` 和明确的缺口，而不是连续多次无依据的点击。

## 附录 D：开源方案评估（bdd2pw / playwright-testgen-from-gherkin-js）

> 评估日期：2026-10-26。只评估“能否替换/引入入口图谱”，不评估它们作为独立工具的价值。

### D.1 结论

**不建议把任何一个项目作为运行时依赖或入口图谱的替代实现。**

它们解决的是**“Gherkin → Playwright TypeScript 测试代码”的编译期脚手架**；本文解决的是**“用例步骤 → 目标页 → 入口证据 → 运行时到达校验”的运行时导航知识**。两者只在“解析步骤、识别动作、选择定位器”这一小段重叠，核心问题不重叠。

可以借鉴它们的**步骤归一化、规则来源标注、定位器优先级、审核报告、增量更新**思路；不建议直接搬 Playwright 运行时、POM/spec 生成器或 Node 服务。

### D.2 两个项目实际做了什么

#### bdd2pw

- 仓库：<https://github.com/javvadivijayprasad/bdd2pw>（MIT）

  - `ts-morph` 扫描已有 `pages/*.page.ts`，做 `reuse / augment / create` 三路决策。

### D.4 为什么不能直接替换

1. **阶段不同**：它们是编译期代码生成；本文是运行时导航。生成的 Playwright spec 再完整，也不能告诉 Nexus“当前 Android 页面是哪个、从首页怎么进提单页、进不去时缺口是什么”。
2. **执行模型不同**：MinoNexus 不 import/运行 Playwright，设备动作经协议交给 Scout；引入 bdd2pw 的 Chromium 启动/POM 执行等于在 Nexus 里再开一条设备通道，违反现有硬约束。
3. **输入模型不同**：它们的输入是 Gherkin `.feature`；我们的输入是 `ProjectCase` 步骤、采集 turn、文档、设计稿、常识规则。Gherkin 只是其中一种可选格式。
4. **输出模型不同**：它们输出 TS 代码；我们需要的是 `nav_page_entries` / `nav_page_gaps` / `PageEntryPlan` 这类可查询、可追溯、可回写的数据；本版不做人工审核。
5. **核心缺口正好是它们的非目标**：bdd2pw 自己把多页面导航、登录流程、运行时自愈列为 deferred/out of scope；这些恰是本文要解决的部分。
6. **工程代价**：bdd2pw 是 Node/TS + Playwright + Express + 20 多个依赖；作为 sidecar 会新增部署单元、job 系统、依赖升级和安全面。其收益（生成 TS 测试）与我们的执行链不匹配。
7. **成熟度**：bdd2pw 有测试和真实 fixture，但社区规模很小（约 4 stars、29 open issues），且是较新的项目；第二个项目更小、更新停在 2025-06。把入口图谱关键路径押上去，风险高于自研一个小而专的入口层。

### D.5 可以借鉴什么（不引入依赖）

| 可借鉴点 | 怎么用 | 不建议 |
|---|---|---|
| Step normalizer | 在 `casework/entry_extract.py` 里做中文/英文步骤归一：全半角标点、引号、空白、尾部括号；把“点击/轻触/点一下”“进入/跳转/打开”收敛 | 直接复制英文正则；我们的用例是中文为主 |
| 规则来源标注 | 每条抽取结果带 `rule_id`、`confidence`、`warnings`，UI 可解释“为什么判成入口” | 只给一个黑盒置信度 |
| 定位器优先级 | 给入口 trigger 定义稳定优先级：resource-id > content-desc > text > class+index > xpath；先做唯一性校验 | 把 Web 的 `getByRole` 顺序照搬到 Android |
| 缺口报告 | 借用 `BDD_REVIEW.md` 的“未匹配/歧义”清单，落到入口缺口和 `nav/entry_gap`；不做人工审核 | 生成一个只有开发能看的 Markdown |
| 增量更新 | 借用 `update-pom` 的 append-only/保留人工修改思路，用于入口重新抽取时合并而不是覆盖 | 每次重抽都重建全部入口 |
| DOM 漂移 hash | 作为“页面结构变了”的快速辅助信号，和我们的结构指纹并存 | 用 accessibility tree sha256 代替页面身份/相似度 |

### D.6 建议

**短期（本文 P0/P1）**

- 不引入两个项目，不新增 Node sidecar。
- 在 `entry_extract` 中实现一个小的步骤归一化 + 规则表，吸收 bdd2pw 的“规则可解释、未命中留缺口”原则。
- 入口 trigger 的定位器优先级和唯一性校验，按 Android/Web 各自定义，不照搬 Playwright。
- 继续用本文的 `nav_page_entries` + `nav_page_gaps` + `EntryRuntime`。

**中期（本轮明确不做）**

- 不把 Gherkin 导入、Playwright 代码导出接入入口图谱；也不新增 Node/Playwright sidecar。
- 如果未来业务真的需要，只作为**独立离线工具**评估，输出到代码仓，不接入 Nexus 运行时，更不进入入口关键路径。
- 当前入口知识只来自用例步骤、已采集 Atlas 边和代码内通用顺序常识；入口抽取后直接 active。

**判断标准**

如果需求变成“把 Gherkin 批量变成可跑的 Playwright TS 测试”，bdd2pw 值得做一次 PoC；如果需求仍是“用例执行时可靠进入目标页、没有入口就报缺口”，本文的方案更直接，开源项目替代不了。

## 附录 F：页面/控件语义收口（2026-10-27）

### F.1 为什么要收口

旧实现把用例里的整句 `nav_target` 当成页面，把 `source_clause` 当成控件兜底，导致：

- `已配置新人折扣的商品详情页`、`退款成功后的该商品详情页` 变成两个页面，而不是同一页面的两个业务状态；
- `生成分享海报或分享至微信生成海报页面` 变成页面，而它其实是“进入海报页”的动作；
- `放弃支付并返回，可通过点击返回或取消实现` 变成页面，而它是流程；
- `进入相机页面后`、`查看提单页吸底模块`、`相机页面状态` 被写成控件，而它们是导航/断言。

收口后的模型：

| 概念 | 边界 | 落点 |
|---|---|---|
| Page | 结构指纹 + 页面角色；名字是短名词 | `nav_fsm_states`（`meta.page_key` 相同即同一页） |
| PageState | 同一页面的业务状态（新人折扣 / 退款成功后 / 支付成功后） | `nav_fsm_states.meta.variant`，不新建页面 |
| Control | 明确的可操作元素/容器 | `ui_controls`；只接受 `semantic_role=element` |
| Action | 步骤级动作（进入、点击、返回、支付） | `do_program_plan.steps`；不写控件表 |
| Assertion | 检查/观察/状态断言 | `check_program_plan.checkpoints`；不写控件表 |
| CaseRef | 用例步骤 → 页面/控件的关系 | `nav_case_page_refs`（`enters` / `operates` / `asserts`） |
| Entry | Page A + 触发控件 → Page B | `nav_page_entries`，运行时只允许单跳并验证到达 |

页面身份仍以 `nav_fsm_states.state_id` 为运行时键；`page_key` 只用于“同一页面的多个状态”聚合，不替换 state_id。

### F.3 判定规则（通用中文，不写死 App）

- 页面目标优先使用规范短名：去掉“已配置…的”“…成功后的”“首条”等修饰；`首条` 落为 `data.position=first`，不是页面状态。
- `进入/跳转/打开/返回 + 页面名词` → `nav`；`生成/分享/支付/授权 + 页面名词` 若主要动作是动作，仍可提取页面目标，但角色是 `action`，仍按页面引用处理。
- `查看/观察/检查/停留在/…状态` → `assertion`，不进控件。
- `放弃/返回/取消/并/，` 组成的流程句 → `flow`，不生成页面；缺页面身份只记缺口。
- 旧 `case_flow` 长句：能提取出规范短页面的 `rename`；同一 `page_key` 的重复状态 `merge`；动作/断言/流程 `reject`；已有采集页的“同页” `attach`。
- 删除不是策略：错误页标 `semantic_status=rejected`，控件保留但 Workbench 不再当元素显示；运行时的 `resolve_state_fuzzy` / 边解析也会跳过 rejected 状态，避免旧入口把执行带回流程页。
