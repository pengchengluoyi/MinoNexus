# 执行链路性能优化

> **状态**：第一轮已落地（任务表读写、启动计时、session 耗时汇总、重复守卫熔断）。后面的改动只在新跑出来的数对得上时再做。  
> **关联**：[开发手册](../../开发手册.md)、[Session Log 与数据库](../../排查手册/01-Session-Log与数据库.md)、[渠道跳过、步骤时序与守卫恢复](../V2/渠道跳过-步骤时序与守卫恢复方案.md)

Studio 上两段体感：点「新建执行」时加载很久；一条任务跑起来也久。先用 2026-09-29 的只读库把时间拆开，再改已经能对上的热路径，并把拆分后的耗时写进启动返回值和 session，方便下一轮只打最大的那一块。

原则：

- 用户感受到的是墙钟。优化前先分清这段墙钟在服务端哪一段。
- 跑批以 `session_events` 为准，不为验证去写 pytest，也不要为了「看一看」去改 `mino.db`。
- 一次只打当前最大的桶。单次模型调用本身的 4–7 秒，在调用次数没有降下来之前不动。

## 1. 基线（2026-09-29，只读 `~/.mino-nexus/mino.db`）

| 对象 | 当时的量 |
|------|----------|
| 库文件 | 约 4.1GB |
| `app_regression_runs` | 400 行，payload 合计约 560MB；最大一条约 30MB |
| `session_events` | 约 29.8 万行，payload 约 3.3GB |
| 在途任务查询（扫完全表 payload） | 约 1.5 秒，还不含解析 |

最大的任务行几乎全是 `cases[].engine_steps[].thumb`。单张约 45KB。同一张图已经在 `observe/screen` 里。

### 1.1 新建执行

Studio「新建执行」会并行打三类请求，弹窗要等它们回来：

| 请求 | 作用 |
|------|------|
| `GET /case-runner/devices` | 在线设备，以及每台是否被任务占用 |
| 项目用例 | 弹窗里的用例树 |
| 项目环境 | 被测应用、运行环境 |

点「启动」再等 `POST /case-runner/run` 返回 `run_id`，按钮上的加载才结束。

当时 `GET /case-runner/devices` 对每台设备各查一次全部任务；`put` 保存一条新任务时，把最多 400 行 payload 读进内存再整表写回，而且启动路径上写了两遍。弹窗的等待主要在这里，不在用例条数。

### 1.2 任务执行

墙钟对得上 `llm/response.elapsed_ms` 与 `tool/result.elapsed_ms` 之和（量级）：

| 会话 | 墙钟 | 大模型 | 设备动作 |
|------|------|--------|----------|
| `cr-1e22f71f64ec::case-a6f46fa9` 通过 | 约 2 分 20 秒 | 88 秒 / 23 次 | 8 秒 |
| `cr-838c253ff785::case-0aebc156` 失败 | 约 2 分 30 秒 | 109 秒 / 28 次 | 26 秒 |
| `cr-1e22f71f64ec::case-a107f75c` 失败 | 约 6 分 30 秒 | 295 秒 / 87 次 | 0.1 秒 |

单次看图决策大约 4–7 秒。点击大多不到 1 秒。`assert_visual` 自己又是一次模型调用，大约 5–7 秒。

`…a107f75c` 停在 prep：焦点一直是「打开被测应用」，模型连续 87 次 `launch_app`，守卫 `skip_repeat_launch_app` 每次都拒绝（应用已在前台），里程碑不往下走。每一轮仍截图、组上下文、再调模型。`fuse_block_streak` 为 0。这一条的写法见 [渠道跳过文档 §2.1](../V2/渠道跳过-步骤时序与守卫恢复方案.md)：已满足的焦点应标 `pass` 并抬起下一条，而不是空转。

同一条会话里，`stream/emit`、`observe/screen`、`context/trace` 合计约 16MB。这会拖慢日志查询，但不是那 4–7 秒的主体。

## 2. 已经做的优化

重启 Nexus 后生效。

### 2.1 任务表按行读写

`mino_nexus/services/run_store.py`

| 以前 | 现在 |
|------|------|
| `put` 读出全部任务再整表 merge，并删掉不在这 400 条里的行 | 只 upsert 当前这一行；超过 400 条时按 `started_at` 删最旧的 |
| `get` / 列表 / 查占用都先把 payload 全读出来 | 先按 `run_id`、`status`、`started_at` 取出本页 id，再只读这些行的 payload |
| 设备列表对每台设备各扫一遍任务 | `running_index()` 只读 `status=running`，整页设备共用这一次 |

`mino_nexus/core/migration.py` 在启动时补索引 `ix_app_regression_runs_started`（`started_at`），让「最近 N 条」不必为了排序去碰 payload。

`GET /case-runner/devices`（`mino_nexus/routers/rCaseRunner.py`）改为调用一次 `running_index()`。

### 2.2 新任务不再把截图写入任务行

`put` 前清掉 `engine_steps[].thumb`。详情时间线的图仍从 session 的 `observe/screen` 合并（`merge_engine_thumbs`）。

读历史大行时，payload 超过 200KB 且含 `"thumb"`，先把截图字段换成空串再 `json.loads`，避免解析几十 MB 的 base64。**已经落在库里的旧行，磁盘上仍然很大**，打开任务列表第一页还会读到它们。新跑的任务不会再涨上去。

启动路径上去掉了紧跟在首次 `put` 后面的第二次 `persist_run_finish`。失败收尾仍会 `finish`，那一次写入是终态，保留。

### 2.3 启动分段计时

`mino_nexus/loop/case_runner.py` 的 `run_cases` 打四个点。数值是从进入 `run_cases` 起的**累计毫秒**，不是该段单独耗时。相邻两点相减才是这一段：

| 名字 | 累计到哪里 |
|------|------------|
| `cases` | 用例列表取完 |
| `devices` | 设备名册与在途占用查完 |
| `assembled` | 环境、包名、provider、用例种子组完，尚未落库 |
| `persisted` | 这一行已经写入 |

日志：

```text
CaseRunner boot run=cr-… cases=… devices=… assembled=… persisted=…
```

任务 JSON 带 `boot_ms`、`boot_phases`（`POST /case-runner/run` 的返回，以及之后的任务详情）。内存里的 `boot_ms` 含落库；第一次写入磁盘的那一版少了 `persisted` 这几个毫秒，下一次 `patch_case` 会把内存里的数写回去。

设备名册在这次启动里只拉一次，不再按 sn 各拉一遍。

### 2.4 Session 耗时

`mino_nexus/loop/session_log.py` 的 `SessionWriter`：

| 事件 | 新增字段 |
|------|----------|
| `turn/end` | `elapsed_ms`：本轮从 `turn/start` 到 `turn/end`。调用方已经写入的 `elapsed_ms` 不覆盖 |
| `perf/summary` | 会话结束前写一条，见下表 |
| `session/end` | `wall_ms` |

`perf/summary`：

| 字段 | 含义 |
|------|------|
| `wall_ms` | 从 `open_session` 到 `close` |
| `llm_ms` | 本会话全部 `llm/response.elapsed_ms` 之和 |
| `tool_ms` | 本会话全部 `tool/result.elapsed_ms` 之和 |
| `other_ms` | `wall_ms - llm_ms - tool_ms`，且不小于 0。截图、组上下文、守卫、落 session 都在这里 |
| `guard_blocks` | `guard/block` 条数 |
| `turns` | 结束时的 turn 计数 |

`llm_ms` 与 `tool_ms` 按事件累加，默认它们在同一条线程上前后发生，不重叠。若以后出现并行模型调用，这两个和可以大于 `wall_ms`，此时 `other_ms` 为 0，以 `wall_ms` 为准。

查最近几次：

```sql
SELECT session_id, seq,
       json_extract(payload,'$.wall_ms')  AS wall,
       json_extract(payload,'$.llm_ms')   AS llm,
       json_extract(payload,'$.tool_ms')  AS tool,
       json_extract(payload,'$.other_ms') AS other,
       json_extract(payload,'$.guard_blocks') AS guards,
       json_extract(payload,'$.turns')    AS turns
FROM session_events
WHERE type = 'perf/summary'
ORDER BY rowid DESC
LIMIT 20;
```

单轮：

```sql
SELECT seq, turn, phase,
       json_extract(payload,'$.elapsed_ms') AS ms,
       json_extract(payload,'$.decision_cap') AS cap,
       json_extract(payload,'$.decision_status') AS st
FROM session_events
WHERE session_id = 'cr-…::case-…'
  AND type = 'turn/end'
ORDER BY seq;
```

### 2.5 重复守卫熔断

`mino_nexus/loop/agent_loop.py`：同一条 `skip_repeat_*` 在本用例里累计拒绝达到 3 次，停止该用例，摘要写明守卫 id。这是兜底，避免再出现 87 轮空转。前两次仍会付完整的截图和模型成本。根因仍是焦点没有在第一次拒绝时标成已完成，见渠道跳过文档 §2.1。

## 3. 后续任务

下面 5 项按顺序做。前一项的数没有出现，就不要开下一项。

| # | 任务 | 什么时候做 | 规模 |
|---|------|------------|------|
| 1 | 重启后采一轮新的 `boot` 日志和 `perf/summary`，和 §1 的旧墙钟对照 | 立刻。没有这组数，后面都是猜 | 只观测 |
| 2 | 历史任务行去掉 thumb（只动 `app_regression_runs.payload`，不动 session） | 任务列表或 `boot` 的 `persisted` 仍以秒计，且慢在读旧行 | 一次压缩，约 400 行 |
| 3 | 确认「已满足则 pass 并抬下一条焦点」在 `skip_repeat_launch_app` 上真的写出 `milestone/already_satisfied` | `perf/summary.guard_blocks` ≥ 3，或同一 `guard_id` 连续出现 | 小，沿用渠道跳过 §2.1 |
| 4 | 同一屏、同一 cap 被拒后，跳过下一轮截图和模型 | `llm_ms / wall_ms` > 0.7，且 `turns` 明显多于 `tool/result` 条数 | 中，只减调用次数 |
| 5 | 缩小每轮写入：`stream/emit`、`observe/screen`、`context/trace` 不要各存一份图 | `other_ms` 接近 `llm_ms`，且单条 `observe/screen` 仍是几十 KB | 中 |

不做的事：

- 不先优化单次模型的 4–7 秒。次数降下来之后，这段才是下一轮的墙钟。
- 不把设备操作搬回 Nexus。
- 不用 pytest 证明变快。用 §4 的查询。

Studio 弹窗若在服务端 `boot_ms` 已经很小之后仍然久，差值在客户端：`loadCases`、`loadDevices`、`loadRunEnvironments` 三者谁返回得晚。那一刀在 Studio，不在本仓继续加服务端缓存。

## 4. 怎么根据插桩继续优化

一轮新任务跑完，按这个顺序看，只处理第一个超线的桶。

### 4.1 启动

看 Nexus 日志里的 `CaseRunner boot`，或返回 JSON 的 `boot_phases`。用后一个点减去前一个点：

| 差值 | 超线（先用 500ms） | 下一刀 |
|------|-------------------|--------|
| `cases` | 用例列表 | `list_app_cases` / 项目用例读取 |
| `devices − cases` | 设备与占用 | `running_index`、名册 |
| `assembled − devices` | 环境、包名、provider | `project_env`、`package_for_app`、`resolve_regression_provider` |
| `persisted − assembled` | 落库 | 这一行 payload 是否又变大（thumb 是否漏清） |

三条都低于 500ms，而 Studio 弹窗仍久：记下接口耗时和 `boot_ms` 的差，转到 Studio 看并行的三个请求。

### 4.2 执行

先看该会话的 `perf/summary`，再决定下钻：

| 最大的一块 | 下钻 | 下一刀 |
|------------|------|--------|
| `guard_blocks` ≥ 3 | `guard/block` 的 `guard_id` 是否同一条；有没有 `milestone/already_satisfied` | 任务 3。熔断已经会停，目标是第一次拒绝就抬焦点 |
| `llm_ms` 占 `wall_ms` 七成以上，且 turn 数远多于工具次数 | 连续 `turn/end` 的 `decision_cap` 是否重复；`observe/screen` 的 `screen_fp` 是否没变 | 任务 4。少调模型，不改模型本身 |
| `tool_ms` 最大 | 按 `tool/result.capability_id` 汇总 `elapsed_ms`，看 p75 | 只改那一个能力（例如 `assert_visual`、`relogin`、`input_text`） |
| `other_ms` 接近 `llm_ms` | 按 `type` 汇总 `length(payload)` | 任务 5。先砍重复的截图字段 |

工具汇总：

```sql
SELECT json_extract(payload,'$.capability_id') AS cap,
       COUNT(*) AS n,
       SUM(json_extract(payload,'$.elapsed_ms')) AS ms
FROM session_events
WHERE session_id = 'cr-…::case-…'
  AND type = 'tool/result'
GROUP BY cap
ORDER BY ms DESC;
```

模型是否在空转：

```sql
SELECT json_extract(payload,'$.job') AS job,
       COUNT(*) AS n,
       SUM(json_extract(payload,'$.elapsed_ms')) AS ms
FROM session_events
WHERE session_id = 'cr-…::case-…'
  AND type = 'llm/response'
GROUP BY job;
```

### 4.3 收束

每一项改完，用同一条查询再采一次，只比较这一项的数：`boot` 的那一段差值，或 `perf/summary` 里对应字段。数没有下降，就撤回这一项，不要叠上下一项。

旧的 560MB 任务行不会因为这次代码自动变小。任务 2 做之前，列表第一页仍可能慢；启动新任务和查在途设备不应该再扫这 560MB。
