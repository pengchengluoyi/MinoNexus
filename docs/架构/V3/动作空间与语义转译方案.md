## 1. 先把安卓这次说准

安卓这条没有跳过看图执行。`exec/vision` 和 `llm/response`（`job=agent-vision-exec`）都在点击之前。模型返回的文案是「发送验证码」，Scout 再用层级里的 `content_desc` 点中节点，回执是 `via content_desc`。模型给出的千分比没有成为最终落点。

浪费发生在顺序上：文案已经和节点对上了，仍然先付一次看图（约 3.5–5 秒），然后设备侧丢掉坐标、改点节点中心。Web 同一步也打了看图，但页面上没有和「发送验证码」同字的按钮，模型把绿色主按钮说成 Continue，派单文案是「通过 Google 继续操作」，像素落点与千分比一致。

所以两端不是「一个走 DOM、一个走视觉」。两端都走了视觉，再在派单时混进 DOM：


|        | 看图有没有跑 | 最终谁决定落点            | 为什么点对或点错                                |
| ------ | ------ | ------------------ | --------------------------------------- |
| 安卓发码   | 有      | Scout 文案锚点         | 按钮字和里程碑标题相同                             |
| Web 发码 | 有      | 模型坐标（Web 不按文案重找节点） | 里程碑是中文「发送验证码」，主按钮是 Continue / Google 继续 |


多语言差异是同一套里程碑标题打在不同屏幕文案上。安卓碰巧同字，Web 没有同字，模型就选画面上最显眼的「继续」。

## 2. 现在混在什么地方

`mino_nexus/loop` 里大约 86 个模块，回合状态机和设备动作写在一起。一次 `tap_element` 实际经过：

1. 看图执行按里程碑标题「发送验证码」出坐标，常常还带一句按钮文案。
2. `enrich_tap_params` 在缺坐标时用层级补点；已有坐标不覆盖，但会留下文案。
3. `lift_selector_target` 把文案写进 `params.target`。
4. Web 再打上 `web_coordinate_only`，Scout 用千分比换视口像素后 `mouse.click`，不按文案重找。
5. 安卓 Scout `_point_for` 先用 `target` 对层级。对上了就点节点中心，模型坐标作废。对不上再把千分比换成像素，并吸附到附近可点节点。

视觉坐标和 DOM 搜索绑在同一次点击上。任一侧「帮忙修正」都会让另一侧的结果消失，而且回执仍是 pass。登录程序链、发码按钮几何、邮箱读回也堆在 `loop` 里，读一条点击要跨编排、转译和渠道三套规则。

Nexus 仍然不连设备。拆目录不能把 `adb` / `uiautomator` / `playwright` 引进来。安卓和 Web 的差异只体现在 **EXECUTE 载荷怎么组装、Scout 承诺怎么解释**。真正的点击还在 Scout。

## 3. 目录：留在 loop 的，和挪出去的

不把 `loop` 整包搬进新目录。状态机（阶段、里程碑、守卫、熔断、会话）留在 `loop`。它只决定「这一步要哪个意图、走视觉还是走 DOM」，然后调用同级的两个包。

```text
mino_nexus/
  loop/            回合。不组装渠道载荷，不解释按钮文案
  action_space/    交给 Scout 的动作
    visual/        只出 x,y（及输入文本）。不补 selector，不吸附节点
    dom/           只出 target / 节点中心。不用模型坐标补洞
    web/           Web 载荷：千分比、web_coordinate_only
    android/       安卓载荷：锚点或坐标二选一，写明 Scout 会不会改点
  semantic/        意图转译。登录动词的多语言表面形式和互斥关系
```

`action_space` 是载荷策略，不是设备驱动。`android/` 与 `web/` 分开，是因为今天 Scout 对同一份 `target + x,y` 的解释相反：安卓文案优先，Web 坐标优先。把这两份解释写在同一个函数里，就会继续出现「模型点了 A、设备点了 B、里程碑算通过」。

搬迁按边界做，不按文件数做。先让 `agent_loop` 的点击出口只走 `action_space` 的一个模式，再把 `tap_enrich`、`device_execute_params`、`ui_dom`、`ui_sms_request` 的调用点挪过去。一次搬完 86 个文件会把还没稳定的登录行为再打散。

## 4. 同一套工具，两条互不改写的路径

一条点击只属于一种模式。禁止「视觉给点、DOM 再改点」或「DOM 没命中、悄悄吸附到别的节点仍算 pass」。

**视觉路径。** 模型产出的动作种类保持该阶段扩展包里的设备技能，不收成只有点、输入、滑。坐标夹到 0–1000 后原样放进 EXECUTE，不写 `target`。Scout 按这个点操作，不再做文案锚点，也不再吸附邻近节点。输入是否写上靠动作后的节点值，不靠回执里有没有 `@` 或「输入 N 字」。程序独占的 hook 不进这一步的菜单，见 §7。

**DOM 路径。** 模型或程序只产意图和节点条件。Nexus 在当前树上找节点，EXECUTE 只带节点标识，不带可回退的模型坐标。找不到就失败，不改走看图。找到了，安卓这种「字和节点一致」的发码可以跳过看图，省掉那次 3.5–5 秒。这才是第 1 点要去掉的浪费。

Web 与安卓都按 `point_policy` 分开。`coordinate` 只点 `x,y`，不按文案改点，也不吸附邻近节点。`node` 只点锚点，锚点未命中就失败，坐标不参与。未带 `point_policy` 但有 `x,y` 时按坐标处理。

选择由用例或上下文的 `action_scheme` 指定，两条方案不因对方失败改道：

- `action_scheme=visual`（缺省，新建执行的「看图」卡片）：只走看图。模型产出点、输入、滑动等基础动作，载荷是 `point_policy=coordinate`。不查 DOM 来决定点哪里。点下去即记成功，不等下一回合对可点表。没有坐标则注入「上次没给坐标」后重试，最多 3 次，然后熔断。
- `action_scheme=dom`（「DOM」卡片）：只在当前树上做整词唯一命中。命中则 `point_policy=node`。没有唯一命中、或层级没有可点坐标，记 `semantic/miss` 或锚点失败，不打看图。
- 同一条点击不会先试一套再改另一套。

## 5. 语义转译层

里程碑标题「发送验证码」是意图，不是屏幕上的字。转译层把意图变成当前语言下可以点的表面形式，以及明确不能点的表面形式。数据放在 `semantic/`，按意图 id 索引，不写进导航、合成或某个 App 的 Tab 表。

登录先覆盖这两个意图。例子就是这次对错的分界：


| 意图             | 可以点                                             | 不能点                                             |
| -------------- | ----------------------------------------------- | ----------------------------------------------- |
| `send_code`    | Send、Send code、Get code、Resend、发送验证码、获取验证码、重新发送 | Continue、通过 Google / Apple 继续、登录、Log in、Sign in |
| `submit_login` | 登录、Log in、Sign in；验证码框里已经有 4–8 位数字之后的 Continue  | 发码按钮、第三方继续                                      |


Continue 的消歧靠上下文，不靠单词本身。验证码还没进框时，Continue 不是发码。验证码已经在框里时，Continue 可以是提交。第三方继续（「通过 Google 继续操作」）两条意图都排除，它是另一条账号通道。

用例步骤写「输入手机号或邮箱验证码并登录」时，转译层按当前 in_progress 的意图 id 取表，不按整句步骤去猜。看图路径把「可以点 / 不能点」放进这一步的说明。DOM 路径只用「可以点」去对节点，对上多个时失败，不挑面积最大的那个。

这一层用表就能挡住这次 Web 的误点。表外说法（「获取短信验证码」）记进 session，再补进该步的 `match`，不为此加载本地模型。字段放在现有登录块步骤上，见 §8。

## 6. 一次看图为什么有 `llm/response` 和 `exec/vision`

不是两次调用。`llm_client._safe_record_llm` 在模型返回后写 `llm/response`，记的是调度：`job`、模型名、耗时、prompt 哈希。`vision_exec.run_vision_exec_turn` 拿到同一个 `AgentDecision` 后再写 `exec/vision`，记的是这一步用了哪个能力、thought 是什么。`cr-23f57686bdc8` 里序号 167 是 `llm/request`，168 是 `llm/response`，169 是 `exec/vision`，中间没有第二次请求。

看图规划是另一个 job：`agent-vision-plan`，同样会有自己的一对 `llm/request` / `llm/response`，再加 `plan/vision`。那才是第二次调用。发码这一步如果 `orchestrator/plan_gate` 是 `skip_seeded_focus`，就只有执行这一次。

## 7. 纯视觉：菜单保持技能目录，回看放在下一回合

视觉路径不把动作收成点、输入、滑。`focus_exec_menu_ids` 今天在里程碑已明确时把菜单收成这一步的一个 `hook_cap` 或 `device_cap`（发码只有 `tap_element`）。扩展包里该阶段允许的设备技能仍然应该能被看见：长按、连点、按键、等待、滑动都在。收菜单是为了不让发码这一步去调 `get_otp` 或 `lease_account`。放开时只放开本阶段的设备技能，程序独占的 hook（租号、取码、清缓存、确认登录态）仍只在对应里程碑上出现。整表技能都放开会退回到模型在发码步直接取码。

回看不要再打一轮模型。下一回合的看图规划或看图执行，在做新动作之前先带上一步的动作和结果，输出上一步是否达成。达成则继续当前 in_progress。未达成则把当前 in_progress 改回 pending，把上一步改回 in_progress。同一次调用里完成，避免每个视觉步再加 3.5–5 秒。

「当前 cap 无需视觉就跳过回看」如果按下一步来理解，会直接退回这次的故障：发码是 `tap_element`，下一步是 `get_otp`。`get_otp` 不用看图，于是发码点到 Continue 之后没有回看，里程碑已经在当回合被 `note_tool_pass_milestone` 记成 pass，接着就去取码。跳过的条件应该是**上一步**本身不需要视觉核对：`lease_account`、`get_otp`、`clear_app_cache`、`wait_ms` 以工具结果为准。`tap_element` 和 `input_text` 即使下一步是 hook，也要回看。

回看不能再问同一句「你觉得点对了吗」。点 Continue 的那次 thought 已经把绿色按钮说成发送验证码，再问一次仍会说完成了。核对要有独立证据：

| 上一步 | 回看证据 | 不能当作证据 |
|---|---|---|
| `input_text` | 动作后节点里的值和本次要填的文本一致 | 回执里出现 `@`、`web_focus` 回声、「输入 N 字」 |
| `tap_element` | 落点控件的文案属于该意图的可点集合，不属于排除集合；或下一屏不再是同一个按钮仍待点击 | 模型 thought、工具 status=pass |
| `get_otp` / `lease_account` 等内部 cap | 工具自己的 pass/fail | 截图 |

输入核对要读节点值。这是观察，不是用 DOM 改点击坐标。纯视觉如果连读回都禁掉，邮箱是否写上只能再看一眼图，短字符串在截图里读不准，空框被记成已填会再出现。

回看做晚了也会空转。今天 pass 在当回合就写上，随后程序可以切阶段。回看必须发生在记 pass 和切阶段之前：视觉步当回合只记「已派发」，下一回合回看通过才记 pass。否则指针已经到 `otp_fetch`，再把 `send_code` 拉回 in_progress 会和取码 hook 抢同一步。

回看判失败时要有次数上限，和现有的重复熔断接在一起。判错一次就来回改 in_progress，发码和取码会交替。同一里程碑连续两次回看失败就停止这一步，把证据写进 session，而不是第三次再点同一个 Continue。

## 8. 语义层：用现有逻辑块数据，不新写脚本词典

库里没有一张「Send = 发送验证码」的表。`catalog_entries` 是能力（`tap_element`、`get_otp`），不是按钮文案。导航别名是页面名，粒度和 App 绑在一起，不能拿来对登录按钮。知识库正文是段落，不能当精确匹配源。

已经有的容器是逻辑块步骤。`fb.global.login` 的每一步在目录里有 `id` 和一句中文 `title`（「发送验证码」「提交登录」）。语义层是给这些步骤加字段，仍然放在同一条块定义里，Console 改数据，运行时只读：

- `match`：可点的表面形式，整词相等，不用子串。
- `exclude`：明确不是这一步的表面形式。
- `when`：可选条件。Continue 只在验证码节点里已经有 4–8 位数字时进入 `submit_login.match`，否则留在 `submit_login` 之外，也永远不进 `send_code.match`。

纯文字、尤其是「包含」，会误伤。「登录」会粘到更长的按钮文案上；`Send` 会粘到 `Send feedback`。匹配用整词，排除表优先于可点表。一个节点同时沾上 `match` 和 `exclude` 时不算命中，DOM 路径失败，交给视觉，并在说明里写明排除原因。

文案意图和步骤意图冲突时，以当前 in_progress 的步骤 id 为准，不用例整句去扩按钮。用例写「完成登录」，当前步仍是 `send_code`，可点集合只有发码按钮，登录和 Continue 仍在排除里。无障碍名和截图上的字不一样时（绿色 Continue，节点名是「通过 Google 继续操作」），两个字符串都去对同一张 `match` / `exclude`。对上排除就拒绝，不因为模型把它们说成同一件事就放过。

准确率用下一轮 session 对。发码步的 `tool/call` 若落在该步 `exclude` 上，记 `semantic/reject` 且里程碑保持 in_progress。安卓节点文案整词属于 `match` 时走 DOM、没有 `agent-vision-exec`。表外文案第一次会失败并留在 session 里，把这句补进该步的 `match` 即可，不必改 Python。

Laya / Jev 不做。

ai11y 和 intentmap 也不进这条链路。ai11y 的 `data-ai-intent` 要写在被测页面自己的 DOM 上，再由它的 `describe → plan → act` 在浏览器里点下去。被测 Web 和安卓都不是我们写的页面，安卓层级里没有这个属性；它的 act 也是另一条点击通路，和 Scout 的 EXECUTE 叠在一起。Nexus 不读 `data-ai-intent`，也不引入这套运行时。

intentmap 是浏览器里的本地相似度匹配，用例句把用户的话归到意图上，没有排除表，也没有「验证码已经进框」这种条件。跨语言例句还是要我们自己写进 `match`，和登录块上的字段重复。它的相似度又是我们明确不用的子串/近邻匹配，`Send` 和 `Send feedback` 会靠得太近。Python 服务再包一个 TypeScript 包，解决不了 Continue 和发码的分界。

## 9. 会退回旧故障的写法

| 写法 | 退回成什么 |
|---|---|
| 下一步是 `get_otp` 就跳过回看 | Continue 被当成发码成功，接着取码超时 |
| 回看只信模型 thought 或工具 pass | 点错的那一次自己证明自己点对了 |
| 当回合就 `note_tool_pass`，下一回合再回看 | 阶段已经切走，拉回 in_progress 时 hook 已经在跑 |
| 视觉步放开全部技能，包括 `get_otp` | 发码没点到就去取码 |
| 纯视觉禁止读节点值 | 空邮箱框再次被回执里的 `@` 记成已填 |
| `match` 用子串 | 「登录」「Send」粘到别的按钮上 |
| 用例句子覆盖当前步骤的排除表 | 「完成登录」把 Continue 又加回发码的可点集合 |
| 回看失败不封顶 | `send_code` 和 `otp_fetch` 来回改状态 |

## 11. 怎么算做成

用同一组登录用例，重启后看 session。

- Web 发码：`tool/call` 的目标落在 `send_code.exclude` 上时有 `semantic/reject`，里程碑仍是 `send_code`，不会接着 `get_otp`。
- 安卓发码：节点文案整词属于 `match` 时，这一步没有 `agent-vision-exec`。点击回执仍是该节点。
- 视觉步的下一回合先回看。上一步是 `input_text` 或 `tap_element` 时，即使下一步是 `get_otp` 也回看。回看未通过时，当前步回到 pending，上一步回到 in_progress。
- 视觉点击的载荷没有 `target`。安卓回执是坐标，不再出现 `via content_desc`，也不再出现 snap。DOM 点击没有 `x,y`，锚点未命中则失败。
