# V9 仓库：一份业务脚本 + pages

日期：2026-10-29。本文修订 [README](README.md) 的仓库布局。三端都读。

一条用例只有一个脚本文件，里面只写业务顺序。渠道差异写在 `pages/` 的定位里。现在 Workbench「应用逻辑」读到的页面、控件、入口，从 Nexus 库表迁到这个目录，不再以 `nav_fsm*` / 控件表为真源。

## 1. 三个目录

一个项目仍对应 `project_script_repos` 里的一个仓库。应用名不进路径。需求 id 不进路径。

```
pretest.py
posttest.py
scripts/                         # 本业务公共函数，只写业务，不含渠道分支
  login.py
tests/
  账号/
    case07fffa13.py              # 一个 case_id 一个文件
pages/
  登录.yaml                      # 文件名 = page_key
  首页.yaml
```

| 目录 | 谁写 | 里面有什么 | 里面没有什么 |
|---|---|---|---|
| `tests/` | 用例的业务顺序 | `run(case)`、步骤编号、调用 `scripts/` 和 `case.*` | 平台后缀、`if platform`、控件定位链 |
| `scripts/` | 多条用例共用的业务函数 | 登录填表、进入某页之后的业务动作 | 渠道选择器、页面锚点 |
| `pages/` | 应用逻辑 | 页面身份、锚点、控件、各渠道定位、入口 | 账号密码、访问次数、评审结论、可执行代码 |

现在仓库里 `cases/<case_id>.android.py` 这种按渠道拆开的文件不再作为执行入口。迁移时把业务收成一个 `tests/<模块>/<case_id>.py`，把各文件里的点按文案收成 `pages/` 里对应渠道的定位。收不完就不要开跑，不要挑一份渠道文件顶上。

## 2. 页面文件

一个 `page_key` 一个 YAML。`page_key` 在仓库内唯一。多个页面状态写在同一个文件的 `states` 里，不拆成多个数据库 `state_id` 文件。

```yaml
page_key: login
label: 登录
states:
  - id: default
    anchors: ["登录", "注册"]
controls:
  - id: submit
    label: 登录
    role: element
    locator_spec:
      uiautomator:
        cardinality: one
        selector: {kind: text, value: "登录", exact: true}
      xcuitest:
        cardinality: one
        selector: {kind: label, value: "登录", exact: true}
entries:
  - from: welcome
    trigger: 打开登录
    platforms: [android, ios, web]
```

`locator_spec` 沿用现有单元格名字：`uiautomator`（android）、`xcuitest`（ios）、`playwright`（web）、`ax`（mac）、`uia`（win）。校验规则与 `mino_nexus/contract/locator_spec.py` 相同。某渠道没有单元格，该渠道执行到这个控件时失败，原因 `locator_missing`。不改用另一渠道的定位，也不因此再写一份用例脚本。

入口 `entries` 只给应用逻辑页展示「从哪进来」。脚本不会按入口自动走图。要进这个页面，用例里写 `case.on_page("login")` 或明确的 `case.tap`。

不放进 YAML 的运行数据：`visit_count`、用例引用数、截图、评审批准状态。引用由「哪些 `tests/` 提到了这个 `page_key`」算出来。访问次数从 `session_events` 算。

## 3. 脚本怎么用页面

开跑载荷里的 `platform` 只用于挑选 `locator_spec` 的单元格。脚本函数签名没有平台参数。

```python
from scripts.login import fill

def run(case):
    case.launch()
    case.on_page("login")
    with case.do(1):
        fill(case)
    with case.check(1):
        case.on_page("home")
```

| 指令 | 行为 |
|---|---|
| `case.on_page(page_key)` | 用该页当前渠道的锚点对照界面。对不上就失败 |
| `case.tap(control)` | `control` 是当前页或点名页上的控件 `id` 或 `label`。定位取本趟渠道的单元格 |
| `case.input(control, text)` | 同上，然后输入 |
| 其余 `launch` / `swipe` / `back` / `wait` / `screenshot` / `vlm` / `account` / `note` / `fail` | 与 [Agent调度](Agent调度.md) 相同，不读页面文件 |

控件 id 写成 `login.submit`（`page_key` + `.` + 控件 id）时可以不先 `on_page`。只写 `submit` 时必须已经 `on_page`。对不上页面文件就失败，原因 `control_unknown`，不用文案在整棵界面树上瞎点。

坐标不写在用例里。某个渠道只能按坐标点时，把坐标写进该渠道的 `locator_spec`，仍然是这一份用例脚本。

## 4. 真源怎么迁

1. 按项目从现有应用逻辑导出：页面状态按 `page_key` 合并成一个 YAML，控件定位抄进 `locator_spec`，入口抄进 `entries`。
2. 导出结果放进该项目仓库的 `pages/`，由人提交。Nexus 不把导出写回数据库。
3. 导出核对之后，这个项目的应用逻辑读仓库。`logic.page.*` / `logic.control.*` / `logic.entry.*` 读 `pages/`。不再写 `nav_fsm*` 和控件表。
4. 库表本批不删，只停写。没有仓库或 `pages/` 为空时，应用逻辑显示空，不回退读库，避免两份真源。

逻辑块（登录七步这类顺序）不进 `pages/`。顺序是业务，放在 `scripts/`。块表同样停写。

## 5. 下发时带上哪些文件

脚本运行载荷的 `files` 包含：

- `script_path` 指向的那一个用例 `.py`
- 根上存在的 `pretest.py` / `posttest.py`
- `scripts/` 下的 `.py`
- `pages/` 下的 `.yaml`

仍禁止 `..` 和绝对路径。单文件 256KB，文件数 256，整包 4MB。超出则拒绝开跑。Scout 只执行那个用例的 `run`，YAML 只用来解析定位，不当成代码跑。
