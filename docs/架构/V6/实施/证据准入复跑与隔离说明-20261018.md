# V6：证据准入复跑与隔离说明

本批继续 2026-10-18 的安全复跑守卫。Android Studio、PyCharm 相关 APK 打包后置；不恢复已取消的组件自动升级/回退。

## 本批实现

1. 严格执行器只在从未尝试打开执行页面、没有派发写入，且最终会话已持久化时，记录 `execution.no_effect.v1`。标记绑定 owner、run、case、执行单元、设备和 finalization；复跑从 session_meta 读取，不能仅信任任务行上的 status 或前端声明。
2. `open_web_v5` 在派发前标记 write_dispatch_attempted。超时、异常或缺失 action_ref 不再误判为尚未执行。
3. 新发布可显式允许 `{on: [not_started], max: 1或2}`。Workbench 提供一次的选项，默认为关闭。历史 effect_unknown 策略不授权重放，也不原地改写旧发布。
4. 复跑明确选择 execution_unit_id，固定原设备、冻结计划、原文身份及环境摘要。新 run、execution_unit 和 session/wire 空间关联到原单元与 attempt。原报告和分母保持不变。
5. 子任务沿用原批次和单元的绝对截止时间，不能重置预算。原单元截止时间持久化后不可被陈旧投影延长。
6. SQLite 写事务内重新核验父任务、资源、证据、次数、选择及预算，再登记收据和子任务。相同请求编号返回原任务，不同请求编号也不能重复领取已复跑的原单元。客户端在发起前保存请求编号，受理不明时沿用该编号恢复。
7. 新增当前安全状态读接口，分别展示写动作、持久组合租约、停止证据、缺失复位证据及迟到对账数量。当前资源状态与历史业务结论分开；仅有资源租约隔离也不会被界面误报为安全。
8. Workbench 取消“核对停止并尝试解除隔离”的误导措辞，改为“核对停止证据”；解释停止与复位的区别，并展示逐单元复跑准入原因。

## HTTP

- `GET /case-runner/tasks/{task_id}/retry-eligibility`：返回批次阻塞项、原预算、逐单元 reason_codes 和 eligible_unit_ids。
- `POST /case-runner/tasks/{task_id}/retry-failed`：必须提供 `client_request_id` 和非空 `execution_unit_ids`。不允许通过 sn 更换目标。成功返回关联任务；拒绝返回结构化 409。
- `GET /case-runner/tasks/{task_id}/write-safety`：读取当前隔离状态、动作和资源；不修改历史报告。
- 原 `POST .../write-safety/recheck` 继续只核对停止，不能单凭停止解除未知效果隔离。

## 隔离的实际含义

写前先保存意图。明确未执行且回执可确认时可以结算；结果丢失、超时后无法确定是否已执行、失败发生在已写入之后、停止未确认、租约过期或代次失效时，保留受影响资源，不把它重新交给其他任务。隔离可涉及设备、账号和显式共享数据域；其他不相关资源仍按各自准入执行。

隔离不修改历史 verdict，也不等于业务失败已经被证实。迟到成功只追加对账，不把原 unknown 翻成通过。服务重启、升级、TTL 到期及任务终态都不是安全证明。

未知效果要恢复使用，仍需绑定原身份的停止证据、业务/资源复位核验以及旧租约失效/新 epoch。关闭浏览器只能证明局部执行停止，不能证明服务端订单、账号或其他共享数据已还原。当前没有通用的业务复位证明消费者，因此本批不开放未知效果的强制释放或复跑。无写入证据分支无需假造“复位成功”，也不会解除旧隔离。

## 验证记录与边界

在独立源码副本、全新临时数据根与本地 HTTP 上完成：

- 实际严格执行器在资源校验阶段拒绝，并生成可追溯的持久 no-effect 会话；没有连接真实设备或模型服务。节点为隔离注册 fixture，无设备传输；不把该检查称为真机验证。
- 实际 HTTP 鉴权、跨账号拒绝、资源租约隔离拒绝。
- 相同用例在两台设备上的失败/通过，只复跑失败单元。
- 原批次和单元 deadline、冻结发布保持一致，新任务使用新身份；父任务完整 payload 不变。
- 重复请求幂等、不同请求重叠拒绝、次数上限；两路并发请求只能受理一次。
- Workbench TypeScript、生产构建通过。全新 Chromium 上访问实际生产构建入口、任务深链、安全状态懒加载、刷新和重新加载通过；91 个本地资源读取、83 个 JS 模块执行，无脚本错误或远程依赖。导航取消的一个旧 API 请求单独记录，不视为资源缺失。

测试脚本和临时数据库仅在本机工作区，不提交 tests/mock、不运行 pytest、不写正式业务库。未发布、未重启正式服务。正式服务升级完成后还需确认安装版包含本批代码，才能验证这批新增功能；本轮源码开发不会自动进入正在下载的安装包。

## 后续增量：迟到停止证据生效

已结束任务收到迟到的 `write_stop.v1` 回执时，仍严格匹配 owner、session、动作、节点、设备与进程代次；V5 同进程证明还须包含 lane 已终止。有效回执在追加对账的同一次任务持久化中更新该动作的当前停止状态，记录来源回执，并使设备应用基线失效。无需为了已经收到的证明再请求节点。

这只满足停止条件，不推断从未写入、不核验业务复位、不释放任何资源，不修改原执行效果、Session verdict 或任务结论。普通迟到成功/未开始回执仍只对账；在途任务只记回执。重复回执幂等，陈旧任务投影不能擦除已持久化的停止证明或替换动作身份。

本地独立 SQLite 与实际 HTTP 验证覆盖有效回执、重复回执、陈旧投影、错误动作/设备/代次、V5 lane 未终止、退役证明缺失与有效证明、在途任务、普通未开始回执及跨账号拒绝。检查原 Session verdict 和 unknown 效果不变，HTTP 仍返回资源隔离、仅移除已满足的停止要求。未连接真实 Scout，不代表正式进程故障验收。
