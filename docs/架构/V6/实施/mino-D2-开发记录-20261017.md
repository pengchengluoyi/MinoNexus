# D2 Nexus 安装升级：开发与验收记录

状态：本地原生停启/升级回退、第三轮故障恢复与 MCP 重连隔离验收已完成，详见文末最新记录。**正式发布包、业务库副本及真实业务并发准出仍未完成，不标记 D2 完成。** 未停启现有业务 Nexus，未迁移或写入现有业务数据，未发布 Release。

## 交付范围

- `core/deployment.py`：安装身份、原子更新账本、每部署控制锁、进程生存锁与后台工作锁；账本属于安装基础设施，业务状态仍在 SQLite。
- `core/release_package.py`：固定 GitHub tag 下载、系统/架构匹配、长度与 SHA256 校验、有界 ZIP 解包、防穿越和不可覆盖的版本目录。
- `core/deployment_cli.py`：本地安装、暂存、取包、离线迁移、服务登记、探测、更新查询/取消与人工恢复入口；助手与解释器固定在 launcher，不依赖 current。
- `core/update_engine.py`：固定 operation_id/参数、30 分钟以内等待、持久 hold、全部 running 批次/编译统计、后台工作退出、停服、完整数据根备份、同源迁移、原子 current 切换、正常启动和三项探测；启动后只回代码，不自动倒库。
- `core/maintenance_gate.py`：新批次/探索准入；周期编译、文档同步、通知暂停；HTTP、用户线程和 IM 后台任务计入实际工作；原任务保留执行和收尾。
- `/sys/updates/request`、`/sys/updates/status`、`/sys/updates/{operation_id}/cancel`：仅部署管理员使用；对应 MCP 工具 `nexus_update`、`nexus_update_status`、`nexus_update_cancel`。源码启动实例明确拒绝升级。
- `probe` token：RPC 每项仅允许 initialize/ping/tools/list；拒绝 tools/call、通知与普通 HTTP API；认证不更新 last_used_at，不创建助手身份或调用记录。
- `/sys/server_info` 增加 instance_id/build_id/health_contract_version/deployment_managed。
- 复用并行 A 阶段的原生二进制包与 manifest，不另建发布流水线。在独立 `mino-maintain` 中增加 `d2` 入口；包声明 maintenance_contract_version=1，旧基线包不能直接作为 D2 可运行版本。CI 与实际发布仍待执行。

## 复用的 A 阶段前置修复

1. run_auto_migration 异常向外传播，失败不再记录 schema ready；离线 CLI 非零退出。
2. 全局 flow block 只允许已知版本序列向上升级。同版、未知版与更新版均保留；不再在旧版初始化中删除 retired ID。
3. 空库演练发现 bootstrap 仍创建已被 writer 拒绝的 guard.* base 行。停止这处过时种子初始化；不放宽 writer 校验、不改既有行，恢复提示继续使用 recovery_for_guard 的代码默认值。
4. 去掉重复 MCP router 注册；退出时等待取消的周期协程。to_thread 的实际运行仍由工作锁保护，不能用协程取消当作线程停止。

合并时保留了并行 A/B 的迁移、种子、bootstrap、probe、开发准备和截图读取实现；D2 只接入维护流程与门禁。这些修复不代表过去已经发布的旧版自动获得兼容性。自动回退必须针对**确切两版包**完成旧版初始化和业务读写演练。

## 安装命令与边界

先生成正式包；不把源码进程作为可更新安装版。以下是操作格式，不是已执行的正式部署：

```text
mino-nexus maintenance install --root <安装绝对路径> --data-dir <保留的现有数据绝对路径或独立新目录> --manifest <manifest文件> --package <zip文件> --port <固定端口>
mino-nexus maintenance provision-probe --root <安装路径>
mino-nexus maintenance register --root <安装路径>
mino-nexus maintenance fetch --root <安装路径> --tag <固定发布tag>
mino-nexus maintenance request --root <安装路径> --operation-id <稳定ID> --build <固定build>
mino-nexus maintenance status --root <安装路径> --operation-id <原ID>
mino-nexus maintenance cancel --root <安装路径> --operation-id <原ID>
mino-nexus maintenance helper --root <安装路径>
mino-nexus maintenance recover --root <安装路径> --mode code-only
```

`mino-maintain d2` 提供同一套维护命令。provision-probe 委托 current 指向的原生应用调用既有 probe issue；它调用实际初始化并生成仅本地保存的 token，不能对未备份的正式库“试运行”。install 只准备文件与 plist；register 才登记并启动服务。旧源码服务如占用端口，安装直接失败，不替用户停止它。

macOS 布局为 launcher / releases / current / config / updates / logs。现有数据根按显式参数登记，不自动搬家。应用与助手各自使用 PyInstaller 自带运行时，独立助手固定在 launcher。原 A 基线的 installation.json 布局不自动转为 D2，须在独立目录准备 D2 安装；不改写已有基线服务。助手 LaunchAgent 的 RunAtLoad/KeepAlive 均为 false；应用 RunAtLoad=true，固定 plist 用 bootout/bootstrap 停启。用户级服务仅承诺登录会话。

## 兼容门禁

`config/compatibility/<旧build>--<新build>.json` 由完成演练的部署管理员登记，绑定 `from_build`、`to_build`、`from_sha256`、`to_sha256`，并包含真实 `evidence` 引用以及以下已验事实：

- `old_start_and_rw_verified=true`
- `migration_reentrant=true`
- `writers_audited=true`
- `no_external_migration_effects=true`

没有该记录，或记录包摘要不符，更新在领取 hold 前拒绝。不能用空记录、模型判断或仅 additive schema 补齐。发布 manifest 不能自行授予这个部署的兼容准入。

## 故障语义

- 等待过期/取消只释放自己的 hold；已有安装不能通过取消清除。
- helper 崩溃后可重查同一 operation；已经进入启动/探测阶段时只重新探测，不重放迁移或安装。效果不能确定时保留 needs_operator 和本地恢复入口。
- 新版正常启动前持久 writes_reopened。之后即使启动探测失败，也只切回兼容旧代码，保留当前数据。
- 离线迁移失败且从未重开写入时，可恢复完整备份；失败数据目录另存保留，不销毁原现场。恢复不确定时停止，不能删锁文件强行继续。
- 有活动本地旧版 wechat-ilink 长驻监听时，工作锁会阻止更新直至其停止或等待过期；首轮不自动中断这类监听。正式准出前需要按实际启用的集成补充退出演练。
- Linux/systemd、Windows、助手自身自动升级、协议预暂存、零停机均未实现，不作跨平台承诺。

## 第二轮：真实 launchd 与本地原生双版本验收（2026-10-17）

本轮修复已应用到 Nexus 源码；未提交 Git、未发布、未切换现有业务服务。所有业务写入仅发生在独立工作区的临时数据根，未使用真实业务库。

### 修复

- 停服不再直接 bootout 活进程：先用 launchctl kill SIGTERM 请求退出，最多等待 40 秒；确认 launchd 无 PID 且 runtime 锁释放后才卸载。超时保留服务登记和进程，交给人工处理，不借 launchd 默认 ExitTimeOut 强杀。
- register 对已登记应用执行不带 -k 的 kickstart：活进程保持原 PID，已退出进程可重新启动；无法查询登记状态时拒绝继续。

## 第三轮：写者排空、故障恢复与 MCP 重连（2026-10-17）

本轮代码已落到 Nexus；没有提交/推送或发布，没有停启现有业务服务。全部故障注入仅针对工作区隔离数据和随机命名 LaunchAgent，端口 19189。没有运行 pytest、提交 tests/mock 或调用外部模型/设备。

### 代码修复

1. MCP `_handle_owned` 的实际线程持有 writers 锁。HTTP/asyncio 等待取消不提前释放仍在执行的线程租约；维护期继续由 MCP 方法门禁限制业务调用。
2. Scout 更新协调进入活动统计，安装/重启/验证/未知或待人工处理且仍占 slot 的操作阻止 Nexus 更新。只排队的 Scout 操作暂停新派发，已派发操作继续查询原回执；异步 tick 的写者锁覆盖完整回执处理。
3. Nexus hold 阻止新建 Scout 更新，但同 operation/参数的重放可查询原结果；参数冲突继续拒绝。
4. 新增本地 `recover --mode restart-previous`。仅 needs_operator、phase=stopping/backing_up、writes_reopened=false 且 current 仍为 previous_build 时允许；确认实际进程退出后重新启动旧版，不恢复/覆盖数据，保留部分备份。迁移及后续阶段明确拒绝，不能替代 prestart-backup/code-only。

5. 修复人工恢复开始后仍保持 needs_operator 的状态错误：在启动前写入 state=restarting、phase=operator_recovery。该错误已在原生助手复现，修复后杀掉恢复进程再续接原操作成功；数据库 inode 与原备份保持不变。

### 实测范围与结果

| 验证 | 结果与证据边界 |
| --- | --- |
| 真实 MCP worker 被 SQLite 写锁阻塞，取消等待协程 | 后台线程仍持有 writers 锁；实际 DB 工作结束后才释放。源码进程隔离验证 |
| Scout 安装/未知状态忙闲、排队状态、维护期新请求及原请求重放 | 隔离 SQLite/真实服务函数验证通过；未连接真实 Scout，不外推设备更新并发 |
| 原生助手等待独立进程的受控写者 | waiting_idle 期间原应用 PID 不变；写者完成真实 SQLite 提交后才升级，提交结果保留 |
| 真实 MCP HTTP 连接经过服务停启 | 旧 socket 读到 EOF；用原 token 新连接 initialize、查询原 operation；同请求重放未再安装 |
| 原生离线迁移失败 | 对新版表制造真实 view/schema 冲突；原生 CLI 非零退出，自动恢复完整备份，旧版 HTTP 读写恢复；失败数据目录保留 |
| 新版完全无法启动 | 迁移期间把隔离监听 host 改成无效值，观察原生进程非零退出；恢复配置后自动退回旧版，旧版读写正常 |
| 新版与回退版均无法启动 | 保留 needs_operator/hold 和恢复错误；取消不能解除；修正配置后显式 code-only 恢复成功 |
| migrating 阶段杀掉助手 | 原生迁移子进程已取得 runtime 锁；续接不重放迁移，进入 needs_operator；解除隔离 SQLite 阻塞并确认进程退出后 prestart-backup 恢复成功 |
| stopping 阶段杀掉助手，无完整备份 | 原有 code-only 拒绝；最终原生助手通过 restart-previous 恢复旧版 |
| backing_up 阶段杀掉助手 | 原数据和已存在的部分备份保留；restart-previous 成功，不把部分备份当完整备份恢复 |
| switching 阶段中断 | 新模式拒绝；确认尚未启动后通过 prestart-backup 恢复旧版 |
| starting 阶段中断 | 根据真实目标探测完成原操作或显式 code-only 恢复；数据库 inode 保持，不倒库 |
| rolling_back 阶段中断 | 重建账本选定的旧版进程后，助手探测完成同一回退，不重做迁移 |
| operator_recovery 阶段中断 | 原生复现旧状态无法续接；新助手先持久 restarting，中断后探测完成原操作，无重复备份/数据库恢复 |
| restart-previous 越界使用 | 持久账本隔离验证：migrating/switching/starting/probing/rolling_back/operator_recovery 或 writes_reopened=true 均在停服/数据操作前拒绝 |
| 收尾 | 本轮隔离应用与助手服务均已卸载；原生包、备份、失败现场和操作账本保留 |
