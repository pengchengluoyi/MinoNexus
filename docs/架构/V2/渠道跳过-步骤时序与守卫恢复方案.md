# 渠道跳过、步骤时序与守卫恢复

> **状态**：已按本文落地。`guest` 承接前置已有字段：未登录 / 已登出 → `logged_out`，游客 → `guest`；设备上的 `guest` 与 `logged_out` 互相满足这两档。  
> **关联**：[扩展包技能与渠道基座.md](扩展包技能与渠道基座.md)、[里程碑-Plan-Exec-状态机.md](里程碑-Plan-Exec-状态机.md)、[看图规划-执行与步骤状态机方案.md](看图规划-执行与步骤状态机方案.md)

一条技能规则覆盖所有渠道。注入时按本趟平台决定哪一行执行、哪一行 `skipped`。一个回合只改一次焦点，然后结束。守卫不再空转阻塞；触发后把恢复方案交给看图规划，由它下发下一条事件。

设备登记簿的 `guest` 不新增前置字段。账号登录 facet 已有三档：`logged_out`（未登录）、`guest`（游客）、`logged_in`（已登录）。前置「未登录」「已登出」「已退出」编译成已有的 `logged_out`；只有「游客」时编译成已有的 `guest`。登记簿里的 `guest` 与 `logged_out` 互相满足这两档。

## 1. 渠道差异写成同一张列表上的 skip

共享逻辑块和前置种子在各渠道用同一条里程碑列表。某渠道没有该技能，或该技能的 `platforms` 不含本趟平台：写入时就是 `skipped`，`skip_reason=channel_absent`。行还在，后面的 id 不变。

| 例子 | 处理 |
|------|------|
| 共享登录块含 `confirm_login_state`，安卓目录没有这条、或 `platforms` 不含 android | 安卓该行 `skipped`，网页照常执行 |
| 前置列表含 `clear_app_cache`，网页没有清应用缓存（`CHANNEL_PLATFORMS` 现为 android） | 网页该行 `skipped`，安卓照常执行 |

`apply_channel_skip` 和 `ensure_single_in_progress` 已经会把渠道缺失标成 `skipped`，并在没有 `in_progress` 时提升第一条 `pending`。还没对齐的是：

- `confirm_login_state` 没有声明平台。`channel_supports` 在目录平台为空时对所有渠道返回真，安卓不会 skip。
- 网页 `clear_app_cache` 的 skip 写在前置种子的 `is_web` 分支里，没有走同一条渠道规则。
- 焦点完成后，下一条若已是 `skipped`，要在**本回合内**继续找到后面第一条 `pending`，把它改成 `in_progress`，然后结束回合。不要把 `skipped` 标成 `in_progress`，也不要在同一个回合里执行这条新焦点。

下一回合只执行刚才抬上来的那条。

## 2. 一个回合只处理一次焦点

`cr-1e22f71f64ec` 的操作步说明了同回合双事件的后果：规划因为协议弹窗，在「点击我的」之前追加了「同意」；点完同意后，本步点击次数和已经命中的「我的」关键词把步骤送进校验，追加行还没完成。`cr-1e22f71f64ec::case-a107f75c` 则是应用已在前台，`skip_repeat_launch_app` 连拒 87 轮，里程碑不往下走。

### 2.1 当前指令已经完成

执行到当前 `in_progress` 的 cap 时，若这条指令的完成条件已经成立（应用已在前台仍要 `launch_app`、清缓存已做过仍要 `clear_app_cache`），不再下发，也不再走 skip/block 空转：

1. 当前行改为 `pass`，证据写明已满足。
2. 跳过紧随的 `skipped`，把后面第一条 `pending` 改为 `in_progress`。
3. 结束本回合。

### 2.2 要插在当前事件之前

看图规划判定当前 `in_progress` 这一步现在做不了，需要先做别的（协议弹窗挡住了「点击我的」）：

1. 当前行从 `in_progress` 改回 `pending`。本回合不执行它。
2. 在它前面插入 N 条，状态都是 `pending`。
3. 把插入的第一条改为 `in_progress`。
4. 结束本回合。

下一回合执行的是刚抬上来的那条，不是原来的那条，也不是两条一起做。

### 2.3 插在当前事件之后

追加在当前行后面时，当前行保持 `in_progress`，新行是 `pending`。本回合如果还要执行，只执行当前这一条。新行留到它自己变成 `in_progress` 的回合。

不能在同一回合里既把当前行打成 `pass`，又把新行执行掉或丢掉。`try_auto_finish_do_when_intents_met` 用「点过一次 + 关键词已在屏上」收工，会把还开着的追加行留在操作阶段外面。阶段收工只认里程碑：必填行都终态，且准出为真。插入的前置步骤没有 `pass` 之前，原步骤不能因为族计数进入校验。

插在后面本身不制造「两条都在本回合执行」。会出问题的是收工路径不看剩余 `pending`。

## 3. 守卫

原则：守卫若只回答「不能执行」且不改里程碑，模型下回合会派同一个 cap，形成死循环。这类改为 §2.1 的完成即 `pass`。留下的守卫必须带恢复方案，交给看图规划下发新事件，然后结束本回合。

恢复文案挂在 Console 扩展包的基座行上（技能目录里 `visible_to=system` 的那张表），不另建表。字段与守卫 id 对齐，例如 `recovery`：触发原因、下一步该派的 cap、不要再派什么。守卫命中时把这段写进本回合的规划上下文。

### 3.1 按阶段保留

| 阶段 | 保留 | 作用 |
|------|------|------|
| 前置 | `prep_clear_before_launch` | 声明了清缓存时，打开应用之前必须先清 |
| 前置 | `exec_script_params` | 脚本参数不齐不下发 |
| 前置 | `action_fuse` | 同一动作无进展时停，并把恢复方案交给规划 |
| 操作 | `action_fuse` | 同上 |
| 操作 | `limit_recovery_retry` | 恢复次数用尽后停，不再换一句相同的拒绝 |
| 操作 | `require_sms_send_before_otp` | 未发码不取码、不填码 |
| 操作 | `require_otp_before_login_tap` | 验证码未填不点登录 |
| 操作 | `block_repeat_get_otp_when_ready` | 码已在手不再取码 |
| 操作 | `block_fsm_off_step_target` | 导航目标必须是本步要去的页 |
| 操作 | `block_back_without_nav_back_semantics` | 没有返回语义不按返回 |
| 操作 | `block_assert_in_do` | 断言只在校验阶段 |
| 校验 | `deny_mutate` | 校验不下发点击、输入 |
| 校验 | `force_case_expectation` | 断言文案用用例预期 |

登录顺序这三条的恢复方案要写成可执行的下一步：未发码 → 点发送；码已取到 → `input_text`；验证码未填 → 先填再点登录。

### 3.2 改为完成即 pass，不再当守卫空转

这些只在重复时拒绝，不把当前里程碑标完成，模型会原样再派：

`skip_repeat_launch_app`、`skip_repeat_clear_app_cache`、`skip_repeat_check_run_env`、`skip_repeat_get_app_version`、`skip_repeat_read_device`、`skip_repeat_structural_cap`、`skip_repeat_swipe_stuck`、`skip_repeat_tap`、`skip_repeat_fsm_open_loop`、`skip_repeat_fsm_declined`、`skip_recover_bring_when_foreground`、`skip_recover_screen_when_display_guard`、`skip_repeat_satisfied_step_action`。

`cr-1e22f71f64ec::case-a107f75c` 的 87 轮 `launch_app` 属于这一类。应用已在前台时，当前 `launch_app` 行改为 `pass`，焦点移到下一条，本回合结束。

### 3.3 拿掉

这些和里程碑收工抢同一件事，或只阻塞、没有下一步：

| 守卫 | 原因 |
|------|------|
| `block_mutate_when_thought_done` | 用思考里的收工字样拦截点击，和「一个回合一条焦点」冲突 |
| `block_do_after_step_goal` | 步骤是否结束只看里程碑，不看另一套 goal 标志 |
| `require_do_work` | 同上，会和里程碑各走各的收工 |
| `block_idle_wait_in_do` | 等待是否多余由规划和熔断决定 |
| `swipe_direction_vs_instruction` | 方向不对应让规划重选，而不是守卫卡住 |
| `block_login_after_guest` | 登录是否允许看本步范围那一条 |
| `block_repeat_email_tab` | 重复点标签交给 §2.1 或熔断 |
| `block_repeat_continue_submit` | 同上 |
| `block_prep_guest_mine_tab` | 按具体 Tab 文案拦截，渠道规则里不保留 |
| `stuck_alternation`、`limit_advise_recovery` | 与 `action_fuse`、`limit_recovery_retry` 重复 |

`action_fuse` 留下，但命中后必须带基座上的恢复方案进入下一回合的规划，不能只返回同一句拒绝。
