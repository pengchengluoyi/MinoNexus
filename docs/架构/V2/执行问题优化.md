| 回合 | 能力 | 结果 |
|------|------|------|
| 0 | `launch_app` | 打开测试站。没有 think/step/result 卡片 |
| 1 | `lease_account` | 租号 |
| 2 | `relogin` | 内部再派 `read_web_auth`，结论 guest |

## 1. 时间轴步数和空步骤

Studio 回放先按 `stream/emit.step` 合并，8 个回合会收成 8 格。接着 `GET /case-runner/traces/{session}` 在 `engine_steps` 为空时（这条取消任务的 `engine_steps` 是 `[]`）把同一批 `events` 再喂给时间轴。这些载荷没有 `seq`，于是用数组下标 `i + 1` 当步号。

26 条流事件因此铺成步 1–26：前 8 格被错位覆盖，第 9 格之后是新格。think 没有 `capability_id`。后半段 think 落在新建的步上，就是只有截图、没有事件的格子：

| 时间轴步号 | 实际内容 |
|------------|----------|
| 11 | 回合 4 的 think |
| 14 | 回合 5 的 think |
| 17 | 回合 6 的 think |
| 20 | 回合 7 的 think |
| 23 | 回合 8 的 think |

11、14、17、20 就是这条会话里看到的空步。

### 1.1 改法

时间轴的一步 = 一个回合（`turn/start` 到 `turn/end`）。think、派发、结果是这一步里的三段，不再各占一格。

轨迹接口只返回按回合合并后的步骤。`events` 原样留下给调试，回放不再把 `events` 按数组下标补进已经按 `step` 合并过的时间轴。`engine_steps` 为空时就显示会话投影，不拿流事件再铺一层。

`run-case` 的 `max_steps: 24` 是回合安全上限，不是时间轴格子数。界面上的步数等于有 `turn/end` 或有工具结果的回合数。这条会话应显示 8 步（另加下面的打开应用），而不是 24。

## 2. 截图和步骤对不上

模型看到的图和界面上的图不是同一份字节。

每一回合开始时 `observe/screenshot` 做成缩略图写入 `observe/screen`，再复制到该回合的 think、step、result。`case-f73bd8a6` 回合 1–8 的缩略图哈希各不相同，但落库长度都是 65526 或 65527，而载荷里的 `thumb_len` 约 69692。`session_log` 把 `thumb` 裁到 65536，并接上 `...(+N)`。JPEG 因此不完整。Studio 仍把以 `/9j/` 开头且长度大于 80 的字符串当成合法图，于是三列和时间轴都去画这张坏图。坏 JPEG 往往只能画出顶部一条，登录页顶栏每回合都像同一张「login」。

模型用的是当回合完整截图（`make_llm_jpeg` 之后送进 vision）。`llm/request` 不存图片，所以调度记录里看不到它，但回复能描述点击和输入后的界面。这不是三列或时间轴单独算错步号，是两边用了不同的图：界面用被裁坏的缩略图，模型用完整图。

同一回合的 result 还贴着动作前的那张图。填入邮箱的结果格不会出现已填上的字，下一回合的观察才会拍到。

### 2.1 改法

缩略图不再裁进 JSON 字符串。`observe/screen` 只存引用（会话内序号、宽高、哈希）。字节按会话落到数据目录的文件里，接口按引用读取。禁止对 base64 做 `...(+N)` 截断。

Studio 拒绝含 `...(+` 的缩略图，缺图就空着，不用半张 JPEG 顶上。

一步两张图，都挂在同一个回合上：

| 图 | 何时拍 | 界面 |
|----|--------|------|
| 决策图 | 看图之前，与送进模型的是同一张 | 时间轴这一步的主图，三列卡片用它 |
| 结果图 | 工具返回之后再拍一次 | 结果区。本地能力（租号、取码）没有界面变化时可以不拍，沿用决策图并标明 |

送进模型的字节要能用决策图的哈希对上。`llm/request` 不重复存整图，记 `screenshot_hash` 即可。

## 3. 三列卡片缺了打开应用

`case-c19f59f9` 的 `engine_steps[0]` 是 `launch_app`（打开测试站，pass），没有 `step` 字段，也没有缩略图。`case-f73bd8a6` 同样在回合 0 写了 `tool/call` / `tool/result`，流事件只有 `phase=start` 的「开始看图执行」，没有这条能力。

三列把卡片挂到前置 / 操作 / 校验时丢掉 `step <= 0`。回合 0 的打开应用因此哪一列都不会出现。

### 3.1 改法

打开应用是前置的第一步，步号用 0，和其他回合一样发 think（程序派发可以没有模型原文）、step、result。三列接受步号 0。挂卡规则：`launch_app` / `open_url` 挂到前置里「已打开」那一行；没有这一行时挂到前置第一张卡片，不丢。

`engine_steps` 写入时带上 `step`。取消的任务也要把已经完成的回合写入 `engine_steps`，避免详情只剩会话投影、批次详情是空列表。

## 4. 第九步没有结论就停住

`case-f73bd8a6` 第九回合不是模型拒绝，也不是守卫拦截。

回合 8 的 `get_otp` 在 `00:08:55` 发出，`00:12:09` 才 `pass`（194287 ms，Gmail 收信）。用例墙钟预算写在 history 里是 150 秒，但预算只在回合开头检查，收信循环里不看。`00:11:53` 会话已被强制 `session/end`（`forced=true`，摘要「已取消」），工具结果仍写在结束之后。循环接着打开回合 9：`turn/start` 之后没有 `observe/screen`、没有 `llm/request`、没有 `guard/block`，只有 `nav/capture_finish`（`run_status=cancelled`）和 `phase=done`。界面上就是第九步没有任何反馈。

收信的 `max_wait_ms` 缺省 90 秒，这次实际等了 194 秒，说明等待没有被取消或墙钟打断。本地工具在 Nexus 里同步跑，`RouterProxy._task_aborted` 只包住发往 Scout 的路径。

### 4.1 改法

本地长等待（取码、租号）每轮轮询都看两件事：任务是否已取消、墙钟是否用尽。命中则立刻返回，`tool/result.status=cancelled` 或 `fail`，摘要写明是取消还是超时。不再把默认等待加长到超过本用例剩余预算。

已经 `session/end` 之后不再 `turn/start`。若工具在结束之后才返回，结果补在结束前的那一回合上，不新开一步。

第九步若没有任何派发，时间轴不留空格。`turn/start` 之后若因取消离开，写 `turn/end`，`decision_status=cancelled`，三列显示「已取消」，而不是一张没有事件的卡片。

## 5. 纯视觉仍在采 hierarchy

这条任务的 `action_scheme` 是 `visual`。回合 1–8 仍各有一条 `observe/hierarchy`（例如回合 8：`source=playwright`，`node_count=23`，`elapsed_ms=174`）。Scout 日志里的 `observe ok … cap=hierarchy` 就是 `hierarchy_slots.capture` → `proxy.observe("hierarchy")`。

`observe_hierarchy_enabled` 默认真，只有环境变量 `MINO_OBSERVE_HIERARCHY=0` 才关，不看 `action_scheme`。`NavRuntime.observe` 每回合都采，并把正文写进 `inspect_slots["hierarchy_text"]`。看图规划和看图执行的槽组装都会带上这个字段。`vision_observation` 只按当前焦点裁剪长度，不区分视觉还是 DOM。所以模型输入里会出现 `hierarchy_text`（如 `text=3D Figurines …`）。

视觉方案下点击坐标来自截图。层级既拖长回合（网页上这条约一百多毫秒，安卓上更长），又把按钮文案灌进模型，和「只看图」不一致。

### 5.1 改法

`action_scheme=visual` 时：

- 不调用 `observe("hierarchy")`，不写 `observe/hierarchy`。
- `hierarchy_text` 保持空串，不放进 plan / exec 的用户槽。
- 导航定位依赖层级的那一段跳过，`nav/localize` 记 `skipped=visual`。不再用层级判断前台、登录表单或协议弹窗。这些判断改看决策图，或等 DOM 方案。

`action_scheme=dom` 时保持现在的采集，层级仍可进槽，供选节点和填坐标。两种方案不因对方失败而互换，这一点不变。

登录块里 `confirm_login_state` 今天先采层级再判断是否还在登录表单。视觉方案下改为看决策图（或程序只根据提交后的结果图做一次看图判断），不再为了这一条去拉 hierarchy。
