# 扩展包技能与渠道基座

> **状态**：已落地。目录分组是通用、预期、恢复、基座。执行阶段仍叫前置 / 操作 / 校验。基座行留在目录里给选路用，模型菜单看不到。`fsm_navigate` 只在模型卡住或当前步就是导航时放回菜单。别名在派发时收成正式 id。看图兜底的多个动作里，渠道上有其中一个即可，不会因为安卓才有的 `press_key` 把网页整步丢掉。

## 0. 要对上的问题

当前 `catalog_entries` 用五类把所有行都铺到 Console：`prep` 11、`do` 22、`check` 2、`generic` 24、`recovery` 16。`do` 里有 `adb`、`ios_wda`、`playwright`、`remote`，以及 `ui_native_input`、`ui_input_text`、`ui_screenshot`、`ui_stream`、`system_shell`。这些是平台入口或执行器提供面，不是可调用技能。为了 UI 上能看见，它们被塞进了「操作」。

同一目的有两套 id。模型用的是 `input_text`（`generic`，`visible_to` 含 `case`），目录里另有一条 `ui_input_text`（`do`，没有平台、没有 `visible_to`）。`press_key` / `key_event`、`set_clipboard` / `clipboard_set`、`clear_app_cache` / `system_pkg_clear`、`assert_visual` / `vision_assert`、两条 `exec_script` 是同一类问题。

`visible_to` 为空时，菜单代码当成对所有受众可见。大量基座行因此可能漏进 `capability_menu`。

规划不核对目录。`hook_cap` 是自由文本。`cr-d9d526436192` 的网页前置追加了 `check_page_loaded` 和 `check_unlogin_home_elements`；`cr-53e80b33da10` 的安卓前置追加了 `wait_for_page_load`。执行把这个名字收成唯一工具，和本阶段菜单取交集为空，然后 `give_up`。目录里对应的技能是 `wait_screen_ready`。`check_unlogin_home_elements` 没有目录行，是规划写出来的。

渠道差被写成两套列表。网页邮箱登录块有 `confirm_login_state`，安卓通用登录块没有。安卓前置有 `clear_app_cache`，网页前置直接不种这一条。列表形状随渠道变，后面的焦点和准出要对着两套结构读。

## 1. 总分总

一条技能规则覆盖所有渠道。调用时按本趟平台选基座实现。写回的里程碑和执行结果用同一种形状。渠道做不到的步骤标 `skipped`，不删行、不换一套 id。

```
技能（case，进模型）
  通用 / 预期 / 恢复（模型可调用的那一部分）
        │ 统一调用
基座（system，不进模型）
  平台入口：adb、ios_wda、playwright、remote
  提供面：点、滑、拖拽、输入、检测在该平台上的实现
        │
同形状结果：milestone.status + EventResult
```

模型只看见技能 id。`RouterProxy` 按本趟平台选基座，把 `executor_order` 和 `selected_impl` 算完再放进 `EXECUTE`。Scout 仍不读目录。

## 2. 技能和基座

### 2.1 怎么拆

| | 技能 | 基座 |
|--|------|------|
| 问的问题 | 这一步做什么 | 这一步在本平台由谁做 |
| 谁看见 | `visible_to` 含 `case` 的进模型；只含 `system` 的只给程序 | 只给程序和 Console 维护 |
| 例子 | `tap_element`、`input_text`、`wait_screen_ready`、`lease_account`、`assert_visual` | `adb`、`ios_wda`、`playwright`、`remote`，以及 `ui_native_input`、`ui_screenshot`、`system_shell` |

基座从扩展包技能列表挪到单独的基座入口。Console 仍可查看，不再占技能的五类。

通用插件是技能，不是基座。模型和 agent loop 调用的是这五个 id，派单时再落到当前平台的基座：

| 插件 | 技能 id | 基座按平台接 |
|------|---------|----------------|
| 点 | `tap_element` | 安卓 adb，iOS ios_wda，网页 playwright，远端 remote |
| 滑 | `swipe_direction` | 同上 |
| 拖拽 | `swipe_element_to_element` | 同上 |
| 输入 | `input_text` | 同上。`ui_input_text` 不再作为第二个事件 |
| 检测 | `wait_screen_ready` | 同上。页面是否加载完走这一条，不另造 `check_page_loaded` / `wait_for_page_load` |

`long_press_element`、`multi_tap`、`press_key` 仍是通用技能，跟这五个插件一起进 prep/do 菜单。

### 2.2 技能只留三类

去掉「前置」「操作」两种 kind。扩展包技能归成：

| kind | 谁在什么阶段调用 |
|------|------------------|
| 通用 | 前置和操作。菜单只有这一类（再滤 `visible_to=case` 和本平台） |
| 预期 | 只在校验。现在的 `check` 收成这一类，保留 `assert_visual` |
| 恢复 | 模型走不下去时。拆成两半，见下 |

恢复的两半：

| 半 | `visible_to` | 何时调用 |
|----|----------------|----------|
| 程序内部 | `system` | 屏幕不可用时程序自己调。安卓黑屏、休眠走 `wake_screen`、`dismiss_keyguard`。不进 `capability_menu` |
| 模型可调用 | `case` | 模型无法从当前页继续时注入。`fsm_navigate` 按当前页和用例要去的页给最短路径。平时的前置/操作/校验菜单里不放 |

`lease_account`、`get_otp`、`clear_app_cache`、`launch_app`、`relogin` 是通用技能，不再因为「像前置」放进单独 kind，也不再放在 `recovery`。平台做不到的，在里程碑上标 `skipped`（§4），不从技能表删掉。

`do` 里其余空平台、空 `visible_to` 的行（`network_mock`、`vision_locate`、`system_shell` 等）先标 `system` 放进基座或下线，不进菜单。确认没有程序在调之后再删。

### 2.3 同目的合并

对外只留一个技能 id。另一种写法并进这个 id 的实现，或标成基座提供面。

| 留下 | 并入或降为基座 |
|------|----------------|
| `input_text` | `ui_input_text` |
| `press_key` | `key_event` |
| `set_clipboard` | `clipboard_set` |
| `clear_app_cache` | `system_pkg_clear` |
| `kill_app` | `app_force_stop` |
| `launch_app` | `app_launch_native` |
| `assert_visual` | `vision_assert` |
| `exec_script`（现有 generic 那条） | `do` 里同 id 的另一行 |

逻辑块、里程碑、`EXECUTE.capability_id` 只用留下的 id。

### 2.4 `visible_to`

| 值 | 含义 |
|----|------|
| `system` | 不进模型的 `capability_menu` 和 tools。程序内部调用，Console 可查看 |
| `case` | 注入模型，作为这一阶段的外部接口 |
| 两个都写 | 模型能看见。程序也能调 |

空列表不再等于全部可见。缺省按 `system`，不进菜单。`read_web_auth`、`wake_screen`、`dismiss_keyguard`、`probe_device_state` 保持只有 `system`。

## 3. 菜单和调用

前置、操作的 `capability_menu` = 本平台、`visible_to` 含 `case` 的通用技能。校验的菜单 = 同样条件下的预期技能。恢复的模型半只在程序判定模型无法继续时加入菜单。程序内部恢复不加入。

规划与执行看同一份菜单。`milestones_append` 的 `hook_cap` / `cap` 必须是这份菜单里的 id。不在菜单里的追加丢掉，并记 `plan_append/rejected`，原因是未注册。不把未注册名字写成 `in_progress`，也不因此 `give_up`。

执行焦点上的能力必须已经是本阶段菜单中的 `case` 技能。`system` 技能只由程序自己派发（清缓存钩子、读网页登录存储、解锁屏幕），不出现在模型 tools 里。

`check_unlogin_home_elements` 不登记。目录里没有这一行；它只在上述网页前置的规划追加里出现过。未注册 id 按本节丢掉即可。

「当前步骤需要的能力不在本阶段菜单里」不再作为用例失败原因。那条路径说明程序把未注册或 `system` 事件交给了模型，属于调用前的上下文错误，在写入里程碑时拦住。

## 4. 对状态机

共享逻辑块和前置种子在各渠道用同一条里程碑列表。某渠道没有该技能，或该技能的 `platforms` 不含本趟平台：这一行写入时就是 `skipped`，`skip_reason` 为 `channel_absent`。行还在，后面的步骤 id 不变。

| 例子 | 处理 |
|------|------|
| 共享登录块含 `confirm_login_state`，安卓没有这条技能 | 安卓把该行标 `skipped`，网页照常执行 |
| 前置列表含 `clear_app_cache`，网页没有清应用缓存 | 网页把该行标 `skipped`，安卓照常执行 |

`skipped` 已是终态。焦点规则补一条：`in_progress` 的下一条若是 `skipped`，同一回合推进到后面第一条 `pending`，不把 `skipped` 标成 `in_progress`，也不为它调用 exec。注入时已经是 `skipped` 的行，`ensure_single_in_progress` 只提升 `pending`，本来就会跳过；缺的是注入时打上 `channel_absent`，以及焦点完成后紧挨着的 `skipped` 不要占一轮。

渠道差只体现在哪一行是 `skipped` 以及基座选了哪条实现。模型看到的菜单、里程碑字段、执行结果字段在各渠道一致。
