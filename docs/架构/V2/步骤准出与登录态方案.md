# 步骤准出与登录态

> **状态**：已落地。§2 准出闩在 `success_criteria.exit_allowed`；校验阶段在预期成立时把闩写成 true 再进入下一步。§4 登录态按接口、能证明的当前屏、测试资源三级写入。同一任务第一次打开网页记为未登录；关闭网页、清缓存、界面退出登录都会写成未登录。同任务里已记录的会话和当前屏不一致时，记在当步结论里。熔断已经判定死循环时，不再推进恢复栈。号池自己的「状态 未知」仍以号池字段为准。Playwright 的 storageState 文件不落库，避免把 Cookie 写进会话记录。  
> **关联**：[里程碑-Plan-Exec-状态机.md](里程碑-Plan-Exec-状态机.md)、[看图规划-执行与步骤状态机方案.md](看图规划-执行与步骤状态机方案.md)

## 0. 要对上的失败

| 现象 | 根因 |
|------|------|
| 点「同意」后 do 直接进入校验，帖子详情还没打开 | 看图兜底只种了一条里程碑。`tap_element` 一通过，列表就没有待完成项，`try_transition_after_tool_pass` 立刻 `do_to_check`。规划器写过「还要进主界面找帖子」，但收工不读它 |
| `step_requirements_complete` 像没生效 | 它只在规划结果上，而且只作为「已经全部终态时再开一条流转」。工具把最后一条点成 pass 时，程序不看这个字段 |
| 前置用截图判登录态 | `relogin` 走 `inspect_session`，协议页或 Log in 按钮就能判未登录。号池回的是「状态 未知」 |
| 守卫自己转圈 | `block_prep_login_when_logged_in_required` 把租号当成登录链，并要求去「我的」看登录态。停机又推进中断，循环接上 |

## 1. 业内怎么做

### 1.1 步骤何时结束

测试框架把「这一下做完了」和「这一步可以交卷」分开。

- Playwright / Cypress：命令成功只说明动作发出去了，断言是另一条语句。动作返回不等于用例步骤结束。
- Appium、Robot Framework：显式等待和关键字结束条件写在步骤末尾，中间关键字成功不会结束整步。
- UML 状态图和 XState：完成事件（子状态都跑完）和准出守卫是两道门。守卫可以提前写成真，转换仍要等最后一个子状态结束。这就是 join / barrier：旗子先落下，人要等队伍走完才放行。

当前实现把「列表里没有 pending」当成准出。列表里若只有一条兜底看图步，点任何控件都会收工。这和上面的分工相反。

### 1.2 登录态从哪来

稳定做法是读应用自己持久化的会话，而不是读画面。

- Web：Playwright 的 [storageState](https://playwright.dev/docs/auth) 就是 Cookie、localStorage、sessionStorage 的快照。官方登录复用走这三条，不走「看看右上角有没有 Log in」。
- Android：非 root 的 adb 没有跨应用的登录态 API。即使用 root，字段也取决于每个 App 把 token 放在哪。业界把 `pm clear` 当成确定的未登录重置，不把截图当会话真源。设备农场里，跨任务留下的登录只是提示；和当前界面矛盾时要重新登录，不把旧缓存当成故障结论。
- 同一趟任务里，清数据、关浏览器、点退出，才会把已建立的会话作废。同一趟里缓存和界面矛盾，才值得当缺陷。下一趟任务的缓存只用来决定要不要先登录或退出。

## 2. 步骤准出

在 `success_criteria` 上增加布尔字段 `exit_allowed`（准出）。每条里程碑的 `status` 保持现在的 `pending` / `in_progress` / `pass` / `failed` / `skipped`。

| 规则 | 行为 |
|------|------|
| 默认 | `false` |
| 谁改 | 每次 `agent-vision-plan` 都要判断。认为剩下的列表执行完就可以进入下一步时改为 `true`，并停止追加。还不行就保持 `false`，先输出还要执行的步骤 |
| 谁读 | 只有当前列表的最后一条已经终态时，程序才读它 |
| 提前写成 true | 仍然把剩余步骤执行完，然后再读。中途的 true 不切换步骤 |

收工条件变成：最后一条终态，且 `exit_allowed === true`，才 `prep_to_do` / `do_to_check` / `check_to_next_step`。最后一条终态但准出仍是 false 时，回到看图规划，让它补步骤或把准出改为 true。不再因为「列表空了」就切换。

`step_requirements_complete` 并入这个字段，不再单独当流转开关。

## 3. 卡片耗时

时间线上每张卡片的数字是这一回合自己的耗时：从该回合 `turn/start` 到这条 result。工具自己的 adb / 接口耗时放在 `tool_elapsed_ms`，不拿来当卡片时间，也不再把整段用例墙钟摊到缺耗时的卡片上。

## 4. 登录态

三条来源，优先级固定：

**工具 API > 当前屏幕 > 测试资源里记下的状态**

### 4.1 渠道

| 端 | 能用的接口 | 不能用的 |
|----|------------|----------|
| Web | Playwright 的 Cookie、localStorage / sessionStorage、storageState | 用按钮文案判断已登录 |
| Android | 没有稳定的跨应用 adb 接口。有应用自己提供的调试接口时走该接口 | 非 root 读不到应用私有会话；root 也不跨应用稳定 |

有接口时，`relogin` 只调这个内部接口，不看当前屏，然后进入下一步。

没有接口时看当前屏。这一屏能够证明已登录或未登录，就把结论写入本趟上下文，并写回该设备在测试资源里的登录态。

没有接口、当前屏也证明不了：跳过这一步看图，把测试资源里的设备登录态写入上下文，继续后面的步骤。

包含登录信息的页面占比少，专门跳过去看的成本高，而且模型不熟悉应用时会把协议页、登录入口看成已登录或未登录。所以当前屏只能在「这一屏已经能证明」时采用，不能为了确认登录态再去点「我的」。

### 4.2 什么操作改登录态

| 操作 | 写入 |
|------|------|
| Android `clear_app_cache` / `pm clear` | 该设备上的被测应用改为未登录 |
| Web 每次 Chromium 启动，以及关闭 Chromium 进程 | 未登录 |
| 用例里登录逻辑块成功，或界面上完成登录 | 设备登录态改为已登录，并记下当前账号 |
| 用例里退出登录 | 设备登录态改为未登录，当前账号清空 |

这些钩子直接改上下文和测试资源，不经过看图。

### 4.3 怎么继承

| 范围 | 规则 |
|------|------|
| 同一趟任务 | 已经通过登录逻辑块登录，且没有清缓存、没有换 Chromium 进程、没有在界面上退出，则后面的用例继承设备登录态和当前账号 |
| 同一趟里和界面矛盾 | 作为缺陷依据：上下文说已登录，界面却是登录入口，或相反 |
| 下一次任务 | 测试资源里的登录态可以接着用，但不能当成百分之百正确。和界面矛盾时只作提醒，引导程序登录或退出，然后继续后面的步骤 |

`block_prep_login_when_logged_in_required` 不再把租号或「去我的看一眼」当成登录态检测。租号仍是账号与数据。登录态检测按 §4.1 的优先级走完即结束，守卫不再对同一步骤反复拦截。
