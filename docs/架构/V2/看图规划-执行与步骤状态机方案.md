# V2.1：看图规划 / 看图执行 + 步骤状态机（程序收工）

> **状态**：看图规划 / 执行 / 校验已落地。步骤准出见 [步骤准出与登录态方案.md](步骤准出与登录态方案.md)  
> **命名**：[命名与优先级.md](命名与优先级.md)（全仓仅 **P1/P2** 优先级；`P6-Pn` 为专题内交付序号）  
> **前置**：[执行改造方案-记忆与FSM逻辑块.md](执行改造方案-记忆与FSM逻辑块.md)  
> **结论**：V2 已落地记忆瘦身、里程碑数据结构、逻辑块种子与部分程序钩，但 **仍把「规划 + 执行 + 收工信号」压在 `agent-decide` 一轮里**，`signal_done` / `step_outcome` 仍由模型主导，导致死循环、卡死、与 milestones 双轨。本方案 **拆 Job、收拢上下文、用程序状态机收工**。  
> **三方边界**（扩展包 / 用例密钥 / Agent Job 谁对谁、如何协作）：见 [三方协作-用例密钥-扩展包-AgentJob.md](三方协作-用例密钥-扩展包-AgentJob.md)。

## 0. 现状缺口（为何「有改但没达标」）

| 现象 | 根因（代码锚点） |
|------|------------------|
| 同一步反复调 LLM、空转 `wait_ms` / 重复 tap | `advance_on: signal_done`（`skill_defs.DEFAULT_SOP`）+ 大量 `block_mutate_when_thought_done` 与模型 `status=done` 博弈 |
| milestones 写了但 phase 仍不收工 | `evaluate_milestones` 与 `decision.status=done` / `step_outcome` **并行**；模型可 `continue` 无视里程碑已 pass |
| check 与 do 决策混在一起 | check 仍走 `agent-decide` + 旁路 `assert_visual`（P0 文档已标未完成） |
| 逻辑块「要不要点哪」与「块内第几步」缠在一起 | 块展开在 `ensure_milestones_before_decide`，但 **每 turn 仍由 agent-decide 同时改 milestones + 选 cap** |
| `history_block` / `checkpoints_block` 在「执行」Job 里拼 | 规划信息在执行轮重复注入，模型既当 planner 又当 executor |
| 每个技能 Prompt 重复写 `milestone_updates` | 应属 **程序写回**，不应进各扩展包说明 |

**目标一句话**：**看图规划**定「本回合要干什么、里程碑长什么样、块内走到哪」；**看图执行**只出 **一条** capability 调用；**视觉校验**只在预期阶段 **批量断言**；**步骤 prep/do/check 何时结束** 只认 **里程碑聚合 + 程序状态机**，不认模型 `signal_done`。

## 1. Job 全景

### 1.1 三个运行时 Job（+ 探索保留独立）

| Job ID | 中文名 | 职责 | 可调用的「扩展包技能」 |
|--------|--------|------|------------------------|
| **`agent-vision-plan`** | 看图规划 | 读截图 + 当前步骤语义 + FSM/块上下文 → **计划**（里程碑、块步骤、本回合执行意图、校验点清单） | 仅 **规划类** 扩展包（如 `plan-milestones`、`plan-checkpoints`、`plan-flow-block`）；**不下发** tap/input |
| **`agent-vision-exec`** | 看图执行 | 在 **已有规划** 约束下，输出 **单个** `AgentAction`（cap + params） | 当前 phase 的 **device/do/prep/recovery** tools（OpenAI functions），与今日 menu 一致 |
| **`agent-vision-assert`** | 视觉校验 | **仅 check**：一次性对规划给出的 **全部校验点** 截图判定 pass/fail | 无业务 mutate；输出结构化 `check_evidences[]`（`llm_jobs` 迁移期保留 `assert-vision` 只读别名） |

**改名**：现有 `agent-decide` → **`agent-vision-exec`**（DB `llm_jobs.id` 迁移期可 alias 双读）。Console / `roles_catalog` 文案同步。

**探索**：`explore-decide` 可暂保留单 Job，或后续拆为 plan+exec；**不在本方案 P6 范围**。

### 1.2 阶段 × Job 调用矩阵（硬约束）

| 用例阶段 `loop_phase` | 允许调用的 Job | 禁止 |
|----------------------|----------------|------|
| **prep** | `agent-vision-plan` →（每执行子步）`agent-vision-exec` | `agent-vision-assert` |
| **do** | 同上；do 可 **连续多轮** plan→exec→plan→exec… | `agent-vision-assert` |
| **check** | ① `agent-vision-plan`（分析 expected，产出校验点）② `agent-vision-assert`（批量校验） | **`agent-vision-exec` 的业务 mutate**；**允许 `recovery` 类 cap**（见下） |

**check 阶段 recovery（已拍板）**：禁止 tap/input/导航等 **业务 mutate**；**放行** `kind=recovery` 能力（与今日 `deny_mutate` + recovery 白名单一致），用于闪屏、弹窗遮挡等恢复后再 assert。

说明：

- **prep / do**：每一 **执行子步** 最少 1 次 plan（可配置「仅里程碑为空或块步进时 plan」以减少调用）。
- **check**：每个用例步的 check phase **固定最多 1 次 plan + 1 次 assert**（除非 assert 失败且策略允许 **仅 replan 校验点**，仍不引入 exec）。

### 1.3 上下文槽归属（1.5）

**全部由 `agent-vision-plan` 消费并写入 trace；`agent-vision-exec` / `agent-vision-assert` 不再注入长上下文。**

| 槽 / 块 | 规划 Job | 执行 Job | 校验 Job |
|---------|----------|----------|----------|
| `checkpoints_block`（当前步要做什么 + 子里程碑摘要） | ✅ 读+写摘要 | ❌ 仅只读 **plan_digest**（≤N 字） | ❌ |
| `history_block`（本步操作史） | ✅ 读+决定是否截断 | ❌ 仅 **last_k** 条摘要 | ❌ |
| `session_json` / `accounts_json` | ✅ | 精简副本（租号/Otp 相关字段） | ❌ |
| `goal` / 当前步文案（precondition / instruction / expected） | ✅ **按 phase 三选一**（见 §1.4） | 只读当前 **active_milestone.title** | 只读 **expected + 校验点列表** |
| `nav_assist` / `knowledge_*` | ✅ | 按需 `skip_if_empty` | ❌ |
| `hierarchy_text` / 截图 | ✅ | ✅ | ✅ |
| `menu_json` / 工具表 | ❌（规划不用 cap 表） | ✅ functions only | ❌ |

**`plan_digest`**（新槽，程序生成）：规划 Job 输出后写入 `cursor.plan_digest` 与 `context/trace`，执行 Job 只读该对象，例如：

```json
{
  "schema": "mino.vision_plan.v1",
  "phase": "do",
  "case_step": 2,
  "active_milestone_id": "m3",
  "intent": "tap_email_field",
  "flow_block": { "block_id": "fb.global.login.email_web", "step_id": "tap_email", "skip": false },
  "constraints": ["no_signal_done", "one_action_only"],
  "exec_hints": { "selector_text": "邮箱", "cap_family": "tap_element" }
}
```

### 1.4 三阶段文案替换（1.4 视觉校验分工）

规划 Job 的 **用户块主文案** 随 `loop_phase` 切换（同一条用例列，不同列字段）：

| phase | 主文案来源 | 规划产出侧重 |
|-------|------------|----------------|
| prep | `precondition` + prep `goal` | 资源/会话/环境里程碑；是否插入逻辑块 |
| do | 当前步 `instruction` | 操作里程碑序列、块内步、跳过标记；**可规划多枚待执行 milestone** |
| check | 当前步 `expected` | **校验点** milestones（元素是否存在、位置、+1、点亮等）；**不规划 mutate** |

**check 与 do 的差异**（产品语义）：

- **do**：plan 可输出 **多个** `pending` 操作里程碑；exec **每次消费一个** active milestone，完成后由 **程序** 标 pass 并可能触发下一轮 plan（或同 plan 内队列）。
- **check**：plan **一次** 列出全部 `kind: checkpoint` 里程碑；**agent-vision-assert 一次** 返回全部点的 pass/fail → 程序 `apply_check_evidences_to_milestones` → **聚合收工**（§4）。**assert 失败不可 replan 翻案**（见 §4.3）。

## 2. 看图规划：逻辑块与技能（1.1 + 1.2）

### 2.1 两层决策

```text
┌─────────────────────────────────────────────────────────┐
│ agent-vision-plan                                        │
│  A. 扩展包技能：要不要走某条能力（租号、OTP、知识、FSM 边） │
│  B. 逻辑块：要不要进入/继续块；块内 step 列表与 skip     │
│  C. milestones：本步子里程碑 DAG/序列（真源写 cursor）   │
└─────────────────────────────────────────────────────────┘
          │ plan_digest + success_criteria
          ▼
┌─────────────────────────────────────────────────────────┐
│ agent-vision-exec（仅 prep/do）                          │
│  单一 AgentAction：cap + params（坐标、文本、wait_ms…）   │
└─────────────────────────────────────────────────────────┘
```

- **1.1 扩展包**：规划 Job 的 tools 为 **元技能**（非设备 cap），例如 `invoke_hook(lease_account)`、`attach_knowledge(id)`、`fsm_suggest_edge`。**是否调用**、**参数草案** 由规划写出，程序在 exec 前把 hook 落成 **milestones(kind=hook)** 并由 **程序执行器** 派发（与今日 `flow_block_runner_v2` hook 步一致）。
- **1.2 逻辑块**：
  - **进入块**：规划输出 `flow_block: { block_id, from_milestone }` 或程序在「需要登录」时 **强制插入**（保留今日 `login_block_top`）。
  - **块内步骤**：`nav_flow_block_catalog.steps_json` 展开为 milestones（已有）；**规划 LLM 与程序执行器均可标记 skip**，须遵守统一规则（§2.3）。
  - **块内「步骤」**指 catalog 里的 `steps[]`，**不是**用例表上的步骤序号。

### 2.3 Skip 规范（已拍板）

| 来源 | 条件 | 写入 |
|------|------|------|
| **规划** | 模型输出 `flow_block_ops: { op: skip_step, step_id, reason }` 或 milestone `status=skipped` | `skip_reason`、`skipped_by=plan` |
| **程序（块执行器）** | `steps_json.optional=true` 且 guard 判定可跳过；或 hook 已成功等价完成 | `skipped_by=program`，须 `skip_reason` 枚举：`optional` / `already_satisfied` / `channel_unsupported` |
| **禁止** | 无 reason 的 skip；必填步被程序静默 skip | 程序拒写，保持 `pending` 并记 `milestone/skip_rejected` |

exec 遇到 `status=skipped` 的 milestone：**不派发 cap**，直接推进到下一条 pending。

### 2.2 与 P4 `flow_block_runner_v2` 的衔接

| 今日 | V2.1 |
|------|------|
| `ensure_milestones_before_decide` 在 decide 前展开块 | 移到 **`plan_turn` 入口**：先程序展开块模板，再调 `agent-vision-plan` 填坐标语义 / skip |
| LLM 在 decide 里 `milestone_updates` | **删除**；执行结果由 **程序** 根据 cap 结果 / guard / fuse 更新 milestone |
| `evaluate_flow_block_guards` | 仍在 **exec 之后**、下一 plan 之前；guard 只影响 **能否继续 exec**，不替代状态机 |

## 4. 步骤状态机（prep / do / check）（需求 2.x）

### 4.1 状态定义

```text
CaseRun
  └── for each case_step_index:
        └── StepPhaseMachine: prep → do → check → (next step | case_done)
```

**`StepPhaseMachine`** 由 **程序** 驱动；LLM **不** 发 `signal_done`。

### 4.2 里程碑聚合规则（2.2）

对当前 `(case_step, phase)` 的 `success_criteria.milestones`：

| 条件 | 程序动作 | 等价旧语义 |
|------|----------|------------|
| 任一 **必填** milestone `failed` | **prep/do**：进入 **failed 复核**（§4.3），不立刻 fail 步；**check**：assert 失败即步失败 | `signal_give_up` |
| 全部必填 `pass`，可选可 `skipped` | `phase_outcome = pass` → **流转** | `signal_done` |
| 全部必填 `skipped`（且策略允许） | `phase_outcome = skipped` → 按产品定义跳 phase 或失败 | `signal_skip` |
| 存在 `pending` / `in_progress` | 保持 phase，继续 plan/exec 循环 | （无） |

**流转**（2.2 末句）：

- `prep` pass → 进入 `do`（同一步 index）。
- `do` pass → 进入 `check`（`enter_check()`，保留指针语义）。
- `check` pass → `advance()` 下一步骤 index，`phase` 重置为 `prep` 或按用例列直接进入 `do`（与今日 `StepCursor` 一致）。
- **任意 phase failed** → 本用例步失败，**不** 依赖模型是否愿意 give_up。

**与 give_up / ask_human**：仅当 **熔断 / guard / 租号失败** 等程序事件时进入；模型 `give_up` 建议改为 **建议字段** `abort_suggestion`，程序判断是否采纳。

### 4.3 里程碑 `failed` 后的规划复核（已拍板）

适用 **prep / do**（**不含 check 的 agent-vision-assert 结果**）。

1. 程序将 milestone 标 `failed` 时写 **`milestone/program_fail`**（cap、guard、证据摘要）。
2. 触发一次 **`agent-vision-plan`（复核模式）**：输入含截图 + 当前 milestones + program_fail 记录。
3. 规划输出 **`failure_verdict`**：
   - `blocking=true`：确认真失败 → 本 phase `phase_outcome=failed`，**禁止**继续 exec。
   - `blocking=false`：误判/可恢复 → milestone 改回 `pending` 或 `in_progress`，写 **`milestone/plan_overturn`**（含规划理由），继续执行。
4. **双记录**：同一条 milestone 可同时保留 `program_fail` 与 `plan_overturn` 轨迹，session 排查对齐。

**check**：`agent-vision-assert` 的 `fail` **不接受** plan 翻案；仅允许 recovery 后 **重跑 assert**（仍不算 replan 校验结论）。

### 4.4 移除 SOP 上的 `advance_on: signal_done`（2.1）

`skill_defs.DEFAULT_SOP` / `sop_runtime`：

```json
{ "id": "prep", "job": "agent-vision-plan", "exec_job": "agent-vision-exec", "advance_on": "milestones" }
{ "id": "do",   "job": "agent-vision-plan", "exec_job": "agent-vision-exec", "advance_on": "milestones" }
{ "id": "check", "job": "agent-vision-plan", "exec_job": "agent-vision-assert", "advance_on": "milestones" }
```

Turn 循环伪代码：

```python
while not cursor.done:
    if need_plan(cursor):
        plan = vision_plan(...)
        apply_plan_to_cursor(plan)
    if cursor.phase == "check":
        if not cursor.check_assert_done:
            evidences = assert_vision(...)
            apply_check_evidences(...)
            cursor.check_assert_done = True
        verdict = evaluate_milestones(cursor, ctx)
    else:
        if has_active_exec_milestone(cursor):
            decision = vision_exec(...)
            dispatch(decision.action)
            update_milestones_from_exec_result(...)
        verdict = evaluate_milestones(cursor, ctx)
    transition_step_phase_machine(verdict)
```

### 4.5 Registry / Guard 与 signal_done（2.1）

| 类别 | 处理 |
|------|------|
| `block_mutate_when_thought_done` | **删除**或改为 `block_mutate_when_phase_complete`（仅程序置位后拦 mutate） |
| `require_do_work` | 改为 milestone：`kind: internal, title: 至少一次有效操作` |
| `login_flow_do_may_finish` 等 | 收拢到 **块 milestones 全 pass** |
| `intent == signal_done` 的 guard | **下线**；prep 会话核对改为 **checkpoint milestone** |

## 8. 风险与未决项

1. **Plan 调用频率**：do 每步都 plan 成本高 → 默认「里程碑空 / active 变更 / guard 失败后」才 plan。
2. **旧用例无 expected 结构化**：check plan 仍靠 `milestones_from_check_plan` + LLM 补点。
3. **探索 run**：暂不拆 plan/exec，避免与本方案耦合。
