# 扩展能力：谁能在哪一阶段派哪一类事件

> **状态**：方案。目录里现在是 `generic` / `check` / `recovery` / `base`，菜单、守卫、逻辑块、本地执行各卡一层，同一条能力在前置和操作走不同代码。  
> **关联**：[扩展包技能与渠道基座.md](扩展包技能与渠道基座.md)、[渠道跳过-步骤时序与守卫恢复方案.md](渠道跳过-步骤时序与守卫恢复方案.md)、[里程碑-Plan-Exec-状态机.md](里程碑-Plan-Exec-状态机.md)

一条能力只回答两个问题：谁来派，在哪些阶段可以派。菜单、守卫、逻辑块都读这一张表，不再各写一份白名单。

## 0. 要对上的问题

`confirm_login_state` 不在用例菜单里，目录里也没有这一行。操作阶段能跑，是因为 `cursor.phase == "do"` 时，逻辑块在看图之前就调用了 `try_dispatch_block_hook`。前置没有这段：看图之前的整段登录宏、系统弹窗宏、逻辑块钩子都包在 `phase == "do"` 里。前置后来补的是另一条窄路径，只在 `hook_cap` 属于代码里的 `PROGRAM_CAPS` 且 `is_local_cap` 为假时才派。`confirm_login_state` 碰巧落在这条窄路径上，换一个同样「不在菜单、也不是本地能力」的 id，前置仍会把它交给看图菜单，再因未注册标 `skipped`。

`cr-0a26d9c2142a::case-f73bd8a6::webe22615fbbb917111` 停在前置。第 8 回合的 `context/menu.tool_kinds` 是 `generic` + `recovery`，实际 `cap_ids` 里没有 `fsm_navigate`，也没有 `confirm_login_state`。SOP 写了 recovery，菜单函数又把 recovery 从阶段种类里拿掉，两处对不上。

## 1. 现有限制字段

目录行（`catalog_entries`，本库 90 行）上，真正参与「能不能派」的字段是下面这些。`exec_class` 全空，不参与。

| 字段 | 现在怎么用 | 实际效果 |
|------|------------|----------|
| `kind` | `generic` 39、`base` 37、`recovery` 13、`check` 1 | 菜单只认阶段函数写死的种类：前置/操作 = `generic`，校验 = `check`。SOP 的 `tool_kinds` 含 `recovery` 也不会把 recovery 加进菜单 |
| `visible_to` | `case` 进模型；`system` 不进；空列表按 `system` | 空的有 `hitl`、`human_input`，以及 7 条 recovery 规则（`restart_target_app`、`screen_asleep_or_locked` 等） |
| `platforms` | 空 = 全平台 | 与代码常量 `CHANNEL_PLATFORMS` 双轨。`confirm_login_state` 的 web、`clear_app_cache` 的 android 写在常量里，不在行上 |
| `enabled` / `lifecycle` | 菜单过滤：`enabled=false` 或 `deprecated` 不进菜单 | 不拦住程序派发。`relogin` 是 `draft` 且 `enabled=0`，上述会话第 2 步仍然派成功 |
| payload 形状 | `actions`/`match` → recovery 规则；`implementations` 或本地编排 id → 原子能力 | 同一 `kind=recovery` 里两种东西。规则不进 `capability_menu`，原子能力是否进菜单另看 `visible_to` |
| `PROGRAM_CAPS` | 代码白名单，约 16 个 id | 允许规划追加、允许里程碑不在菜单里。其中 `confirm_login_state`、`open_url`、`open_app` 没有目录行 |
| `LOCAL_CAPS` 与 `LOCAL_ORCH_IDS` | 两份本地名单，不完全相同 | `is_local_cap` 决定不出网。`get_phone`、`release_account` 在编排名单里，不在 `LOCAL_CAPS` 里 |
| 阶段 `guards` | `run-case` 前置 3 条、操作 8 条、校验 2 条 | 回答「这一下能不能发」，不回答「这个 id 属于哪一阶段」。操作里的 `block_assert_in_do`、校验里的 `deny_mutate` 是在用守卫补种类 |

同 id 占两行的有 `accept_legal_consent`、`dismiss_ime`、`request_sms_code`：一行 `generic`（`visible_to` 含 `case`），一行 `recovery`（平台只有 android/ios）。菜单和逻辑块各命中一行，改一处另一处不动。

基座（`kind=base`，含 `guard.*`）只给 Console 和选路，不是事件。别名在派发时收成正式 id（`ui_input_text` → `input_text` 等），见 [扩展包技能与渠道基座.md](扩展包技能与渠道基座.md)。

## 2. 不在菜单、也不是本地能力

「不在菜单」= 阶段菜单（`audience=case` 且种类被阶段函数留下）里没有这个 id。  
「不是本地能力」= 不在 `LOCAL_CAPS` / `recover_*` / `human_*` / `signal_*`，Scout 或纯程序都会去跑它。

本库里属于这一类、而且程序会自己派的：

| id | 目录 | 为什么不在菜单 | 谁在派 |
|----|------|----------------|--------|
| `confirm_login_state` | 无行。`CHANNEL_PLATFORMS` 标 web，`PROGRAM_CAPS` 收录 | 没有行就不可能进菜单 | 逻辑块在 `login_state` 上直接调 `_dispatch_login_state`。操作阶段看图前必走；前置只在窄路径里走到 |
| `read_web_auth` | `generic`，`visible_to=system`，仅 web | 只有 system | `relogin` 内部再派，不单独出现在菜单 |
| `wake_screen` / `dismiss_keyguard` | `recovery`，`visible_to=system`，仅 android | 阶段函数不放 recovery；即便放，也只有 system | 屏幕不可用时程序自己调 |
| `probe_device_state` | `generic`，`visible_to=system`，仅 android | 只有 system | 程序探活 |
| `open_url` / `open_app` | 无行，在 `PROGRAM_CAPS` | 无行 | 白名单允许写入里程碑，没有对应派发实现时会被菜单判未注册 |

`fsm_navigate` 是本地能力（`LOCAL_CAPS`），平时也不在菜单。它和上面不是同一类，特殊处理见 §4。

`lease_account`、`get_otp`、`launch_app`、`clear_app_cache` 既在菜单里，也是程序会派的。它们不是本节的缺口。缺口是：**程序要派的 id 没有单一登记处**。有的靠目录 `visible_to=system`，有的靠 `PROGRAM_CAPS` 字符串，有的靠逻辑块里的 `if cap == ...`。

## 3. 什么时候能派、什么时候不能派

现在一次派发要连续穿过四层，而且四层的答案可以互相矛盾。

```
里程碑 hook_cap
  → 渠道：platforms / CHANNEL_PLATFORMS 不含本平台 → skipped
  → 菜单：不在 case 菜单且不在 PROGRAM_CAPS → skipped(unregistered)
  → 阶段种类：prep/do 只留 generic，check 只留 check；recovery 被丢掉
  → 守卫：SOP 列表按顺序，第一条拒绝就停
  → 阶段补丁：do 在看图前跑逻辑块；prep 只对「程序白名单且非本地」再跑一次
```

`phase_kinds` 不读 SOP 里多出来的 `recovery`。所以 `run-case` 前置/操作写了 `tool_kinds: [generic, recovery]`，模型菜单仍只有通用技能。recovery 进菜单的唯一口子是 `allow_model_recovery` 时把 `fsm_navigate` 塞进 `extra_ids`。

守卫再卡一遍阶段语义，例如操作的 `block_assert_in_do`、校验的 `deny_mutate`。种类已经说「校验才能断言、校验不能改界面」，守卫又说一遍。改阶段允许的事件要同时改 `phase_kinds`、SOP `tool_kinds`、守卫和逻辑块分支。

### 3.1 改成一张派发资格表

每条可调用技能增加 `caller`，取代「kind + visible_to + PROGRAM_CAPS + 是不是本地」叠在一起猜。

| caller | 谁派 | 进模型菜单 | 阶段 |
|--------|------|------------|------|
| `case` | 看图执行 | 进。前置和操作共用通用动作；校验只有预期 | 行上写 `phases`，缺省：通用 = prep+do，预期 = check |
| `program` | 看图之前，由当前里程碑钩子派。前置和操作同一条函数 | 不进 | 行上写 `phases`。登录块的钩子在前置、操作都能派 |
| `system` | 仅程序内部（读登录存储、点亮屏幕） | 不进 | 不跟用例阶段走，由触发它的程序点调用 |
| `base` | 不作为事件派发 | 不进 | 无 |

`kind` 只保留给 Console 分组（通用 / 预期 / 恢复 / 基座），不再参与能不能派。`visible_to` 由 `caller` 推出：`case` → 菜单；其余 → 不进菜单。空的 `visible_to` 不再单独解释。

`PROGRAM_CAPS`、`CHANNEL_PLATFORMS` 删掉，平台只留目录 `platforms`。没有目录行的 id（今天的 `confirm_login_state`）先补行：`caller=program`，`phases=[prep, do]`，`platforms=[web]`。逻辑块只写里程碑 id 和这个能力 id，不再写 `if cap == "confirm_login_state"`。

本地不出网仍然由执行器归属决定（`internal` / `hitl` / `vlm`），和 `caller` 分开。`LOCAL_CAPS` 与 `LOCAL_ORCH_IDS` 收成一份，菜单过滤和派发读同一份。

`enabled=false` 或 `deprecated` 对程序派发和模型派发生效。`relogin` 这种草稿不能再被本地执行器悄悄跑通。

### 3.2 阶段只卡一次

| 阶段 | 模型能选 | 程序钩子能派 | 守卫还留下的 |
|------|----------|--------------|--------------|
| prep | `caller=case` 且 phases 含 prep | `caller=program` 且 phases 含 prep | 清缓存必须在打开应用之前；脚本参数不齐不下发；同一动作无进展则停并把恢复方案交给规划 |
| do | 同上，phases 含 do | 同上 | 熔断；发码/取码/点登录的顺序；导航目标必须是本步要去的页；没有返回语义不按返回 |
| check | `caller=case` 且 phases 含 check（现在就是 `assert_visual`） | 不派业务钩子 | 不下发点击和输入；断言文案用用例预期 |

操作禁止断言、校验禁止改界面，改由「这个 id 的 phases 不含本阶段」在派发前拒绝，并记 `guard/block`，原因是 `phase`。`block_assert_in_do` 和 `deny_mutate` 不再各维护一张能力名单。

恢复原子（`caller=case` 且 Console 分组是恢复）默认不在菜单。只有 §4 的条件成立才放回。`caller=system` 的恢复（点亮、解锁）始终不进菜单。

未注册 id 仍然在写入里程碑时丢掉，记 `plan_append/rejected`，不写成 `in_progress`，也不因此 `give_up`。这与 [扩展包技能与渠道基座.md](扩展包技能与渠道基座.md) §3 一致。

## 4. FSM 导航和 FSM 逻辑块

这两处今天在阶段表之外又各加了一套分支。收成 `caller=program` 或「有条件放回菜单」之后，分支只保留下面这些差别。

### 4.1 `fsm_navigate`

| 点 | 现在 | 改完 |
|----|------|------|
| 谁算路径 | Nexus 本地，最短路不发给 Scout | 不变。执行器归属仍是本地 |
| 菜单 | 平时拿掉。`allow_model_recovery` 时用 `extra_ids` 塞回来 | 不变触发条件：当前焦点的钩子就是 `fsm_navigate`，或规划空转 / 熔断已发生。放回的是菜单临时项，不是改 `caller` |
| 操作阶段 | `block_fsm_off_step_target`：目标必须是本步要去的页 | 保留这条守卫。它卡的是参数，不是这个 id 能不能出现 |
| 逻辑块 | 操作步需要换页时，程序计划把钩子写成 `fsm_navigate` | 钩子是 `program` 时程序自己派第一跳；模型只有在上面的触发条件里才继续选它 |

### 4.2 逻辑块钩子

看图之前只留一次程序派发，前置和操作都走它。删除「整段宏只在 do」和「prep 再补一条非本地白名单」这两段。

程序派发的顺序：

1. 当前 `in_progress` 的钩子 `caller=program`，且本阶段在它的 `phases` 里。
2. 渠道不做：里程碑 `skipped`，`skip_reason=channel_absent`，本回合结束。规则见 [渠道跳过-步骤时序与守卫恢复方案.md](渠道跳过-步骤时序与守卫恢复方案.md)。
3. 钩子有特殊完成条件（验证码已在屏上不再取、账号已在手上改为填写）仍然写在该能力的派发函数里，但入口只有这一个。
4. 派完改焦点，结束回合。同一回合不接着看图再派一条。
5. 钩子是 `caller=case`：不在这里派，交给看图执行，菜单里必须有它。

登录块结尾的 `confirm_login_state` 就是第 1 步的普通程序钩子。前置要求已登录、操作里提交登录，都用它判断是否离开登录表单，不再因为阶段不同而有的能跑、有的被菜单丢掉。

操作阶段今天多出来的登录宏（发码后的填码提交链、系统权限弹窗宏）保持为程序钩子的实现细节：它们展开的每一步仍是目录里的一个 id，每一步一个回合。不在宏里再判断 `phase == "do"` 来决定整段是否存在。前置里程碑里没有这些步，就不会跑到。
