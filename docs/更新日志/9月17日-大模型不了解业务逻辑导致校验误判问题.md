# 9月17日 — 大模型不了解业务逻辑导致校验误判

**问题类型**：`assert_visual` / 读屏校验在 **操作与截图均正常** 时仍 fail，或 fail 理由与用例意图不一致。  
**优先级**：**P1（体验/误杀）** — 不阻塞设备链路，但拉高人工复核成本与对 Agent 的信任损耗。  
**关联批跑（样例）**：`cr-b883511e01ec`、`cr-77e8880d7ac1::case-8b53a494`（校验二 / decide 登录态混淆，见 §0.2、§0.3）

---

## 0. 问题边界

### 0.1 属于本文

| 模式 | 说明 |
|------|------|
| **产品语义不在屏上** | 预期写的是业务概念（页面类型、流程阶段、权限态），VLM 只能看见控件，不知道概念边界。 |
| **否定 / 排他断言** | 「未展示 X」「不应出现 Y」需要 X/Y 的可操作定义，否则模型保守 fail 或过度联想 fail。 |
| **同屏多义** | 两个业务态 UI 相似（预览 vs 沉浸式、列表 vs 详情、弹层 vs 全页），仅靠标题/按钮不足以区分。 |
| **跨步状态** | 登录态、草稿态、会员态等 —— 若未注入运行上下文，校验会重复猜（与 `session_persist` / 登录态槽互补，见 §1.3）。 |

### 0.2 样例 A — 业务页排他（非全文主题）

某校验预期同时要求：**可见元素 checklist** + **「未展示某类业务页」**。截图已满足 checklist，仍因模型不理解「某类页」与当前页的差异而 fail。  
此类个案 **不应用代码里写 App 文案 if/else 修**；应走 §3 的通用治理。

### 0.3 样例 B — 登录态语义（`cr-77e8880d7ac1::case-8b53a494` 校验二）

| 现象 | 说明 |
|------|------|
| 屏态 | 登录页：手机号 / 验证码 / 「登录」按钮可见 |
| `session_block` / run_context | `session=logged_out`（**正确**） |
| 误判 | agent-decide 或 `assert_visual` 因 **局部控件像「已走完登录」** 或 **重复 session 槽** 判成 **已登录** / 校验通过方向错误 |

**根因**：模型缺业务词典 —— **`logged_out` + 登录页控件 = 未登录**，不等于 `logged_in`；与「用户昵称出现在别页」不同。  
**已补程序侧**：`assert_session_context` 在 expected 含「已登录」而 fact 为 `logged_out` 时追加 **禁止误判** 句（`session_persist.py`）。  
**仍建议**：用例 knowledge 写清「登录页控件清单 ≠ 登录成功」；校验 expected 用 **可观测 logged_in 证据**（头像区、退出登录入口等），避免只写「已登录」三字。

### 0.4 不属于本文

- **步骤未做完就进校验**（动作族 / guard / probe 过早收工）—— 步骤合同与 `require_do_work`。  
- **截图失败、能力未执行、导航 declined** —— 设备链路与 NavFSM。  
- **纯 OCR 级错字** —— 可先调 expected 文案或单点 knowledge，不必上升 ontology。  
- **session_block 字符串重复拼接** —— 见 `9月17日—执行时上下文参数异常问题.md`（修 merge 后仍可能要 §0.3 知识）。

## 1. 根因（通用）

### 1.1 校验输入 = 像素 + 自然语言，缺少「业务词典」

`assert_visual` 主路径：`expectation` + 可选 `knowledge_context` + 截图。  
用例里的 many 预期本质是 **产品规则**（什么算「空间页」、什么算「提交成功」），不是纯视觉特征列表。未挂知识时，模型只能 **猜**。

### 1.2 断言句式结构决定难度

| 句式 | 难度 | 常见失误 |
|------|------|----------|
| 肯定、可枚举控件 | 低 | 漏检、错字 |
| 肯定 + 布局关系 | 中 | 区域理解偏差 |
| **否定 / 不应** | 高 | 无负样本定义 → inconclusive 当 fail |
| **排他（A 且非 B）** | 高 | A 看见但 B 未定义 → 误杀 |

### 1.3 与 RunContext / 会话槽的分工

- **RunContext**（`runtime/run_context.py`）早就有 `session_fact` / `task_session` / `session_dirty` 等字段 —— 表示「本 task 内可复用的结构化事实」。  
- **inspect-session** 产出的是 **当轮 prompt 槽** `session_block`，供 agent-decide 读。  
- 缺口曾是：**do 阶段得到登录结论后，未稳定写入 ctx，check 的 assert 也未强制带上该结论**（现由 `session_persist` + check 入口刷新 / `assert_session_context` 补链）。  
- **业务页类型** 没有等价的一键槽位，仍依赖知识库或结构化 probe（§3）。

---

## 2. 设计原则

1. **业务语义进知识 / Console / Atlas 标注**，不进 `nav_*` 编译器硬编码（`no-app-keywords`）。  
2. **能力目录不写校验策略** —— 只改善 assert 输入与可选 job 形态。  
3. **宁可 inconclusive + HITL，也不要未定义规则 silent pass**。  
4. **个案复盘写进批跑 doc 或 case 注释**，本文件只描述 **可复用机制**。

---

## 3. 治理手段（按成本）

### 3.1 用例与知识（优先）

- **步骤级 / 用例级 knowledge**：`match_step_knowledge` → check 前 `expand_named_knowledge` → `assert_visual.knowledge_context`。  
- **AppIntel / 页面类型条目**（见 `9月12日_AppIntel信息基座.md`）：为 assert 提供「当前应处于 page_type=*」的短文 + 负向对照。  
- **编写规范**：否定句改为 **可观测肯定句** + reference 图；排他句拆成「必须有 A」与「禁止出现组件 id / 入口 id」（由知识解释 id 含义）。

### 3.2 结构化 facts + VLM 分工（中期）

- Nexus 侧产出 `probe_facts`（localize、hierarchy、Atlas 组件 registry、计数、标题区 hash）。  
- VLM 只判 facts **未覆盖**的细项；**否定/排他** 尽量落在 facts（「不存在 component_id=…」）。  
- 弱 hierarchy 与 `vlm_hierarchy` 策略一致，避免双标。

### 3.3 Assert 专用 job（中期）

- Checklist 化输入；JSON 输出 per-item `pass|fail|inconclusive` + evidence。  
- 聚合规则：**否定项无像素级证据 → inconclusive**，不直接 fail。  
- 真源：`llm_jobs` / Console（`docs/PROMPTS.md`）。

### 3.4 产品与 QA（长期）

- 批跑第三态 **inconclusive** 与报表口径。  
- 用例保存 lint：含「未展示/不应」且无 linked knowledge → 警告。  
- 可选 **`assert_business_context`**：从 DB 按 app/project/tag 拉业务块（类比 `assert_session_context`，不写死在 Python 分支里）。

---

## 4. 推荐落地顺序

1. 建立 **「业务断言」标签** 与 knowledge 链接要求（Console / 用例规范）。  
2. 选 1～2 类高频模式（否定句、同类页排他）做 **assert job v2 + inconclusive** 试点。  
3. Atlas / 组件 id 与 probe_facts 对齐，减少 VLM 独自扛规则。

- 未定义业务概念前，全局自动 pass 所有否定断言。
