# 9月15日 — 大模型单步骤「是否达成」判断异常

分析对象：`cr-04b827be9cc5::case-99ab0675`（用例「点击开始造物跳转到开始造物」）

- 用例：`case-99ab0675`，`app_id = 3d2b9799-0027-4c7d-bfe7-8c5b88f4087d`（造物相机 / 移动端）
- 结果：`failed`，5 turn，50 秒，最终 `decision/give_up`
- 失败摘要：**「当前在拍摄页面，未找到底部tab『开始造物』，无法完成本步操作。」**
- 优先级只有两档：**P0**（本例直接卡死，必须改）、**P1**（放大故障面 / 降低复发率）

---

## 0. 结论

**用户的判断是对的：步骤一实际已经达成，程序侧没有任何机制发现这件事。**

`tap_element` 在 turn 3 成功点中「开始造物」，App 已跳到拍照页 —— 这正是步骤一的预期（`expected[1] = 跳转到拍照页`）。但循环在 turn 4、turn 5 仍然把「步骤 1：点击底部tab 开始造物」原样喂给模型，模型在拍照页上找不到「开始造物」这个 tab（**它本来就因为跳转成功而消失了**），于是判定本步未达成并 give_up。

根因不是模型判错，而是**程序侧的达成判据设计本身有结构性缺陷**：

> **do 阶段只告诉模型「要做什么操作」，从不告诉它「做成了长什么样」。**
> 于是模型只能用「操作对象是否还在屏上」来反推达成 —— 而对「点击 X 跳转到 Y」这一类步骤（用例库里占绝大多数），**操作成功的必然结果就是 X 消失**。达成的证据，恰好被当成未达成的证据。

这个 failure mode 是**必然复发**的，不是偶发。任何「点击某入口 → 跳到另一页」的步骤都会踩。

## 2. 程序侧根因

### RC-1（主因，P0）do 阶段的 prompt 里没有「本步预期」

`loop/step_pointer.py` 的模板表：

| 模板 | 内容 | 含 expected？ | 用在哪 |
|---|---|---|---|
| `step_active_do`（`:33`） | `[>] 步骤 {n} 操作中：{instruction}` | ❌ | **do 阶段当前步** |
| `do_current`（`:23`） | `【当前只做步骤 {n}】{instruction}` | ❌ | **do 阶段收尾指令** |
| `step_pending_check`（`:35`） | `[ ] 步骤 {n} 未到，禁止执行：{instruction} ｜ 做完后校验` | ❌ | 后续步 |
| `step_active_check`（`:34`） | `[>] 步骤 {n} 校验中：{instruction} ｜ 预期：{expected}` | ✅ | check 阶段 |
| `check_current`（`:29`） | `【当前只验步骤 {n}】{expected}` | ✅ | check 阶段 |

`decide_success()`（`:519-523`）同样只回 instruction：

```
完成步骤 1 的操作：1. 点击底部tab 开始造物。不要用整案成功标准，也不要为了后面的字去改界面。
```

实际喂给模型的 `checkpoints_block`（turn 4，原文）：

```
【执行纪律：严格按步骤编号。禁止跳到后面的步骤，禁止提前验后面的预期。】
[>] 步骤 1 操作中：1. 点击底部tab 开始造物
[ ] 步骤 2 未到，禁止执行：2. 点击底部的白色拍照按钮 ｜ 做完后校验
【当前只做步骤 1】1. 点击底部tab 开始造物
做完本步操作后调 signal_done，表示本步操作结束（不是整案结束）。目标已在屏上达成时也须 signal_done，禁止用 signal_give_up 表示本步完成。禁止去做后面步骤。
```

「跳转到拍照页」这五个字**一次都没出现**。`do_tail` 里那句「目标已在屏上达成时也须 signal_done」是空话 —— 模型不知道「目标达成」的样子是什么。

**这是一个语义陷阱：** 「点击底部tab 开始造物」这句话，在跳转成功后的页面上重读，得到的结论必然是「屏上没有这个 tab，做不了」。指令本身在成功之后会自我否定。

### RC-2（P0）达成判定 100% 依赖模型自述，程序侧零校验

`loop/agent_loop.py` 里 `advance()` / `enter_check()` 的**全部**调用点：

| 行 | 触发条件 |
|---|---|
| `:571` | fork_state 恢复现场 |
| `:1076` | check 阶段模型 `status=done` 且 `step_checked` |
| `:1110` | do 阶段模型 `status=done`（经 `require_do_work`） |
| `:1362-1363` | `assert_visual` 返回 pass |
| `:1375` | 执行后 `status=done` 且 in_check |
| `:1378` | 执行后 `status=done` 且 in_do |

**没有一条是程序观察屏幕后自行判定的。** 整条推进链的唯一入口是模型主动喊 `signal_done`。模型判错一次，用例直接 `give_up`，没有任何兜底。

而程序侧其实**已经握有判据和现成机制，只是没接上**：

- 判据：`expected[n] = "跳转到拍照页"`，`case_store` 里就有，`apply_force_case_expectation`（`loop/registry.py:264`）已经会把它塞给 VLM —— **但只在 `cap_id == "assert_visual"` 时**，也就是只在 check 阶段。do 阶段用不到。
- 机制：`nav_runtime.py:405 evaluate_effect_assert` —— 「执行完某个动作后，用 hierarchy 回判效果是否发生」这套逻辑**已经实现并在跑**，但只服务 NavFSM 的**导航边**，不服务**用例步骤**。
- 原语：`loop/hierarchy_slots.py:199` 的 `match_any` / `node_matches` 是 guard / localize / effect_assert 三处共用的匹配原语，**可直接复用，无需新造轮子**。

### RC-3（P0）history 把动作意图擦掉了，模型无法自证已点过

turn 4 的 `history_block` 原文：

```
1. launch_app → pass: 启动 com.mathmagic.magicam
2. wait_ms → pass: 等待 3000ms
3. tap_element → pass: 点击 「?」(600,2494)[snap inside]
```

模型发出的 params 是 `{"selector_text": "开始造物", "x": 500, "y": 953}`，但 history 只留下 `「?」`。

出处：`MinoScout/mino_scout/executors/adb_executor.py:718-729 _point_label()`

```python
if how == "snap":
    s = audit.get("snap") or {}
    name = s.get("text") or s.get("content_desc") or "?"     # ← 只取命中节点的文案
    return f"「{str(name)[:20]}」({x},{y})[snap {s.get('how')}]"
```

`event.params["selector_text"]` 从不参与。于是模型回看历史时，看到的是「我点了个不知道什么东西」，**无法把「已达成」和自己的动作连起来**。对无文案控件（本例的「开始造物」正是）这条必然触发。

### RC-4（P0）nav_assist 在用例跑批里抢方向盘，并把模型带沟里

每一 turn 注入的 `nav_assist`（原文）：

## 3. 程序侧解法

### P0 —— 本例直接卡死，必须改

#### P0-1 do 阶段注入「达成信号」，并显式声明「操作对象消失是正常的」

改 `loop/step_pointer.py`：

| 位置 | 改法 |
|---|---|
| `:33 step_active_do` | `[>] 步骤 {n} 操作中：{instruction} ｜ 达成信号：{expected}` |
| `:23 do_current` | 追加一行 `【本步达成信号】{expected}` |
| `:25-28 do_tail` | 追加：「**达成信号一旦在屏上出现，即视为本步完成，立刻 signal_done。跳转类步骤成功后，原操作对象（入口/tab/按钮）会从屏上消失，这是达成的正常表现，不构成未达成，禁止因此 signal_give_up。**」 |
| `:505-523 decide_success` | do 分支改为「完成步骤 {n} 的操作：{instruction}。**达成信号：{expected}。以达成信号为准，不以操作对象是否可见为准。**」 |
| `:477 / :457` | 把 `cur.expected` / `node.expected` 传进去 |

`expected` 为空时保持现状（`｜ 本步无预期（做完即过）`），不引入新分支。

**这一条单独就能修好本例**：模型在 turn 4 会读到「达成信号：跳转到拍照页」，而它自己都说了「当前在拍摄页面」。

#### P0-2 新增程序侧「步骤效果探针」（step effect probe）

新建 `mino_nexus/loop/step_effect.py`，复用 `hierarchy_slots` 的匹配原语，**纯文本比对，不调 LLM，零额外延迟**：

```python
def probe(expected: str, nodes: list[dict]) -> tuple[bool, list[str]]:
    """本步预期文案是否已在屏上出现。返回 (命中, 命中的关键词)。

    切词只做保守拆分（去掉「跳转到/显示/出现/页面/界面」等虚词），
    命中判据复用 hierarchy_slots.match_any —— 与 guard / localize / effect_assert 同一套。
    """
```

接入 `agent_loop` 的 do 阶段（在 `observe` 之后、组 slots 之前）：

1. **命中即提示**：在 `checkpoints_block` 末尾追加
   `【达成提示】本步预期已在屏上出现（命中：拍照 / 入镜）。若无其它待办，立即 signal_done。`
2. **连续命中即接管**：同一步骤连续 2 turn 命中而模型仍未 `done` → **程序侧直接 `cursor.enter_check()`**，把判定交给 check 阶段的 `assert_visual`（那里本来就是看图判的，且 `apply_force_case_expectation` 会自动塞入用例原文预期）。

探针只负责「提请注意」和「转场」，**不直接判 pass** —— 真正的通过与否仍由 `assert_visual` 出具，判据不降级。

#### P0-3 give_up 前强制走一次 check

在 `agent_loop` 处理 `decision/give_up` 之前插一道拦截。同时满足以下条件时**不接受 give_up**：

- 非探索任务（`not is_explore`）
- `cursor.phase == "do"` 且当前步有 `expected`
- `cursor.step_ops > 0`（本步已执行过至少一次设备操作）
- 本步起始屏面指纹 ≠ 当前屏面指纹（**界面确实变过**）

处理：改走 `cursor.enter_check()`，并注入一行
`【纠偏】你在本步已执行过操作且界面已发生变化。先按本步预期校验一次（assert_visual），再决定是否放弃。`

需要 `StepCursor` 增加 `step_start_fp` 字段，在 `advance()` / `finish_prep()` 里刷新。

本例中 turn 5 的 give_up 会被这条拦下 → 转 check → `assert_visual("跳转到拍照页")` 看图 → pass → 步骤 1 过 → 进步骤 2。

#### P0-4 history 保留动作意图

**主改（Nexus 侧，不跨仓）**：`agent_loop._record` 记步时把 `params.get("selector_text")` 存进 step 的 `extra`；history 行渲染时优先用它：

```
3. tap_element → pass: 点击「开始造物」→ 命中无文案节点 (600,2494)
```

**可选（Scout 侧）**：`MinoScout/mino_scout/executors/adb_executor.py:718-729 _point_label()`，在 `snap` / `fallback_xy` 两个分支回填 `event.params.get("selector_text")` 作为 name 的兜底，`"?"` 降为最后一档。这只改 summary 文案，不动协议，不需要两仓同步 fixture。

#### P0-5 用例跑批时 nav_assist 不抢方向盘

`services/nav_compiler.compile_assist` + `services/nav_fsm.build_plan`：

- `plan.goal_state_id` **来自 `meta.recover.default_goal_state_id`（而非 case 的 `nav_goal_state` 字段）时**，判定为「无用例级导航目标」：
  - 不输出【导航目标】
  - 不输出【建议边】
  - 不输出【本步允许】（这三段是把模型往 case 之外拽的元凶）
  - 只保留 `【导航 assist】loc=... (conf)` 一行作为位置参考
- `default_goal_state_id` 的语义应收窄回它原本的用途：**迷路后 `fsm_navigate` 的恢复终点**，而不是「每一步都该往那儿走的目标」。

配套：清掉正式库里的百分比噪声 state（与 `9月15日-导航架构页与探索循环问题核对.md` 的 **P0-6** 是同一件事，两边都要改到）。本例里 `page.0/14/11/10` 及 `edge.0_to_14 / 14_to_11 / 11_to_10` 应被删除。

### P1 —— 放大故障面 / 降低复发率

#### P1-1 hierarchy 采集剔除系统 UI 节点

在 `loop/hierarchy_slots.capture` 或 `services/nav_capture_store.append_turn` 层过滤：

- `resource_id` 属于 `com.android.systemui`
- `bounds` 完全落在状态栏高度内（顶部 ~80px）
- `content_desc` 匹配「…通知：」「信号强度」「正在充电」「已完成百分之」等系统播报

收益：`11%` / `18:27` 这类文案不再进 identify、不再进 `stable_chrome_texts`、不再造噪声 state，同时让 `确保物品完整入镜` 这类真正有判别力的文案浮上来。

#### P1-2 无文案控件的定位策略

「开始造物」在 hierarchy 里既无 `text` 也无 `content_desc`，`tap_element` 只能靠坐标兜底 —— 本例侥幸点中了，但这是运气。

- 底栏槽位解析已有现成实现（`services/nav_tab_slots.py`），本例底栏是 3 槽：`灵感 [60,407]` · `[无名] [407,794]` · `我的 [794,1140]`，中间槽完全可由两侧锚点推断。
- 建议给 `tap_element` 增加 `anchor_between: [左锚点, 右锚点]` 或 `tab_slot_index`，让无文案控件有稳定锚点，而不是每次都回落坐标。
- 同时 `nav_fsm` 的 tab 边 `execute` 里应带上这个槽位信息，而不是裸 `{"steps": ["tap_element"]}`。

#### P1-3 步骤达成探针的判错率遥测

新增 `nav_telemetry.step_effect(run_id, case_id, step_n, probe_hit, model_done, turn_id)`，记录「探针命中」与「模型 done」的差异。

- `probe_hit=True & model_done=False` 连续出现 → 就是本文这类故障，可直接拉出清单
- `probe_hit=False & model_done=True` → 模型虚报达成，是另一个方向的风险

没有这个指标，「模型判断达成」的准确率现在是不可观测的。

#### P1-4 `case_step` 没有进 slots

`turn/start` 事件里有 `case_step=1`，但 `context/slots` 的 `slots` 字典里没有 `case_step` 键（实测全部 turn 为 `None`）。UI / 遥测无法从 slots 还原步骤位置。在 `skill_envelope` 里补上。

#### P1-5 `expected` 缺失时的 do 阶段提示

若 `expected[n]` 为空，P0-1 的「达成信号」无内容可注。此时应在 do 阶段就明示
`【本步无预期】做完操作即视为完成，不要试图找校验依据。`
而不是等到 `_finish_case` 才以 `unverifiable` 收场。
