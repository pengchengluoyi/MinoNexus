# 9月17日 — 同一事件大模型在不同用例处理效果不一致（稳定性）

> **维护说明**：现象保留本文；**程序选路（登录宏 / fb.global.login）** 见 [`9月18日-fsm导航能力提升.md`](9月18日-fsm导航能力提升.md) §4 与 [`9月18日-意图识别与大模型注意力集中.md`](9月18日-意图识别与大模型注意力集中.md) §1.4。

**问题类型**：同一 **结构化能力 / 同一屏上形态**（典型：`request_sms_code`、发送验证码链路），在批跑里 **有的用例稳定成功、有的用例失败**，差异主要来自 **LLM 选型与提示上下文**，而非 Scout 执行器随机失败。  
**样例批跑**：`cr-8e4116e8c715` — `case-51fef028` 失败、`case-112f10ef` 成功（同属短信/登录相关，但前置与步骤叙事不同）。  
**优先级**：**P0（登录主路径）** — 失败会直接卡死后续步骤与校验。

---

## 0. 在执行架构中的位置

```text
observe → inspect 槽 / menu → agent-decide(LLM) → guards → RouterProxy
                              ↑
                    compile_*_hint（软引导，非强制）
                              ↓
              request_sms_code → local_executors（几何找发送钮 → tap）
```

| 层级 | 角色 |
|------|------|
| **能力** | `request_sms_code`（recovery/local，`ui_sms_request` 几何，不硬编码 App 文案） |
| **引导** | `compile_sms_send_hint`（租号 + 手机号已填 + 同行发送控件可见 + menu 含该 cap） |
| **决策** | 仍由 **agent-decide** 在 `tap_element(发送)` / `request_sms_code` / 跳过发送直接 `get_otp` 之间自选 |
| **校验** | `enrich_assert_expectation` 收紧「已发码 vs 仅填手机号」—— 与 **校验误判** 文档不同类（见 §6） |

**本文解决的是「该不该点、用哪个 cap 点」的决策方差**，不是「点到了但 assert 判错」。

---

## 1. 现象与对比（为何同批不同案）

| 维度 | 容易导致 fail 的上下文 | 容易导致 success 的上下文 |
|------|------------------------|---------------------------|
| **Hierarchy** | `text_len=0` / degraded，发送钮只能靠 VLM 坐标 tap | 节点带 text/bounds，hint 与 recovery 更易对齐 |
| **前置顺序** | 先 launch 再清缓存 / 落在系统页，手机号页未稳定 | prep 顺序正确，登录页一次到位 |
| **租号与槽** | `accounts_brief` 空、hint 不出现，模型盲 `input_text` | 有租号 + `compile_sms_send_hint` 进 `otp_prep_hint` |
| **Menu 可见性** | `request_sms_code` 未进当 phase menu（目录/recovery 过滤） | cap 在 menu，模型可见工具 |
| **历史与 fuse** | 前几步 tap/input 触发 `action_fuse`，发送步被拦或改道 | 进展清晰，fuse 不误伤 |
| **模型路径** | 用 `tap_element` 点短文案，坐标漂 / IME 挡发送 | 走 `request_sms_code`（内部 `press_key BACK` + 几何 tap） |

同一 **用户可见事件**（「点发送验证码」）在系统里对应 **多条等价实现**；LLM 选路不一致 → **批跑稳定性差**。112f10ef 成功不能证明链路可靠，只说明 **该上下文下模型选对了路**。

---

## 2. 根因（分层）

### 2.1 结构能力仍是「可选工具」，不是「状态机下一跳」

`accept_legal_consent` / `dismiss_ime` 已走 **几何 + local executor**；`request_sms_code` 同样已实现 **程序点击**，但 **触发条件** 主要是：

1. LLM 主动选 cap；或  
2. recovery 规则（若 seed 命中）；或  
3. 文本 hint（`【短信登录】…先 request_sms_code…`）—— **不违反 guard 时模型可忽略**。

因此 **同一屏** 在不同用例里，hint 强度、menu、history 不同 → **不同策略**。

### 2.2 Hint 是必要条件链，任一断则回到纯 LLM

`compile_sms_send_hint` 要求同时满足（见 `session_gate.compile_sms_send_hint`）：

- 已租号（`accounts_brief` 有效）  
- `phone_field_filled` + `find_send_code_button`  
- menu 含 `request_sms_code`  

缺 hierarchy 时 `find_send_code_button` 失败 → **无 hint** → 模型更常 **tap_element 盲点** 或 **跳过发送**，与 51fef028 类失败一致。

### 2.3 与 `get_otp` / `input_text` 的竞争

`compile_otp_prep_hint` 与 sms hint 并列写入 `cursor.otp_prep_hint`。模型若先看到「取码填入」，可能 **未发码就 get_otp + input_text**，assert 阶段被 `enrich_assert_expectation` 判 fail —— 表现为「操作做了但流程错序」，根因仍是 **发送步未程序化**。

### 2.4 用例叙事差异放大方差

- 登录模块用例：额外 `refresh_session_block`、`compile_login_session_hint`，占用 turn 与注意力。  
- 功能用例中 **顺带登录**：步骤里没有「发验证码」字样，但屏上是短信页 → 模型行为更随机。

---

## 3. 稳定性目标（定义）

| 指标 | 说明 |
|------|------|
| **同屏同态** | 几何判定「手机号已填 + 发送控件存在」时，**不依赖** LLM 选择 `request_sms_code` vs `tap_element` |
| **跨用例** | 51fef028 / 112f10ef 在同等屏态下走 **同一程序路径** |
| **可观测** | trace 里发送步统一为 `request_sms_code` pass/fail，而非 scattered `tap_element` |

---

## 4. 方案（按侵入性）

### 4.1 P0 — 程序触发（推荐，与 consent 对齐）

**当** `phone_field_filled` 且 `find_send_code_button` 成功 **且** 本步/场景含短信登录语义（租号 + session_block 或 instruction 命中验证码流程）：

- **方案 A**：do 阶段 turn 开头 **预执行** 一次 `request_sms_code`（失败再交给 LLM + recovery）。  
- **方案 B**：recovery 规则 **自动 execute**（`when: geometry_match`，`action: request_sms_code`），LLM 仅处理失败后续。  
- **方案 C**：guard **`require_sms_send_before_otp`**：history 无 `request_sms_code → pass` 时拒绝 `get_otp` / 拒绝填 `sms_code` 域。

A/B 降方差；C 防错序。三者可叠加。

### 4.2 P1 — 削弱等价路径

- menu 在「发送几何成立」时 **隐藏** 与发送同行的 generic `tap_element`（或 steer 强指向 `request_sms_code`）。  
- catalog description 统一：**发送验证码必须 request_sms_code，禁止 tap 短文案代替**（Jobs/SOP 同步）。

### 4.3 P1 — Hierarchy 降级仍要发送

- degraded 时用 **VLM hierarchy**（`inspect-session` / turn `vlm_hierarchy`）喂 `ui_sms_request`，与 consent 共用节点池。  
- 发送失败 summary 进 `correction_hint`，避免模型无限 `input_text`。

### 4.4 P2 — 登录微流程状态机

在 **RunContext** 增加 **`sms_login_phase`**（`phone_empty | phone_filled | send_clicked | code_filled`），由程序在 cap pass 后推进；agent-decide 只填当前 phase 允许的工具。  
与 **步骤语义拆分**（另一文档）正交：状态机管 **登录子流程**，拆分管 **单步多动作**。

---

## 5. 验收

1. 固定 fixture 屏（手机号已填 + 发送钮）：连续 N 次跑 **不同用例壳**，发送步 cap_id 均为 `request_sms_code`。  
2. `cr-8e4116e8c715` 复跑 51fef028 / 112f10ef：发送失败率不高于单一用例。  
3. trace：`compile_sms_send_hint` 为空时若仍应发送，必须有 recovery/预执行记录（可审计）。

## 6. 与其它 9/17 文档的关系

| 文档 | 关系 |
|------|------|
| **单步骤多意图识别和立即流转** | 解决 **一步内少下发**（多 tap / 滑动+点击）。本文解决 **同一步内「发送」事件选 cap 不一致**，不是计数不够。 |
| **达成预期立即流转** | 解决 **步已完成仍继续点**（如误进整段登录）。若发送成功后模型又去「从头登录」，属流转文档 + 本文 hint 叠加。 |
| **大模型校验误判** | 解决 **check 断言**；本文是 **do 阶段工具选型**。发码成功但 assert fail 应拆成两条线分别修。 |
| **动作族 `step_contract`** | 族级 `tap` 无法区分「点发送」与「点 Tab」；发送稳定性 **不应** 靠再加一个 tap 族，应 **程序化 request_sms_code**。 |
