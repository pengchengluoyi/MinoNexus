## 2. 附带发现（核对过程中确认的次生问题）

- **`screen_count` 恒为 0。** `_atlas_cluster_doc` 构造 `screen_list` 时 `if st.get("entry"): continue`（`nav_screen_registry.py:1081`）。本应用两个节点都是 entry → `screen_list` 空 → API 的 `screen_count` / `screens` 为 0，而工具栏「N 屏」读的是 `graphDoc.states.length`（2）。同一份数据两个口径。
- **前端还会再丢一层节点。** `utils/navRelationGraph.js:329`：`if (isAtlas && variant === 'arch' && !hasWf && sid !== launchId && sid !== homeStateId) continue` —— 没有线框的节点（launch/home 除外）不画；边的另一端被滤掉后线也一起没了。工具栏计数按完整 `graphDoc`，画布上更少。
- **未提交 diff 顺手删掉了反向「返回」边。** `nav_screen_registry.py` 原先会为每条 nav 转移补一条 `reverse / action_type: back` 边，现已移除。跳转图上「返回」路径整体消失。
- **`_finish` 与 `_leave` 的不对称是双向的。** 探索**失败**时走 `_leave` → `nav.shutdown()` 会跑（trace 里 `nav/capture_finish {"captures_recorded": 4, "run_status": "fail"}` 确实存在）；探索**成功**时走 `_finish` → 不跑。即「只有失败才有收工事件」。
- **`session/start` 事件里 `sop_id` 记成 `run-case`**，而同一份事件的 `skill_id` 是 `explore-app`。会话日志的 SOP 归属与实际执行的 SOP 不一致。

## 3. 报告未提及、但更直接杀死执行的三个卡点

### 3.1 每一次探索都被判定成「登录用例」

`DEFAULT_EXPLORE_GOAL`（`loop/explore_case.py:11`）里有这句：

> 不要停在**登录页**反复点同一按钮；已无法发现新页面时调用 signal_done 结束。

而 `_LOGIN_TEST_STEP_RE`（`runtime/session_gate.py:23-26`）正好匹配「登录页」：

```python

    r"登录方式|登录页|游客|一键登录|微信登录|苹果|账号密码|手机号登录|验证码登录|账号登录",
    re.I,
)
```

实跑验证（`build_explore_case()` → `ensure_case_scene()`）：

```
is_login_module_case: True
scene: {'session_prep': 'logout', 'required_session': 'guest', 'auth_under_test': True,
        'device_need': 'app', 'reason': '登录/游客用例，前置只退出不登录'}
required_session: guest
hint: 【登录态】本用例测登录流程，起点应为未登录或完整登录页；若屏幕为个人主页/昵称页，先退出再点登录方式。
```

**三重后果：**

1. 跑前 `reset_native_app_before_case(login_module=True)` 冷启动并退登。trace 里 `app/cold_start {"login_module": true, "package": "com.mathmagic.magicam"}`。
2. 模型的 history 第 0 行就是「本用例测登录流程」——所以 trace 里 turn 1 它去点了「我的」，在找退登入口，**而不是在探索**。
3. `loop/agent_loop.py:752-762`：`login_module_case` 为真时**每 turn 额外跑一次 `refresh_session_block`**（一次完整 LLM 调用）。trace 实测 `inspect-session` 耗时 3577 / 3623 / 4171 / 5329 / 4577 ms，占每 turn 12–13 秒里的 **约 40%**。

**这条同样命中普通用例。** 任何用例文本含「登录方式 / 游客 / 一键登录 / 微信登录 / 苹果 / 账号密码 / 手机号登录 / 验证码登录 / 账号登录」的，整条用例每 turn 都多一次 LLM 调用；`run-case` 的 `max_steps=30` 下白烧约 2.5 分钟。

### 3.2 ProgressGate 的里程碑预算对探索永不复位

`ProgressGate.reset_milestone(phase, step)`（`loop/action_fuse.py`）以 `f"{phase}:{step}"` 为 key，同 key 直接 `return`。

- `StepCursor` 在 `advance()`（`loop/step_pointer.py:388`）和 `enter_check()`（`:402`）都会复位；
- **`ExploreCursor` 只在 `__post_init__`（`loop/explore_cursor.py:49`）复位一次**，之后 `phase` 恒 `"do"`、`step` 恒 `1`（`enter_check()` 把 phase 设回 `"do"`，`advance()` 恒返回 `False`）。

于是所有熔断阈值都变成「整场探索」的全局预算：

| 阈值 | 值 | 对探索意味着 |
|---|---|---|
| `MILESTONE_BUDGET["do"]` | 10 | **整场探索总共只有 10 次设备操作**，第 11 次起必熔断【熔断·里程碑】 |
| `STATE_MAX_UNIQUE` / `STATE_MIN_SAMPLES` / `STATE_WINDOW` | 2 / 6 / 10 | 近 10 步只在 ≤2 个界面间走 → 判【熔断·困局】。**两个底栏 Tab 来回切，定义上就是困局** |
| `_detect_state_cycle`，period 2..4 重复 3 轮 | — | A→B→A→B→A→B → 判【熔断·状态循环】。这正是探索的形状 |
| `FUSE_BLOCK_STOP_THRESHOLD` | 2 | 连续 2 次熔断 → `loop/agent_loop.py:1190 record_fuse_block` 返回 stop → `_leave(status="fail")`，整个 run 失败 |

结论：`max_steps=80 / max_idle_steps=15` 是**不可达**的，探索的真实预算是 **10 次操作、且不许重访任何屏面**。
