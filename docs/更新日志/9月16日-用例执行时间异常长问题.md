## 2. 空转如何把时间放大

单 turn 固定成本大致是：

1. observe 截图 + hierarchy  
2. localize / context-pack / 文档检索  
3. **一次多模态 LLM（主耗时，中位 ~14s）**  
4. 可能的 tool（本次空转里 tool 经常是 no-op 或 skip）

因此：

- 正常 6 步用例若每步 1–2 turn，大约 **2–4 分钟**
- 打满 30 步 ≈ **30 × 14s ≈ 7 分钟起步**，加上 observe / 双图决策可到 **8–10 分钟/条**
- `303b8168` + `fdd16b38` 两条就占了 **18.8 分钟**

下面四条代码缺陷决定了「该 1 次点击结束的步骤」变成「30 次看图」。

## 3. 四条缺陷与本批现象

### 3.1 `fsm_navigate` 连续触发但不导航（`case-303b8168`）

**步骤 1**：点击底部「开始造物」Tab，预期进入拍摄页。

**日志**：turn 4–20 共 17 次 `fsm_navigate`，全部 `plan_ok=true`、`arrived_at_target=true`、`hops=0`，摘要「已在目标屏 `page.sk3f5a31a92f9fs4`」，**一次点击都没有发出**。

**根因**：

1. 拍摄页 `page.sk3f5a31a92f9fs4`（展示名「拍摄取景框」）的 **alias 含「开始造物」**（边点击文案写回目标页，解析上合理）。
2. `to_state=开始造物` / `点击底部「开始造物」Tab` 被解析成**当前页** → `hop_count=0`。
3. `_fsm_navigate` 在 hops=0 时直接 `PASS`，不编译 tap。
4. `fsm_navigate` 不在 `action_fuse` 集合里：`check()` 直接放行，`record_pass` 虽按 `tap_element` 记账，拦截却拦不到下一次 `fsm_navigate`。
5. hops=0 也不计入 `MUTATE_CAPS`，后面即使想 `signal_done` 也会被 `require_do_work` 拦住。

模型看到「pass / 已在目标屏」，以为还要再导一次，于是空转 17 轮 ≈ **4.5 分钟**。

**修复**：

- hops=0 且 `to_state` 能抽出可点文案时，**仍 tap 该文案**（`same_page_click_label`），不再空 pass。
- 抽不出文案时：第一次 PASS + 纠偏「请 signal_done 或直点」；第二次 **declined**。
- `fsm_navigate` 进入 `MUTATE_CAPS` 与 `action_fuse`：同屏无进展会熔断。

### 3.2 `limit_recovery_retry` 失败（同案 turn 23–30）

17 次空导航之后，模型改调 `recover_screen_secure_or_no_capture`（相机页常见 FLAG_SECURE 黑图）。advise 两次后守卫拦截 **8 次**，文案却是「请点授权按钮」——这条规则与权限弹窗无关。拦截后**不写 `correction_hint`**，模型继续点同一 recover，直到 30 步耗尽。又烧掉约 **2 分钟**。

**修复**：

- 守卫文案按 `rule_id` / `prompt_snippet` 区分（secure 规则改为 BACK / wait / 问人）。
- 拦截写入 `correction_hint`；连续 3 次同类拦截直接结束用例，避免把 30 步打满。

### 3.3 `recover_screen_secure_or_no_capture` 被跳过（同案 turn 21–22）

规则 `mode=advise`、`actions=[]`。`apply_rule` 只填 `advice`，`applied=False`、`recovered=False` → 循环记 **`skipped`**，摘要只有「给出处置建议」，**snippet 不进 history**。模型既看不到「不要反复 wake / 用 BACK」，又把 skip 当成没执行。

**修复**：

- advise 成功改为 **pass**，摘要带完整 `prompt_snippet`，并写入 `correction_hint`。
- 证据明显不匹配（例如并非全黑）→ **declined** + 说明勿再调。
- 仍走 `bump_advise_recovery`，两次后由 3.2 的守卫收口。

### 3.4 `require_do_work` 一直跳过（`case-fdd16b38`）

**步骤 1**：点击底部「灵感」Tab。turn 5 冷启动后，`nav_assist` 已是「当前屏：灵感（72%）」，VLM 顶栏也是灵感 / 开始造物 / 我的。模型从 turn 6 起连续 **25 次 `signal_done`**，全部被 `require_do_work` skip：「尚未执行任何设备操作」。

**根因**：

1. 守卫只认 `step_ops > 0`。`fsm_navigate` 不在 `MUTATE_CAPS`，turn 3 的一次真实 tap **不计 ops**；`recover_restart_target_app` 带 `recover_` 前缀也不计。
2. 达成探针只扫 Scout hierarchy。本批 `hierarchy_text` 恒空，`probe_hit` 全程 false，无法靠「屏上已有灵感」自动进 check。
3. 步骤指令里的「灵感」在引号内，探针原先不抽取引号 token。

结果：目标页已经在了，却不许收工，再空转 **~6 分钟**。

**修复**：

- `fsm_navigate` 记入 `step_ops`。
- 探针合并 VLM nodes，并抽取步骤引号内文案。
- localize 的 `display_name` / 精确 alias 已覆盖本步目标时，视为 `step_goal_met`，允许 `signal_done`。
- 连续两轮命中仍可自动 `enter_check`。

## 7. `cr-1bf78f403a5f`：点启动 → 第一条用例真正开环

**任务**：`cr-1bf78f403a5f`（造物相机，2 条用例，`20:08:07` → `20:18:26` = **10 分 19 秒**）  
**第一条**：`cr-1bf78f403a5f::case-ee6bf6db`（作品集），会话 `20:08:08` → `20:10:34` = **2 分 26 秒**  
**模型**：火山 `doubao-seed-2-0-lite-260215`

「点了启动却半天没开始点屏幕」拆成两段：**开环前固定开销**（本节）和 **前置阶段**（§8）。设备点击几乎不占时间。

### 7.1 墙钟

| 时刻 | 事件 | 距启动 | 这段在干什么 |
|------|------|--------|----------------|
| `20:08:07` | `app_regression_runs` 落库，`status=running` | 0 | HTTP 返回 run_id，后台线程 `_run_in_background` |
| `20:08:08` | `session/start` | **+1s** | `run_case`：建 `RunContext` / `RouterProxy` / 打开会话 |
| `20:08:13` | UI `开始看图执行` | **+6s** | 会话已开、第一条尚未 turn：装 NavFSM + 文档向量 |
| `20:08:15` | `app/version` = `1.3.0` | **+8s** | 预飞截图、recover、读包版本，再按版本重载 FSM |
| `20:08:18` | `turn/start`（prep t1） | **+11s** | 第一条用例循环真正开始：截图 → inspect-session |

启动到「第一条用例正式开环」= **11 秒**。第二条 `case-9b9687f9` 在上条结束后立刻 `session/start`（`20:10:34`），同样要 **~9 秒** 才到自己的 `turn/start`（`20:10:43`）。这是**每条用例都会付的固定税**，不是队列卡住。

### 7.2 这 11 秒里有没有特别慢的点

有，而且能复现。`session/start` 到 `turn/start` 之间主循环还没进 `for seq`，做的是：

1. **`bootstrap_case_doc_query`**：整份用例文本打一次 embedding（HTTP，超时上限 60s）。本条没有单独打点，但和下面那次图合成叠在同一段 5 秒窗口里。
2. **`NavRuntime.for_run` → `load_fsm_doc(use_live=True)` → `get_live_graph(sync=False)`**。`sync=False` **并不跳过合成**：仍会 `iter_cumulative_turns` + `atlas_doc_for_navigation`（内部 `build_atlas`）。采集越多越慢。这段对应 `20:08:08` → `20:08:13` 的 **5 秒**。
3. `emit(start)` 之后：预飞截图、`recover_if_needed`、`ensure_target_app_foreground`、**再 `get_app_version`**。
4. 拿到版本后 **又一次** `load_fsm_doc(use_live=True, app_version=…)` 做版本视图物化。对应 `20:08:15` → `20:08:18` 的 **3 秒**。

因此开环前的热点不是 Scout、也不是「任务创建」，而是：

- **每条用例冷加载一遍 Screen Atlas / live graph（还加载两次）**
- 可选的 embedding
- 一次预飞截图 + 读版本

量级约 **9–11 秒/条**。47 条批跑的话，光开环税就可能到 7–9 分钟，且发生在「第一条步骤还没点下去」之前。两条用例的这次 run 里，开环税约 **20 秒**，不是 10 分钟的主因。

## 8. `case-ee6bf6db`：前置 → 操作

前置从 **t1 `20:08:18`** 到 **t5 `signal_done` `20:10:06`**，共 **108 秒**，然后 **同一秒**进入 do（t6）。中间没有额外排队。

### 8.1 时间账

| 轮 | 阶段 | 墙钟 | 动作 | LLM | 设备 |
|----|------|------|------|-----|------|
| t1 | prep | 08:18–08:44（26s） | 桌面 → `launch_app` | inspect-session **5.8s** + agent-decide **17.7s** | launch 324ms |
| t2 | prep | 08:44–09:02（18s） | `get_app_version`（循环里又读一次） | decide **16.5s** | 91ms |
| t3 | prep | 09:02–09:20（18s） | `lease_account` | decide **17.3s** | 12ms |
| t4 | prep | 09:21–09:49（28s） | `relogin` 失败（session=unknown） | decide **17.1s** + inspect-session **9.2s** | 观察为主 |
| t5 | prep | 09:49–10:06（17s） | `signal_done` 进入操作 | decide **15.7s** | 无设备动作 |
| t6 | do | 10:06– | 步骤 1「点击底部『我的』Tab」 | decide **13.2s** | — |

前置 5 轮 LLM 合计约 **99 秒 / 108 秒 ≈ 92%**。hierarchy / localize / context-pack / 文档检索都在 decide 前，日志上是同一秒内完成，不是主因。

### 8.2 为什么前置要五轮、约两分钟

前置文案是：已登录、作品集 ≥ 2、测试包。模型按「看图 → 调一个工具 → 再看图」拆：

1. 开环时在**系统桌面**（上一次批跑没把 App 留在前台），必须先 `launch_app`。这是本条相对「已在 App 内开环」多出来的一轮 decide（~18s）。
2. `get_app_version` 在开环预飞里已经读过并写入 `app/version`，prep 又让模型调了一次。多一轮 ~17s。
3. `lease_account` 本地 12ms，但前后仍要一轮 decide。
4. `relogin`：账号标签已是「已登录、有作品」，屏上也已在灵感页。inspect-session 判 `session=unknown` → relogin **fail**，没有真去登。白烧 decide 17s + 二次看图 9s。
5. 下一轮才 `signal_done` 结束前置。

没有空转 30 步，也没有 Scout 卡住。慢在 **每轮必看图的 agent-decide（15–18s）× 前置工具次数**。可压缩点：

- 批与批之间把目标 App 留在前台，或开环预飞已在桌面时由程序 `launch_app`，不要再等模型决定
- 预飞已写入的版本不要再进 prep 工具菜单（或 history 里标「已确认版本」并挡住重复 `get_app_version`）
- 屏上已是目标 App 且账号标签已登录时，少调一次失败的 `relogin`

按此压缩，前置有望从 **~108s** 降到 **2–3 轮 decide（约 40–50s）**，do 仍从 `signal_done` 当秒开始。

### 9.6 立即修复：`cr-83b57d410a49::case-c516fa0a` `fsm_navigate` declined

**现象**：t1 `fsm_navigate(from=潮玩悟空作品详情页 → to=我的)`，3ms `declined`。
