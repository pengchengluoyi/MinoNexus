# 9月15日 — 探索发现的新页面在架构图中丢失

分析对象：`cr-8982083156e0::__explore__`（应用探索，第一次跑通 P0 修复后的循环）

- 应用：`app_id = 3d2b9799-0027-4c7d-bfe7-8c5b88f4087d`（造物相机 / 移动端），包名 `com.mathmagic.magicam`
- 结果：`status = pass`，436 事件，26 帧采集，3 分 53 秒，摘要「连续 15 步无新屏，探索结束（共 7 个屏面）」
- 症状：**探索本身跑得很好，但这 26 帧在架构图上一帧都没出现**
- 优先级只有两档：**P0**（导致页面丢失，必须改）、**P1**（丢失修好之后，画面仍然读不懂）

## 0. 结论

不是聚类的问题，不是画布的问题。**这 26 帧在 `build_atlas` 的第一行就被判成「系统屏」全部丢弃了。**

```
build_atlas capture: {'turns': 47, 'turns_app': 19, 'explore_turns': 4}
                                    ↑ 全是旧数据      ↑ 上一次旧探索的 4 帧

cr-8982083156e0__explore__   dropped = True   26 / 26      ← 一帧没留
```

根因是一句包名推断：**造物相机的深层页面没有任何带包名前缀的 `resource_id`，`infer_foreground` 因此认定「当前前台不是被测 App」，把这些页面标成 `screen_kind = foreign`，采集时冻结写入 meta，之后再也没有机会翻案。**

这是一个 **「越往里探索越看不见」** 的反向机制：探索只要走出有原生底栏的那两个 Tab 页，App 在包名推断里就消失了。

> 这个洞一直存在，但之前探索活不过 4 步（见 `9月15日-导航架构页与探索循环问题核对.md`），从来没走到过深层页面，所以没暴露。**P0 把探索放开能跑 26 步之后，它才第一次被撑到明面上。**

### 2.2 旧数据为什么没事

对比同一个 app 的旧采集：

## 3. 第二层：就算传了 scope 也救不回来

meta 里存的 `target_scope` 是**正确的**：

```
{'platform': 'android', 'target_id': 'com.mathmagic.magicam', 'kind': 'package'}
```

`turn_matches_scope(t, scope)` 实测 **26/26 全部通过** —— 因为它开头就有一条短路：

```python
def turn_matches_scope(turn, scope):
    stored = TargetScope.from_dict(turn.get("target_scope") ...)
    if stored and stored.target_id == scope.target_id and stored.platform == scope.platform:
        return True          # ← 存的 scope 对得上，直接放行
```

但 `is_system_screen` 的判定顺序把这个结论废掉了：

```python
def is_system_screen(turn, *, scope=None):
    if is_overlay_screen(turn):
        return True
    scoped = ...
    if scoped and not turn_matches_scope(turn, scoped):
        return True                                       # 不触发（上面放行了）
    kind = str(turn.get("screen_kind") or "").strip()
    if kind in ("launcher", "foreign"):
        return True                                       # ← 无条件后置检查，覆盖前面的放行
```

实测：

```
build_atlas 用的  is_system_screen(t)            → 丢弃 26 / 26
合成用的         is_system_screen(t, scope=…)    → 丢弃 26 / 26      ← 传了 scope 也一样
turn_matches_scope(t, scope)                     → 通过 26 / 26      ← scope 复核本来是过的
```

**采集时冻结的、推断错误的 `screen_kind`，压过了读取时 live 的、正确的 scope 复核。**

## 5. 修复清单

### P0 —— 页面丢失，必须改

#### P0-1 `infer_foreground`：没暴露包名 ≠ 不是本 App（根因）

`services/nav_target_scope.py:182-188`，当前逻辑：

```python
if pkgs:
    if target and target in pkgs:
        fg, kind = target, "app"
    elif target:
        fg = sorted(pkgs)[0]          # ← {'android','com.android.systemui'} → 'android'
        kind = "foreign"              # ← 判死
```

改法：**`pkgs` 为空、或去掉系统包之后为空时，不得判 `foreign`。**

```python
_SYSTEM_ONLY_PKGS = frozenset({
    "android", "com.android.systemui", "com.android.inputmethod.latin",
    "com.baidu.input", "com.sohu.inputmethod.sogou", "com.google.android.inputmethod.latin",
    # 输入法 / 状态栏 / framework —— 它们出现在任何一屏上，不代表前台归属
})

app_pkgs = {p for p in pkgs if p not in _SYSTEM_ONLY_PKGS}
if target and target in pkgs:
    fg, kind = target, "app"
elif not app_pkgs:
    # 这一屏根本没暴露任何业务包名（Flutter / RN / 自绘视图 / 游戏引擎）
    # 无证据 ≠ 反证。回退到 target，交给 launcher 特征与 overlay 判据去兜底。
    fg, kind = target or "", ("app" if target else "unknown")
elif target:
    fg, kind = sorted(app_pkgs)[0], "foreign"
```

`is_launcher`（`:139-140`，靠 `shortcut_menu_layer` / `drag_layer` / `workspace` / `hotseat` 等 rid 特征）保持在前面独立判断，真桌面照样能识别 —— 本例的 turn 2/3 就是这么被正确丢掉的。

**判据的方向要改过来：`foreign` 应该是「看到了别的业务包」的正向证据，而不是「没看到本 App 包」的反向推论。** 自绘 App 在 Android 上是常态，「看不到包名」必须默认无害。

#### P0-2 `is_system_screen` 的判定顺序：stored scope 匹配 = 终局放行

`services/nav_capture_store.py:88-112`。把 `screen_kind` 从无条件后置检查，降级为「没有可信 scope 时的兜底」：

```python
def is_system_screen(turn, *, scope=None):
    if is_overlay_screen(turn):
        return True

    scoped = scope if isinstance(scope, TargetScope) else TargetScope.from_dict(scope)
    stored = TargetScope.from_dict(turn.get("target_scope") if isinstance(turn.get("target_scope"), dict) else None)

    # 真桌面永远丢（launcher 靠结构特征判，不靠包名推断）
    if str(turn.get("screen_kind") or "") == "launcher":
        return True

    # 采集时记下的 scope 与当前作用域一致 → 这帧就是本 app，终局放行
    if scoped and stored and stored.target_id == scoped.target_id and stored.platform == scoped.platform:
        return False
    if scoped and not turn_matches_scope(turn, scoped):
        return True

    # 只有在没有可信 scope 可比时，才退回采集时冻结的 screen_kind
    return str(turn.get("screen_kind") or "").strip() in ("launcher", "foreign")
```

同时 `build_atlas`（`services/nav_screen_registry.py:1397`）必须把 scope 传进去：

```python
scope = resolve_app_target_scope(app_id)
filtered = [t for t in ordered if not is_system_screen(t, scope=scope)]
```

现在这行是裸调用，`scoped = None`，上面所有 scope 逻辑直接被跳过。

#### P0-3 `screen_kind` 不在采集时冻结，读取时按当前 scope 复核

`services/nav_capture_store.py:305-320 read_turn()` 已经有重算分支：

```python
if not meta.get("foreground_package"):
    pkg = infer_screen_package(nodes, ...)
    row.update(pkg)
```

但 meta 有值就不重算 —— 而本例 meta 里存的恰恰是**错的**值。改成：读取时无条件用当前 scope 复核一次 `screen_kind`，让 P0-1 的修复能**回溯救回已有的历史采集**，不需要重跑探索。

这一条决定了：修完之后，`cr-8982083156e0` 这 26 帧能不能立刻出现在架构图上，还是必须重新探索一遍。

### P1 —— 丢失修好之后，画面仍然读不懂

> 以下三条不影响「能不能显示」，只影响「显示出来能不能看」。P0 修完后会立刻变成主要矛盾。

#### P1-1 11 个节点里 10 个叫「灵感」

修复后的节点全部显示 Tab 名，`display_name` 退化：

```
turn 12 chrome  = ['返回', '3D 预览', '浏览器通知：', '醒图通知：']
atlas_page_label → '灵感 · profile page · banner · grid_2col'
前端渲染          → 「灵感」
```

chrome 里明明有 **「3D 预览」** 这个完美的标题，但 `atlas_page_label` 按设计「chrome 仅进 identify，不进标题」（`nav_screen_registry.py` 的 docstring），标题只由 Tab + role + framework 拼出来。

改法：**非 entry 页的标题优先取 chrome 里第一个非噪声、非 Tab 名的短文案**；取不到再退回现在的 `Tab · role · widgets` 拼法。entry 页保持用 Tab 名。

#### P1-2 3D 预览页被判成 `profile_page`

```
turn 12  detect_layout_framework → kind = 'profile_page'
```

3D 预览是典型的 detail 页（有返回、有标题、无底栏）。`profile_page` 的判据（`nav_layout._profile_stat_hits`：顶部多组「数字 + 短标签」）被 `前 / 后 / 左 / 右` 这类短标签误命中。

有 `has_back` 且无底栏时应优先判 `detail`，而不是让 `profile_page` 抢先。当前聚类键是 `role:kind:chrome`，`kind` 判错会直接让不同页挤进同一个桶。

#### P1-3 通知栏文案混进 chrome 与 identify

```
chrome = ['返回', '3D 预览', '浏览器通知：', '醒图通知：']
```

`'浏览器通知：' '醒图通知：'` 是系统通知播报，进了 chrome 就会进 `identify`，也会挤掉真正的标题候选。

这就是核对文档里的 **P1-1「hierarchy 采集剔除系统 UI 节点」**，尚未落地。同一个来源也解释了之前的 `'11%'` 噪声 state。本文 P1-1 的标题提取依赖它先做掉，否则「chrome 第一个非噪声文案」还是会取到通知文案。

#### P1-4 无底栏页的 Tab 归属存疑

3D 预览页被挂到 `page.tab_灵感.*` 下，但它实际是从拍照 / 造物流程进的。无底栏帧沿用「上一帧的 Tab」是当前的兜底策略，在深层流程里会把整条链错挂到一个 Tab 上。

建议：无底栏且 `has_back` 的帧不强行归 Tab，走 `parent_state_id` 挂到来源页下面，Tab 字段留空。
